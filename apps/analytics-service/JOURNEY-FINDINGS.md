# Journey findings — what driving the API as a UI revealed

Written by the 10 agents that authored `tests/test_*_journeys.py`. They were forbidden
from editing `app/`, so everything here was REPORTED rather than accommodated — no
journey test was bent to fit a bug.

Two sections. **Suspected defects** are behaviours believed wrong; they have NOT been
through the adversarial refutation pass that `DEFECTS.md` entries went through, so treat
them as leads, not verdicts. **UI ergonomics** are places the API is correct but awkward
for a frontend — no bug to fix, but worth knowing before you design the screen.

27 suspected defects · 70 ergonomics findings · from 82 journeys / 1388 HTTP calls


## Suspected defects (unverified — leads, not verdicts)


### quality

- app/features/quality/api.py:139-143 — PATCH /datasets/{ds}/rules/{id} with an explicit null for a NOT NULL column is reported as a name collision that never happened. `RuleUpdate` declares name/severity/enabled as `X | None` only so they can be omitted, but `model_dump(exclude_unset=True)` keeps an explicitly-sent `null`, `repo.update_rule` writes it into a NOT NULL column, and the `except IntegrityError` handler assumes EVERY IntegrityError is the (dataset_id, name) unique-index collision. Reproduced over HTTP on a rule created as {'name':'r1','rule_type':'row_count_min','sheet_selector':'orders'}: PATCH {"name": null} -> 409 "A rule named 'None' already exists on this dataset"; PATCH {"severity": null} -> the SAME 409 "A rule named 'None' already exists"; PATCH {"enabled": null} -> the same again. Expected: 422 (problem+json, a shape code such as invalid-rule-shape) naming the field that may not be null. Observed: 409 code 'conflict' whose detail names a rule called 'None'. Impact on a UI: an edit drawer that serializes a cleared severity dropdown or an indeterminate enabled toggle as null gets "that name is taken", attaches the error to the wrong form control, and the user's name field is flagged for a field they never touched. Contrast PATCH {"sheet_selector": null}, which is correctly a 422 'invalid-rule-shape' because check_rule_shape catches it — the three NOT NULL columns simply have no equivalent guard. Not covered by a test, and I did not write one for the current behaviour.

### transform

- app/features/library/service.py:273-282 (resolve_publishable_artifact) - every publish refusal except 'already published' is a bare `HTTPException(409, ...)`, so problem_response falls back to the generic `code: "conflict"`. 'Run is not completed (status: running)', 'Run is not completed (status: failed)', 'Run produced no publishable artifact' and 'Run artifact no longer exists' are therefore indistinguishable to a client. Expected: distinct slugs (e.g. run-not-completed / run-failed / run-has-no-artifact) as the sibling `run-already-published` has. Observed: `code == "conflict"` for all of them. - app/features/transform/service.py:177 (update_transformation) - `if body.description is not None: fields["description"] = body.description` treats absent and explicit-null identically, so `PATCH {"description": null}` is a silent no-op that still answers 200 with the old description. ## UI ergonomics — correct but painful for a frontend


### quality

- Quality's own error branches carry no machine-readable code slug, so a screen has to branch on English prose. Confirmed over HTTP: duplicate rule name -> 409 code 'conflict'; validate with zero enabled rules -> 400 code 'bad_request' (only 'no enabled' in the detail distinguishes it); validate a non-ready version -> 409 code 'conflict'. Every OTHER gate in the same flow does have one — 'validation-required', 'validation-failed', 'invalid-rule-shape', 'sheet-selection-required' — so the three states the Quality tab most needs to distinguish (name taken / no rules to run / version not ready) are the three it cannot distinguish safely. Suggested slugs: rule-name-taken, no-enabled-rules, version-not-ready.

- GET /datasets/{ds}/rules returns a Page envelope but has no `pagination` dependency, so it silently ignores limit and offset and reports `limit` as the item count. Confirmed: with 3 rules, ?limit=1&offset=2 returns all 3 items with {"total":3,"limit":3,"offset":0}. A UI that trusts the envelope (limit==total==len(items)) concludes it is on the only page — which happens to be true today only because the endpoint never pages. A dataset with hundreds of rules ships them all in one response, and the field a paging control reads is meaningless. There is also no `enabled` filter, so an "N active rules" badge must download every rule and count client-side.

- No per-version validation badge. GET /datasets/{ds}/versions items carry only checksum/created_at/id/manifest_checksum/processed_at/row_count/sheet_count/size_bytes/source_checksum/status/tags/version_number — nothing about quality. A version-history screen that wants a green/amber/red dot per row must issue one GET /datasets/{ds}/versions/{n}/validations per version: N+1 on a screen whose whole point is the list. The capability clearly exists at the level above (GET /datasets exposes `validation_status` per dataset and even filters on it), so this is a missing projection, not a missing concept.

- No dataset-wide validation-run list. Runs can only be listed per version (GET /datasets/{ds}/versions/{n}/validations), so a "recent quality activity" panel or an audit view across a dataset's history must fan out one call per version and merge/sort client-side. A `GET /datasets/{ds}/validations` (optionally ?version_number=) would collapse it to one call and would pair naturally with the existing GET /datasets/{ds}/validations/{run_id}.

- Nothing tells the UI whether the promotion gate is armed before it tries. The gate fires on count_enabled_rules > 0, but the only way for a screen to predict a 'validation-required' 409 — and therefore whether to show "Validate first" or "Promote" — is to fetch every rule and count the enabled ones itself (see the paging point above), then fetch the version's runs and find the newest COMPLETED one, since the run list cannot be filtered by status. Two speculative calls to grey out one button.


### relationships

- POST /joins/execute returns `run_id` but no `definition_id`, and there is no GET /analytics/runs/{run_id} anywhere in app/features/library/api.py (only the definition-scoped list at line 151). The only way the wizard can show 'view this run' after executing is to GET /datasets/{ds}/analytics and match the definition by its generated name `join:{relationship_id[:8]}:{how}` — a name the UI has to reconstruct from a string slice. Adding `definition_id` to JoinExecuteResponse (schemas.py:113) would remove an entire extra round trip and the string-matching.

- The join wizard's `select_columns` response returns `output_columns` in the order the JOIN emits them, not in the order the user ticked them: requesting ['tier','order_id','customers_region_code'] answers ['order_id','customers_region_code','tier']. A UI that renders its own tick order will disagree with the parquet column order it then reads back from /samples/{file}/data. Not wrong, but it needs to be documented on the field or the projection order needs to be honoured.

- When a sheet rename breaks a relationship, /joins/preview answers 404 code=sheet-not-in-version with only `version_number`. The repair — POST /datasets/{ds}/versions/{n}/confirm-rename — lives in a different feature, and the problem body carries no logical_sheet_id, no expected sheet name and no hint, so the UI cannot render a 'Fix this' action from the error alone. Adding the missing sheet's last-known key (or the logical_sheet_id) to the problem would make the repair one click.

- GET /datasets/{ds}/relationships filters only by `status`. There is no filter on `method` (the fk_rule/statistical/manual badge the inbox renders as a facet) and no filter on `to_dataset_id`, so a 'show me only cross-dataset edges' or 'only auto-discovered' view has to page the whole list client-side.

- There is no team- or dataset-agnostic way to find a join: /joins/preview and /joins/execute take a relationship_id, and relationships are only listable per dataset. A 'Joins' landing screen therefore has to iterate every dataset the user can read and call GET /datasets/{ds}/relationships on each — an N+1 over the dataset list.

- POST /joins/{run_id}/publish with mode=new_version is not idempotent and gives the UI no way to detect a repeat: publishing the same run twice silently produced version 2 and then version 3 of the left dataset with identical content (test_a_join_output_is_published_as_a_new_version_and_lineage_names_both_parents, last section). Neither JoinExecuteResponse nor the run row exposes 'already published', so a double-clicked Publish button duplicates a version.

- SuggestResponse echoes only the first 100 suggested edges (api.py:76-77 hardcodes limit=100) and carries no total, so a discovery run on a wide workbook gives the screen a silently truncated inbox until it re-fetches GET /relationships, which does have a total.


### library

- A failed run's id is unobtainable from the call that created it. `POST /analytics/{def}/run` returns `RunResponse` only on success; on failure the route re-raises the underlying 4xx (library/service.py:262-263), and the problem body carries no run id even though a run row WAS written and closed as failed. A UI that wants to deep-link the user from the red toast to that run's history row has to re-issue `GET /analytics/{def}/runs` and guess which row is theirs by timestamp. Journey 2 and journey 5 both have to do exactly that. Adding `run_id` to the problem extras would close it.

- The same collision answers two different machine-readable codes depending on the verb. `POST /analytics` and `POST /charts` raise a plain `HTTPException(409, ...)` (library/api.py:60, :232) so the envelope emits `code: "conflict"`, while `PATCH` on either raises `ProblemException(..., code="definition-name-taken" / "chart-name-taken")` (api.py:114-118, :281-285). A UI that branches on `code` to show "that name is taken" under the name field needs two branches for one condition, and the create path additionally has no `name` extra field to echo back. Journey 7 pins both codes.

- `GET /datasets/{id}` (DatasetMetadataResponse, data_accelerator/schemas.py:287-299) has no `name`. After `POST .../runs/{run}/publish` the UI holds only `dataset_id`/`dataset_name` from the publish response; the moment the user navigates to the published dataset by id, the breadcrumb has to be recovered from a second, unrelated `GET /api/v1/datasets` catalog call and filtered client-side. Journey 4 does that and comments on it.

- A dashboard cannot predict which tiles will fail. `GET /charts` rows carry `definition_id` but not the definition's `kind`, and a `profile` definition is happily accepted as a chart source (`_validate_chart_source` only checks existence) yet 400s with `kind-not-chartable` at render. So a dashboard built from the list endpoint alone contains a tile that can never load, with nothing on the list row to grey it out - it must issue an N+1 `GET /analytics/{definition_id}` per tile just to learn the kind. Journey 6 demonstrates the whole shape.

- Rendering a chart computes an aggregate that running the same definition refuses to compute for the same caller. `POST /charts/{id}/render` requires DATASET_READ (library/api.py:326) while `POST /analytics/{def}/run` requires DATASET_WRITE (api.py:144). Journey 3 asserts the viewer's render output is numerically identical to the editor's run result. That is probably the intended split (render persists nothing), but the UI consequence is that a viewer sees a greyed-out Run button next to a chart showing the exact numbers that button would have produced - worth an explicit product decision rather than an accident of which permission each route picked.

- Chart render has no paging or limit of its own. The view-backed branch is hard-capped at VIEW_RENDER_LIMIT = 1000 (api.py:41) with no way for the caller to ask for a different page, and the definition-backed branch has no cap at all, so the payload size is whatever the definition returns. A UI cannot render a "showing 1000 of N, load more" affordance because there is no cursor or offset parameter on the render route.

- `total_rows` means two different things on the two render branches. For a view-backed chart it is the source's true match count (`page.total`), so `total_rows > row_count` is meaningful. For a definition-backed chart it is literally `len(rows)` (api.py:345), so the field is always equal to `row_count` and conveys nothing. The response model documents it as "Rows the source matched in total. Larger than row_count means the render read only the first page" - a UI that renders a "showing X of Y" label from it will be silently wrong on every definition-backed tile.


### transform

- Run-history rows cannot show 'Published as v2' without N+1 calls. `TransformationRunOut` (app/features/transform/schemas.py:118) has no published_* fields; only `TransformationRunDetail` (schemas.py:133) adds published_version_id / published_dataset_id / published_version_number. So GET .../{definition_id}/runs returns rows the panel cannot badge, and the UI must issue one GET .../runs/{run_id} per visible row.

- The transformations index has no last-run information. `Page[TransformationOut]` carries only definition metadata, so a 'Transformations' list screen that wants 'last run 2h ago - failed' (the single most useful column on that screen) needs GET .../{definition_id}/runs?limit=1 per row.

- There is no way to answer 'which versions still contain this sheet?'. The `sheet-not-in-version` problem names the version that lacks the sheet, but nothing exposes the inverse, and dataset_sheets/logical_sheet_id is not queryable over versions. The recovery UI the journey performs by hand (re-pin to a version that still has the sheet) has to walk GET /datasets/{id}/versions and probe GET /datasets/{id}/versions/{n}/sheets one version at a time, matching on sheet name - which is exactly the name-based matching logical ids exist to avoid.

- An async run comes back with `job_id: null` (attach_job runs inside the handler, not at dispatch), so at the exact moment the UI shows 'queued' it cannot link to or poll /api/v1/jobs/{id}. It must poll the run detail instead - workable, but the job id the response model advertises is null precisely while it would be useful.

- GET .../transformations is hard-ordered by name (app/features/transform/repo.py:55) with no sort parameter. A builder list cannot offer 'recently edited first' without client-side sorting, which is wrong the moment the result is paged.

- A saved definition's output column list is not readable. `TransformationOut` has no `output_schema`, so to render the columns a saved pipeline produces the UI must POST .../preview (which executes SQL over a sample) or POST .../compile (which requires resending the whole step array it just read back). Folding the schema is pure and already computed at save time; exposing it on the definition would make the read a GET.


### explorer

- Two counts named 'duplicate rows' on one screen disagree by design. GET /versions/{v}/duplicates reports duplicate_rows = rows inside duplicate groups (2 for one duplicated pair, app/features/explorer/data_quality.py:65), while the profile run's `duplicate-rows` insight reports duplicate_row_count = rows - distinct rows (1, app/features/data_accelerator/services/profiling.py:241). Both surfaces are on the Data Quality tab. A UI that prints the insight's message ('1 fully duplicated row(s)') next to the duplicates tab's 2 looks broken. Pinned in journey 3 step 6 as `insight == duplicates.duplicate_rows - duplicates.group_count`.

- Row payloads are keyed by PHYSICAL column names; every other explorer surface is keyed by NORMALIZED names. /preview and /query (unprojected) return {"Region", "Amount", "Amount.1", "Notes"}, while /duplicates keys, /missing columns, and every column reference the caller SENDS use region/amount/amount_2/notes. The grid therefore has to carry a normalized->physical map from GET /versions/{v}/sheets just to bind a header to a cell, and a filter chip built from a duplicates group key cannot be applied to the rows the grid already holds without that map. Projecting (`columns: [...]`) aliases back to the requested names, so the two conventions are reachable from the same endpoint depending on whether a projection was sent.

- A views-list screen cannot show which saved views are broken without running them all. GET /datasets/{ds}/views returns the stored spec with no validity/health field, and a stale view only reveals itself as a 400 unknown-column from POST /views/{id}/run. Rendering 20 tiles with a 'needs attention' badge costs 20 run calls (each of which loads the parquet and does a COUNT(*)). A `valid`/`last_error` field on the list item, or a bulk validate endpoint, would collapse the N+1.

- A stale saved view's failure is indistinguishable from a user typo. Running a view whose column vanished returns code=unknown-column - exactly what a bad manual edit returns - with no view_id, no version_number, and nothing saying 'the stored spec is stale against the current version'. The screen has to infer 'your view is out of date' from the fact that it was a run and not an edit.

- The duplicates drill-down is unreachable on a dataset with a sensitive column. The group `key` is the only way to build the /query filter that fetches all rows of a group (examples are capped at 5, EXAMPLES_PER_GROUP), but for a masked column the key value is replaced by a digest (data_quality.py:248) and, even with the real value, guard_masked_query refuses filters on that column. So 'show all 40 rows in this duplicate group' has no implementation for a non-elevated caller. There is no group id or opaque group token the UI could use instead.

- POST /versions/{v}/profile-runs returns a bare list[ProfileRunOut] while GET on the same path returns Page[ProfileRunOut]. A typed client needs two shapes for one resource, and the create response has no total, so a UI that renders the create result and then re-fetches the list must handle both.

- The SQL console has no way to name, list, or reuse a result. Every execution mints query_<uuid>.parquet with no dedupe and no cap (proved: two runs of the identical SQL produce two artifacts), and result_file is returned only in that one response - there is no 'my recent query results' listing scoped to the dataset, so a user who navigates away loses the handle and the blob is retained anyway.

- No explorer endpoint accepts a tag or 'current' in the version path segment - it is always an integer version_number - while saved views DO accept version_selector {mode: tag|current}. A screen showing 'you are looking at production' has to resolve the tag to a number via a separate tags call and then hard-code that number into every explorer URL, and it will silently keep reading the old version after a tag rollback moves the pointer.


### discovery

- Three of the seven facet buckets have no matching list filter, and passing one is SILENTLY IGNORED rather than rejected. app/features/discovery/api.py:49 FacetsResponse emits classification, source_system and deprecated counts, but app/features/data_accelerator/api.py:198 list_datasets accepts only q/domain/favorites/include_deprecated/validation_status/has_schema_drift/documentation. Verified over HTTP: GET /api/v1/datasets?classification=internal and ?source_system=sap and ?deprecated=true each return 200 with the FULL unfiltered list (total 1 of 1), while ?documentation=mostly correctly 422s. A facet rail that renders 'Internal (1)' as a clickable chip therefore looks like it filtered and did not - the user sees the same rows and no error. Either add the three filters or drop the buckets; at minimum reject unknown facet params the way documentation does.

- The dataset-detail screen's Activity feed and Usage panel disagree about whether anything has happened, because uploads are not attributable to the dataset. app/features/discovery/repo.py:614 dataset_usage matches audit_log rows on path LIKE '%/datasets/{id}%', but POST /api/v1/upload carries the dataset id in the FORM BODY, not the path. Observed: a dataset with two uploads plus four governance writes reports writes=4, and a dataset whose ONLY activity is an upload reports downloads=0/writes=0/total_events=0/last_activity_at=null while its timeline shows version_created events. A 'Last activity' field that is null for a dataset uploaded five minutes ago is the panel's single most visible number.

- A /search/columns hit cannot tell the UI whether that column is already documented, so a 'Document this column' results list is an N+1. ColumnHit (app/features/discovery/api.py:37) carries dataset/sheet/column identity and dtype but no dictionary state, so decorating a 50-row result page with 'documented / needs docs' badges costs one GET .../sheet-metadata/{sheet_key}/columns per distinct (dataset, sheet) pair. Adding a `documented: bool` (or `business_name`) to the hit removes the whole fan-out.

- ColumnMetadataOut carries no orphan flag, so the dictionary editor cannot render 'documented but this column is gone' without a second endpoint and a client-side diff. app/features/discovery/api.py:129 - the list route returns entries for columns that have left the current schema with exactly the same shape as live ones, and sheet_key is always the sheet's current_sheet_key. The screen must additionally GET /datasets/{id}/sheets and subtract (this is what the journey does). The consequence is user-visible: PUT and PATCH 400 with unknown-column on precisely the rows the UI cannot mark as un-editable, so the Edit button on an orphan row is a guaranteed error.

- Timeline events have no id and no cursor, so the activity feed can only page by offset. app/features/discovery/api.py:149 TimelineEvent is (event_type, occurred_at, actor, details) - nothing addressable. A UI cannot deep-link an event, cannot de-duplicate client-side except by hashing the whole object (what the journey has to do), and any event written while the user is scrolling shifts every subsequent page by one. app/features/discovery/repo.py:736 orders by occurred_at DESC with no tiebreaker; I could not produce a microsecond tie through the API (version/tag/validation/profile events all landed on distinct timestamps, including four profile runs from one request), so this is latent rather than observable today - but a stable sort key would make the guarantee real instead of incidental.

- There is no DELETE on /datasets/{id}/sheet-metadata/{sheet_key}. app/features/discovery/api.py:196-251 offers PUT/PATCH/GET only, so 'undo documenting this sheet' means a PUT with an empty body relying on replace-by-omission semantics. That works (the record's fields all go null and documented_sheets drops), but the row stays, and it is the one place in the discovery surface where the UI's Delete affordance has to be implemented as a Save.

- A steward can record a retired sheet's grain but not its columns. PUT /sheet-metadata/{sheet_key} deliberately resolves against dataset_sheets so a sheet dropped from the current version can still be documented (api.py:217-221), but _resolve_dictionary_target with require_current=True (api.py:326) raises 404 code=sheet-not-in-version for the columns of that same sheet. The editor therefore shows an enabled grain/PK form and a dead column form on the same screen for the same sheet.

- /datasets/{id}/health tells the UI HOW MUCH is undocumented but not WHAT. The documentation dimension's evidence (health.py:283-288) is four counts - documented_sheets/total_sheets/documented_columns/total_columns - so a 'Finish documenting (1 of 2 columns)' CTA cannot link to the specific columns without re-fetching /sheets and the dictionary and diffing them. Returning the undocumented column names in evidence would make the CTA actionable in one call.

- Columns of HIDDEN sheets appear in /search/columns with nothing marking them. Verified: uploading the standard test workbook (whose 'Secrets' sheet is sheet_state='hidden') and searching q=k returns a hit with sheet_name='Secrets'. dataset_version_sheets rows are joined regardless of visibility (repo.py:40-48) and ColumnHit has no visibility field, so a catalog search surfaces scratch/hidden-sheet columns among real ones and the UI cannot gray them out or offer a 'hide hidden sheets' toggle.


### files

- POST /api/v1/tus/ returns 201 with a Location header and an EMPTY BODY (api.py:531-534), yet it has already created both the dataset and the version row. The UI cannot learn dataset_id or version_id from the create response; it must issue a second call, GET /api/v1/tus/{id}/status, purely to find out what it just made. Every other create in this service returns the id it minted. Asserted in test_a_cancelled_upload_can_be_retried_without_stranding_the_dataset step 2.

- Because POST /api/v1/tus/ creates the dataset row before a single byte arrives, a user who opens the upload dialog and walks away leaves a dataset in GET /api/v1/datasets with no readable version — and the catalog listing carries no 'has ready data' / current-version-status field, so a UI cannot filter it out or badge it. Proven in the same journey (the catalog contains the dataset id while the upload is still at offset 15). The same shape shows up after a cancel: the dataset stays listed with only a 'failed' version.

- A rejected sheet replace burns a version number. app/features/files/services/replace.py:53-58 creates the version row before the uploaded file is read, so posting a multi-sheet workbook into a single-tab slot 400s AND leaves a permanent (3,'failed') row in GET /datasets/{id}/versions — the version history a UI renders gets polluted by user typos, and there is no endpoint to remove it. Asserted in test_fixing_one_tab_of_a_workbook... step 7.

- GET /api/v1/datasets/{id}/versions/{v}/download accepts only `format` and `sheet` (api.py:792-803), while GET /api/v1/datasets/{id}/download also accepts `columns`, `limit` and `filter_expr` (api.py:767-789). A download panel that offers 'columns / row limit / filter' has to grey those controls out the moment the user pins a version, with no way to explain why. There is no version-pinned equivalent of the filtered download.

- GET /api/v1/samples/{filename}/data is the busiest JSON route in this area and has NO response_model (api.py:874-909) — it returns a bare dict built in read_sample_data. In the OpenAPI document it is an untyped object, so a generated TypeScript client gets `any` for filename/total_count/filtered_count/offset/limit/columns/data, which are precisely the fields the results table renders. Its siblings in the same file (Page[FileEntry], ExportResponse, SheetReplaceResponse, StorageUsageResponse) are all typed.

- There is no HTTP way to make an artifact collectable, so the admin screen's headline loop — 'run GC, watch usage fall' — cannot be driven as a UI drives it. Retention deadlines are stamped at write time (minimum 7 days for `export`) and orphans are protected by a 24-hour grace window, and nothing exposes a force-delete, a delete-artifact, or an expire-now action. The existing suite only reaches this state by UPDATE-ing `artifacts.expires_at` directly in Postgres (tests/test_artifact_retention.py::_expire). My journey therefore asserts the honest invariant instead (a sweep with nothing due frees nothing and deletes no live artifact). The missing capability is a DELETE /api/v1/samples/{filename}, or any admin action that makes bytes reclaimable.

- GET /api/v1/samples is the only listing of derived outputs and it has no filters at all — no `dataset_id`, no `file_type`, no date range (api.py:835-864). A 'files produced by this dataset' panel has to page through every artifact the caller can see and filter client-side, even though the underlying rows carry dataset_id and artifact_type.


### platform

- No machine-readable code distinguishes the two 'no team context' states. `POST /api/v1/upload` with no resolvable team returns 400 `code: "bad_request"` with detail 'Ambiguous team context — specify the X-Team-Id header' (app/features/auth/deps.py pick_active_team) for BOTH 'you belong to several teams, pick one' (show a team picker) and 'you belong to none' (show 'create your first team'). Those are opposite UIs and the only way to tell them apart is to have already called GET /auth/me — or to string-match the prose. A distinct code (e.g. `no-team-context` vs `ambiguous-team-context`) would let the interceptor branch.

- `GET /api/v1/jobs` has no `dataset_id` filter (app/features/jobs/api.py list_jobs takes only status/job_type). A dataset detail page that wants an 'Activity' panel must fetch the team-wide page and filter client-side, which silently truncates at limit=200 and makes its own pagination wrong. `GET /api/v1/jobs?dataset_id=` is the missing capability.

- An unknown `status` or `job_type` on `GET /api/v1/jobs` returns 200 with an empty page, indistinguishable from 'nothing is in that state'. The datasets list already fixed exactly this for `validation_status`/`documentation` by typing them as closed vocabularies that 422 — jobs did not get the same treatment, so a typo'd filter in a saved console view reads as 'all clear'.

- Inline-JSON uploads (`POST /api/v1/upload` with the `data` field) create no `jobs` row at all — only the file path goes through `process_uploaded_file_async`, which is the sole caller of `jobs.create_job("import", ...)`. A 'recent activity' or 'ingestion history' screen therefore shows some dataset creations and not others, with no way for the UI to know which.

- The audit trail's `team_id`/`resource_type`/`resource_id` are NULL for every platform-governance write, because `audit.resolve_target` only resolves dataset_id / version_id / team_id PATH params: `POST /api/v1/teams` and `POST /api/v1/webhooks` have no path params at all. So a compliance console can filter 'everything that happened to dataset X' but cannot filter 'every membership or webhook change in team Y' — the governance events are exactly the ones that fall out of the team scope. Verified in the journey: the four newest rows after a burst show a populated dataset attribution for the promote and nulls for the team creation.

- The webhook diagnostics drawer can only re-send a synthetic ping (`POST /webhooks/{id}/test`); there is no redeliver endpoint for a delivery row that failed. After the repair step in journey 3, the real `tag.promoted` event that was lost while the receiver was dead is unrecoverable through the API — the operator has to re-promote the tag to regenerate it, which is a governance write with real side effects.

- There is no way for a UI to page or sort `GET /api/v1/teams` or `GET /api/v1/teams/{id}/members` — neither accepts limit/offset (they wrap the full list in a Page). A team with a few thousand members renders in one unbounded response, and the member table can offer no server-side search.

- A cross-origin preflight (OPTIONS) response carries no `X-Request-Id` and none of the security headers, because CORSMiddleware is installed outermost (app/main.py) and short-circuits the preflight before RequestIDMiddleware/SecurityHeadersMiddleware run. Correct for CORS, but it means a preflight rejection is the one failure a UI cannot attach a request id to when filing a bug.


### datasets

- A UI cannot get the sheet_key of an UNCHANGED sheet from the workbook diff. WorkbookDiffResponse.unchanged is list[str] of display NAMES (schemas.py:431) while added/removed/modified all carry sheet_key. sheet_key is what PUT /datasets/{id}/sheet-metadata/{sheet_key} and quality rules' sheet_selector are addressed by, so the promotion-review screen has to make a second call (the sheet diff, or GET /sheets) purely to translate a name into a key before it can declare the primary key the row diff needs. My journey has to do exactly that.

- GET /datasets/{id} and GET /datasets/{id}/versions report DIFFERENT row_counts for the same version and both call the field row_count. DatasetMetadataResponse.row_count/column_count/columns/file_path describe only the default sheet's parquet (services/datasets.py:117 reads ver['path']), while VersionInfo.row_count is the workbook total. On a 2-sheet workbook the detail header says 3 and the version dropdown says 5. Nothing in either payload marks the grain, so a detail page that renders both shows two numbers that look like a bug.

- An aggregate with a caller-supplied `limit` gives a UI no way to know there are more groups, and no way to reach them. group_count is the size of the returned page, truncated is False by design when the caller (not the server cap) did the limiting (aggregation.py:310), there is no total-group-count field, and the persisted result_file artifact holds only the limited page (aggregation.py:405 COPYs agg_result, already LIMITed). So a grouped table cannot render a pager or a 'showing 2 of N' label without re-running the query at a larger limit and counting.

- The sub-collection list routes return a Page envelope whose limit/offset are meaningless. `_collection` (data_accelerator/api.py:83) sets limit=len(items), offset=0, and the routes accept no limit/offset query params — so GET /datasets/{id}/tags on a dataset with no tags answers {items: [], total: 0, limit: 0, offset: 0}. A generic paginated-list component that computes hasMore from limit/offset/total has to special-case /sheets, /versions, /tags and /versions/{n}/sheets, and none of them can be paged at all if a workbook ever gets large.

- The promotion gate's 409 validation-failed payload gives the run id but not the failing rules, so the release screen needs a second round trip (POST or GET the validation run, then map rule_id -> rule) before it can tell the user WHICH rule blocked them. The 409 already knows error_failures; carrying the failing rule names would collapse a three-call flow into one.

- There is no way to un-declare a sheet's primary key except by PUT-ing the whole sheet-metadata record with primary_key_columns omitted (REPLACE semantics), which also blanks grain and description. There is no DELETE on /datasets/{id}/sheet-metadata/{sheet_key}, so a UI that wants a 'clear key' button has to re-send grain and description it may not have loaded.


### mcp

- No tool lists a dataset's tags. `GET /datasets/{id}/tags` exists in REST, but manage_tags only reads the history of a tag you can already name, so a UI (or model) rendering 'which tags exist, and where do they point' must scrape the `tags` cell of describe_dataset's version table — which shows only the newest 10 versions, so a tag pinned to an older version is invisible.

- list_artifacts cannot page its matches. With dataset_id or kind set it suppresses `total` and emits no next-offset (offset moves the raw scan window, not the match list), so the only way to see more than `limit` matches is to raise limit toward 1000. An artifacts panel therefore has no page count and no cursor.

- Nothing on the surface can RUN saved work. list_saved_objects renders a view/analytics/chart definition in full and says outright it 'cannot create or run them', so an assistant that finds a colleague's saved view must retype its filter tree into query_rows by hand — the id is obtainable, the action is not, even though the same surface has eight write tools.

- aggregate and pivot hand back an artifact filename but never the artifact's column names, and read_artifact's `columns` must match the aliases the aggregation produced (not the source column names). The only way to learn them is to read the artifact once unprojected, which is exactly the token cost projection exists to avoid.

- get_dataset_health scopes its validation dimension to the CURRENT version, while manage_tags promote gates a NAMED version. After validating v1 the health screen still reads 'validation: unknown — No completed validation run for the current version', so a UI cannot tell from it whether the version it is about to promote will pass; no tool lists validation runs per version (check_quality shows only the latest run for one version at a time).

- get_activity's event_types filtering runs client-side over a bounded scan window because /timeline has no event_type parameter; the tool is honest about the window, but a UI filter over a busy dataset is structurally incomplete. Same shape for the jobs section (/jobs has no dataset filter).

- manage_relationships action='suggest' requires dataset:write because it persists suggestions, so a read-only reviewer cannot even ask what discovery would propose — the 'review the suggestions' screen is unavailable to precisely the role most likely to be reviewing.
