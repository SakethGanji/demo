# API / backend test automation: requirements catalog and coverage check

Perspective: a QA lead at a large regulated bank (hundreds of testers, existing Postman/Newman, RestAssured or Karate suites, SOAP and REST services, MQ/Kafka, Jira + Xray/ALM, Jenkins or GitLab CI). Scope excludes MFA/SSO (handled upstream).

Assessed on 2026-10-19 by reading code in `apps/test-builder/` and `apps/workflow-engine/src/`. `test-builder` is being actively extended by another agent (the `approve` command, `totp`, downloads and `bank-app/` were all new while I read), so its ratings are a snapshot. Nothing was edited and no servers or test suites were run.

Checks run: `node src/cli.ts --help` (lists `explore`, `run`, `verify`, `explore-api`, `check-trace`, `approve`); `npx tsc --noEmit` in test-builder (clean, no output); `python -m py_compile` on `engine/assertions.py`, `services/smoke.py`, `nodes/integrations/http_request.py` (ok); greps for `soap|wsdl|xml|kafka|oracle|postman|newman|xray|jira|junit|oauth|client_credentials|mtls` across both trees. Everything else was verified by reading.

## How to read the ratings

- **TB** = test-builder (Node/TS + Playwright CLI). **CS** = Command Studio (workflow engine, nodes, studio SDK, data tables, releases, app builder), as it ships today.
- **Covered** = a bank team could use it for this requirement today without writing new platform or tool code (writing the test itself is fine). **Partial** = a real piece exists or a workaround is possible, but a material part of the requirement is not met. **Missing** = would need new code (or is only achievable by an author writing raw code around the tool, with no support from it).
- I did not give credit for "Playwright can do anything in TypeScript": that is true of any code, and the requirement is whether the tool helps. Where hand-coding is the only route, the rating is Partial or Missing.
- One structural point drives many CS ratings: Studio's testing machinery (`engine/assertions.py`, `services/test_runner.py`, `fuzz.py`, `test_ai_service.py`, drift, smoke) tests **Studio workflows** (outside calls are mocked by default, `TEST_UNMOCKED_EFFECT`). It is not a framework for testing an external bank API. For API testing the realistic form is a workflow, or a `studio` Python backend calling nodes through the broker, whose nodes hit the system under test.

## 1. Requirements catalog and coverage

Priority is for a bank pilot (Must / Should / Could). 58 requirements: 40 Must, 16 Should, 2 Could.

Do not read the Partial numbers as "two thirds done": most Partials are a mechanism that exists but is missing the part a bank needs (identity on an approval, a token cache, a results model). The two tools are strong in different places and nearly disjoint: test-builder covers authoring, execution, evidence and CI contract for a single run; Studio covers environments, secrets, scheduling, versions and notification. Neither covers governance (identity, audit, retention), enterprise protocols (SOAP, MQ, Oracle, mTLS) or coexistence with existing suites.

### Platform building blocks vs testing-specific

- **Platform (helps any Command Studio team):** real identity/RBAC/audit; artifact store with retention; HttpRequest upgrades (mTLS, OAuth2, timeout, form/multipart, proxy, XML/XPath); database nodes (Oracle, DB2, SQL Server); messaging nodes (Kafka, MQ); remote runner agents and parallelism; JUnit/results ingestion endpoint; vault backends; HA scheduler.
- **Testing-specific (only a QA app needs it):** Xray/Jira sync and traceability; Postman import; requirement links; test review/approval workflow; flaky tracking and trend reports; data-driven per-row reporting; WSDL-driven generation; test-builder's own gaps (tags/`--grep`, shard flags, CSV data, DB/MQ helpers).

## 3. Verdict

**Not yet. A bank QA team cannot realistically build and run its API testing on Command Studio plus test-builder today, and cannot coexist with its current tooling.** Both pieces are credible foundations, but the combination fails the pilot on governance (gaps 1 and 4), on coexistence (gaps 2 and 3), and on protocols (gaps 6 to 9).

**Do Command Studio's existing pieces already let a team build a usable API-testing app without new code? No, only a demo.** What works today with zero new code:

- Chains of `HttpRequest` nodes with expressions, `If`/`StopAndError` as in-run assertions, `Poll` for async, `Loop` over data-table rows, `Postgres` for DB checks, per-environment `$vars` secrets with log redaction, a `Cron` trigger, `SendEmail` notification, workflow versions and release diff, and the app builder with data tables for a dashboard.
- A `studio` Python backend calling those nodes through the broker could implement a runner plus a results table. I did not exercise this path, and the Python sandbox has no network of its own, so everything must go through broker-exposed nodes.

What is missing even for the simplest bank flow: no OAuth2/mTLS/SOAP/Oracle/MQ; no JUnit export or ingestion; no result model or per-row/flaky/trend reporting; engine assertions score workflow test runs rather than live calls; tests run sequentially in one process; and authz, audit and an artifact store are absent. An app assembled from the existing nodes would be a hand-built, ungoverned toy that the bank's risk function could not approve.

**test-builder** is the better fit for the execution side and for coexistence: plain Playwright specs in git, local runs, exit codes plus JUnit, sha256 evidence manifests, secret scrubbing including inside trace zips, a `verify` determinism gate, and a builder-enforced policy layer. Its limits are narrow API generation, no SOAP/MQ/DB/data-driven support, `workers: 1`, no tags, approvals with no identity, and no central place for results.

### Minimum missing to make the answer "yes" (pilot slice)

Treat Studio as the control plane (identity, scheduling, results, dashboards, approvals) and test-builder as a runner that reports into it, since that is how it can sit beside Jenkins, Xray and Newman:

1. **Platform: real identity and audit.** Enforce `authz.authorize` with roles (author, reviewer, runner, admin), put the verified actor on approvals, runs and releases, make the audit log append-only, and remove bulk execution deletion.
2. **Platform: artifact/results store.** An endpoint that accepts a run (`junit.xml` + `evidence.json` + artifacts), stores objects with retention and hash verification, and exposes a results table. This single piece also serves ingestion of Newman/Karate/RestAssured JUnit (gap 3) and feeds dashboards (gap 5).
3. **Platform: HttpRequest and credentials.** OAuth2 client-credentials with token cache, mTLS/CA/proxy, timeout and retry, form/multipart bodies, XML response with XPath ops in `engine/assertions.py`.
4. **Platform: one enterprise database node (Oracle first) and one MQ/Kafka node.**
5. **Testing: Xray/Jira bridge** (push results with evidence, requirement id on each test) and a Postman collection importer.
6. **test-builder hardening:** make the approver identity-bound and stored centrally, add tags with `--grep`, `--workers/--shard` flags, CSV data-driven specs with one result per row, DB/queue helper fixtures, and ship results to the store in (2). Fix the policy bypass for raw clients by documenting that specs must import from `src/fixtures.ts` and lint for it.

With items 1 to 3 and 5 done, a pilot on REST APIs with an Xray-synced dashboard and governed approvals is realistic. SOAP, Oracle and MQ coverage (3, 4) determine whether it can take over from existing suites rather than sit beside them.
