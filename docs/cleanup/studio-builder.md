## Chat flow verdict and stuck states (BUG category)

Overall: the flow plan -> build -> preview -> edit is built as three separate state machines glued by a navigation. It is too complicated for the product; states below can get a user stuck.

- B1 (high). Composer is dead for most of the journey. BuildStudio FlowChat: `canDescribe` is true only in phase `describe` or `finished` (usePlanFlow.ts:124). During drafting, questions, review, input and building the textarea is disabled and the placeholder says "Answer the questions above to go on" etc. The user cannot say "actually make it for loans" mid-plan; they must use cards. In AppBuilderShell the same: `locked` while building (AppBuilderShell.tsx:787). A build that hangs or a card that fails to render leaves a blank dead chat.
- B2 (high). Partial or failed build: BuildStudio switches to AppChat only when `readyApp(build)` i.e. status === 'done' (studioLogic.ts:17). A `partial` build already has an app (builtAppId) but the studio keeps FlowChat, where `canDescribe` makes the user describe a NEW app via `revise` (usePlanFlow.ts:54) instead of fixing the half-built one. The preview shows the app but you cannot chat to edit it unless you navigate manually to /apps/<id>.
- B3 (high). Global singleton stores not reset in BuildStudio. `useAppBuilderChatStore` (messages, isStreaming) and `useAppDocumentStore` are module-level. AppBuilderShell resets both on appId change (AppBuilderShell.tsx:245-257), BuildStudio only resets the doc store inside LivePreviewPane (:180) and never clears the chat store. A previous app's messages or a leftover `isStreaming` can appear in a new app's chat; `conversation_history` (last 6 messages, useAppBuilderChat.ts:119) then feeds the AI the wrong app's history. Needs a repro, but the code path exists.
- B4 (med-high). Chat memory is reconstructed, lossy. After "Open app" or reload, restoreChatMessages rebuilds the chat from version prompts (lib/restoreChat.ts), one line per answer. Tool rows, errors and replies vanish; the plan thread vs AI thread are two different lists (`prelude` + messages). Server keeps no transcript. A bank user returning to an app sees a different conversation than the one they had. Fix: persist the chat server-side per app (single source), delete restoreChat.
- B5 (med). Concurrency/409 handling in useAppBuilderChat: sends `base_version_id` from the in-memory doc store (:162); a failed autosave sets `dirty` (:106) so the next message gets 409 and the error says "Reload the app" (:194), which the user may not know how to do; the recursive retry (:330-333) runs inside `finally` after `setStreaming(false)`, with `removeLast(2)` which assumes exactly the two messages it just added. Simplify: server always applies on head, client does not send base_version_id for chat turns; one app, one writer.
- B6 (med). Auto-fix loop: AppBuilderShell.tsx:345-365 auto-sends a fix message when preview errors appear (once per version), via refs (`autoFixPending`, `fixedVersions`) declared after use. It can fire a message the user never typed while a visual save/stream is racing. Combine with `search.prompt` auto-send through a module-level Set (:82). Two hidden auto-senders. Prefer an explicit "Fix with AI" button only.
- B7 (med). Phase derivation depends on `planFlowStore.flows[pid]` (per PROJECT, in memory, lost on reload) plus `plan.draft` and the active build list (usePlanFlow.ts:26-43). A user with a second project tab, a reload, or a previous finished build gets different phases for the same URL; `visible` for an app depends on `flow?.appId === appId || making`. One conversation per project means two apps in one project share one flow. Fix: key the flow by app id (create the app row first).
- B8 (low). Mode state: AppBuilderShell has `mode` (plan/preview/code), `userPickedMode` ref, auto-switch effect (:320) and `?view=plan`; BuildStudio has `tab` plus responsive `show()` (:352) with 'chat' mapped to 'preview' on non-phone widths. Easy to land on the wrong pane after resize.
