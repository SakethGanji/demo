## Verdict

- **Data-loss paths were found.** Each one is reported below with a repro.
- **What holds:**
  - The migration itself is sound on a quiet system.
  - Every live CSV-era version round-trips exactly.
  - Old compare, explain, `POST …/verify`, run and holdout JSON are byte-identical outside `storage` (106 of 106 calls).
  - Every old run re-verifies, before and after cleanup.
  - The job survives a kill mid-version and a kill between the commit and the rename. It is idempotent.
  - GC never lists a live blob.
- **What breaks:**
  - Concurrency: a run started while its version is being migrated (critical).
  - Cleanup's verify-all gate.
  - Three kinds of evidence that are never made blobs: Feature Lab job records, the split a tombstoned version's run trained on, and a split drawn mid-migration.
  - Laundering of some outside changes.

| Rank | # | Finding |
|---|---|---|
| critical | C1 | A run created while its CSV-era version is being migrated loses its split. The new split JSON is not migrated or pinned, the run's re-verify fails, and cleanup deletes the JSON. The job reports success. |
| major | M1 | Cleanup counts verify-all passes since the last *finished* job, not per folder. A cleanup during a later job deletes a folder migrated seconds earlier, with 0 passes since its migration. |

| major | M5 | Outside changes made with DB access are laundered, although the evidence to catch them exists:<br>• split JSON + `split_files.sha256`: the recorded `content` copy is not compared;<br>• `data.csv` + `datasets` hashes: the hash-chained audit row `dataset_version_created` is not compared. |

### C1 (critical): a run created during its version's migration loses its split

- **Where:** `lake/migrate.py`.
  - `inspect()` lists the split files and `_runs_of()` lists the runs before the transaction.
  - Nothing stops the app from drawing a split or creating a run for that version until the commit.
  - The folder rename then moves anything new into `<id>.migrated/` without making a blob of it.
- **Effect:**
  - The run trained on a split JSON that is not migrated (no Parquet split, no `legacy_json` blob) and is not pinned. Its `run_inputs.split_id` stays NULL.
  - Re-verify fails.
  - Cleanup deletes the JSON.
  - The only other copy is `split_files.content`, which P23 plans to drop.
  - The job and `lake_migrations` say `migrated`: silent.
- **Repro:**
  ```
  cp -a $S/build/snap_head $S/build/data
  x2/run_hook.sh $S/build/data 8712 X2_SLOW=1.5 X2_SLEEP_AFTER_RUNS=ds_28492196:25
  python x2/during_job.py build/state.json 8712 out.json   # posts the run on A3 with label 'active' inside the window
  GET /api/admin/lake/runs/<rA3c>/verify                  # ok:false, split.now null
  ls build/data/datasets/ds_28492196.migrated/splits/     # random-stratified__active-….json, no blob with its sha
  ```
- The window is the version's read/write/proof time. It is milliseconds here and seconds at 10M rows (§5.11 "a few seconds per 10M-row version").
- **Fix direction:** one of:
  - refuse new runs, splits and edits on a version while its migration holds it (a `migrating` flag checked by `queue_run` / `ensure_splits` / the edit);
  - or, inside the commit transaction, re-list the folder's split files and runs and roll back if they changed.

### M1 (major): cleanup's two-pass gate is global, not per folder

- **Where:** `_verify_passes` counts passes after `catalog_meta lake_migrate:finished_at`, which only a *finished* job writes. `cleanup` doesn't check whether a job is running or when each folder was migrated.
- **Effect:**
  - A cleanup during a later job deletes folders migrated after the last two passes.
  - So does a cleanup after a killed job that has not finished yet: `finished_at` is still the previous job's.
  - In the repro, the only thing that saved the data was the `legacy_csv` blob. Files never made blobs (M2, C1) are lost.
- **Repro** (from a migrated dir with 3 skipped versions):
  1. Undo the outside changes.
  2. `GET /admin/lake/verify-all` ×2.
  3. Start `x2/run_hook.sh … X2_SLOW=5`, then `POST /admin/lake/migrate?dry_run=0`.
  4. Once `ds_2e281f4a.migrated` exists, run `POST /admin/lake/migrate/cleanup?dry_run=0`.
  5. The answer is 200 and the folder is deleted (`output/cleanup_midjob.json`).
- **Fix direction:**
  - count passes per folder, after its own `lake_migrations.at`;
  - refuse cleanup while a `migrate` job is queued or leased.

### M2 (major): Feature Lab job records are dropped

- **Where:**
  - `_evidence()` skips directories.
  - `finish_folder()` copies only top-level `*.json` and `KEEP_NAMES`.
  - `featurelab/` holds `fl_<job>.json`: the request, the search journal (kept and rejected candidates, the leakage verdicts) and the result that made a version.
- **Effect:**
  - Right after migration, `GET /datasets/{id}/feature-lab` lists 0 jobs (it was 1, or 2).
  - Cleanup deletes the files (4 of them).
  - fl2 v2 is a Feature Lab version, so the record of *how it was derived* is gone.
- **Repro:**
  1. `record.py` before and after → `featurelab_ds_3d74a646: jobs[len] 1 → 0`.
  2. `x2/unpreserved.py build/data` → 4 `featurelab/*.json` with no other copy.
- **Fix direction:** keep every file under the folder (recursively) as a `legacy_json` blob, and copy `featurelab/` into the fresh folder. Or at least refuse `cleanup` while a `.migrated` folder holds a file with no blob.

### M3 (major): a tombstoned version's split is not kept

- **Where:**
  - `_migrate_tombstone` keeps only the folder's files (TOMBSTONE.json, lineage.json, holdout_sample.csv).
  - The deleted version's split JSON was removed with its data by the DL2 delete. It is now only in `split_files` (`content`, sha = `run_011a72eb`'s `splits_sha256` `d57d5498…`).
  - No blob is made, the run pins nothing, and `verify_run` returns early for a deleted version, so the split is never checked.
- **Effect:**
  - §5.10 says "the splits pinned by runs … stay" on delete.
  - Here the split survives only in a table the plan calls retired. P23's note says to carry `split_files` "only while CSV-era versions remain", which is no longer true after a full migration.
- **Repro:** after any full migration:
  ```sql
  SELECT dataset_id, file, sha256 FROM split_files WHERE sha256 NOT IN (SELECT sha256 FROM blobs)   -- ds_15143c8e ×2
  SELECT role FROM blob_refs WHERE owner_id = 'run_011a72eb'                                          -- none
  ```
- **Fix direction:** in `_migrate_tombstone`, make each `split_files.content` a `legacy_json` blob, pinned by the runs whose `splits_sha256` equals it. Or keep `split_files` permanently.

### M4 (major): pre-DL4 split files are migrated without the evidence check that exists

- **Where:** `inspect()` marks a split with no `split_files` row and no run-recorded hash as "unrecorded" and migrates its current bytes. P10 documented this decision.
- **What it ignores:** every pre-DL4 run's `holdout_predictions.csv` names its holdout rows. `inspect` could compare them with the JSON's holdout (here they differ by 1 row).
- **Effect:**
  - An outside edit made with file access only becomes the version's Parquet split.
  - A new run on the migrated version gets a holdout that differs from the old run's.
  - `roundtrip.py` shows Parquet holdout ≠ rL1's `holdout_predictions` rows, and Parquet fold ≠ the original.
- **Repro:**
  1. `tamper.py state.json <copy> e`
  2. dry run → `ds_3d74a646 migrate "hashes match"`
  3. job, then `roundtrip.py` → `run_0fa8bca1 parquet_fold_eq_original: False, parquet_holdout_eq_pred_rows: False`
- **Fix direction:** for an unrecorded split, require every run that read it (`splits_path`) to have `holdout_predictions` rows equal to the JSON's holdout. Otherwise skip it as `split_changed`.

### M5 (major): outside changes with DB access are laundered although evidence exists

1. **Split JSON + `split_files.sha256` on a version with no runs** (accounts v3, change c):
   - the dry run says "hashes match", and the job migrates the changed split;
   - `split_files.content`, the compressed copy taken when the split was drawn, still holds the original bytes but is never compared.
2. **`data.csv` + `datasets.sha256` / `legacy_sha256`** (loans relabel, change f):
   - migrated with the changed bytes;
   - `audit_log` row 28 `dataset_version_created` (hash-chained) still names the original hash `2aceec23…`.

With runs, change d was caught (`MISMATCH (runs)`).
- **Repro:** `tamper.py state.json <copy> c f`, dry run → both `migrate`.
- **Fix direction:**
  - compare `sha256(zlib.decompress(content))` with the file;
  - compare the stored hash with the version's creation audit row (the audit chain is verifiable).

### M6 (major): versions without a row map lose their pairing in diff

- **Where:** fresh ids for `root_rows_source = "none"`, with the edge set `inferred = 1`. `GET /datasets/diff` still pairs by `__row_id`.
- **Effect:**
  - Before: SQL load v1 vs refresh v2 (and v3) → `method: row_hash, identical: true, matched 3000`, "identical tables".
  - After: `method: row_id, identical: false, matched 0, added 3000, removed 3000`.
  - The diff of an old pair changes meaning, which §7 risk 9 rules out.
- **Repro:** `GET /api/datasets/diff?a=ds_3dff21e6&b=ds_0e8fe4bb`, before (acfe988) and after (head). Output: `before/` and `after/` are in `output/jdiff_m1.txt`.
- **Fix direction:** diff must honour `inferred` edges (fall back to `row_hash` / identical-sha as before). Or give a no-map version the root's ids when its table sha equals an ancestor's.

### Minor

- **m1:** `frames._v1_column` turns a bool column with nulls into `arr.to_pandas().astype(object)`, which gives `None`. The CSV read gave `NaN`.
  - `_equal` (`Series.equals`) and `assert_frame_equal` treat them as equal.
  - `astype(str)`, `map` and `type(v)` don't. 5 pre-DL4 loans versions are affected (column `flag`).
  - Compare and explain were unaffected here.
  - Fix: set `v[pd.isna(v)] = np.nan`, as the text branch does.
- **m2:** `POST /datasets/{id}/edit` on a CSV-era version with no row map → 500 (`datasets._edit_base`: `pr.p.attach`).
  - A version skipped by the migration (an outside change) that has no row map can't be edited until it is resolved.
  - Repro: `POST /api/datasets/ds_0e8fe4bb/edit` on `snap_head` with the head.
- **m3:** `cleanup` checks only the `legacy_csv` blob. A missing `legacy_json`, split or `frozen_holdout` blob of the folder would not stop the delete.
- **m4:** old run configs carry absolute paths. With a data dir copied to another path, acfe988's explain and holdout calls return 404 (pre-existing).
  - The migration itself is path-independent, by folder name.
  - `verify_run` reads `Path(cfg["splits_path"])` absolutely for a split it has no blob for. That reads outside the data dir if the old path exists.

## Deviations

- **"GET /compare"** is `POST /api/compare {a, b}` (as in P09/P10).
- **Fault injection** is a wrapper process around the head API (`os._exit(9)` at chosen points), not a timed `kill -9`. The effect on the process and on the queue's lease is the same; the janitor saw a dead pid and re-queued the job.
- **Concurrency:**
  - The window was widened with a sleep hook to make the race reproducible.
  - The code path is the production one. Without the hook the window is the version's read and write time.
- **Not run:**
  - multi-million-row versions;
  - S3/MinIO (P10b);
  - Postgres (P23);
  - a crash during cleanup;
  - concurrent Doctor, Feature Lab or SQL refresh during the job.
