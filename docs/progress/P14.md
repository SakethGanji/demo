# P14: saved joins, join frames and runs on a join (lane D2)

**Plan:** `docs/plans/data-platform-final.md` §5.8, §2 (`joins`, `join_frames`, `run_inputs` role `join_input`,
lineage kinds `join_frame` / relations `joined_from`, `merged_from`), §9.1 row P14, §7 risk 11 (one join path), §11.

**Base:** `motion-components` @ 5c5edd0. Merged with P13, P21 and F-X2 (a30fe3d) before the push. After the merge the
SQLite chain was run again, and its output was identical.

## Result

- **Saving a join.** `POST /datasets/{root}/joins` saves a join spec on a dataset root. The spec is checked against
  a concrete version first.
  - A bad spec gets a 400 with a code and nothing is saved. Bad specs include: 1:n without an aggregate, an n:1 whose
    right side is not a key, an unknown table or column, an aggregate of the wrong type, and two output columns with the
    same name.
  - A good spec answers 201 with the coverage of every joined table.
- **Materialising a frame.** `POST …/versions/{v}/frames {join_id}` builds the frame. It has exactly the grain's rows
  and `__row_id`s; this is asserted. The frame is written once as a content-addressed `join_cache` blob. Asking again
  returns `cached: true` (200).
- **Training on a frame.** `POST /runs {dataset_id, join_id, label}` trains on the frame.
  - The run uses the grain table's pinned split.
  - It goes through the P11 budget: under the budget the whole frame is read; over it, the recorded sample is used.
  - It records the frame's cache sha as `table_sha256` and `read_sha256`, with `join_frame_id`, plus one `join_input`
    row per input table.
  - Re-verify passes.
- **Comparing runs.** `POST /compare` of a table run and a join run on the same grain is **paired** on the same 800
  holdout rows.
- **Blocking deletes.** Deleting a version that a join run read through its frame is **blocked by that run**. This
  holds for a table in another dataset too (a `merged_from` edge). Usage and lineage show the frame and the run.
- **Both engines.** SQLite and Postgres give the same output: the same `frame_sha256`, cache-blob sha, scores and
  coverage.

## What was built

| Piece | Where | What it does |
|---|---|---|
| **Spec** (`ensemble.join/1`) | `catalog/joins.normalise` | `{grain, joins: [...], where: null}`. Each join is one of:<br>• `n:1` / `1:1`: `table`, `on` (`[[grain col, table col]]` or `["col"]`), `columns` (default: every column except the key), `prefix` (default `<table>__`);<br>• `aggregate`: `aggs: [{name, fn, column?, window?}]`, where `fn` is count / count_distinct / sum / mean / min / max and `window` is `{date, relative_to, days}` (negative days look back). There is an optional `prefix`.<br>`table` is a table of the version the join is applied to, or `{root_id?, version_id, table}`: another dataset, pinned to a version.<br>The canonical form (defaults filled) is stored and hashed (`spec_sha256` = sha256 of the canonical JSON). There is no free SQL. |
| **Validate** | `joins.validate` | **Checked against a concrete version:**<br>• the tables exist (400 `table_unknown`, naming the version's tables);<br>• the columns exist (400 `column_unknown`, naming the join and the column);<br>• the `on` columns compare (400 `join_types`: a number vs a text column);<br>• sum / mean need a number column (400 `agg_type`);<br>• output names are unique and never `__row_id` (400 `column_collision`).<br>**Explicit `1:n`** gives 400 `one_to_many`.<br>**The right side of an `n:1` / `1:1`** must be unique among its non-missing values. A declared key (`table_keys`) is marked `how: declared`; otherwise it is counted now (`checked`). Repeats give 400 `one_to_many` with the count. A `1:1` also checks the grain side (`not_one_to_one`).<br>**Coverage, per joined table:** `matched`, `coverage`, `orphans` (a key with no match), `missing_key`, and `rows_aggregated` for an aggregate. |
| **Saved joins** | `joins.save`, `list_joins`, `get` | **Versioned by name:** a changed spec under the same name is `spec_version + 1`. The same spec and name returns the existing row (200). The same spec under another name gives 409 `same_spec`: one frame identity, one join.<br>The version it is checked against is `version_id`, else the root's default, else its latest version.<br>Audited as `join_saved`, with the coverage. |
| **`frames.materialise`** | `frames.py` (`join_sql`, `materialise`, `GrainError`) | **The only join code path.** It is one DuckDB `COPY (SELECT …) TO frame.parquet` on a job connection, so the job's memory limit and spill cap apply and pandas is never involved:<br>• the grain's rows, `LEFT JOIN` each n:1 table;<br>• an aggregate is `LEFT JOIN (… GROUP BY key)`. With a date window it is grouped by the grain row instead, using `agg FILTER (WHERE date in window)`;<br>• count is `COALESCE(…, 0)`; sum and mean are DOUBLE;<br>• columns with different types in a join condition are cast to one family;<br>• `ORDER BY g.__row_id` with `preserve_insertion_order = true` turned back on for the COPY.<br>**Then the assert:** `count(frame) = count(grain)`, `count(DISTINCT __row_id) = count(*)`, and the ids strictly increasing. Otherwise `GrainError`: 409 `grain_violated` (audited `join_frame_refused`), and nothing is cached. |
| **Join frames + cache** | `joins.frame` | **Identity:** `frame_sha256 = sha256(canonical({spec_sha256, input table shas in spec order}))`.<br>**Cached:** when a row with that identity exists and its blob is live in the store, the answer is `cached: true` with no work. Otherwise the frame is materialised into `store.tmp_dir`, then:<br>• `store.put_file` (content-addressed; no path is built from a key);<br>• a `blobs` row (kind `join_cache`, live);<br>• `blob_refs (join_frame, <id>, cache)`;<br>• the `join_frames` row (inputs pinned: version, table, table_sha256, rows; the schema; `cache_blob`);<br>• the edges: `dataset -joined_from-> join_frame`, one per input version, whose meta lists its tables; `merged_from` for another root's version.<br>A lost cache blob is written again, and `rematerialised` is reported. Audited as `join_frame_materialised`. |
| **Reading a frame** | `frames.py` | `JoinFrame(id)` reads like a one-part lake table, whose part is the cache blob with role `frame`. `lake_table`, `read`, `columns`, `n_rows`, `hash_table` and `input_sha256` all take it.<br>`ReadHash` gives the **cache file's sha256** for role `frame`. That is the hash the worker's data gate compares, and the one recorded as `read_sha256`.<br>`use_join(id)` makes `input_ref_for(v)` name the frame, while `table(v)` stays the grain. That is how the profile, split and checks of `_create_run_on` work unchanged. |
| **Runs on a join** | `engine/api.py` | **`RunCreate.join_id` → `_create_join_run`:**<br>• the frame (materialised or cached);<br>• the label must be a grain column (400 `label_not_in_grain`), because the split is the grain's;<br>• the profile of the frame (`joins.profile`, cached by frame identity and target; a sample above `PROFILE_FULL_ROWS`);<br>• then the normal run path, under `use_table(grain)` and `use_join(frame)`.<br>**`queue_run` → `_join_input`:**<br>• the expected hash is the cache sha;<br>• `input_table` carries `join_frame_id`;<br>• `cfg.join` holds the join id, name, spec version and sha, the frame sha, the cache blob and the pinned inputs;<br>• the grain's split gate (P09);<br>• the cache file and every pinned input are hashed again now. A difference gives 409 `data_integrity`, audited, unless an admin override is armed.<br>**After the run row exists:** `joins.record_run` writes one `join_input` row per input, `blob_refs (run, join_frame)` and the `join_frame -trained_on-> run` edge. |
| Worker / P11 | `engine/worker.record_run_input`, `lake/frame.plan` | **The train row:** `join_frame_id` (one column added to the insert).<br>**`LF.plan`:** treats a join frame like a Parquet table, so the P11 estimate, sample, `read_rows` and batched holdout scoring work on it. |
| **Usage / blockers** | `catalog/dsets.usage`, `_guard` | **`usage(ids)`** adds the runs reached through `joined_from` / `merged_from` → join frame → `trained_on`. Each has `via_join {join_frame_id, tables, relation}`. A new `join_frames` list is returned too.<br>**Blockers and the delete guard** therefore block a version that a queued, running or succeeded join run read. The message names the table and the frame. |
| **Lineage** | `catalog/lineage.py` | The tree includes `join_frame` nodes (join name, spec version, frame sha, rows, cache) and their edges.<br>`UP` walks `joined_from`. It does not walk `merged_from`, so a join run's root stays its grain's root. |
| **Routes** | `catalog/joins_api.py` (new), `main.py` (one include) | **Saved joins:**<br>• `POST /api/datasets/{root}/joins` (`data.version`);<br>• `GET …/joins`, `GET …/joins/{id}` (with its frames), `POST …/joins/{id}/validate` (`data.read_meta`).<br>**Frames:**<br>• `POST /api/datasets/{root}/versions/{v}/frames` (`run.train`: "also join materialisation" in the policy);<br>• `GET …/versions/{v}/frames`;<br>• `GET /api/datasets/{root}/frames/{id}?verify=1` (the cache and every input hashed again; the runs on it).<br>Authz coverage at startup: 168/168. |

## Deviations and notes for dependants

- **Every frame is cached, whatever its size.** The plan has a cache blob only from `JOIN_CACHE_MIN_ROWS` (1M) rows.
  Here the cache blob is the frame:
  - the worker reads it;
  - a run's `read_sha256` is its file hash, so re-verify is a byte comparison;
  - a 4,000-row frame is 81 KB.

  Below 1M rows the bytes are small, and re-running the join on every read would make `read_sha256` the hash of a
  recomputation instead of a stored file. Revisit if small frames ever dominate storage.
- **`where` is refused** (400 `where_unsupported`). A frame has every grain row, so the grain's pinned split maps
  1:1 onto it by `__row_id`. A filtered frame would need its own split.
  - The workaround is to filter the grain table with an edit, which makes a version, and join that.
  - Adding `where` later means drawing the split on the frame. The edit compiler's AST is the plan's whitelisted form.
- **The label is a grain column.** The holdout is the grain table's pinned split, which is why a table run and a join
  run on the same grain pair in `/compare`. A label made by the join (an aggregate) gets 400 `label_not_in_grain`.
- **The frame identity is content only.** Applying the same join to another version whose input tables have the same
  shas (for example a version that only declared a key) returns the existing frame with `same_frame_as_version`.
  The `joined_from` edges point to the version the frame was first made on.
- **`cached: true` checks that the blob exists, not its bytes.** Every run on the frame re-hashes the cache file and
  every pinned input at queue time, and again in the worker's data gate. `GET …/frames/{id}?verify=1` re-hashes on
  request.
- **Compare is `POST /compare {a, b}`.** That is the existing route; the plan's row says GET.
- **Files outside the row** (small, all D / D2):
  - `engine/worker.py`: one column (`join_frame_id`) in the train row's insert;
  - `lake/frame.py`: one line, so `plan` treats a join frame as Parquet;
  - `main.py`: one `include_router`.

  P21's `engine/api.py` changes merged cleanly except one hunk in `queue_run`. F-X2's `_csv_hold` around
  `store.create` was kept, and the P14 record follows it.
- **P15 (registry, parity):**
  - a join run's config has `input_ref {kind: join_frame}`, `input_table.join_frame_id` and `cfg.join` (join id,
    spec version and sha, `frame_sha256`, `cache_blob`, pinned inputs);
  - `frames.input_sha256(cfg)` returns the cache file's sha (so `registry/build` gets the right data hash);
  - `run_inputs` has the `join_input` rows;
  - the serving parity check should rebuild the frame from the pinned inputs with `frames.materialise(spec, inputs,
    out)`, the one code path, and compare rows by `__row_id`;
  - batch scoring a join model needs a frame over the batch files, with `frames.join_sql` on lake tables built from
    them.
- **P21 / cross-team:** a join input in another dataset is only checked to exist and be live. It goes through no
  visibility or share check. P21's `visible_teams` should be applied in `joins.inputs_for` when a pinned input is in
  another team.
- **P24 (GC):** `join_cache` blobs are referenced by `blob_refs (join_frame, cache)` and by every run on the frame
  `(run, join_frame)`. A frame with no runs is re-creatable, so its cache is a GC candidate once unreferenced by runs.
- **U2:** the join builder:
  - `POST /datasets/{root}/joins` for validation and coverage (400 codes: `one_to_many`, `column_unknown`,
    `table_unknown`, `join_types`, `agg_type`, `column_collision`, `bad_spec`, `bad_agg`, `where_unsupported`);
  - the list and `…/validate`;
  - `POST …/versions/{v}/frames`;
  - the run form's `join_id`, with the label taken from the grain;
  - usage's `via_join` and lineage's `join_frame` nodes.

  No UI file was changed, so there was no `npm run build`.
- Scratch data dirs, the Postgres cluster and the API processes were removed or stopped. The pinned venv is in the
  session scratchpad only.
