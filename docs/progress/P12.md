# P12: multi-table datasets and Excel (lane D)

**Plan:** `docs/plans/data-platform-final.md` §2 (version_tables, table_files, table_keys, table_relations), §3.2,
§5.1 step 2, §5.2, §9.1 row P12, §11 item 5 (python-calamine, openpyxl as the fallback).

**Base:** `motion-components` @ c386e96 (X2 done; F-X2 and F-JOBS running in parallel).

## Result

- An upload can hold several files. A CSV or Parquet file is one table; a workbook gives one table per non-empty sheet.
- A plan PATCH says, per table, what happens: new, rewrite (matched to the parent's table, as in P06), append, skip;
  and for the parent's tables that were not uploaded, carry (the default) or drop. It also declares keys and relations.
- The commit writes one version. Carried tables keep their table sha and add no bytes. An appended table reuses the
  parent's parts and adds an `append` part. Keys, relations and splits follow the carried tables.
- `PUT …/tables/{t}/key` and `PUT …/relations/{name}` make a new version with every table carried.
  `GET …/relations` returns the orphan counts.
- `POST /runs {dataset_id, table}` trains on the named table (the primary table or any other).
  `?table=` / `{table}` works on diff and edit too. Verify covers every table.
- A bad workbook, an empty or header-only sheet, and two sources that would give the same table name all answer
  400. None answers 500.
- One CSV goes through exactly the P05 / P06 path as before.
- The whole chain gives the same output on SQLite and on Postgres (`ENSEMBLE_DB_URL`). The only difference is one
  time-limited fit's score. The table and data shas are equal on both engines.

## What was built

| Piece | Where | What it does |
|---|---|---|
| **Excel reader** | `lake/excel.py` (new) | `read_workbook` reads every sheet with **python-calamine**. **openpyxl** takes over when calamine is not installed or cannot open the file.<br>Each sheet is streamed to a UTF-8 CSV in staging, so it gets the same typed import as a CSV (§5.1 step 3: leading zeros kept as text, failed casts as text with a warning, ambiguous dates as text).<br>**How cells become text:** a whole number has no `.0`; a date is ISO; a date-time is `YYYY-MM-DD HH:MM:SS`; booleans are true / false; an error cell (`#N/A`) is missing; text keeps its exact characters (`"0042"` stays `"0042"`).<br>**Header:** the first row with a value. Trailing empty rows and columns are dropped.<br>**Hidden and chart sheets** are left out and listed.<br>**Limit:** 200 MB per workbook.<br>**400 `excel_unreadable`:** a file that is not a zip, an old `.xls` or password-protected (OLE) file, or a broken workbook. |
| **Sources** | `lake/upload._sources` | Lists an upload's tables in order. A table's name comes from the file name or sheet name (lower case, `[a-z0-9_]`).<br>**`sheets`** lists every sheet as included, `empty sheet`, `hidden sheet: name it in the plan…`, or `left out by the plan`.<br>**400s:**<br>• `empty_workbook` when a workbook has no sheet with data;<br>• `duplicate_table` when two sources give the same name (two sheets, a sheet and a CSV, the same workbook twice). Nothing is renamed silently.<br>A sheet's typing error names the sheet: `header_only.xlsx, sheet 'only_header': This file has fewer than two data rows.` |
| **Plan PATCH** | `lake/upload.patch_plan`, `_parse_tables_plan`, `norm_relation` | **`tables: {name: {action, types, formats, match, key}}`**<br>• `action` is one of new / rewrite / append / carry / drop / skip;<br>• `match` is P06's `{method: key / declared / row_hash / none, columns}`;<br>• `key` is a column or a list of columns.<br>**`primary_table`**<br>**`relations: [{name?, from: {table, columns}, to: {table, columns}, cardinality: n:1 / 1:1}]`**<br>Shapes are validated (400 `bad_plan` / `bad_action` / `bad_relation` / `bad_key`). A changed plan clears the check, as in P05. |
| **Check (several tables)** | `lake/upload._check_multi` | **Per table:** the typed file `typed.<i>.parquet`, the schema with reasons, the warnings and blocks (each with its `table`), and the `action`:<br>• the default is `rewrite` when the parent has the table, else `new`;<br>• **rewrite** gets P06's `next_version` (candidates, every method simulated, preselect). Only the primary table gets the parent's holdout and target;<br>• **append** types the file with the parent table's types (`soft_types`) and blocks on different columns (`append_columns`) or types (`append_type`). It reports `parent_rows / rows_added / rows_after`.<br>**Whole version:** `carried`, `dropped`, `primary_table` (from the plan, else the parent's, else the first table) and `target_unknown`, which names the table that does have the column.<br>**Keys and relations:**<br>• the plan's keys are checked on the typed files (`key_invalid` block);<br>• the plan's relations get orphans, coverage and whether the `to` side is unique (`relation_to_not_unique` block);<br>• **`suggested_relations`** comes from shared key-like columns, with orphan counts. Suggestions are never stored.<br>`commit_needs.match` names the rewritten tables. |
| **Commit (several tables)** | `lake/upload._commit_multi` | One `VersionWriter` (job_id = the upload). The parent's tables come first, in their order, then the new ones.<br>**Per table:**<br>• **new:** ids `0..n-1` for a new dataset, else from the root counter (`reserve_row_ids`);<br>• **append:** `w.append` with new ids above the table's max and each column `CAST` to the parent's type, written as an `append` part. On the primary table the holdout is carried by join, and new rows get the seeded share (§5.7);<br>• **rewrite:** P06's match. `match` is `{table: {…}}`, or the bare form when exactly one table is rewritten, or the plan's `tables.<t>.match`. Without it: 400 `match_required` naming the table, with its candidates;<br>• **carried:** zero bytes, and the table's splits come with it.<br>The plan's keys (400 `key_invalid`) and relations are declared. Every file is kept as a `source` blob. The audit row `upload_committed` lists the action of each table. |
| P06's match, per table | `lake/upload._write_matched` | The match-and-write step of `_commit_next`, moved into a helper. The single-file path calls it unchanged, and the multi-table path calls it once per rewritten table.<br>`_Parent` gives no target and no holdout to a table that is not the version's primary. It used to draw a split on it. |
| **Writer** | `lake/writer.py` | **`append`** checks the parent's keys again over the old parts plus the new rows. Before, an appended table lost its keys.<br>**`relation`:**<br>• checks that both tables and all columns exist;<br>• refuses a `to` side that is not unique (400 `relation_to_not_unique`);<br>• counts orphans over non-missing `from` values;<br>• returns 400 `relation_types` for incomparable columns.<br>**`_carry_relations`** (at commit): the parent's relations stay while both tables are in the version, with orphans counted again. One that no longer holds is dropped, and `relation_dropped` in the ops says why.<br>**`_parent_order`** (at commit): the parent's tables keep their ordinals, whatever order they were written in.<br>**`carry_splits(t)`:** a carried table's splits are carried unchanged, with `carried_from`.<br>**`declare_version`:** a version that only declares a key / relation (or drops one). Every table is carried, its splits come with it, `dedupe` is on, and it becomes the default when its parent was. |
| **Routes** | `catalog/datasets_api.py` | **`GET /api/datasets/{root}/versions/{v}`:** every table with its sha, rows, columns, schema, parts, change and from-version, keys and splits; the relations; the hashes.<br>**`PUT /api/datasets/{v}/tables/{t}/key`** `{columns, kind?, reason?}` → 201 with the new version. Repeating it → 200 `deduped: data`. 400 `key_invalid` gives the counts, and 400 `table_unknown`.<br>**`GET /api/datasets/{v}/relations`:** the declared relations (stored `n_orphans`, plus `n_from_rows`, `coverage` and `to_unique` read now) and `suggested`.<br>**`PUT` / `DELETE /api/datasets/{v}/relations/{name}`:** a new version.<br>**Diff:** `?table=` on `GET …/{a}/diff/{b}` and `/datasets/diff`. An unknown table gets 400.<br>**Edit:** `POST …/edit {table}`. The route is now `edit` → `_edit`, wrapped in `frames.use_table`. |
| **Which table a request names** | `frames.py` | **`use_table(name)`** sets a context variable. `table(v)`, `read_version(v)`, `input_ref_for(v)` and `lake_table(Table(v, "data"))` then name that table instead of the primary one.<br>This is how runs, diff, edit and the split draw reach a named table without new parameters threaded through every reader.<br>`path_of` of a named Parquet table is a path that never exists (runs read `input_ref`). |
| **Runs on a table** | `engine/api.py` | `RunCreate.table`. An unknown table gets 400 `table_unknown`. The primary table runs as before.<br>**Any other table:**<br>• needs `label` (400 otherwise);<br>• gets its own profile (`DatasetStore.table_profile`, cached in `profiles/`);<br>• gets its own split, drawn for that table and viewed at `splits/tables/<t>/…`;<br>• is recorded in `input_ref {table}` and `input_table`, and in `run_inputs.table_name`. |
| Legacy record, splits, edit | `datasets.py` | **`finish_lake_version`** always describes the primary table (it picks the primary's check, under `use_table(primary)`). `profile.tables` lists every table, primary first.<br>**`_ensure_lake_split`** draws for the request's table.<br>**Edits:** an edit of another table keeps the version's primary table, and carries the other tables' splits.<br>**`read_upload`** (legacy single-file routes) takes a one-sheet workbook. With several sheets it points to `/api/uploads`. |
| **Multi-table sample** | `samples_p12.py` (new), registered in `datasets.py` like G3–G8 | `credit-book` is one version with three tables:<br>• **applications:** 4 000 rows, target `defaulted`;<br>• **bureau:** 3 194 rows, about 6 % of applicants have no record;<br>• **payments:** 19 395 rows.<br>Its keys are `app_id`, `customer_id` and `payment_id`. Its relations are `applications_bureau` (220 orphans) and `payments_applications` (0).<br>`samples.py` is not edited, so the existing samples' fingerprints are unchanged. |

Further cases, run on the dev data dir:
- **Both the rewrite and append paths in one upload.** The next version of a 4-table version took `bureau.csv`
  (rewrite) and `payments.csv` (`{action: append}`), with `products: {action: drop}`.
  - The check showed `commit_needs.match {bureau}`.
  - The commit without a match gave 400 `match_required` naming bureau.
  - `{match: {bureau: {method: declared}}}` gave 201:
    - bureau rewritten: matched 2404, changed 1, added 1, removed 5;
    - applications carried;
    - payments appended, with parts `[base, append, append]`;
    - products removed, and the relation `applications_products` dropped with `relation_dropped` in the ops.
  - `diff ?table=bureau` gave the same counts.
- **File names give table names.** Without a plan, `bureau2.csv` would be a new table `bureau2`. `{action: skip}`
  leaves a file out and lists it.
- **Legacy routes:**
  - `POST /api/datasets` with a one-sheet workbook makes a dataset;
  - `POST /api/datasets` with `book.xlsx` makes a 3-table dataset, the legacy record being the primary table;
  - a bad workbook gives 400 in words.
- **The sample.** `GET /datasets/credit-book/versions/credit-book` lists 3 tables with keys.
  `GET …/relations` gives `applications_bureau` with 220 orphans (coverage 0.9450) and `payments_applications`
  with 0.
- **Logs.** The final runs on both engines logged no tracebacks.
- **Tests.** `tests/test_upload.py` has the same 4 failures before and after (P05's CSV-store layout assertions).
  None are new.

## Deviations and notes for dependants

- **Files outside the row** (all lane D files, no other lane's):
  - **`lake/upload.py`.** P05/P06's upload pipeline lives there, not in `datasets.read_uploads`, so that is where the
    multi-table check and commit are.
  - **`lake/excel.py`.** New.
  - **`frames.py`.** `use_table`, plus a named-table branch in `table`, `input_ref_for`, `lake_table` and `path_of`.
  - **`engine/api.py`.** `RunCreate.table` and the `_create_run` wrapper.
  - **`profiling.py`** needed no change. The per-table profile reuses `lake_profile` in `datasets.py`.
  - **`samples.py`** is not edited. Registering the sample there would change every sample's generator fingerprint
    and regenerate them all.
- **F-JOBS:** `POST /datasets/{id}/edit` is now `edit` (the P12 `table` wrapper) → `_edit` (the old body,
  unchanged). If you move the edit commit to a job, keep the `frames.use_table(table)` around the work. The
  context variable is copied into `run_in_threadpool`, but not into a queued job. Pass `table` in the job payload
  and wrap the job body in it.
- **F-X2:** none of `migrate.py`, `splitstore.py` or `gc.py` is touched. `writer.carry_splits` only reads
  `splitstore.rows_of_version` / `read_blob`.
- **A key or a relation is a new version.** §2's `table_keys` / `table_relations` are part of `data_sha256`, and
  versions are immutable, so `PUT …/key` and `PUT …/relations/{name}` make a version with every table carried
  (zero bytes). Declaring the same thing twice returns the existing version (dedupe). The new version becomes the
  default only when its parent was.
- **A relation's `to` side must be unique** (n:1 / 1:1). Otherwise the answer is 400. `n_orphans` counts the
  `from` rows with a non-missing value that matches no `to` row.
- **Writer changes that apply to every op:**
  - a parent's relations are carried (recounted) while both tables remain;
  - an appended table keeps its keys (checked again);
  - the parent's table order is kept.

  Before, an edit of a multi-table version lost its relations, and an append lost its keys.
- **Fixed on the way (P05):** a column *declared* VARCHAR (PATCH `types`) always got a `declared_type_mismatch`
  block: "1 value(s) do not read as VARCHAR". The scan's VARCHAR slots hold other counts. A declared VARCHAR
  never fails now. Appends declare the parent's types, which is how this showed up.
- **Top-level `types` / `formats`** in a multi-table plan apply to the first (or `primary_table`) table. Other tables
  take `tables.<t>.types`.
- **A CSV-era parent** can only be continued with one file, as in P06. A multi-table upload on it gets 409
  `parent_not_parquet`, telling the person to migrate it first.
- **A stale multi-table sample is not regenerated.** When its generator changes, the version in use is kept and the
  change is logged. Regenerating a sample as a new version (`_sample_as_version`) handles one table only.
- **U2:**
  - a table picker on the run form (`POST /runs {table, label}`) and on diff / edit (`?table=` / `{table}`);
  - the upload's multi-table check: `tables[].action`, `sheets`, `carried`, `dropped`, `keys`, `relations` and
    `suggested_relations`;
  - the plan PATCH `tables` / `relations` / `primary_table`;
  - `commit {match: {<table>: …}}`;
  - `GET …/versions/{v}`, `PUT …/key`, `GET` / `PUT …/relations`.

  No UI file was changed, so there was no `npm run build`.
- **P13 (deltas)** can reuse `_commit_multi`'s append branch for insert-only deltas: cast to the parent's types,
  ids from `reserve_row_ids` above the table's max, then `w.append`.
- **P14 (joins)** gets declared relations with orphan counts, valid keys per table, and runs that already pin a named
  table (`run_inputs.table_name`).
- Scratch data dirs, the Postgres cluster and the API processes were removed or stopped. The pinned venv is in the
  session scratchpad only.
