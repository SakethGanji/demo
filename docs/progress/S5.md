## What works

**A. Robustness: heavy work out of the API process (S4's open problem 1)**
- `app/engine/pool.py`: a `ProcessPoolExecutor` (spawn, `ENSEMBLE_HEAVY_WORKERS`, default 2, `nice +5`) started with
  the API; each worker imports AutoGluon once at start, caches up to 3 predictors keyed by path **and the modification
  time of the predictor's files** (a new threshold or a custom ensemble reloads it), exits when the API process goes
  away, and a broken pool (a killed worker) is replaced on the next call.
- Moved into it: Kernel SHAP for holdout rows, on-demand permutation importance, `POST /runs/{id}/predict`,
  `GET /runs/{id}/oof`, and everything new (latency profiles, version builds, Try It with SHAP, batch scoring with
  drift, MLflow reads and writes). Results stay cached (SHAP per row in the run folder, importance in the run record,
  latency profiles in the run record). Light reads (threshold grid, explain, fairness) stay in the thread pool.
- Proof, `tests/test_concurrency.py`: 6 uncached SHAP rows on a 12-feature table plus a 30-shuffle importance run at
  once (≈2 s of work) while `/api/health`, `/api/runs/{id}` and `/api/status` are probed in a loop: 57 probes, median
  17 ms, max 66 ms (asserted: health < 0.5 s, run read < 1 s, median < 0.15 s). A 60,000-row batch scores while health
  stays under 0.5 s and the progress rises monotonically. Killing a worker with SIGKILL: the next request works.

**B. Registry and use**
- **MLflow, as a library, local.** Every finished run is logged by its fit worker (`tracked` event; `run.mlflow`):
  parameters flattened from the resolved `TabularPredictor(...)` / `.fit(...)` call, holdout metrics, validation score,
  fit time, threshold; light artefacts (config, resolved call, leaderboard, holdout metrics, ensemble, importance,
  holdout predictions, the predictor path). Experiments are `ensemble/<dataset>`. Each registered version is an MLflow
  model version whose `source` is its own predictor folder, tagged with the model and data SHA-256; stage changes and
  reviews are mirrored (`transition_model_version_stage`, `production` / `staging` aliases, approval and reviewer
  tags). The store is `data/mlflow/mlflow.db` + `data/mlflow/artifacts/`: MLflow 3.18 puts the plain `./mlruns`
  folder store in maintenance mode and **refuses it** without `MLFLOW_ALLOW_FILE_STORE`; the SQLite file is the local
  store MLflow recommends and needs no server. The registry's own SQLite tables are the source of truth; MLflow is the
  mirror (a failed mirror shows as a failed step, the version still works).
- **Register** (`POST /runs/{id}/register`, 202, built in a worker): `clone` → `refit_full` (`model='best'`, or
  `'all'` with a latency budget) → `infer_limit` (every candidate's batch time per row measured on the holdout, or
  AutoGluon's own `predict_1_time` when the run was fit with one; m* = argmax s_val among models within τ;
  `set_model_best`; if none fits, the fastest is kept and flagged) → `clone_for_deployment` (or `clone`) → measure →
  hash → MLflow. Steps are recorded live. The run's predictor is never touched.
- **Real measured trade-off**, source run vs version, same holdout rows, same machine: size on disk; batch µs/row
  p50/p95 over 7 repeats of 1,000 rows (models persisted first); one-row ms p50/p95 over 40 calls; throughput; holdout
  metrics with 95% percentile-bootstrap intervals (B = 500). On credit-default (medium, 60 s): the run's
  `WeightedEnsemble_L2` is **169.3 MB, 14.9 µs/row p50, 10.4 ms one row**; registered with refit_full + τ = 14 µs/row
  + clone_for_deployment it serves `CatBoost_FULL`: **148.4 KB (× 0.001), 7.29 µs/row (2.05× faster), 5.31 ms one
  row**, holdout accuracy 0.918 [0.907, 0.928]. `GET /runs/{id}/latency` profiles every model for the register
  panel's frontier.
- **Stages and reviews.** None → Staging → Production → Archived. Production needs an approved review; promoting
  archives the model's previous Production version (audited as "superseded by vN"); a rejected version cannot go live
  and a rejection archives a live one; a rejection needs a comment; **four eyes**: the reviewer cannot be the
  registrant; one review per version. There is no sign-in, so the UI asks for a name ("acting as", kept in the browser)
  and every action records it.
- **Audit log** (append-only SQLite table): who, action (registered, stage_changed, approved, rejected, card_edited,
  batch_scored), version, from → to stage, comment, the model's SHA-256 at that moment, details. Shown globally and
  per version.
- **Lineage graph**: dataset → run → version → `models:/name`, with the existing Graph and catenary strings (the live
  gradient for Production, dashed for pending or staging, dotted red for rejected).
- **Model card** (`GET …/card?format=json|md|html`, a page and two downloads): summary (stage, approval, served model,
  MLflow URI, model hash); intended use and limitations as a template the owner fills in (purpose, users, intended use,
  out of scope, limitations, monitoring plan, owner, validator, risk tier; edits audited); data (rows, columns, features,
  train/holdout counts, label balance per split, feature table, warnings, file and split SHA-256); the resolved fit
  call; the stacked ensemble ŷ(x) = Σ wₘ fₘ(x) with its weights; holdout metrics with formulas and bootstrap CIs for the
  version and the source run; the threshold record; permutation importance with t-intervals and p; fairness (every
  group computed in Explain is stored and shown); the measured deployment trade-off; monitoring (batches with their
  PSI); approvals with the audit trail and sign-off lines. It states that it documents and **does not replace
  independent validation** under SR 11-7 / OCC 2011-12.
- **Try It** (`POST …/predict`): a form generated from the version's schema (number inputs with μ, category selects
  from the profile's top values, a text area for text), the prediction, probabilities, threshold rule, and Kernel SHAP
  for that row (same background and method as Explain) with the top 5 reasons (▲ raises / ▼ lowers p̂, in pp) and the
  waterfall. Computed in a worker (≈0.2–2 s).
- **Batch scoring** (`POST …/batches`): upload a CSV, scored in chunks in a worker with progress; preview of 50 rows;
  download the input plus `prediction` and `p_<class>`; extra columns pass through; missing feature columns are scored
  as missing and reported.
- **Drift** on every batch: PSI = Σᵢ (aᵢ − eᵢ)·ln(aᵢ/eᵢ) per feature against the source run's training rows (numbers:
  training deciles; categories: top 19 + other; text: length; missing is a bin; shares floored at ε = 10⁻⁴), with the
  bank bands < 0.10 stable, 0.10–0.25 watch, > 0.25 shift; per-bin counts, shares and terms; means before → after;
  unseen categories. The output's PSI (p̂ of the positive class on the deciles of the version's own holdout
  predictions; the predicted class for multiclass; ŷ for regression) and a two-sample KS. Shown as a table with band
  bars, the per-bin chart of any feature (eᵢ vs aᵢ with each term), and the output distribution. Example batch
  (3,000 applicants, utilisation ×1.35, 30% set unemployed): employment PSI 0.667 shift, utilization 0.320 shift,
  income 0.044 stable, output PSI 0.202 watch, KS D = 0.205.
- **Home on real data** (live): runs as strings (holdout score when finished, a wave up to t / τ while fitting),
  best scores per dataset/label/metric, registry counts and the last audit events, the **Training Monitor** following
  the active run's events (each model's validation score at t seconds, the best-so-far staircase, min for errors) or
  replaying the last run, and its AutoGluon log. The hero line, toolkit footers and command palette show real counts.
  The status bar adds "N in production · M pending review" and active worker jobs.
- **No fake identities or data in live mode**: Registry and Home are real; the Training Gym and Autopilot (S6/S7) get
  a SIMULATED banner in live mode; Vela's scripted patches are labelled SIMULATED with a note; the toolkit's prototype
  tools say "prototype · simulated". Mock mode keeps its simulations, labelled SIMULATED (Registry, Home).
- Entry points: "Register" on Experiments rows, "Register Model Version" on New Model's results, "Register a run" on
  the Registry.
- Shared now: `ShapWaterfall` / `ShapEquation` (Explain and Try It), the navy KPI strip and the prediction form styles.
  The navy strip's lead cell is `.eh-cell.lead` (it was `.main`, which collided with the shell's `.main` once the CSS
  moved to `shared/`).

## What doesn't / not done

- A version serves the run's best model (or the infer_limit choice); registering another model of the run, a
  custom ensemble's copy for example, is not offered yet.
- `infer_limit` is applied after the fit by measuring each model (AutoGluon's own `infer_limit` is a fit-time
  argument that also prunes the stack while fitting; pass it in `fit_kwargs` for that). With refit_full and a budget,
  every model is refit (`model='all'`), which costs a refit of the whole run.
- Latency numbers are measured while the machine does whatever else it is doing (a fit, other workers); they are real
  but noisy. p95 over 7 repeats is a coarse tail.
- Batch drift compares against the training rows only; there is no monitoring over time (a series of batches) or
  alerting yet; batches are not compared with each other.
- Try It explains with Kernel SHAP (model-agnostic, exact additivity); on very wide tables it samples coalitions.
- MLflow stages are deprecated upstream (aliases are the future); both are written.
- The four-eyes rule compares typed names; there is no authentication, by design (no sign-in in this build).

- Export as Python: `registry/card.py`'s `fit_call(resolved)` already turns `run.resolved` into the
  `TabularPredictor(...).fit(...)` code; the registry adds the deployment steps (`RegisterPanel`'s `register-call`).
- Python client: the registry endpoints are listed in the README; `POST /registry/versions/{id}/predict` and the batch
  endpoints are what a notebook client wants; MLflow can also be read directly
  (`MlflowClient("sqlite:///backend/data/mlflow/mlflow.db")`, `models:/<name>/<version>` → the predictor folder).
- Heavy new work belongs in `engine/pool.py`'s pool (`await request.app.state.heavy.run(fn, …)` with a top-level
  `fn`); anything that writes into a run's predictor folder must make the workers reload (they key on the predictor
  files' mtimes, so `predictor.save()` is enough).
