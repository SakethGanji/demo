## What changed

**Sample `loan-stream` (`backend/app/samples_f18.py`, new and seeded; the other samples are untouched).**
- **Training data:** 9,000 labelled applications dated 2024 (`application_id`, `application_date`, 10 features, `defaulted`).
- **Stream:** `stream_month(m)` returns twelve 2025 months of 1,200 rows each. Each month is seeded by (seed, m).
- **Labels:** the labels of month m arrive on the last day of month m + 3, keyed by `application_id`.
- **From month 7, recorded in `stream_truth.json`:**
  - **Covariate drift:** debt_to_income rises (Beta + δ, δ = 0.08 → 0.14) and credit_score falls (−15 → −40).
  - **Concept change:** for online applications, logit + 1.3 for the same x. The channel mix is unchanged.

**Batches carry a date.**
- `batch_jobs.data_date` is added in place to older databases.
- `POST …/batches` takes `data_date`. When it is missing, the default is the latest date in the run's time column, then the upload day.
- Batch & Drift has a data-date field and column.
- The summary gains the score quantiles.

**`registry/monitoring.py` (the numbers, pure functions).**
- `perf_binary`:
  - AUC with DeLong (F15's `delong`);
  - log loss and Brier;
  - observed rate with a Wilson interval vs mean p̂;
  - z = (Σy − Σp̂)/√Σp̂(1 − p̂);
  - recall and precision at the served threshold;
  - F7 cost per 1,000 decisions when the run has a cost.
- `perf_other` for multiclass and regression.
- `paired_delong`: ΔAUC with Var(Δ) = Var(A₁) + Var(A₂) − 2Cov(A₁, A₂), from DeLong's structural components.
- `paired_bootstrap` of Δ log loss (B = 2,000).
- `shadow_compare`: score PSI on the champion's deciles, KS, Spearman ρ, same-decision share and κ.
- `alerts_for` with fixed, documented rules:
  - any feature PSI > 0.25;
  - PSI(p̂) > 0.25;
  - adversarial AUC lower bound > 0.60;
  - AUC upper bound < AUC₀ − 0.03;
  - |z| > 3;
  - performance needs ≥ 200 labelled rows.
- `summarize_alerts`:
  - the first covariate, score and performance alert, and when each became visible;
  - active = the latest batch's drift alerts plus the latest *labelled* batch's performance alerts.

**`registry/monitoring_api.py`.** The endpoints are listed in the README's API table.
- **Monitoring config per registered model** (audited `monitoring_configured`). It holds the thresholds, the challenger, the id and label columns, and the retrain window.
- **Challenger rules:** it must be a ready Staging binary version with the same label. Otherwise the call returns 409 or 400.
- **`GET …/monitoring` (`monitoring/1`) returns:**
  - the points in data order (PSI per feature, PSI(p̂), the score distribution);
  - F15's batch adversarial AUC when a check was run;
  - performance with its label date and lag;
  - shadow and paired results;
  - alerts;
  - the baseline (the version's own holdout);
  - the challenger with its pooled paired comparison;
  - the stream state.
- **`POST /registry/batches/{bid}/labels`:** the label file is joined on the id in a worker (`scoring.attach_labels`). It records coverage, unmatched rows, duplicates, the lag, performance, and paired results when the batch was shadow-scored. Audited `labels_attached`.
- **Shadow scoring:** `score_batch` gets `shadow` only for the Production version whose model has a challenger. The challenger scores the same rows with its own features and threshold. Its output goes to `shadow.csv` and `result.shadow` and is never served.
- **Retrain proposal (`GET` / `POST …/monitoring/retrain`):**
  - the champion's `run_body` (F12 / Gym re-run body) on the latest W labelled **whole months**;
  - the F6 split strategy and time column are kept, and a cut-off that lies before the window is re-drawn (the latest 20 %);
  - the window becomes a dataset whose `lineage.json` holds the batches, their label dates, the champion's version and run, and rows by source;
  - the run gets `parent_run_id` = the champion's run and `source = monitoring`;
  - audited `retrain_launched`;
  - GET has no side effects.
- **Stream:**
  - `GET /monitoring/stream` returns the sample's spec.
  - `POST …/monitoring/stream {month}` scores month m as a batch dated its last day. It then attaches every earlier month's labels whose arrival date is on or before that day (the as-of rule).
  - Feeding the same month twice returns 409.

**Model Doctor.** `run_doctor` passes `monitoring` (`doctor_context`) into `diagnose`. The shift check's rule is extended:
- a performance alert on the latest labelled batch → **critical**;
- a drift alert on the latest batch → **major**;
- the prescription is then **`retrain`**, which opens the version's Monitoring tab, where the launch is a click;
- the evidence is `monitoring`, and the source reads "F6 + F15 + F18";
- with monitoring and no alert, the shift check is *clear* with the batch count, not *missing*.

**Promotion is never automatic.** Nothing in F18 changes a stage. The smoke checks two things: the challenger is still Staging after everything, and moving it to Production without a review returns 409.

**UI: Registry → Monitoring** (`MonitoringPanel.tsx`; tabular versions).
- **Hero:** first drift alert, first performance alert with its visible date, labels up to, active alerts, challenger.
- **Sample Stream:** the 12 months with fed / labelled / alert marks, "Feed month" and "Feed the rest".
- **Which Signal Caught What.**
- **Charts:**
  - PSI per feature over time, with θ and the watch line;
  - score distribution over time (mean, quartiles, q₁₀ / q₉₀, flagged share, the challenger's mean);
  - performance with the label lag (AUC ± 1.96 SE, AUC₀, AUC₀ − δ, unlabelled months marked ○, the challenger's AUC);
  - observed vs predicted rate with Wilson bars.
- **Batches In Data Order,** with Attach Labels.
- **Champion · Challenger:**
  - set or clear the challenger;
  - agreement, κ, score PSI, ρ, paired ΔAUC and Δ log loss;
  - the paired-variance formula with every symbol bound;
  - per-batch rows;
  - "open to review" leads to the four-eyes flow.
- **Retrain Proposal:** why, window, rows, config chips, split note, Launch.
- **Advanced:** the alert thresholds (audited).
- **Elsewhere:** Doctor's `retrain` prescription → Monitoring. The audit tables know the new actions.

**Smoke section `monitor`** (`scripts/smoke.py`). It trains:
- a champion: GBM + LR, time split on application_date, approved → Production;
- a challenger: XGB → Staging, refused as challenger before Staging.

Then it feeds the 12 months and asserts the acceptance plus:
- the label-delivery schedule;
- channel PSI < 0.1 every month;
- the lag of 85–95 days;
- no performance point for months 10–12;
- the paired champion AUC equal to the batch AUC;
- the refusals;
- the doctor;
- the retrain run's lineage and audit.

## Open problems
- **Alert statistics.** The alerts are fixed per-batch thresholds with no multiplicity control over months or features, and no sequential test (CUSUM / SPRT). The first alert is reported as a fact, not as a p-value.
- **The concept change barely moves AUC.** 2025-07 has AUC 0.772 vs baseline 0.776, so the performance alert fired on calibration (|z|), not on the AUC drop. A smaller concept change would show only in the calibration chart. Segment-level performance (e.g. by channel) would localise it, but it is not built (F16's slice search could be run on a labelled window).
- **The adversarial AUC per batch is not automatic.** It is F15's batch check, started per batch (the smoke runs it on months 6 and 7 with `null_refits = 0`). Only one shift check runs at a time across the workbench. Running it on every batch of a 12-month stream costs about 15 s per batch.
- **Some views are binary only.** The challenger shadow and the paired tests are binary only. Multiclass and regression get the series and performance only.
- **The retrain run's comparison is narrow.** The retrained model is compared with the champion only on the retrained run's holdout (by the smoke, not on the page). Registering it and making it the next challenger is the usual manual flow.
- **The sample stream is synthetic, and the as-of date is the fed month.** "Visible" for drift alerts uses the batch's data date (scored at month end in the simulation); the wall-clock `scored_at` is also kept.
- **Unrelated, not fixed:** the smoke registers into `smoke.loan-stream` each run, so versions accumulate (v1, v3, v5 …) until `make reset`.
