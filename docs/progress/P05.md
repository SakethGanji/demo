## What was built

| Piece | Where | What it does |
|---|---|---|
| Staged uploads | `backend/app/lake/upload.py` (new) | **Stage.** `SinkFile` streams each file part to `lake/tmp/<up>/<n>.src`, with sha256 and a UTF-8 check on the fly; nothing is held in memory.<br>**Limits.** The cap is `ENSEMBLE_MAX_UPLOAD_GB` (5) and gives a 413. The free-disk guard wants 3× the size and gives a 507.<br>**Rows.** `uploads` rows follow §2.1: staged → checked → committed / discarded / expired. Staging expires after 7 days and is swept when the next upload starts. |
| Typed import (§5.1 step 3) | `upload.check` | **Detect.** CSV / TSV / TXT, or Parquet (a `__` column is refused). XLSX gets a 400 pointing to P12.<br>**Encoding.** A file that is not UTF-8 is transcoded: UTF-16 by BOM, else cp1252, else latin-1.<br>**Separator.** The legacy `sniff_sep` picks it; `;` means decimal comma.<br>**Header.** Names are stripped. Duplicates and `__` names are refused, and fewer than 2 columns or 2 rows are refused.<br>**Types.** DuckDB `sniff_csv` proposes a type per column. Then **one `all_varchar` scan** counts, per column: non-null values, values with a leading zero, values that fail the proposed cast (and the DOUBLE cast for an integer proposal), and slash-date day/month evidence.<br>**Rules:**<br>• a leading zero → VARCHAR, "leading zeros: kept as text";<br>• a failed cast → VARCHAR plus a `cast_failed` warning with 5 examples (an integer column with decimals is widened to DOUBLE);<br>• a dd/mm vs mm/dd order no value settles → VARCHAR plus `date_ambiguous` "declare the format";<br>• a `;` file's decimal-comma column → DOUBLE.<br>**NA tokens** come from the team `policy.na_tokens`, with §6.4's defaults.<br>**Declared types and formats** (`PATCH`) win. A declared type that does not fit gives a `declared_type_mismatch` block with examples.<br>**Typed file.** It is written to `tmp/<up>/typed.parquet` in file order (`preserve_insertion_order`), with the same cast expressions the scan counted.<br>**Check result.** The schema with a reason per column, warnings, blocks, a 5-row preview, `plan_sha256` and `check_sha256`. |
| Commit (§5.1 step 7) | `upload.commit` | **Refusals:**<br>• 409 `check_required` when the upload is not checked;<br>• 409 `check_stale` when the given `check_sha256` is not the stored one, or the plan changed after the check;<br>• 409 `check_blocked` when the check found blocks.<br>**Write.** It runs `VersionWriter(op="upload", job_id=<upload id>)`. `committed_for_job()` comes first. The table is written from `SELECT file_row_number AS __row_id, … FROM read_parquet(typed)`, so for a new dataset the row ids are the file's row order.<br>**Keep the source.** The uploaded bytes become a `source` blob (`blob_refs owner_kind='upload'`), and the manifest's `provenance.sources` lists them with `kept: true`.<br>**Idempotent.** A per-upload lock serialises concurrent commits; a repeat returns the committed version (200, `repeat: true`). |
| Routes | `catalog/datasets_api.py` | `POST /api/uploads` takes streaming multipart (a `python_multipart` push parser fed from `request.stream()` in 4 MB batches on a worker thread) or a raw body with `?filename=`.<br>The other routes: `GET` and `PATCH /api/uploads/{u}`, `POST /api/uploads/{u}/check`, `POST /api/uploads/{u}/commit`, `DELETE /api/uploads/{u}`. |
| `POST /datasets` as a wrapper | `main.py` (one hunk) and `datasets.create_from_upload` | The wrapper does stage → check → commit (target from the form), then `finish_lake_version`.<br>**`finish_lake_version`** writes the legacy record, so `GET /datasets`, `POST /runs` and the UI keep the same shape:<br>• the full `profile_frame` shape, with target and kind;<br>• `kept_as_text` and the warnings;<br>• `filename` is the uploaded name, and the note carries the encoding and separator;<br>• up to 1M rows, the drawn split (above that, the split is drawn on first use).<br>**Profile.** At ≤ 1M rows it is the whole table. Above that it is a seeded 200k reservoir sample for types, examples and statistics. Rows, missing, distinct (approximate) and the classes are exact from DuckDB, and the class names are the ones the fit sees (an int label with nulls is `1.0`).<br>The old 200 MB cap is replaced by the 5 GB one. Errors keep the legacy messages (400). |
| `frames.py` reads Parquet | `frames.py` | **Reading.** `Table(v, "data")` on a `storage='parquet'` version reads its committed table parts (`lake_table`). `"data"` means the primary table.<br>**`engine_v1`** gives what the same values gave the fit from CSV:<br>• int without nulls → int64;<br>• int with nulls → float64;<br>• DOUBLE / DECIMAL → float64;<br>• VARCHAR → object, with NaN for missing;<br>• DATE / TIMESTAMP → ISO text;<br>• BOOLEAN → bool.<br>**`native`** keeps the Arrow types. The index is `__row_id`.<br>**`ReadHash`** (`hash_into`): each part's bytes are read once, hashed, then parsed from that same buffer, and `hexdigest()` is the table's `table_sha256` recomputed from them.<br>**Other helpers:** `hash_table(ref)`, `is_parquet`, `storage`, `lake_sql`, `kind_of_type`, `input_sha256(cfg)`, and `columns` / `n_rows` / `export_schema` for Parquet. P04's `read_version` and `version_file` work unchanged on top. |
| Runs | `engine/api.py` (`queue_run` + `_parquet_input`) | **Config.** A run on a Parquet table carries `input_table {version_id, table, table_sha256, n_rows, parts, read_mode}` and `data_sha256_expected = table_sha256`, plus the split file's hash as before.<br>**Queue-time check.** The parts are **re-hashed before queueing**. A changed byte gives `409 data_integrity` with the stored and read shas; the version is flagged (`verified_ok=0`) and audited (`dataset_integrity_failed`, `training_refused`).<br>**One-line change in `_create_run`:** the A2 M7 ID-tie check reads only `[id columns, label]`, not the whole table (it made `POST /runs` at 10M take 66 s; now 7.6 s). |
| Worker | `engine/worker.py` | **`load_frames`** hashes while it reads (`frames.ReadHash`), and `info.read` records `kind`, `mode`, `table_sha256`, `parts` and `parts_differing`.<br>**`data_gate`** compares with the committed `table_sha256` (event `data_hashed {match, storage, table, table_sha256}`). It writes one insert-only **`run_inputs`** row per run with:<br>• `role='train'`, `version_id` and `table_name`;<br>• `table_sha256`, `read_sha256` and `match`;<br>• `legacy_csv_sha256` for CSV-era inputs;<br>• `split_legacy_sha256` (the JSON split's hash);<br>• `read_mode`, `rows_total`, `rows_used` and `columns_dropped`.<br>**`run_other`** (the other kinds) hashes the Parquet parts at the start. |
| Export from Parquet | `catalog/datasets_api.py` (`_export_parquet`) | **The CSV.** DuckDB writes `data.csv` from the table in `__row_id` order, cached at `lake/exports/<version>/<table>.csv` (re-creatable, not a blob).<br>**The zip:** `data.csv`, plus `schema.json` (P04's `ensemble.export_schema/1` with each column's stored type and reason), plus `manifest.json` (the stored lake manifest, verbatim), plus `export.json` (the chain, the table sha committed and now, and the csv sha).<br>**Headers:** `X-Ensemble-SHA256` and `X-Ensemble-Table-SHA256`. The export is audited `dataset_exported`. |
| Verify / verify-all | `catalog/dsets.py` (`verify`, a minimal branch) | A Parquet version is re-hashed part by part through `lake/verify.verify_version`. It is never "file missing". |
| Registry data hash | `registry/build.py` (2 lines) | `data_hash = frames.input_sha256(cfg)`. Before, it hashed the would-be data.csv, which does not exist for a Parquet run. |
| Seed | `lake/seed.py` (new) | `python -m app.lake.seed --rows N --out f.csv` writes a deterministic CSV via DuckDB. 10M rows is 1 139 007 765 bytes, in 15 s. It has 13 columns: zip, account_no and branch with leading zeros, dates, decimals, ints, categories, free text, and y with 0.1 % missing. |

### 5. The check / commit contract

```
small upload → check c1 de1abec7…
PATCH {types:{dmy:DATE}, formats:{dmy:"%d/%m/%Y"}, name} → status staged (the check is cleared)
commit             → 409 check_required
check again        → c2 c4deaf77…;  dmy DATE "declared DATE"
commit {check_sha256: c1} → 409 check_stale {check_sha256: c4deaf77…}
two commits at once {check_sha256: c2} → ds_796b428b 201 (repeat false) and ds_796b428b 200 (repeat true)
```

Other cases checked during development:
- **Parquet upload** (raw body, `?filename=p.parquet`): committed with types as stored. A file with `__row_id` gives 400 `reserved_column`.
- **The cap** (`ENSEMBLE_MAX_UPLOAD_GB=0.0001`): 413 `too_large` for multipart, for a chunked raw body and for `POST /datasets`. The tmp files are removed.
- **cp1252 file:** read and committed (the note says "read as CP1252").
- **`;` file with `1,5`:** `amount` is DOUBLE "numbers (decimal comma)", and `code` `007` stays text.

### 8. The exported run script reads Parquet (P04's handoff)

P04 moved the exported script's body to `gym/export_body.py.tmpl` and asked P05 to switch its reads to Parquet.

**What changed.**
- **`gym/export.py`.** For a Parquet input it writes `DATA_PARTS = [[role, sha256, path], …]`, `DATA_CSV = None` and
  `DATA_SHA256 = table_sha256`, and `UNLABELED_PARTS` for a Parquet pseudo-label set. Before, it read the would-be
  data.csv, which fails for a Parquet run.
- **The template.**
  - `read_parts()` hashes each part as it is read and recomputes the table sha (§3.3); a mismatch exits unless
    `--no-check`.
  - It parses from the same buffer and applies the engine_v1 dtypes inline. The script stays standalone: pyarrow,
    pandas, numpy.
  - `--data some.csv` still works for a Parquet run, but that CSV's bytes are not hash-checked, and the script says so.

**What was run** (a fresh dir and an idle machine):

```
upload small.csv (3 000 rows, zip/account_no with leading zeros) → ds_c9021596 (parquet)
POST /runs {label y, time_limit 20} → run_825fd1c9 succeeded
GET /runs/run_825fd1c9/export.py → 200; DATA_CSV None, DATA_PARTS [1 part], DATA_SHA256 07c3234d… (the table sha)
python export_run_825fd1c9.py --out repro → train 2,400 rows · holdout 600 rows · 4 features; …
                                          leaderboard check: 13 models, max |Δ score| = 0     (exit 0)
```

So the standalone script re-trains a Parquet run exactly.

A first attempt ran while another fit was training: LightGBMXT took 20 s instead of 0.4 s under the time limit, so
LightGBM was never fitted and the script reported it missing. The re-run on an idle machine matched every model.

A CSV-era run's script (`credit-default`, `DATA_PARTS = []`) still builds and runs through the unchanged CSV branch. It
differs from its run by up to 0.0073 on 3 models even when idle. That branch of `load()` is untouched (same `read_csv`
call), so this is the existing fit's nondeterminism at a 20 s budget, not P05.

## Deviations and notes for dependants

- **Files outside the P05 row (all minimal):**
  - `main.py`: the `POST /datasets` hunk only;
  - `catalog/dsets.py`: a Parquet branch in `verify`;
  - `registry/build.py`: 2 lines, `frames.input_sha256`;
  - `gym/export.py` and `gym/export_body.py.tmpl`: Parquet reads in the exported script (P04's handoff, §8);
  - `engine/api.py` `_create_run`: one line, the ID-tie read limited to its columns.

  New files: `lake/upload.py` and `lake/seed.py`.
- **Merge with P04 (lane R):**
  - P04 removed `DatasetStore.load_frame` in favour of `frames.read_version`. My Parquet branch lives in `frames.read`, so
    every swept reader reads Parquet with no further change. I dropped my `load_frame`.
  - `ensure_splits` reads only the target for a random split.
  - `schema()` is Parquet-aware.
  - The Parquet export uses P04's `frames.export_schema`, which is extended for Parquet.
- **Splits stay DL4 JSON** under `datasets/<id>/splits/` for Parquet versions, keyed by position. This is valid because a
  new upload's `__row_id` is `0..n-1`. Parquet splits are P09's. The writer's `split()` is not used yet.
- **Typed import vs the old pandas read:** a column like `$12,000` was coerced to numbers by A1 #5 and is now text
  ("text", or `cast_failed` with examples when DuckDB proposed a number). This follows §5.1: a failed cast → VARCHAR plus
  a warning. Codes with leading zeros, `;`/decimal-comma files, encodings and the legacy error messages behave as before.
- **Above 1M rows** the legacy profile is sampled (marked `profile.sampled`), and the split is drawn on first use, not on
  upload. `duplicates.rows` and `conflicting_labels` are `null` there. P08's `table_stats` replaces this profile.
- **Still slow at 10M** (not on P05's path; P08 / P11):
  - `GET …/split-options` takes about 42 s (a full pandas frame);
  - `/grid`, `/intake` and `/rows` read the whole table into pandas: 17 s and 5.2 GB at 10M;
  - the worker's post-fit scorecard on 2M holdout rows takes minutes.
- **Tests:** `tests/test_upload.py` has 4 failures, against 1 on the base commit (`test_upload_returns_full_profile`,
  which P02 noted). The 3 new ones assert the CSV store's layout or old refusals that P05 changes on purpose:
  - `datasets/<id>/data.csv` and `splits.json` on disk;
  - "a .parquet upload is not a CSV".

  Tests are not this project's verification method; they need updating when the suite is next touched.
- **For P06:**
  - `upload.commit` refuses nothing about next versions yet: an upload has no `parent_version_id` path.
  - `/uploads/{u}/check` is the place for `match` and `holdout_identity_lost`.
  - `PATCH` plans take `types`, `formats`, `name`, `target`, `project_id` and `table`.
- **For P09:** `run_inputs.split_legacy_sha256` holds the JSON split's hash. `split_id` / `split_sha256` stay NULL until
  splits are Parquet.
- **For P11:** `frames.read` on Parquet reads each part into memory once (hash, then parse). At 10M × 13 the engine_v1
  frame is 5.2 GB.
- The kept source blob is referenced by `blob_refs(owner_kind='upload', role='source')`. Retention of sources (§6.4
  `sources.keep_days`) is P24's.
- Scratch data dirs, the seeded CSVs and the API process were deleted after the run.
