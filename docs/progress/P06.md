# P06: upload as the next version, with an explicit match (lane D, DLA4 #2)

Plan: `docs/plans/data-platform-final.md` §4.2, §5.3, §9.1 row P06, §11. Base: `motion-components` @ 64b1f7a.

## What was built

| Piece | Where | What it does |
|---|---|---|
| The matcher | `dataset_versions.py` (`Matcher`, `type_family`, `parse_match`) | **Inputs.** One DuckDB connection with three objects: `_p` (the parent table with `__row_id`), `_n` (the new typed file with `__fr` = its row number) and `_h` (the parent's holdout `__row_id`s).<br>**Shared columns.** A column is shared when both sides have it by name in a compatible type family: number, text, date or bool. CSV-era text dates compare as ISO text.<br>**`candidates()`** is `key_candidates()` (§5.3 step 1). It considers every shared column, **whatever its profile role**, plus the parent's confirmed `table_keys`, composite keys included. For each it reports count, distinct, nulls on both sides, and overlap (by semi join).<br>**Score.** uniqueness_both × non_null_both × overlap. Ties go to an id-like name or shape. The top 3 are returned. It proposes and never decides.<br>**`simulate(method)`** gives matched / changed / unchanged / added / removed / `holdout_identity_lost` for `key`, `declared`, `row_hash` (DuckDB `hash()` with occurrence numbers, ephemeral only) and `none`.<br>**`key_problems()`** returns the counts and the first 10 repeated values per side.<br>**`warnings_for()`** gives three warnings:<br>• `identity_loss` (≥ 1 % of the parent holdout) needs an acknowledgement;<br>• `better_key_available` (a valid candidate matches ≥ 1 % more of the file's rows) needs one too;<br>• `low_overlap` (< 50 %) only informs.<br>**`contract()`** holds the DL1 contract checks in SQL: target gone, type changed, new target category, rows dropped, column gone, target missing more often, and "renamed?" hints by P04's `rename_hints` rule.<br>`guess_key` and `rename_hints` are kept (see "Deviations"). |
| Next-version staging | `lake/upload.py` | **Naming the parent.** `POST /uploads` takes `parent_version_id` or `root_id` (the root's default version), as a query or a form field. `PATCH` takes the same fields plus `match`. `uploads.parent_version_id`, `root_id`, `project_id` and `team_id` follow the parent's root.<br>**`/check`** adds `next_version` to the result: the candidates, the simulated methods (best candidate, declared key, row hash, and the plan's `match` if it has one), each method's warnings and `needs_acknowledge`, a `preselect` (declared key, else the top valid candidate), the contract, and `parent_holdout`. The table name becomes the parent's table, because the version rewrites it. |
| Commit | `lake/upload.py` (`_commit_next`) | **Refusals:**<br>• **400 `match_required`** without `match`, with the candidates, the methods and the preselect;<br>• **400 `key_invalid`** when the chosen key is not unique and present on both sides, with the first 10 offending values (masked when `column_tags` marks the column PII);<br>• **400 `acknowledge_required`** when the chosen method raises `identity_loss` or `better_key_available` and `acknowledge` lacks `"holdout_identity_loss"` (or the warning codes themselves);<br>• **400 `no_declared_key`** for `declared` when the parent has none.<br>**Re-simulation.** The commit simulates the chosen method again, and the best candidate with it, so nothing relies on stale numbers.<br>**Row ids** (§5.3 step 4). Matched rows keep the parent's `__row_id`. New rows get `next_row_id + k` in file order. `next_row_id` = max(`dataset_root_tables`, the parent's max id + 1).<br>**Write.** It is written through `VersionWriter(op="upload_version", parent_id=…, job_id=<upload>)`. Other parent tables are carried. The parent's keys are re-validated, and a chosen key is saved as a confirmed `table_keys` row (`declared_by` = the person).<br>**The manifest records the decision.** `provenance.ops[] {op: upload_version, match: {method, columns, confirmed_by, matched_by, candidates [[cols, "score"]…, ["row_hash", "share"]], matched, changed, added, removed, holdout_identity_lost, parent_holdout, acknowledged, warnings, best_candidate, next_row_id}}`. All warnings (typing, contract, match, each with `acknowledged`) go into `provenance.checks.warnings`. There are no floats: shares are decimal strings.<br>**Default.** The version becomes the default only when it has no warnings and `make_default` is not false. |
| Dedupe by `data_sha256` | `lake/writer.py` | `upload_version` is in `DEDUPE_OPS`. When the data (row ids, values and keys) equals a live version of the root, that version is returned: `deduped: "data"`, 200, and no new row is written. |
| CSV-era parents | `lake/upload.py` (`_Parent`) | A CSV-era parent (the samples, older uploads) is read through `frames.read_version`. Its ids follow §5.11 step 3, the rule P10 will use: `lineage.json.root_rows`, else `0..n-1` for a root. A non-root version with no row mapping gets 409 `parent_unmapped`. The new version is Parquet in the same root. |
| Bridge until P09 | `lake/upload.py` (`_write_legacy_bridge`), `datasets.py` (`list_splits`, 1 line) | Splits are still DL4 JSON by position, so the commit writes two files:<br>• **the new version's split JSON**, carried by `__row_id`. Matched rows keep the parent's fold and holdout. New rows go to the holdout share by `splitmix64(__row_id ⊕ seed)` (§5.7), otherwise to a fold by the same hash. `ensure_splits` adopts the file.<br>• **a `lineage.json`** with `root_rows = __row_id` and `parent_rows`, so the CSV-era readers (`diff` pairing, compare root rows) pair on the same rows the manifest records. It is labelled "P06 bridge".<br>`GET …/splits` shows `carried {from, by: __row_id, kept_holdout, new_rows, new_holdout}`. A structured split (group / time) is not carried; it is drawn fresh on first use. |
| The old route | `catalog/datasets_api.py` `POST /datasets/{id}/versions` | It is now a wrapper: stage (parent = `{id}`) → check → commit. **Nothing is guessed.**<br>**`row_key`:** a column or `a,b` → key; `hash` → row_hash; `none` → none.<br>**New form field `acknowledge`:** a comma list.<br>**Without `row_key`:** **400 `match_required`**, whose message names the best candidate: "type it as the key column, or pick exact row hash".<br>**`preview=true`** answers the DL2 shape (200, nothing written). With no key it shows the best candidate's counts, labelled "the best candidate, not chosen yet", plus `candidates`, `methods`, `needs_match` and `needs_acknowledge`.<br>**The success shape is unchanged:** `{…detail, upload: {matched_by, row_key, matched, changed, added, removed, checks, default}}`, plus `holdout_identity_lost`, `acknowledged`, `match` and `deduped`.<br>**Staging is cleaned up.** A preview or refused upload is discarded, so no staging is left behind. |

## Deviations and notes for dependants

- **Files outside the row:**
  - `lake/upload.py` is P05's new file in this lane: next-version staging, check and commit;
  - `datasets.py`: 1 line, `list_splits` passes `carried` through.
- **The bridge files** (P09 / P10):
  - **Split JSON.** A Parquet next version gets a DL4 split JSON carried by `__row_id`. P09 replaces it with a Parquet split carried by join; the rule is the same, `newfold = splitmix64(__row_id ⊕ seed)`.
  - **`lineage.json`.** It is written so that `catalog/dsets._pairs` and `compare.root_info` pair on `__row_id` without being changed. It is not a record (the manifest is). It holds one int per row, about 8 MB at 1M rows. P09's grep gate (`root_rows|splits\.json`) should replace the readers with `__row_id` joins and drop it.
- **The silent guess is gone from every user path.** `guess_key` / `match_rows(None)` survive for two callers:
  - `datasets._sample_as_version`, the system regeneration of an in-use sample (P07's file, `derive`);
  - `adopt-disk-file`, which passes `"hash"` explicitly on CSV-era files.

  P07 should move `_sample_as_version` onto `Matcher` with an explicit method.
- **Today's UI:**
  - **Preview** works and shows the best candidate's counts, labelled as not chosen.
  - **Create without a key column** gets a clear 400 that names the key to type into the existing "or a key column" box. A typed key or "exact row hash" then works.
  - **Row hash** with identity loss gets 400 `acknowledge_required`: the UI has no acknowledge control yet.

  **U1 must:**
  - use `POST /uploads?parent_version_id=` → `/check` (`next_version.candidates` / `methods` / `preselect`);
  - send `match` and `acknowledge` on `/commit`;
  - show the counts and `holdout_identity_lost` for each method.
- **CSV-era → Parquet typing** shows up as warnings, not silently:
  - the CSV sample's `defaulted` (Yes/No) comes back as BOOLEAN and `application_date` as DATE, so `type_changed` warnings appear;
  - the version is then not made the default automatically;
  - a column whose type family changed is left out of "changed" comparisons and of row_hash, as DL1 did.
- **`better_key_available`** is measured against the new file's row count. **`identity_loss`** is measured against the parent's holdout rows, the holdout of the default split (parent target, random-stratified), which is drawn if missing.
- **Dedupe** compares `data_sha256`, which includes the table's confirmed keys (with `declared_by`). The same file with the same key returns the existing version. The same rows with a different key choice make a new version, because the key is part of the data's identity (P02).
- **Default.** A next version with any warning (typing, contract or match) is not made the default unless `make_default: true`. This follows DL2's rule.
- Scratch data dirs, the seeded CSVs and the API process were removed after the run. The pinned-stack venv lives only in the session scratchpad.
