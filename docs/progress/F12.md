## What changed

**The run's fit call, reusable (`engine/worker.py`).** The ~90 lines between loading the frames and `predictor.fit` are now
`prepare_fit(cfg, train, holdout, tuning, info)` and `fit_predictor(cfg, prep, train, path, callbacks)`.
- The run's worker uses them unchanged in behaviour. The `config_resolved` event now also carries `post_fit` /
  `cost_metric`, which used to be added to the stored `resolved` only after the event.
- The learning curve calls the same two functions, so each subsample fit is the run's exact call:
  - presets and hyperparameters;
  - the F7 cost scorer as `eval_metric`;
  - the F8 `*_MONO` subclasses;
  - the F11 SCORECARD;
  - the F6 `tuning_data` and `groups=` folds;
  - TF-IDF models, column types, pseudo-labelling and distillation.

  After each fit, the run's threshold rule (`_decide_threshold`) and holdout scoring (`holdout_metrics`) are applied, so
  every point means the same as the run's own holdout score.

**The curve (`engine/learning_curve.py`, new; its own process, `python -m app.engine.learning_curve <run_dir>`).**
- **Subsamples inside the run's split record** (F4/F6). They are nested per seed: 10 % ⊂ 25 % ⊂ 50 % ⊂ 100 %.
  - **Random split:** stratified by the label where the split is, with k_c(f) = max(min(n_c, 5), round(f·n_c)).
  - **Group and time + group splits:** whole entities, drawn inside each of the split's bagging folds. Every fold keeps
    about f of its rows, and no customer is cut in half.
  - **Tuning slice:** kept whole.
  - **Holdout:** the same rows for every point; the smoke checks one `holdout_sha`.
- **The 100 % point is the run itself.** It is the same call on the same rows (`reuse_full: false` refits it).
- **Fit:** u(n) = A − b·(n/N)^(−c) in the metric's improvement direction, with b ≥ 0, c ∈ (0, 2] on a grid, and A ≤ the
  optimum. A and b are found by least squares through the means per fraction.
- **Gain per doubling:** Δ₂ = b(1 − 2^(−c)). The curve is extrapolated to 2N and 4N.
- **Intervals:** a parametric bootstrap, B = 1,000.
  - Each fraction's mean is redrawn from N(mean, σ_pop(f)²/k), with σ_pop(f) = sd_f/√(1 − f). The seeds share one pool
    of N rows, so their raw spread understates the spread over fresh samples.
  - The 100 % point gets the largest subsample's σ_pop.
  - The curve is refitted for each replicate.
- **The verdict is a fixed rule:**
  - **data-limited** if CI(Δ₂) > ε;
  - **saturated** if CI(Δ₂) < ε;
  - **noisy** otherwise.

  ε defaults to 2.5 % of the remaining gap to the optimum and can be set with `min_gain`.
- **State:** `runs/<id>/learning_curve/state.json` is written atomically after every fit. On finish, the headline is
  merged into the run result as `learning_curve`. The fitted predictors are deleted after scoring; only the scores are kept.

**The verdict for F17 (stable shape, `schema: "learning_curve/1"`)**, in `GET /runs/{id}/learning-curve` → `verdict` and in
the run payload's `learning_curve.verdict`:
```
{label: data-limited|saturated|noisy, reason, metric, greater_is_better,
 slope_per_doubling: {value, ci: [lo, hi], level: 0.95, units},
 extrapolation: {n_full, score_at_n, x2: {n, score, ci, gain}, x4: {n, score, ci, gain}},
 evidence: {min_gain, min_gain_rule, seed_sd, observed_last_step: {from_fraction, from_n, to_n, gain, gain_per_doubling, ci},
            monotone_within_noise, n_points, fractions, seeds, fit_rmse, power_law: {A, b, c, asymptote}, B, se_means,
            sd_population_full, interval_method}}
```
Scores are in the metric's own units; `slope` and `gain` are in the improvement direction (+ = better).

**API (`engine/learning_curve_api.py`, new router).**
- `POST /api/runs/{id}/learning-curve` returns 202. Body: `{fractions, seeds, time_limit, min_gain, reuse_full}`.
- Refusals:
  - 400: not a finished tabular run, fewer than 3 fractions, no 1.0, a fraction outside (0, 1], or a smallest subsample
    under 30 rows;
  - 422: seeds outside 1–10;
  - 409: a curve is already running. One curve runs at a time across the workbench.
- `GET …/learning-curve`:
  - status `none` with the defaults and a time estimate;
  - progress while it runs;
  - when finished: points, summary, fit, curve, band and verdict.
- `POST …/learning-curve/cancel`: kills the process group (Ray included).
- The process watches the API, and the reloader under dev reload. After a restart, a dead job is reported as failed.
- `POST /api/admin/reset` refuses while a curve runs.

**UI (Explain → Learning Curve, every tabular run).**
- **Hero:** the verdict, Δ₂ with its CI and ε, the score at N, 2N and 4N with CIs, and the reason sentence.
- **Chart** (on PlotFrame + XYPlot): score against n on a log₂ axis.
  - every seed fit;
  - the means with t-interval whiskers;
  - the fitted power law with its bootstrap band;
  - the dashed extrapolation with 2N / 4N marks.
- **Formula panel:** bound to the fitted A, b, c and Δ₂, with a where-list: u, n, N, A, b, c, CI, ε.
- **"How the subsamples were drawn":** the split key, nested ✓ and whole groups ✓, and the fit call in a fold-out.
- **Table:** per sample size, x̄, s and the 95 % t-interval for every fit.
- **Start card:** guided defaults (9 fits, the time cap, the estimate). Advanced: fractions, seeds, time limit, ε.
- **While it runs:** progress, Cancel, and the points as they arrive.

## Open problems

- **Both acceptance datasets come out *noisy* with 3 seeds.** On credit-default, the cost metric's seed spread (σ ≈ 0.02,
  mostly the threshold) dwarfs ε. A curve on ROC AUC for the same model would be tighter, but the curve deliberately
  uses the run's metric. 5–10 seeds (Advanced) cost proportionally more fits.
- **The intervals cover subsample variation, not the holdout's own sampling error.** That error is common to all points
  and does not move the slope much. The 100 % point's spread is borrowed from the largest subsample, which is an
  assumption. The fit has 3 parameters through 4 means; c can hit its grid edge (0.02 on credit-default, i.e. nearly
  log-linear), and then the extrapolation is close to linear in log n.
- **Time splits subsample randomly inside the training period.** "More data" there would usually mean more history or
  newer rows, and a forward-in-time curve is not drawn. Group-split subsamples are fold-balanced but not label-stratified.
- **Scheduling.**
  - One curve at a time; it is not queued with runs, so it competes for CPU with a fit in progress.
  - Starting a new curve replaces the previous one's result.
  - Under a time limit, small subsamples get relatively more time per row than the run did.
- **Verdict for F17.** A model that never changes its predictions (the majority-class GBM) gets *saturated* with a
  zero-width interval. That is correct for the config, but F17 should read it together with the train–validation gap.
