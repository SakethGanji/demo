# F5 · LLM layer: fast and reliable

Status: **done. `SMOKE_ONLY=llm,core,autopilot make smoke`: 34/34 green in 513 s (`llm` alone 5/5 in 86 s); `npm run
build` passes; `pytest tests/test_vela.py` 10/10.** Acceptance: the Vela ask p95 is reported for both paths, a timeout
falls back cleanly, and `/api/health` is never blocked.

**Which path was measured for real.** This container has no `ANTHROPIC_API_KEY`, so the **Claude CLI path is measured
for real** (`claude -p --model claude-sonnet-5-5`, real answers). The **Anthropic SDK path** (anthropic 2.10.0,
`AsyncAnthropic.beta.messages.create`) is the real SDK code, exercised end to end against a stand-in Messages API
(`scripts/fake_llm.py server`, 0.25 s per call) through `ENSEMBLE_ANTHROPIC_BASE_URL`; its latency numbers are the
fake's, not Anthropic's. No key is in the repo; the smoke passes `sk-fake-smoke-not-a-key` to its throwaway API only.

## Cause, confirmed

Each ask ran `claude -p` in a request thread (`run_in_threadpool`), twice on a parse failure, 60 s each. With the
CLI at 5–15 s per answer, ~40 asks in flight used up the threadpool shared with every sync route: `/api/health`
(a sync route) stalled. Measured on the pre-F5 commit (`5008042`) with a fake CLI that takes 8 s, 48 asks at once:

| `/api/health` while 48 asks are in flight | before (5008042) | after F5 |
| --- | ---: | ---: |
| p50 / p95 | 17 / 72 ms | 17 / 35 ms |
| **max** | **5,088 ms** | **79 ms** |
| asks: wall for 48 · p95 | 17.6 s · 17.0 s | 12.5 s · 12.1 s |

(`/tmp` bench: same harness both sides, throwaway data folder, tiny GBM run.)

| SDK path (fake Messages API, 0.25 s/call), 20 asks 4 at a time | — (httpx, after the CLI) | p50 0.44 s / p95 0.67 s |
| a 1 s timeout on the real CLI | `subprocess.run` timeout; one more CLI try | computed in 1.02 s, the CLI process group killed (0 left) |
| SDK times out (T_sdk = 1 s) → CLI | — | CLI answers, 1.14 s total |
| both paths time out (T_sdk 1 s, T_cli 2 s) | up to 3 × 60 s | computed in 3.01 s |

The CLI path is only marginally faster: its cost is the `claude` process (≈ 3 s of start-up and teardown on top of
1.3–2.5 s of API time per answer, measured with `duration_api_ms`). I tried a pre-started CLI (`--input-format
stream-json`, prompt sent later): still 3.4–4.9 s per answer, and turns share a conversation, so I did not use it.
Lean flags (`--tools "" --strict-mcp-config --no-session-persistence --disable-slash-commands`, a short system prompt)
cut tokens and cost, not wall time.

## What changed

**Backend.**
- `app/llm.py` is the one router for Vela's question box, Vela's wording and Autopilot (decisions, synthetic rows):
  - Order: **Anthropic SDK** when `ANTHROPIC_API_KEY` is set (`claude-sonnet-5-5`, effort `low`, server-side refusal
    fallback `fallbacks="default"`, `max_retries=0`, one pooled `AsyncAnthropic` per event loop; optional gateway
    `ENSEMBLE_ANTHROPIC_BASE_URL`) → **claude CLI** (`asyncio.create_subprocess_exec`, own process group, killed on
    timeout) → **computed** (`None`, the caller's computed text). A refusal, a 5xx, prose instead of JSON or a timeout
    hands over to the next path.
  - Asynchronous: `ask_json_async` awaits on the event loop; no thread is held. `ask_json` is the blocking wrapper for
    Autopilot's own thread.
  - Cache by `(model, sha256(prompt), sha256(canonical facts))`, TTL 1 h, 512 entries, in the API process. Only model
    answers are cached. Identical asks in flight share one call (single-flight).
  - Timeouts: `T_sdk` 20 s, `T_cli` 45 s, total `T` 60 s; each path gets `min(T_path, T − elapsed)`. Defaults from the
    environment (`ENSEMBLE_LLM_SDK_TIMEOUT`, `ENSEMBLE_LLM_CLI_TIMEOUT`, `ENSEMBLE_LLM_TIMEOUT`, `ENSEMBLE_LLM_CACHE_TTL`),
    overridden by `PUT /api/llm/settings` (stored in `data/llm_settings.json`) and per ask (`timeout`).
  - Every reply carries `source`, `decider`, `model`, `seconds`, `attempts` (the whole route, including skipped paths
    and why), `cached`, the hashes; latency per decider (last 200) for the status route.
  - Number guard: `unsupported_numbers(answer, facts)` (numbers in the answer absent from the facts, after rounding;
    0–10 allowed as counts). Vela's wording keeps its stricter guard (every computed number must survive).
- `app/llm_api.py`: `GET /api/llm`, `PUT /api/llm/settings` (400 on unknown keys or out-of-range values),
  `POST /api/llm/cache/clear`. `main.py` loads the settings and pre-imports the SDK at start.
- `POST /api/vela/ask` awaits the router; takes `timeout`, `cache`; returns `decider`, `cached`, hashes, `guard`.
- `app/vela/wording.py`: `word_async` through the router (the old `_via_cli` / `_via_api` are gone); the wording route
  is async. Autopilot records `decider` on layer-2 decisions; synthetic rows get `max_tokens` 8000.
- `anthropic==2.10.0` in requirements.txt and the lock (`make lock`: adds anthropic, docstring-parser, jiter, sniffio).

**UI.**
- Vela sidecar: while asking, which decider is being asked and a live elapsed timer; on the answer, **decided by**
  (Anthropic SDK / Claude CLI / cached / no model), the model, **latency**, the route (each path ✓ time, ✗ timed out
  at T, – skipped and why), the facts and the cache key `(h(prompt), h(facts))`, and the number guard line.
- Settings → **Language Model** (live mode): the route with availability, `T_sdk`, `T_cli`, n, t̃ (p50), τ₉₅ (p95),
  last per decider, the budget rule `min(T_path, T − elapsed)` and every symbol defined, the cache (key, h_rate =
  hits ÷ calls, size, TTL, shared in-flight) with Clear Cache; Advanced fold-out: the timeouts, TTL, the three switches,
  Restore Defaults.
- The wording line names the SDK decider and its latency or "cached".

## Open problems

- **The real SDK latency is not measured**: no key here. Set `ANTHROPIC_API_KEY` and run `SMOKE_ONLY=llm make smoke`:
  the "real path" step then measures the SDK (route starts with `anthropic-sdk`). The `fallbacks="default"` +
  `server-side-fallback-2026-07-01` beta was not exercised against the real API; if a gateway rejects it, the SDK
  attempt fails and the CLI answers (logged in the route).
- The CLI path stays at seconds per answer (p95 11–20 s at 4 concurrent asks, varies run to run): it is the process,
  not our code. The cache and the non-blocking design hide it for repeats and keep the app responsive; they do not
  make a first answer fast.
- A cache hit still recomputes the facts (findings, ~150 ms) to hash them; the cache is per process (lost on restart).
- The number guard flags, it does not block: one of 8 real CLI answers in the smoke used a number the facts lack
  (e.g. a derived difference). The UI shows which numbers.
- The ask is still one HTTP request that waits for its answer (bounded by T, 60 s by default); it no longer ties up a
  server thread. A job-and-poll API was not needed for the acceptance.
- Unrelated: none found.
