# D2 · Powerful, then simple: the model ladder and Feature Lab

**What it does.**
- **Model ladder.** One training request now yields a **model ladder** on the run's Results tab, with four rungs:
  - 0: baseline;
  - 1: scorecard (linear for multiclass and regression);
  - 2: single GBM;
  - 3: AutoGluon's best, the stack.

  Every rung is scored on the same holdout, with its gap to the best (paired-bootstrap CI), its one-row latency and its size. The card recommends **the simplest rung within the interval of the best**, shows the rule, and has one primary action: **Serve &lt;rung&gt;**.
- **Feature Lab** (Build → Advanced). A journal search over a whitelisted, typed feature DSL:
  - each candidate is scored on the training folds only, never the holdout;
  - it is kept only if a family-wise CI of the gain is above 0;
  - the leakage and decision-time rules run on every candidate;
  - the kept transforms become a new dataset version with the same holdout.

## Backend

### `backend/app/engine/ladder.py`

**Rungs.** All of them are models the run already trained, so there is **no extra fit**:

| Rung | Model | Source |
|---|---|---|
| 0 | Baseline | Computed from the training rows: the event rate (AUC 0.5), the class shares, or the mean |
| 1 | Scorecard | Binary runs: the run's own `SCORECARD` (F11, on by default). Other runs: the best level-1 `LR` or `TFIDF_LR` model. |
| 2 | Single GBM | The best level-1 LightGBM, CatBoost or XGBoost by validation score. If there is none, the best other single level-1 model. |
| 3 | AutoGluon best | `predictor.model_best`. If it is the single GBM itself, the rung is marked "= rung 2". |

**Score.**
- Binary runs: holdout AUC.
- Other runs: the run's eval metric.
- **Paired bootstrap:** every rung is scored on the same resample of holdout rows. Binary runs use B = 1,000; others use B = 300.
- `gap` = best − rung, with its CI. `within` means the CI includes 0.

**Rule.** Serve the simplest servable rung whose gap interval includes 0.
- **Small data.** D1's `sample_size` check runs on the run's own columns. If it is medium or high, the interval is **99 %** instead of 95 %, and the card says so: "Small data (… 15 events per feature): the interval is 99 %, not 95 %, so a more complex rung must win more clearly."
- **Latency:** the measured one-row p95, with the pipeline pruned to what the model reads (F3's `fastpath.pruned`).
- **Size:** bytes on disk of the model and every model it needs.

**Distillation.** It is offered only when the stack is the recommendation and its lead over the single GBM is clear (the CI excludes 0). It is not offered for monotone or quantile runs. The offer opens Register with `distill` ticked (`registry?register=…&distill=1`).

**Where it runs.**
- At the end of each fit, `worker.py` computes the ladder (8–20 s on the crafted data) and stores it as `result.ladder`. It also emits a `ladder` event.
- `GET /api/runs/{id}/ladder` returns it. It recomputes in the heavy pool for older runs, after an error, or with `?refresh=true`. Recomputing gives identical scores and gaps (the bootstrap seed is fixed).

**Serving.** **Serve &lt;rung&gt;** opens Register with `serve=<model>` preselected. This reuses F19's `serve_model`, which calls `set_model_best`, so the version serves exactly that model. The smoke checks that the version's `best_model` is the rung's model.

### `backend/app/featurelab.py` and `featurelab_api.py`

**The DSL.** Typed JSON only; no free-form code is ever run:

| op | Arguments | Computes |
|---|---|---|
| `ratio` | a, b | a ÷ b (b = 0 → missing) |
| `diff` | a, b | a − b |
| `agg` | entity, col, fn | per-entity mean / sum / max / min / std, or the row count |
| `date_part` | col, part | year, quarter, month, day of week, day of year, hour |
| `bin` | col, k | quantile bins, edges fit on the **training rows** and stored in the spec |
| `log` | col | sign · log1p\|x\| |
| `cross` | a, b | two categories combined (≤ 50 values each) |

Each transform is validated: columns exist and are not the target; types fit the op; an entity column must repeat.

**Proposals.**
- The heuristics rank quantity columns (numbers with more than 20 distinct values, so status codes such as PAY_0 are left out) by a quick LightGBM's gain. They then propose:
  - ratios, with the limit / income / total-like column as the denominator;
  - differences of amounts;
  - date parts;
  - per-entity aggregates, when an entity is named;
  - crosses of the top categories.
- They skip log and bins, because trees are invariant to monotone transforms.
- **D4's LLM** can send `candidates` (typed transforms) through the same API instead.

**Checks.** These run on every candidate, before it is scored:
- **Decision time:** a column answered "not known", a fairness-only column, or a Smart Intake leak suspect is never read. A candidate that reads one is rejected and names the rule.
- **Leakage:** D1's `single_auc` on the training rows. AUC ≥ 0.90 is rejected (regression: \|Spearman ρ\| ≥ 0.95), with the hint that the source columns may encode the outcome together.

**Scoring.**
- The scoring model is a fixed LightGBM (200 trees, no row or column subsampling, so the new column is the only change), 3-fold, on the **training rows only**, capped at 30k rows.
- The gain is ΔAUC on the same out-of-fold rows (binary). Multiclass uses Δ log-likelihood; regression uses −ΔRMSE.
- The CI is a paired bootstrap (B = 400), **Bonferroni-corrected for the number of candidates tried** (z = 2.84 for 11). Without the correction, one of 7 noise ratios was kept on the leaky table, with a CI lower bound of +0.00002.
- Greedy: a kept feature joins the base for the next candidate.
- Budget: `max_candidates` (default 20, at most 100) and `time_limit` (default 240 s).

**Output.**
- **The holdout is used once.** The same LightGBM is fit on all training rows with and without the kept features, and the holdout Δ is reported with a CI.
- With `apply` (the default), the kept transforms become a **new dataset version** through D1's `create_version`:
  - lineage `kind: feature_lab`, with `transforms` (including bin edges), `search` and `by`;
  - the same holdout rows;
  - the decision-time answers carry over.

**Routes.**
- `POST /api/datasets/{id}/feature-lab` `{target?, entity?, candidates?, max_candidates?, time_limit?, apply?, by?}` → 202 with the job (it runs in a thread).
- `GET /api/datasets/{id}/feature-lab`: the dataset's jobs and the DSL.
- `GET /api/datasets/{id}/feature-lab/{job}`: the live journal, the result and the version.
- Refusals: a non-DSL `op` → 400 ("free-form code is never run"); a bad target, entity or budget → 400; an unknown dataset → 404.

## UI

- **Results → Model ladder** (`src/features/quick-train/results/LadderCard.tsx`). It sits directly under the result hero.
  - The card holds the sentence, the small-data note when it applies, and a table: rung, model, holdout score, the gap to the best with its CI, one-row p95 and size.
  - The recommended row is tinted and marked "serve"; the other rungs within the interval say "within CI".
  - The rule is written under the table.
  - The single primary action is **Serve &lt;rung&gt; →**. Distillation is a secondary button that appears only when it is offered.
- **Build → Advanced · Feature Lab** (`src/features/build/FeatureLab.tsx`). A fold-out under the suggestions.
  - Controls: an entity picker (from Smart Intake's entity roles) and **Search features**.
  - It shows the live journal: candidate, its words, Δ out-of-fold with the CI, the AUC alone, kept / rejected and why.
  - A summary line gives the holdout before → after.
  - "↳ New version … **Use it →**" switches Build to that version.
  - The rules are on screen.
- **Register** reads `distill=1`.
- The CSS class is `.mladder`, because `.ladder` already belongs to the race view.

## Real data (`scripts/realdata_d2.py`; files in `backend/data/realdata/`, not committed)

**Training setup** (one run per dataset):
- AutoGluon `medium_quality` defaults, 5-fold bagging, one stack level (L3 weighted ensemble).
- The scorecard is on for binary runs. Taiwan drops `ID`.
- **Bank's `duration` is still in**: no decision-time answer was given, so this is the leaky setting.

| Dataset (holdout) | Recommended | Score vs stack | Gap (CI) | Latency p95 / size: recommended vs stack |
|---|---|---|---|---|
| **German credit** (200; small: EPV 15 → **99 %**) | **Scorecard** | AUC 0.767 vs 0.778 | 0.011 [−0.032, +0.051] | 16 ms / 70 KB vs 287 ms / 22 MB (18×, 320×) |
| **Taiwan** (6,000) | **Single CatBoost** (it *is* the best rung) | AUC 0.780 vs 0.778 | stack −0.0025 [−0.001, +0.006] | 4.5 ms / 2.0 MB vs 609 ms / 1.5 GB |
| **Bank marketing** (8,238) | **Single LightGBM** | AUC 0.956 vs 0.957 | 0.001 [−0.000, +0.003] | 15 ms / 2.5 MB vs 778 ms / 1.1 GB (51×, 443×) |
| **Banking77** (2,001; accuracy) | **Linear model (TF-IDF)** | acc 0.872 vs 0.880 | 0.008 [−0.000, +0.016] | 60 ms / 30 MB vs 9.8 s / 6.3 GB (163×, 206×) |

The scorecard rung on each binary dataset:
- **German:** within the interval. The plan's expectation holds, and the single LightGBM is *not* within (0.742, gap 0.036 [+0.003, +0.074]).
- **Taiwan:** 0.755, 0.025 below, clearly outside.
- **Bank:** 0.932, 0.025 below, outside.

**The stack never clearly beat the simplest-within-CI rung on these four public tables**, so distillation was never offered on them. Banking77's interval only just includes 0 (lower end −0.0003).

**Feature Lab on Taiwan** (24,000 training rows, 3-fold out of fold, base AUC **0.7793**):

| Run | Tried | Kept | Best candidate |
|---|---|---|---|
| Heuristics (20, 59 s) | ratios and differences of BILL / PAY_AMT / LIMIT_BAL | **none** | BILL_AMT1 − LIMIT_BAL +0.0027 [−0.0006, +0.0061]; utilisation BILL_AMT1 ÷ LIMIT_BAL +0.0019 [−0.0011, +0.0049] |
| The plan's ratios, given (7, 22 s) | BILL_AMT1..3 ÷ LIMIT_BAL, PAY_AMT_i ÷ BILL_AMT_{i+1}, two differences | **none** | utilisation +0.0019 [−0.0008, +0.0046] |

**Honest Δ ≈ 0.** The gradient-boosted model already approximates these ratios from the raw columns, and Taiwan sits at its information ceiling (≈ 0.78). The first heuristic pass, before the quantity filter, wasted its 20 tries on ratios of the PAY_0 *status code*. That is fixed: quantities need more than 20 distinct values.

## Smoke

### `ladder` (crafted data in the new `scripts/ladder_data.py`)

1. **Simple world** (additive logistic, 2,500 rows; GBM, CAT, LR, bagged k = 3; the scorecard is on):
   - rungs 0–3 are present and rung 3's AUC equals the run's own holdout AUC;
   - the baseline is 0.5;
   - the recommendation is the simplest rung within the interval: **Scorecard**, 0.701 vs stack 0.709, gap 0.008 [−0.012, +0.027], 2.1 ms vs 22.9 ms;
   - no distillation offer;
   - `?refresh=true` is identical.
2. **Serve.** `register(serve_model=Scorecard_BAG_L1)` gives a ready version whose `best_model` is the scorecard (1 model, 41 KB).
3. **Stack world.** An additive part over 60 weak columns plus a sign(x·z) interaction and a threshold pair.
   - Setup: LightGBM capped at 100 rounds, LR, and one stack level. **With full-strength CatBoost, a single model matched the stack.** This is honest, and it is why the smoke uses the capped single model.
   - Result: the stack wins, 0.836 vs single 0.746, gap 0.090 [+0.077, +0.103]. **The stack is recommended and distillation is offered.**
4. **Small data** (700 rows): D1 `sample_size` is medium, the interval is 99 %, and the 99 % CIs contain the 95 % ones.
5. **Refusals:** an unknown run → 404.

### `featurelab`

1. **Planted ratio** (debt ÷ income drives the log-odds; income is lognormal with σ 2.2):
   - `debt_per_income` is proposed first and **kept**: out-of-fold ΔAUC +0.0163 [+0.0111, +0.0214], AUC alone 0.854;
   - the 10 other candidates are rejected;
   - **holdout 0.9293 → 0.9409 (+0.0116 [+0.0058, +0.0187])**;
   - the new version has the column, `kind: feature_lab` lineage and the same 1,600 holdout rows, and the original is unchanged.
2. **Leaky ratio** (paid ÷ billed ≈ the label): rejected **before scoring** with AUC alone 0.991 ≥ 0.9; nothing else kept.
3. **Decision time.**
   - `amount_paid` is answered "not known": it is blocked, never in the base, and the given candidate that reads it is rejected by the rule.
   - A candidate with an unknown column is rejected as invalid.
   - `apply: false` gives no version.
4. **Every DSL op:** the 8 transforms (all 7 ops) equal pandas, and all are scored through the API.
   - Refusals: `op: python` → 400 "free-form code"; an extra field is rejected as invalid in the journal; a bad target, `max_candidates` or entity → 400; an unknown dataset → 404.

`ladder` and `featurelab` are added to the Makefile's `SMOKE_ONLY` and to the smoke default list.

## Notes for D3–D5

- **D3 (Model Doctor):**
  - `result.ladder` (or `GET …/ladder`) gives a ready "at the data's limit" signal: on Taiwan the single GBM equals the stack.
  - The gaps' CIs measure "a bigger model won't help".
  - Feature Lab's journal is the measured Δ for the "new features" lever in How-to-improve. On Taiwan every ratio gives Δ ≈ 0 with CIs about ±0.003.
- **D4 (review loop):**
  - Hypotheses of the "add a feature" kind map to `POST /api/datasets/{id}/feature-lab {candidates: [...], apply: …}`. The journal entry (Δ, CI, kept or rejected, reason) is the experiment record; invalid specs come back as rejected entries, not 500s.
  - The DSL description is in `GET …/feature-lab` (`dsl`), ready for the prompt.
  - "Serve a simpler rung" is `register(serve_model=…)`.
- **D5 (real data):**
  - `scripts/realdata_d2.py` reproduces the ladder table, about 50 minutes on 4 CPUs.
  - Bank was run with `duration` in. After the decision-time answer, the ladder should be rerun; expect about 0.80.
  - The assertion for "simpler rung when within CI" holds on all four datasets.
- **Known limits:**
  - Rung 2 is a *bagged* single model (k fold children). Its latency and size are as trained; Register's `refit_full` makes it a single fit.
  - The ladder's binary metric is AUC even when the run optimises a cost. The cost view stays in CostCompare.
  - Feature Lab's leakage line (AUC 0.90) can reject a genuinely strong ratio. The rule is on screen, and a person can still add the column by hand.
  - Per-entity aggregates are computed over all rows, holdout included. They read features only, never the label, so no label leaks, but the aggregate is transductive.
