# G1 · Counterfactuals: "what would change the decision"

**What it does.** For a declined (adverse) applicant on a registered binary version, it finds up to 3 different small, realistic sets of changes. Each set flips the served decision at the version's own threshold t. Every option is re-scored by the served model, the same `predict_proba` that /score uses.

## Backend

- **`backend/app/engine/recourse.py`** (new) runs a greedy coordinate search over the served predictor. It is vectorised: each step scores every candidate of every row in one `predict_proba` call.
  - **The decision:** margin m = s·(p̂ − t). Adverse means F10's `Reasoner.decide`, the same rule as reason codes and /score.
  - **Distance:** d(x, x′) = Σⱼ |Δxⱼ| / IQRⱼ + #categories changed.
  - **Plausibility:** π(x′) = the share of approved training applicants whose nearest approved neighbour is at least as far as x′'s.
  - **Steps:**
    1. **Greedy.** Take the nearest flip, else the best margin drop per unit of distance. At most 3 changes.
    2. **Shrink.** Walk each change back toward the applicant's own value.
    3. **Diversity.** Each new option forbids the main feature of the earlier ones.
  - **Rules:**
    - fixed features never move;
    - `increase`/`decrease` features move one way only;
    - F8 monotone features move only in the direction that lowers P(adverse);
    - numbers stay on a grid of 41 training quantiles, rounded to the column's precision;
    - categories stay among those seen in training (≥ 0.5% of rows).
- **Zero-config (G0): `intake.actionability()`** takes what can change from the roles plus name rules.
  - **Fixed:** the id, entity, date, geography, surname and zip roles, plus age/sex/marital-type names.
  - **Only down:** history columns (delinquencies, prior defaults, inquiries).
  - **Only up:** time-in-job or tenure columns.
  - **Editable per registry model** (audited); the UI shows "set by you" on an override.
  - **New G0 suggestion `recourse`, "What would change the decision":**
    - It shows when the table has a ready binary registry version (`Ctx.versions`, filled in by `main._binary_versions`).
    - It opens `#/registry?version=…&tab=Reason Codes`.
    - Before training, the yes/no suggestion is the way in.
- **API:**
  - `GET /api/registry/versions/{id}/recourse`: per feature, the action, its effective value after F8, why, and the range; plus the stored check.
  - `PUT /api/registry/versions/{id}/recourse`: `{actor, actions}`. Audited as `recourse_edited`.
  - `POST /api/registry/versions/{id}/recourse`: `{rows}` (≤ 200) returns the options per row.
  - `POST /api/registry/versions/{id}/recourse/check`: `{rows: 120}` runs the acceptance check on the first adverse holdout rows. The result is stored as `recourse_check.json` beside the version.
- **Batch scoring.** The first 20 adverse rows get a `recourse` column (the nearest valid change, in words), and the summary gets `summary.reasons.recourse`.
- **Model card.** A "Counterfactuals (recourse)" section (JSON, Markdown, HTML) with the method, the overrides and the check.

## UI (no new navigation)

- **Try It:** "What would change the decision" sits inside the Reason Codes card. It loads only for an adverse row. Each option shows p̂ before → after against t, with d and π.
- **Reason Codes tab:** a Recourse panel with:
  - the formulas, bound to t;
  - one primary action, "Run the check";
  - a hero strip with the check's numbers;
  - the first holdout row's options;
  - a closed fold-out, "What may change", with the detected action and why for each feature, editable.
- **Batch & Drift:** a "recourse k / 20" hero cell, plus a closed fold-out with the nearest change per row.
- **Model Card:** a recourse paragraph.
- **Build:** the recourse suggestion card routes to the registry.

## Numbers (credit-default, zero-config)

The run used exactly the intake pre-fill: drop the IDs, split out-of-time + group, business cost FN = 10·FP. It added debt_to_income ↑ (F8) and trained GBM + XGB. The served model is WeightedEnsemble_L2 at t = 0.0560.

- **Stored check:** **119/120 adverse holdout rows (99.2%)** have at least one valid counterfactual.
  - 336/336 options flip the decision.
  - Median 1 change, median d = 0.78, median π = 0.26.
  - **0 fixed features moved**, 0 values outside training, 0 direction breaks.
  - Speed: 1.7 s for 120 rows (~70 rows/s).
- **Independent re-score in the smoke.** 110 adverse holdout rows (found via /score) gave 306 options. The smoke rebuilt each option from its listed changes and re-scored all of them through `/score`:
  - 306/306 flip;
  - **109/110 rows (99.1%)** have at least one;
  - 0 fixed features moved;
  - 0 out of range or wrong direction.
- **Batch of 400 rows:** 20/20 of the first adverse rows got a valid change, in 0.6 s.
- **Try It, one row:** about 2 s cold (engine set-up), then a few hundred ms.

**Smoke.** `SMOKE_ONLY=recourse,core make smoke`: **26/26 passed in 170 s** (recourse 5 steps, core 21). `npm run build` is OK.

## Limits and open problems

- **Greedy, not optimal.** Options are short, not guaranteed minimal. The search sees ≤ 3 changes on a 41-quantile grid. One of 120 rows had no flip within those limits.
- **Plausibility is often low** (π ≈ 0.02) for options that move one feature far, e.g. debt_to_income 0.42 → 0.066. π is shown, not used to filter. A plausibility floor or a π-weighted cost would be a reasonable next step.
- **No causal model.** Changing utilization does not move credit_score with it. Each option is "if these values were different", not a plan.
- **Actionability rules are name-driven** beyond the roles. An unusual column name gets "either way" until a user edits it. Edits are per registry model.
- **Intake overrides are not persisted (G0 behaviour).** Recourse re-detects roles from the training CSV, not from Build edits.
- **Not in the Model Doctor or Vela.** G10 should expose `POST /recourse` as a tool.
- **Mock mode:** the new endpoints are not mocked. The panels show their error state without the API.
- **Smoke data:** the smoke's override (home_ownership → fixed) persists for model `smoke.credit.recourse` across runs. It is harmless, and the smoke re-asserts it.
