## What was built

| Piece | Where | What it does |
|---|---|---|
| **The per-column estimator** (R12) | `lake/frame.py` (`estimate`, `_scan`) | One DuckDB pass over the committed table gives each column's non-null count and, for text columns (VARCHAR, and DATE / TIMESTAMP, which engine_v1 reads as text), the mean length and the approximate distinct count.<br>Bytes per cell of the engine_v1 pandas frame: **8 B per number / bool cell; 8 + share non-null × (50 + mean length) per text cell; + 8 B of index per row**.<br>The estimate is deterministic: the same table always gives the same rates, and so the same sample. |
| **The budget** | `lake/frame.budget`, `config.train_frame_share()` | `frame_budget_mb` on the run (new `RunCreate` field), else **ENSEMBLE_TRAIN_FRAME_SHARE (0.10) × the worker's RAM**. The RAM is ENSEMBLE_WORKER_RAM_MB, else the cgroup limit when it is lower, else the host's RAM.<br>The default is also **capped by the calibrated run peak** of the preset (`config.FIT_PEAK`): base + slope × frame ≤ 80 % of RAM. |
| **The frame** | `engine/worker.load_frames` | **Under the budget:** `frames.read` of the whole table, exactly as before.<br>**Over it** (a Parquet table with a pinned split):<br>1. read only `__row_id` + the label, and map the pinned split onto them (P09's `_pinned_split`);<br>2. prune (§5.9 step 1): > 99 % null, constant, ID-like short unique text. Never the label, a text column or a typed column;<br>3. draw the sample over the training rows (folds ≥ 0 with a label);<br>4. read exactly the kept training rows, the whole tuning slice and a holdout diagnostics subset from the parts. Every part is memory-mapped and hashed in full (DL3: the data gate still compares the table's `table_sha256`); row groups with no wanted id are skipped by their `__row_id` statistics.<br>An int / bool column with nulls anywhere in the table is typed float64 / object even when the rows read have none, so a sampled frame has the full read's dtypes. |
| **The sample** (R13) | `lake/frame.draw`, `holdout_subset` | Keep a row when **splitmix64(`__row_id` ⊕ seed·φ) mod 10⁶ < 10⁶ · rate[stratum]**. It uses `manifest.splitmix64` (numpy, uint64), with no engine hash and no RNG state.<br>**Classification:** strata = classes. A class with ≤ 1,000 training rows is kept whole; the other classes share the rest of the budget.<br>**Regression:** one rate; per-decile counts are recorded.<br>Rates are decimal strings with 6 places, rounded down, and the threshold is computed from the string.<br>The seed is `sample_seed`, else the split's seed (42).<br>The rate is `(budget / bytes per row − tuning rows) / (training + holdout rows)`, with a floor of 1,000 training rows. |
| **What is recorded** | `info.frame` (GET /runs/{id} → `data.frame`), `run_inputs`, blobs | **`data`:** `rows_total`, `rows_used`, `sample_sha256`.<br>**`data.frame`:** the plan (estimate per column, budget and rule), `sample_spec` {method, seed, rate, rates, per_stratum, rows_total, rows_used}, `sample_blob`, `columns_pruned`, holdout {rows, scored, in_memory}, and the card text.<br>**`run_inputs`:** `rows_total` (table rows), `rows_used` (rows fitted), `sample_spec` (canonical JSON), `sample_sha256` (§3.3), `frame_mb`.<br>**The kept ids** are a content-addressed Parquet blob (`blobs.kind 'sample'`), pinned by `blob_refs (run, sample)`. A repeat run pins the same blob. |
| **Batched full-holdout scoring** (§5.9 step 3) | `lake/frame.score_holdout`, `holdout_batches`; `worker.score_full_holdout`, `holdout_result` | Every holdout row is scored in batches of ENSEMBLE_HOLDOUT_BATCH_ROWS (500,000). The batches come from the lake (by `__row_id`, cast with the wizard's column types) when the run was sampled; otherwise they are slices of the in-memory holdout.<br>Per batch: `predict_proba` (or `predict`), and the rows are appended to `holdout_predictions.csv`. Then **one `evaluate_predictions` over all rows**, which is what `predictor.evaluate` does internally.<br>`holdout.scored = {rows, batches, batch_rows, seconds, of}`.<br>`holdout_metrics` is kept as a wrapper of the same `holdout_result` for its other callers (learning curve, AL, threshold, registry build). |
| **Model card** (§11) | `registry/card.py` | `data.sampling` holds sampled, text, rows used / total, seed, rates, sample_sha256, budget and pruned columns. The markdown card adds a "Sampled training rows" paragraph when the run was sampled. |
| **The P09 bug and its siblings** | see the next section | Holdout rows were taken by position from a frame indexed by `__row_id`, or by `__row_id` from position arrays. |

### `__row_id` vs read position: what was wrong and where

A Parquet frame's index is `__row_id`, which has gaps after an edit. Split files hold **read positions**, while
`holdout_predictions.csv`'s `row` is the **`__row_id`**. Mixing the two reads the wrong rows, or raises.

| Site | Was | Now |
|---|---|---|
| `vela/doctor.py` `_fit_gap` (P09's find) | `df.loc[holdout positions]` | `df.iloc[…]` |
| `vela/missing.measure` (the doctor's gap analysis) | `hp.row` used as positions into arrays → **IndexError** on the gapped run | `get_indexer(hp.row)` → positions; reported rows stay `__row_id` |
| `vela/missing.overlap` | `hp.row` looked up among holdout positions → seen rows silently missed | `get_indexer` |
| `engine/explain.py` fairness | `data[group].iloc[hp.row]` → **wrong groups** (verified below) | `.loc` |
| `engine/slices_api._frame` | `.iloc[hp.row]` | `.loc` |
| `fairlending/api.py` | `data.iloc[hd.row]` | `.loc` |
| `registry/credit_report_api.py` (holdout periods) | `.iloc[hold.row]` | `.loc` |
| `vela/findings.f_segment` | `.iloc[hp.row]` | `.loc` |
| `engine/annotations.py` (OOF p̂) | OOF index (`__row_id`) intersected with training positions | OOF index mapped to positions |
| `engine/annotations_api.py` | positions used as labels on a `__row_id` frame | the frame is read with `reset_index(drop=True)`, as `derive()` expects |

**Not changed, P22's files:** `engine/active_learning.py:262` `_missing_pool` does `fold[pool.index]`, where
`pool.index` is the `__row_id`. It should be `fold[np.flatnonzero(sel)]`.

## Calibration (AutoGluon 1.6.3, default preset medium_quality, through the real worker)

`calibrate.py` uploads the table and reads it in-process with `frames.read`, which is what an unsampled worker reads:
the R12 estimate is compared with the frame's real `memory_usage(deep=True)` and the read's RSS peak. It then starts
`POST /runs {presets: medium_quality, time_limit, frame_budget_mb: 10⁶}` (never sampled) and polls the worker's process
tree (`python -m app.engine.worker <run_dir>` + children) every 0.25 s. The run includes the read, the fit, holdout
scoring, the ladder and the importance. Raw: `P11/calib.jsonl`.

| rows × 27 | estimate | real frame | estimate / real | read peak (× real) | time_limit | models fitted | **run peak RSS** | peak / estimate |
|---|---|---|---|---|---|---|---|---|
| 1,000,000 | 539 MB (565.5 B/row) | 481 MB | 1.12 | 1,228 MB (2.55 ×) | 600 s | NN_FastAI, LightGBMXT, LightGBM, CatBoost, WE | **3,436 MB** | 6.37 × |
| 5,000,000 | 2,697 MB | 2,405 MB | 1.12 | 5,984 MB (2.49 ×) | 1,200 s | LightGBMXT, LightGBM, CatBoost, WE | **8,669 MB** | 3.21 × |

- **The estimator is conservative by 12 %** on this mix. It is kept as is, because it errs towards sampling.
- **The read peaks at ≈ 2.5 × the frame, not R12's 1.6 ×.** `frames.read` holds the part bytes (hashed), the Arrow table
  and the pandas frame at once, while R12 measured `pd.read_parquet` alone. `config.FRAME_LOAD_PEAK` is now 2.5.
- **The run peak is not one multiple of the frame.** It is ≈ **2.13 GB fixed** (torch, AutoGluon, the model libraries)
  **+ 2.43 × the estimated frame**, the line through both points. This is recorded in `config.FIT_PEAK["medium_quality"]`.
- **The budget rule, calibrated.** The default budget is min(10 % of RAM, (80 % of RAM − 2.13 GB) / 2.43).
  - On this 16 GB host: 1.6 GB of frame → a predicted peak of 6.0 GB (37 % of RAM).
  - The 10 % share binds on workers with at least ≈ 4 GB of RAM.
  - Below that, the calibrated cap binds: a 3 GB worker gets a 112 MB frame, predicted peak 2.4 GB (80 %).
  - Presets other than medium_quality are not calibrated, so only the 10 % share applies to them.
- **Caveats.**
  - The 5M run stopped adding models after 458 s of fit (no NN), so its peak is from the GBM families.
  - `best_quality` (bagging, stacking) was not measured.
  - One synthetic table shape was measured.

## Decisions

- **The holdout is not sampled, but the in-memory holdout is.**
  - On a sampled run, `holdout` (what `load_frames` returns) is a splitmix64 subset of the holdout at the training rate.
    It feeds the leaderboard's `score_test`, permutation importance, the ladder, the scorecard and the monotone check, so
    a 50M-row table never puts its 10M holdout rows in memory.
  - **`result.holdout` (metrics, confusion matrix) and `holdout_predictions.csv` cover every holdout row.** So do the
    threshold, compare, slices and everything else that reads the predictions file. The subset's size is in
    `data.frame.holdout.in_memory`.
- **Reading by `__row_id` with pyarrow, not a DuckDB SEMI JOIN.** §5.9 says "kept ids → DuckDB SEMI JOIN → tmp
  parquet". Instead, the worker memory-maps each part, hashes it, and parses only the wanted row groups from the same
  bytes. The data gate therefore still hashes exactly the bytes parsed (DL3), and no temporary Parquet is written. The
  sample blob is still written and pinned.
- **Sampling needs a Parquet version with a pinned split.** A CSV-era version has no `__row_id` and is read whole, as
  before; P10 migrates it. Its plan says so (`plan.why`).
- **`rows_total` in `run_inputs` keeps P05's meaning** (the table's rows). `data.frame.train_rows_total` is the
  denominator of the sample.
- **Pruning (step 1) runs only when sampling**, so an unsampled run's features are unchanged from before P11.
- **A regression sample uses one rate.** With hash-Bernoulli selection, per-decile rates equal to the overall rate select
  the same rows as no strata, so only the counts per decile are recorded.
