## Findings

### Critical

**C1. A 20 KB wide CSV OOM-kills the API at `/check`.**
- **Symptom.** A CSV with 5,000 columns and 2 data rows (about 20 KB) sent to `POST /uploads/{u}/check` held the CPU at 100 % for more than 2 minutes. The API reached **12.86 GB RSS** and the kernel OOM-killed it: `Killed process … (python) anon-rss:12861772kB`. Every running fit died with it ("The API stopped while this run was in progress").
- **Growth is quadratic in the column count:**

  | Columns | `/check` time | Peak RSS |
  |---|---|---|
  | 250 | 0.8 s | 0.51 GB |
  | 500 | 3.0 s | 1.13 GB |
  | 1,000 | 11.6 s | 3.31 GB |

- **Likely cause.** The one-pass `all_varchar` scan builds about 4–6 `count(*) FILTER` aggregates per column into one query (`lake/upload.py` ~L509–545), so planning blows up.
- **Repro:**

  ```python
  open("w.csv","w").write(",".join(f"c{i}" for i in range(5000))+"\n"+",".join("1"*5000)+"\n"+",".join("2"*5000)+"\n")
  ```

  `POST /api/uploads?filename=w.csv&by=x` (raw body), then `POST /api/uploads/{u}/check`.
- **Fix.** Batch the scan, for example 100 columns per query, or one query per column group. Cap the column count with a 400, for example 2,000 columns. Bank datasets with 1–2k columns are realistic.

**C2. Data Doctor and Feature Lab read the whole table into pandas inside the request.**
- **Measurements at 10M rows** (13 columns, 1.14 GB CSV, 2.84 GB peak at upload):
  - `GET /api/datasets/{id}/data-doctor` (opening the Data Report) went past **12 GB** and my watchdog killed the API. On this 15 GB box it is an OOM kill.
  - `POST /data-doctor/apply {"transforms":[{"op":"drop_columns","columns":["note"]}]}`: the same.
  - `POST /feature-lab {max_candidates:2, apply:false}` holds the request for **174.6 s** and peaks at **10.68 GB**.
- **This is §7 risk 4**, and P08's "no full-table pandas read on any request path" is not true for these routes.
- **Still present at 5fe4afa** (`frames.read_version(...)` in both routes).
- **Fix, before P10 at minimum.** Refuse these routes above a row budget with a typed 400 ("sample first"), or read a recorded sample (P11's training-frame sampler exists at head). Move Feature Lab's `_prepare` read into the job.

### Major

**M1. Concurrent sibling uploads hand out the same new `__row_id`s to different rows.**
- **Repro.** Stage three next-version uploads of v1 (parent `ds_ae365f0a`). Each adds 50 *different* new accounts (`Z0…`, `Z1…`, `Z2…`). Commit all three at once with `match {key: acct}`.
- **Result.** All three versions give their new rows ids **3138–3187**. `GET /datasets/{a0}/diff/{a1}` then reports "matched 3,050, **changed 50**" for 50 rows that are different accounts.
- **Contrast.** Sequential siblings get distinct ids: 3000–3034, then 3035+.
- **Cause.** `nxt = parent.next_row_id(db)` (`lake/upload.py` `_commit_next`, L1018 at 5fe4afa) is read before the commit transaction. `next_row_id = max(...)` inside the transaction does not re-allocate.
- **Impact.** It breaks the "same `__row_id` = same row" contract across one root, and so diff, carry and paired compare. The edit `add_rows` path should be checked for the same race.
- **Fix.** Allocate the id range inside the commit transaction, and rewrite the ids if the range moved, or reserve the range with a compare-and-set before writing.

**M2. `restore-splits` returns 500 when the tampered split was carried into a child version, and the child can't be fixed either.**
- **Repro.**
  1. Take version w1 (`ds_9cfc78b3`). It has runs, and an edit child `ds_affdb562` whose split has `carried_from = spl_b6eb915f2297`.
  2. Forge w1's split in place: new blob, and `UPDATE splits` with the trigger dropped.
  3. `POST /restore-splits {by}` offers run_4d9f5cb6's blob.
  4. `POST /restore-splits {by, reason, split_key, blob_sha256}` → **500** `sqlite3.IntegrityError: FOREIGN KEY constraint failed` at `splitstore.restore` `DELETE FROM splits WHERE id = ?`, because the child row references the id.
- **What happens next.** The transaction rolls back cleanly and the triggers are back. Meanwhile the child fails check 5 ("8,571 surviving rows of spl_b6eb915f2297: 170 changed fold"), so it can't train either.
- **Scope.** P09 restored only a leaf. Any split that has been carried, which is the normal case after one edit, can't be restored.
- **Still at 5fe4afa** (`splitstore.py:648`).
- **Fix.** Keep the row id and repoint it with `UPDATE … ` under a narrowly scoped trigger exception, or insert the restored row first and repoint the children's `carried_from` in the same audited transaction. Map the error to 409, never 500.

**M3. Model Doctor's overfit check fails on `__row_id` gaps (`vela/doctor.py:152`).** This confirms known item 10.
- **Repro.** Version w2 = w1 with every 7th row deleted by edit. Run on it (run_820b36ba), then `GET /api/runs/run_820b36ba/doctor`.
- **Result.** The overfit check is **"n/a: The training score could not be computed"**. The stored error is `fit gap: KeyError: '[21, 28, 210, …] not in index'`. On the gap-free parent the same check gives "accuracy 0.9163 vs holdout 0.7825, z = 14.5".
- **Worse case.** Where the gaps happen to fit (for example only row 0 deleted), `df.loc[positions]` would evaluate the wrong rows **silently**.
- **The same pattern** is in `engine/annotations_api.py` (`df.loc[hold]` and `df.at[r, …]` with split positions on a `__row_id` index). I did not reproduce it.
- **Status at head.** **Fixed in b38e2bc/5fe4afa** (`.iloc` in doctor.py; `reset_index` in annotations). Not re-verified by me. Add a gapped-version doctor check to P11's chain.

**M4. Data Doctor apply returns 500 on integers above int64, and quietly coerces junk.**
- **Repro, on `POST /api/datasets/{v2}/data-doctor/apply`:**
  - `{"transforms":[{"op":"rescale","column":"x1","date_column":"x2","from":9223372036854775808,"factor":9223372036854775808}],"by":"x"}` → **500**: `CanonicalError: $.provenance.ops[1].changes[0].from: integer 9223372036854775808 does not fit in int64`.
  - The same with `2**64`, and `{"op":"relabel","rows":[0],"labels":[9223372036854775808]}` → 500, 4 times in total.
- **Silent coercion.** In the same fuzz (184 calls), `drop_rows` with `rows: [1.5]` or `[true]` drops row 1, while `[-1]`, `[1e30]`, `[10**12]` and `null` are silently ignored. Each of these still writes a new version ("1 fix applied", 3,010 → 3,010 rows), and identical results are **not deduped** (ds_ff5e3c21, ds_cecd05ea, ds_943f58ac, … are the same bytes).
- **Why it matters.** DLA4 #1 says "400, never 500", and non-integral floats and bools are refused for int targets.
- **Fix.**
  - Validate Doctor transform arguments with `lake.values.check`: row positions must be ints within range, and labels must fit the target type.
  - Map `CanonicalError` to 400.
  - Refuse a no-op apply, or dedupe it like edits.

**M5. A user column named `_row_id` is accepted, then hidden by the system id.**
- **Repro.** Upload `_row_id,b\n1,2\n3,4\n`. It is accepted (201, schema `_row_id BIGINT`). `GET /rows` and `GET /grid` then return `{"_row_id": 0, "b": 2}, {"_row_id": 1, "b": 4}`.
- **Impact.** The user's values 1 and 3 are invisible, and an edit addressed by the grid's `_row_id` means the system id. `__row_id` is refused (`reserved_column`), but `_row_id` (and `_row`) are not.
- **Fix.** Refuse or auto-rename `_row_id` / `_row` at upload, or namespace the API's id key.

**M6. `run_inputs` rows can be deleted, which removes check 4's evidence.**
- **Repro.** Take the forged w1 split from M2. Rewrite the `split_created` audit row (`audit_ro_u` dropped), then `DELETE FROM run_inputs WHERE split_id = 'spl_b6eb915f2297'`. No trigger refuses the delete.
- **Result.** Verify → **ok** on all five checks, and `POST /runs` → run_fe4d067f **succeeded on the forged split**.
- **Status at head.** P19 (4ef749d) hash-chains the audit and makes check 3 use the chain, so the audit rewrite should now break check 3. Not re-verified. `ri_ro_d` still does not exist at 5fe4afa: there is only `ri_ro_u`.
- **Fix.** Add `ri_ro_d` (BEFORE DELETE ON `run_inputs` → RAISE). Let check 4 also use the runs' `blob_refs` split pins.

### Minor

- **m1. Integrity failures at fit fail safe, but with engine text.** I flipped a byte *after* `POST /runs` returned 201.
  - A data part gives a run error of `OSError: ZSTD decompression failed: Data corruption detected`.
  - A split blob gives `ValueError: split rows must be in strictly increasing __row_id order`.

  Neither names the check (`data_integrity`, or `split_integrity` check 1). Hash before decode, or map the decode error to the named check. Verify does name both.
- **m2. A 409 after a failed verify has another shape.** `POST /runs` returns `detail` as a **string with no code** ("…'s last integrity check … was a MISMATCH…"), not `{code: split_integrity | data_integrity}`.
- **m3. A repeat commit with a different `match` is ignored.** It returns 200 `repeat: true` and the earlier version, with no error. It should be 409 "already committed with match …".
- **m4. Edit dedupe skips any edit with `add_rows`.** New ids are allocated each time, so repeating the same edit makes a new version (ds_22cf8aa4, then ds_091f2caa). Without `add_rows`, a repeat dedupes (200 `created: false`).
- **m5. Grep gate 1 prints one line:** `backend/app/dataset_versions.py:402` (a docstring mentioning `read_parquet(…)`). The gate must print nothing, so reword the docstring.
- **m6. Grep gate 2 has 30 lines in 12 files** (`datasets.py` 11, `catalog/schema.py` 4, `compare.py`, `dsets.py`, `splits.py`, `lake/upload.py`, `vela/experiments.py` 2 each, and 1 each elsewhere). This confirms known item 10, left for P10.
- **m7. Uploads and edits accept some odd values.**
  - An upload accepts `1e400`, `-1e400`, `inf` and `nan` in a DOUBLE column; `/rows` shows them as `null` with no `non_finite` flag.
  - Edits coerce strings into BIGINT: `"１２３"` (full-width) → 123, `"-0"` → 0, `" 7 "` → 7.

  Either document this or refuse it.
- **m8. Odd headers and fields get unhelpful handling.** A 100,000-character column name is accepted. A 2 MB field gives the misleading 400 "Could not read line 2".
- **m9. `holdout_identity_lost` counts removed holdout rows.** For key matching it counts *removed* parent holdout rows (3 here). That is conservative and consistent, but the UI copy says "new ids", so say "new ids or removed".
- **m10. The plan contradicts itself on the threshold.** §4.2 says "more than 1 %", §5.3 says "≥ 1 %". The code follows §5.3 (6 of 600 needs an ack). Fix the plan text.
- **m11. ZIP search is slow at 10M.** `?q=02139` takes about 2 s (the zip column is searched); `st7` and `refinance` are under 0.5 s.
- **m12. Parquet columns are kept as stored.** A Parquet file whose columns are all strings stays all VARCHAR, so survival's zero-config then fails ("duration_column: no column was detected"). Consider the CSV typing rules for string columns in Parquet, or say so in the check.
