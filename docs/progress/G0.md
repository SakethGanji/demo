# G0 · Smart Intake and the Build page

**What it does.** One upload, guided from there. `#/build` is the single entry point: upload or pick a table, then see what each column is for, then choose what to build. Each role is an editable chip with its confidence and evidence. The suggestions come best first, and each opens its flow pre-filled. **Advanced** opens the Training Gym.

## Backend

- **`backend/app/intake.py`** holds the detector and the suggestion registry. It uses rules only, with no LLM.
  - **Roles:** target, date, entity, id, money, duration, event, lgd, ead, surname, zip, geography, multilabel, segment, category, text, leak, constant and feature.
  - **What each role carries:** a confidence (the rule's own weight, 0–1, not a probability), its evidence, and the other roles the column could have (`also`).
  - **What it builds on:** the profiler's `detect_type`, plus F6's date/entity finder. F6's finder is moved out of `DatasetStore.split_options` into `splits.date_and_group_columns`, so the split options and Intake now share one code path.
  - **Target:**
    - The name reads like a label. This uses a stricter pattern than the profiler's `LABEL_NAME`, which would also take `merchant_category`.
    - Or it is the last column (a regression target also needs an amount/value-like name).
    - A time-series table whose last column is only a weak label makes the series value the target.
  - **Leaks:**
    - a post-outcome name;
    - one numeric column that alone separates the binary target (AUC ≥ 0.99);
    - a category in which every value has one class;
    - a column filled in only for one class (e.g. LGD, known only for defaulters).
  - **Series:** a date plus an item whose values share one calendar, with one row per (item, date).
- **`SUGGESTIONS` is a plain list of `Suggestion(id, title, route, match)`.** `match(ctx)` returns (score, reason, prefill) or None. G1–G9 append their own entry; nothing else changes. The G0 entries are:

  | Entry | Opens | Pre-fills |
  | --- | --- | --- |
  | binary ("Default/Churn/Fraud risk model") | New Model | target, the split from the date/entity roles, dropped IDs/leaks/constants, and `expected_cost` (the F7 default cost) |
  | multiclass | New Model | target, split, dropped columns |
  | regression | New Model | target, split, dropped columns |
  | forecast | Forecast | dataset |
  | anomaly | Anomaly | dataset (top when there is no label) |
  | import | Import | — |

- **API.** `GET /api/datasets/{id}/intake` returns the roles and suggestions. `POST` with `{"roles": {col: role}}` applies the user's edits: confidence 1, evidence "set by you", and the old target is demoted. An unknown role returns 400.

**Honest caveat.** I wrote the truth table from each generator's code, but I tuned the rules while looking at these same 8 samples, so 100% is in-sample.

**Out of sample: `scripts/fresh_data.py`, uploaded without a target.**
- card_fraud gives "Fraud risk model", y = is_fraud.
- complaints gives "Classifier", y = product_team. It is found as the last 7-class column (confidence 0.68), not by its name.
- deposit_balances gives "Predict a number", y = avg_balance_next_q_gbp.
- By my reading, all 30 columns of these three files get a sensible role (see the smoke output and the evidence table).
- A synthetic check of the roles no sample exercises gave the expected roles: surname, zip, LGD (+ leak), EAD, a leaky recovery amount, a `;`-delimited multi-label column, a constant, a product segment, and a leaky status code.

**Smoke.** `SMOKE_ONLY=intake,core make smoke` passes 31/31 (intake 10 steps, about 3 s; core 21). `npm run build` is OK.

## Limits and open problems

- **The roles are name-driven for the semantic ones** (money, duration, LGD/EAD, surname, segment, geography). A column named `x17` gets only a structural role. The structural ones (ID, entity, date, constant, leak, text, multi-label, series) use values.
- **The duration role is broad.** `tenure_months` (account-churn, deposits) and `customer_tenure_days` are marked as durations. G6 decides whether duration + event make a survival suggestion. The event role currently needs a 0/1 flag named like an outcome. For churn, the event is the target itself, and it is listed as the target.
- **Business cost:** the binary suggestion pre-fills `expected_cost` with F7's default costs (c_FN = 10·c_FP). The user edits them on the Goal step. No cost is inferred from money columns.
- **Mock mode:** Build needs the API. In mock mode it shows a note and the simulated New Model (the old in-browser profiler).
- **Not done here (G11):**
  - the toolbelt removal, Settings in the footer, and the Models/Vela items;
  - updating `docs/demo-script.md` and `scripts/demo_walk.cjs` to start from Build;
  - checking the Playwright live specs that clicked New Model's dataset list (`dataset-<id>` buttons, now gone in live mode). I ran no e2e (speed mode). `e2e/pages.spec.ts` gets the `build` route.
- **No model-card or Doctor change:** Intake is about a dataset, not a model. G10's tool registry should expose `GET /api/datasets/{id}/intake` as a Vela tool.
