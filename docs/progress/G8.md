# G8 · Multi-label classification

**What it does.** Some tables give each row several labels at once, such as complaint topics. This feature trains one AutoGluon yes/no model per label. This is AutoGluon's MultilabelPredictor pattern, with the labels modelled independently. Every label's model uses the same rows, the same inputs, the same config and one shared column-type declaration. Each label also gets its own threshold. A row's prediction is the set of labels that clear their thresholds: Ŷ(x) = {l : p̂_l(x) ≥ t_l}.

Where it lives (no new navigation):
- **Build:** a "Multi-label: topics" choice that opens `#/multilabel?dataset=` and lights up Build.
- **Models:** the run page `#/multilabel?run=`. The run kind is `multilabel`.
- **Registry:** a version with a **Labels** tab, plus Try It (a label set), Batch & Drift and the Model Card.

## Backend
- **`multilabel/core.py`: a new run kind, `multilabel`.**
  - It runs through `run_other` (same queue, events, SSE and MLflow).
  - Each label is fitted with F12's `prepare_fit`/`fit_predictor`: binary, log loss, `medium_quality`, 15 s per label.
  - The text column (from G0's `text` role) is declared text once, as `column_types`. The same `feature_metadata` and the TF-IDF text models go to every label's fit.
  - **Per-label threshold:** `predictor.calibrate_decision_threshold(metric="f1")` runs on that predictor's validation rows. That is the split's tuning slice, or AutoGluon's own holdout when there is none. The run's holdout never chooses a threshold.
  - A label with fewer than 20 positive (or 20 negative) training rows gets no model. The page says why.
  - **Holdout metrics:**
    - per label: F1 with a bootstrap CI, precision, recall, AP and the PR curve, plus F1 at 0.5 for comparison;
    - overall: macro F1, micro F1 and Hamming loss, each with a row-bootstrap CI (B = 300);
    - also: exact-set accuracy, Jaccard, labels per row, and the Hamming loss of predicting no labels, as the baseline.
- **Two upload forms** (`find`):
  - a delimited column (`;`, `|` or `,`), from G0's existing `multilabel` role;
  - **one 0/1 column per label.** This is new in G0: three or more 0/1 columns that share a prefix (`topic_fees`, `topic_fraud`, …) and overlap get the `multilabel` role. Generic prefixes (`is_`, `has_`, `num_` and others) never form a group.
  - Either form is now kept out of the single-target candidates.
- **`multilabel/api.py`:**
  - `GET /api/multilabel/detect`;
  - `POST /api/multilabel/runs`, which works with `{dataset_id}` alone;
  - `GET /api/multilabel/runs/{id}`;
  - `card_section`.
  - The split defaults to out-of-time by the date role, so the tuning slice sets the thresholds.
- **Registry:**
  - `build_other` gains a multilabel branch (latency, holdout macro/micro F1 and Hamming loss; labels and thresholds on the version).
  - Try It and `/score` return `labels` plus p̂ and t for each label.
  - The batch output adds the columns `labels`, `n_labels` and `p_<label>`, with PSI of the inputs and of |Ŷ| against the holdout.
  - `"multilabel"` is added to every non-tabular kind guard.
- **Model card:** a "Multi-label classification" section (JSON, MD and the view).
- **G0:**
  - a `multilabel` suggestion that scores 97 when at least 10% of rows carry two or more labels;
  - the intake truth row for the new sample.
- **Sample `samples_g8.py` → `complaint-topics`** (no existing sample touched):
  - 6,000 complaints: product, channel, tenure, amount disputed, a free-text `narrative`, and `topics`;
  - 6 overlapping topics, with 47% of rows carrying 2 or more;
  - label correlations, topics that the text sometimes leaves out, and passing mentions of other topics.

- **Overall:**
  - **macro F1 0.959 [0.953, 0.965]**;
  - micro F1 0.957 [0.951, 0.963];
  - **Hamming loss 0.0241** [0.0206, 0.0276], against 0.290 for predicting no labels;
  - exact label set 86.5%; 1.61 labels per row predicted against 1.74 true.
- **Acceptance: met.**
  - Macro F1 is reported per label, with a CI, a threshold and AP for every label. Smoke checks that macro F1 is the mean of the per-label F1.
  - Try It on a written multi-topic complaint (an unknown card transaction, a long hold, an overdraft fee) returns **{service, fraud, fees}** (p̂ 1.00/1.00/0.99 against t 0.13/0.50/0.22). `/score` matches it, and a 120-row batch and the card section pass.

## Limits and open problems
- **The sample is easy** (macro F1 ≈ 0.96), because the narrative comes from phrase banks. Real complaint text will score lower. The machinery, the CIs and the thresholds are the same.
- **Several thresholds land on exactly 0.500.** AutoGluon's threshold search keeps 0.5 when no grid point beats it on the tuning slice. That is honest but looks coarse.
- **Labels are independent:** there is no classifier chain (AutoGluon's `consider_labels_correlation`). Correlations reach a label only through the shared inputs.
- **Thresholds can't be changed after training.** They are fixed by the F1 rule; the PR curves show the trade-off, but there is no per-version threshold editor yet.
- **Versions are large** (~370 MB for 6 labels, because each label's model holds its own TF-IDF and n-gram pipeline). Latency is ≈ 350 µs per row in batches and ≈ 190 ms for one Try It row.
- **Not wired:** reason codes, monitoring, the credit report, fair lending, the Model Doctor and Vela. Each refuses multilabel versions through the kind guards. Vela (G10) can call `POST /api/multilabel/runs`.
- **The 0/1-columns form** is checked in code (intake on a reshaped sample) but has no smoke step of its own.
