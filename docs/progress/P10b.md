## Result

- `ENSEMBLE_BLOB_STORE=s3` runs the whole app on a bucket with no change to its callers. The full chain works:
  - upload → commit;
  - next version → diff;
  - edit;
  - two runs → compare;
  - verify-all and GC dry run;
  - migrate (P10's CSV-era data), restore-splits, and the split store.
- The results equal the same chain with `ENSEMBLE_BLOB_STORE=local`: same `data_sha256`, diffs, holdout metrics and compare.
- **Writes are once only.** Puts carry `If-None-Match: *` and an SHA256 checksum, and are HEAD-checked afterwards.
  - Eight concurrent puts of one sha make one object version with no error.
  - So do two API commits of the same new file at the same moment.
- **The read cache is keyed by sha and filled verified.**
  - When the cache directory is deleted, it refills.
  - A cached file changed on disk is detected (even with its mtime put back) and fetched again.
  - An altered object in the bucket fails verify, and a fill refuses it (409 `blob_integrity`).
- **Object Lock (GOVERNANCE, 30 days) is tested on MinIO.**
  - The locked original survives an overwrite and a delete without the bypass.
  - `delete_blob(…, bypass_governance=True)` removes it, and both outcomes are audited.
- **The local → S3 sync** copies, verifies every sha in the bucket, and resumes after a crash.
- **httpfs works offline** from a bundled extension directory.

## The server used

- **MinIO, built from source.**
  - `dl.min.io` answers **410 Gone**: "the open-source MinIO Server, MinIO Client (mc) and MinIO KES projects are
    archived and no longer maintained".
  - I built the last release tag with Go 1.x: `go install github.com/minio/minio@RELEASE.2025-09-07T16-13-09Z`. It took
    about 4 minutes to a 151 MB binary.
  - It ran single-node, single-drive on the scratch disk at `127.0.0.1:9000`, with throwaway root credentials passed as
    environment variables only.
- **Object Lock was tested.** Buckets were created with `ObjectLockEnabledForBucket` (`ENSEMBLE_S3_CREATE_BUCKET=1`,
  dev only), so versioning was on.
- **What MinIO does not support:** a lifecycle rule with `AbortIncompleteMultipartUpload`. It answers `InvalidArgument`,
  or silently drops the action when another action is present.
  - MinIO aborts stale uploads itself (`api stale_uploads_expiry`, 24 h by default).
  - The store still tries the rule, which is AWS's way. When the rule is refused, `/admin/lake/status` says so, and
    `abort_stale_uploads()` sweeps uploads older than a day at start on any server. The sweep was tested: a dangling
    upload was aborted.
- **For the deployment:** MinIO OSS is archived upstream. Choose a maintained build (a vendor's, or another
  S3-compatible store) for the bank. The code only needs the S3 API listed below.

## What was built

| Piece | Where | What it does |
|---|---|---|
| **S3BlobStore** | `lake/s3store.py` (new) | The `BlobStore` interface on S3 / MinIO. Same keys: `blobs/<aa>/<sha>.<ext>`, under an optional prefix. Its behaviour is described in the next table. |
| **Read cache** | `lake/blobcache.py` (new) | Stored as `<cache>/blobs/<aa>/<sha>.<ext>`, with a `.meta` sidecar holding size, mtime, ctime, inode and fill time. The sidecar's mtime marks the last use.<br>**Fill:** the object is streamed into a temp file and hashed; a file whose sha is not its name is never renamed in (`CacheIntegrityError` → 409). The rename is atomic and the file is chmod 0444.<br>**Hit check, `ENSEMBLE_CACHE_VERIFY`:**<br>• `stat` (default): size, mtime, ctime and inode must equal the fill's. Any write, chmod or utime bumps the ctime, which user space cannot set back. On a difference the file is re-hashed; a bad one is dropped and fetched again.<br>• `always`: re-hash every hit.<br>• `fill`: trust after the fill (B §6.2's original rule).<br>**LRU:** capped at `ENSEMBLE_CACHE_MAX_GB` (20). An entry used within `ENSEMBLE_CACHE_PIN_S` (300 s) is never evicted, because a caller may still hold its path. Several processes may share the cache directory. |
| **Store choice** | `config.lake_store_kind` / `s3_config` / `cache_dir` / `duck_extension_dir`; `store.open_store` | `ENSEMBLE_BLOB_STORE=local\|s3\|s3://bucket/prefix` (P02's `ENSEMBLE_LAKE_STORE` is still read).<br>Other settings: `ENSEMBLE_S3_ENDPOINT`, `_BUCKET`, `_PREFIX`, `_REGION`, `_URL_STYLE`, `_READ`, `_LOCK_DAYS`, `_CONDITIONAL`, `_MULTIPART_MB`, `_CREATE_BUCKET`; `ENSEMBLE_CACHE_DIR`, `_MAX_GB`, `_VERIFY`, `_PIN_S`; `ENSEMBLE_DUCK_EXTENSION_DIR`.<br>There is one store instance per configuration per process, so the boto3 client, its stats and the cache counters are shared. **No credential is a setting.** |
| **Audited delete** | `store.delete_blob(db, store, sha, by, reason, bypass_governance)` | The one way GC and purge (P24) remove bytes. It writes audit `blob_deleted` or `blob_delete_refused` (hash-chained, `object_kind = blob`). `LocalBlobStore.delete` takes the same keyword. |
| **DuckDB over S3** | `duck.s3_attach` (called from `configure`) | With `ENSEMBLE_S3_READ=httpfs`:<br>• `SET extension_directory` = `ENSEMBLE_DUCK_EXTENSION_DIR`, then `LOAD httpfs`. `autoinstall` / `autoload` stay off, so nothing is downloaded.<br>• `CREATE OR REPLACE SECRET` from the AWS chain's credentials, in memory only.<br>• `enable_http_metadata_cache`.<br>With the default (`cache`) nothing is loaded and DuckDB reads the verified cache files. |
| **Readers** | `frames._store` → `open_store` (it was a hard-coded `LocalBlobStore`); `frames.lake_table` | A part's `path` is now `local_copy(key)`: the blob itself when local, the verified cache file on S3. A missing blob keeps the `FileNotFoundError` path.<br>`pages` (previews, filters, search) reads `uri(key)`: the cache file, or `s3://…` with httpfs.<br>`pages.source` memoises sources, so on S3 + cache a memo hit re-checks its parts with `local_copy` (a stat and the sidecar), refilling or re-verifying them. Before this fix, a deleted cache directory gave DuckDB "No files found" (500). |
| **Local → S3 sync** | `lake/sync_s3.py` (new), `python -m app.lake.sync_s3 [--from DIR] [--dry-run] [--deep-verify] [--by NAME]`, `POST /api/admin/lake/sync-s3?dry_run=1` | For each local blob:<br>• re-hash it; a file whose bytes do not match its name is not copied;<br>• if it is already in the bucket, check its length and `x-amz-meta-sha256` (with `--deep-verify`, re-hash it) and skip it; this is what makes it resumable;<br>• else put it write-once.<br>Then **every `blobs` row** (pending / live) is re-hashed from the bucket. Progress is kept in `catalog_meta sync_s3:progress`, and there is an audit `lake_synced_to_s3`. The local lake is not changed. |
| Admin | `lake/api.py` | `GET /api/admin/lake/status` now shows `blob_store`: kind, read mode, Object Lock / mode / days, versioning, the multipart rule, setup notes, put/get stats and MB/s, and cache stats.<br>`POST /api/admin/lake/cache/verify` re-hashes every cached file and drops bad ones.<br>`CacheIntegrityError` → 409 `{code: blob_integrity}`. |
| Requirements | `requirements.txt` | `boto3==1.44.5`, which was already in the lock through AutoGluon; the lock line now also says `-r requirements.txt`. |

**How S3BlobStore behaves:**

| Area | Behaviour |
|---|---|
| **put** | `PutObject` with `If-None-Match: *`, `ChecksumSHA256` = base64(sha) (MinIO and S3 refuse other bytes: `XAmzContentChecksumMismatch`), `x-amz-meta-sha256`, and Object Lock retention when the bucket has it. Then a HEAD with `ChecksumMode=ENABLED`: length, checksum and meta must all match.<br>**412** → the key exists → its length and meta sha are checked → no-op.<br>**409** `ConditionalRequestConflict` → wait until the other put lands, then check it.<br>**501** → fall back to HEAD then PUT (also `ENSEMBLE_S3_CONDITIONAL=off`). |
| **multipart** | Above `ENSEMBLE_S3_MULTIPART_MB` (4,096 MB). It starts with a HEAD, because an existing key's 412 would otherwise come only after every part was sent. Each part carries a SHA256 checksum; the completion carries `If-None-Match`. The composite checksum is verified after. A failed upload is aborted. |
| **reads** | `open()` streams the bucket, so verify, verify-all, GC and sync re-hash what is really stored.<br>`local_copy()` goes through the cache.<br>`uri()` is the cache path, or `s3://bucket/prefix/key` with httpfs. |
| **Object Lock** | Read at start (`GetObjectLockConfiguration`). When enabled, each blob gets **GOVERNANCE** retention for `ENSEMBLE_S3_LOCK_DAYS` (30). **That figure needs model-risk approval: retention is bank policy.** Compliance mode is never used.<br>`delete(key, bypass_governance=…)` removes every version of the key (and its cache file); a refused version raises `ObjectLocked`. |
| **scratch** | `tmp_dir()` and `exports/` stay on local disk (`Settings.lake_dir`). `list("tmp")` lists that scratch, so GC phase 2 is unchanged. |

- **Step 8 shows what Object Lock does and does not do.** Retention keeps the original version, which cannot be
  deleted or overwritten. A writer with `PutObject` rights can still stack a newer version on top of it, so a plain GET
  then returns the new bytes.
- **The app catches that**, since every read and verify checks the sha. The original stays recoverable.
- **To stop the overwrite itself**, give the app role only `PutObject` with `If-None-Match` (AWS supports the
  `s3:if-none-match` condition key in bucket policy). No human or other role should have write rights on `blobs/`.
  MinIO's policy engine has no such condition key.

## Decisions and deviations

- **Default read mode = cache.** DuckDB reads verified local files, and httpfs is opt-in.
  - This follows §7 risk 10 ("verified on fill, never stale") for every reader.
  - Readers that open part paths with pyarrow or `open()` (`frames`, splitstore, gym export) need a local file anyway.
  - B §6.2 suggests range reads for previews. The httpfs mode gives that and is verified here.
- **`stat` + ctime on every hit**, rather than B §6.2's "verified on fill, then trusted". The check costs about
  0.04 ms, and it is what makes tamper detection (steps 7a and 7b) work. `fill` mode keeps the original rule.
- **Retention 30 days by default** (`ENSEMBLE_S3_LOCK_DAYS`). It needs model-risk approval, like the other retention
  figures in config.
- **GC (P24) also needs the bypass.** Unreferenced blobs inside the retention period can only be deleted with it, so
  P24 should call `delete_blob(..., bypass_governance=True)` (audited), or set the retention below the GC grace
  periods.
- **The sync endpoint is synchronous.** It runs in the threadpool and is fine for small lakes. Large lakes use the CLI
  (same code). It is not a queued job: that would mean adding a handler to `engine/workerd.py` (the jobs lane).
- **MinIO compose profile (B7):** none was added. The repository has no compose file, and the upstream MinIO OSS
  project is archived (see "The server used").

## For dependants

- **P24 (GC deletes, purge):**
  - use `lake.store.delete_blob(db, store, sha, by=…, reason=…, bypass_governance=True)`; it removes all versions and
    the cache file, and writes the audit row;
  - give that role `s3:BypassGovernanceRetention`;
  - the `abort_stale_uploads()` sweep can run with GC.
- **Deployment:**
  - credentials come only from the AWS chain;
  - bucket policy: allow the app role `PutObject` only with `If-None-Match`, and allow no other writers on `blobs/`;
  - pick a maintained MinIO build or another S3 store;
  - bundle httpfs if `ENSEMBLE_S3_READ=httpfs` is used;
  - put `ENSEMBLE_CACHE_DIR` on a fast local disk sized to `ENSEMBLE_CACHE_MAX_GB`.
- **All lanes:**
  - do not build paths from keys;
  - use `store.local_copy(key)` for a local file and `store.uri(key)` for DuckDB;
  - never memoise a cache path without re-checking it (see `pages._ensure_cached`).
- **Scratch:** removed. That covers the MinIO binary and data, the venv, worktrees of the three old heads, the data dirs
  and the buckets.
