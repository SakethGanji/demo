# D4 · Review loop and changes after deployment

**What it does.**

- **Review** (run page → Doctor tab → Review, one primary action **Run Review**). Claude reads the run in four roles:
  perceive the data, describe the task and the decision point, analyse the errors, propose hypotheses. Each hypothesis
  must map to **one typed experiment**. The platform runs it on the same holdout and records it in a **journal**:
  hypothesis → experiment → paired Δ with CI → verdict. The search is greedy on the best node and capped.
- **Improvement plan.** The review ends with what was tried, what helped (with numbers), and what the bank should do
  next: collect or join X, redefine label Y, drop Z, confirm the cost ratio, serve a simpler rung.
- **Domain gaps.** Claude's suggestions fill What's missing's slot (`missing_info.domain_gaps.items`, `{title, why}`).
  They stay labelled as suggestions and carry no figures.
- **Number guard.** It blocks any figure in Claude's text that is not in the journal; the computed text then stands.
- **Audit.** Every review goes to the audit log with its inputs' hash, each prompt's hash, the model and the decider.
- **Offline.** Without a language model, the deterministic Doctor proposes the same experiment kinds from its rules,
  and the plan is the computed one.
- **Changes after deployment** (Registry → version → Monitoring → **Changes**). On a registered version with a newer
  labelled batch: a threshold move, a recalibration, a retrain on the recent window, or dropping a drifted feature,
  each scored on the newest labelled batch against the version as it serves today. A result that is better beyond noise
  becomes a **request**: a new registered version, approval pending, then the usual four-eyes review and promotion.
  Nothing changes the live version on its own. The review proposes the instant ones too.
- **Vela agent:** new tools `review_run` (write: it trains child runs; it waits within the session's time) and
  `read_review`.

**Verification (the user's rule):** no smoke suites and no new smoke sections. The APIs were called by hand, chained the
way the UI calls them, on the four real datasets and on crafted data, plus `npm run build` and `tsc --noEmit`.

## Backend

### Typed experiments (`app/vela/experiments.py`, `POST /api/runs/{id}/experiments`)

`KINDS` is the whitelist. Anything else is refused with 400 ("experiments are typed, never free-form"). `validate()`
checks a spec against the run without starting it, and the review uses the same function.

| Kind | What runs | Δ |
|---|---|---|
| `ablate {columns}` | child run without the columns | paired, the run's metric |
| `budget`, `preset` | child run, 2× time / next preset | paired |
| `monotone {constraints}` | child run with F8 constraints (binary / regression) | paired |
| `apply_data_fix {transforms}` | D1 `_apply` → a dataset version with the parent's holdout rows → child run | paired through `root_rows` |
| `add_features {candidates?}` | D2 Feature Lab on the training folds; the kept ones → version → child run. If none is kept: `no-change`, no child | paired through `root_rows` |
| `clean_labels` | cleanlab (D1's out-of-fold quick model) on the **training rows only**; the flagged training rows are dropped in a version; the holdout is untouched; then a **full-ensemble** child run | paired through `root_rows` |
| `serve_rung {rung}` | instant: the D2 ladder against the model the run serves | ladder's paired bootstrap (exact when either is the best rung) |
| `cost_ratio {c_fn, c_fp}` | instant: the same model at the cost-optimal threshold of another ratio, chosen on one half of the holdout and applied to the other (cross-fitted) | cost per 1,000 under that ratio, served threshold vs its own |
| `segment {column}` | a G5 segmented run (one model per value) | G5's routed vs global, DeLong |

- **Refusals:**
  - `merge_classes` on the target changes the task. The scores would not be comparable, so it belongs in the plan.
  - `drop_rows` could drop holdout rows; use `clean_labels`.
  - `cost_ratio` needs a cost run; it also refuses the run's own ratio.
  - `serve_rung` refuses the model that is already served.
- **Δ across dataset versions:**
  - `delta()` maps both runs' holdout rows to root rows (`lineage.root_rows`) before pairing.
  - The metric is the run's own: expected cost per 1,000 at each run's served threshold for cost runs, AUC for binary,
    accuracy for multiclass, RMSE for regression.
- **Instant and G5 experiments** are recorded in the run's `result.experiments_extra`, and `GET …/experiments` lists
  them with the child runs.
- **Small edits elsewhere:**
  - `data_doctor.label_issues(..., all_rows=True)` returns every flagged row;
  - `llm.ask_json_async(path_timeout=…)` sets a per-path timeout for the long role prompts.

### Review loop (`app/vela/review.py`; routes in `app/vela/api.py`)

- **Routes:**
  - `POST /api/runs/{id}/review {by, max_experiments 1–8 (5), max_minutes 5–240 (30), offline}` → 202. It runs as an
    asyncio task on the API's loop and calls the routes in process (httpx ASGI): the same chain as the UI.
  - `GET …/review` lists the reviews; `GET …/review/{rid}` is the live record.
  - 409 when a review is already running on the run.
- **Roles.** Each is one prompt; the prompt's SHA-256, the facts' SHA-256, the decider, the model and the seconds are
  recorded:
  1. perceive the data;
  2. task and decision point;
  3. errors: Data Doctor, Model Doctor, What's missing and Holdout Errors, plus the domain gaps;
  4. propose hypotheses;
  5. word the plan.
- **Journal entry:** `{step, hypothesis{title, why, expected, source}, experiment{kind, spec}, node, run_id, status,
  result{metric, parent, child, delta, ci}, verdict, reason}`. An identical experiment that already finished on the same
  node is **reused**.
- **Verdicts:**
  - `kept`: the CI is above 0; the child becomes the best node.
  - `kept-honest`: the ablation of a Doctor leak suspect; the child becomes the node.
  - `equivalent`: a simpler option within noise.
  - `info`: a cost-ratio sensitivity.
  - `request`: a post-deployment change better beyond noise.
  - `rejected`: within noise, worse, nothing changed, or refused.
- **Policy** (written on screen):
  - Greedy on the best node.
  - At most `max_experiments` trained experiments and `max_minutes`, checked before each start.
  - A second proposal round only after a new node.
  - Stop after 3 trained experiments in a row that do not beat noise.
  - Instant experiments are not counted.
- **Post-deployment.** If a ready version of the run has a newer labelled batch, the review runs the instant changes
  (threshold, recalibrate) on it, and better ones become `request` actions.
- **Plan** (`compute_plan`), computed from the journal and the final node's Doctor:
  - drop + confirm decision time (leak);
  - adopt (kept);
  - serve a simpler rung;
  - confirm the cost ratio;
  - request (post-deployment);
  - then the What's missing gaps as data requests: join (twins), collect (thin feature, concentration, more rows),
    redefine the label (overlap), fix capture (missingness).

  The LLM may replace the summary and add actions. **Number guard:** every figure must appear in the journal (which
  includes the context the review read); a blocked text leaves the computed one, and the block is listed in `guard`.
- **Domain gaps:** `{title, why}`. Any item with a figure is dropped. They fill `missing_info.domain_gaps` on the
  Doctor (`status: done`, the review's id, decider and model).
- **Audit:** one `review` entry per review: inputs SHA, every prompt's SHA and model, the decider, each experiment's
  Δ / CI / verdict, and the best node. Example: entry 20, `review rv_e189b1bb (llm, Claude CLI): 3 experiments, 1 kept`,
  inputs `c185b5542d94e06c`, perceive prompt `8d6a91570ae9932d`.
- **Offline** (no route, or `offline: true`): `rule_hypotheses` proposes the same kinds:
  - leak ablation;
  - the pre-selected D1 fixes (current features only);
  - clean labels when the label check fires or its measured Δ's CI reaches above 0;
  - Feature Lab when it has not run;
  - budget / preset findings;
  - a concentrated category segment;
  - the ladder's simpler rung;
  - ratios at half and twice the run's.

  The plan is the computed one.
- **API restart:** a review whose task is gone reads `interrupted`. Starting again reuses the finished experiments.

### Changes after deployment (`app/registry/changes.py`, `changes_api.py`)

- **Routes:**
  - `GET /api/registry/versions/{vid}/changes`: eligibility, the newest labelled batch, drifted features (PSI ≥ 0.1),
    the experiments;
  - `POST …/changes {kind, column?, actor}`;
  - `POST …/changes/{cid}/request {actor}`.
- **Kinds:**
  - `threshold`: cost-optimal threshold, cross-fitted on the batch's halves; Δ cost per 1,000.
  - `recalibrate`: Platt on logit p̂, cross-fitted; Δ log loss, plus cost at the calibrated Bayes threshold. It is served
    as the equivalent raw-score threshold.
  - `retrain_window`: the version's body on the labelled batches **before** the newest (plus the training data if they
    hold under 300 rows). The newest batch is the evaluation.
  - `drop_feature`: the version's body without the column, on its own training data.

  Retrained models are compared at their own cross-fitted cost-optimal thresholds (so only the model differs), with
  DeLong's paired AUC too.
- **Costs:** the run's business cost, or the ratio its threshold implies ((1 − t) / t), stated on screen.
- **Request:**
  - Only for a result that is better beyond noise (409 otherwise, and 409 if already requested).
  - Threshold and recalibrate register the same run with `decision_threshold`: a new `RegisterRequest` option, set on
    the version's copy in `build.py`.
  - Retrain and drop register the experiment's run.
  - The new version is **approval pending**. The requester cannot approve it (the four-eyes rule already in
    `review`), and Production needs the approval.
  - Audited as `change_experiment` and `change_requested`.
- **Registry fix:** a version may now come from a **version of the model's dataset** (lineage parent or root: a fix,
  Feature Lab, a monitoring window). Before, retrain-window requests were refused with "a version must predict the
  same label on the same dataset".

### Vela agent (`app/agent/tools.py`)

- `review_run` (write): it starts a review, or follows the running one, and waits within the session's time left. It
  returns the journal digest, the plan, the domain gaps and the guard.
- `read_review` (read).
- The tool count goes from 40 to 42; both link to `models?run=…&tab=Doctor&review=1`.

## UI

- **Doctor tab → Review** (`src/features/models/explain/components/ReviewPanel.tsx`):
  - The card sits under How To Improve. Its one primary action is **Run Review** (then "Run Review Again").
  - A status line: mode, decider and model, caps, live progress, the stop reason.
  - The **journal** table: hypothesis with why, experiment with a link to its run, Δ [CI] and parent → child, a verdict
    pill with its reason.
  - Refused hypotheses sit in a fold-out with the whitelist's reason.
  - The **improvement plan**: the summary with a "Claude · numbers checked" or "computed" badge, a "do next" table
    (kind pill, title, why, source, links: open the run, register the simpler rung, open the version's Changes),
    the domain gaps as "suggestions to investigate (not measured)", and the guard's blocks.
  - Advanced fold-out: caps, offline, the roles table (decider, seconds, prompt hash), the rules and the audit entry.
  - It polls every 4 s while the review runs.
- **What's missing:** the domain-gap line becomes a list of `{title: why}` under its label, or the slot's note.
- **Registry → version → Monitoring → Changes** (`src/features/registry/components/ChangesCard.tsx`, binary versions):
  - The newest labelled batch, the threshold, where the costs come from, and the drifted features.
  - One primary action, **Evaluate**, with a kind picker (and a column for drop feature, the most drifted first).
  - The table: now → with it, Δ [CI] (plus AUC and cost for some kinds), the operating point (decline and catch, t),
    the verdict, and **Request →** only on "better".
  - A fold-out with the rules.
- **Client and types:** `api.runs.reviews / review / startReview`, `api.registry.changes / startChange /
  requestChange`; types `Review`, `JournalEntry`, `ReviewPlan`, `ChangesState`, `ChangeItem`.

**Requests.** Each case was requested, giving new versions `mv_66e3fd06` (t 0.0718), `mv_736e8bfb` (t 0.3043),

- Promoting the threshold request before approval → **409** "Production needs an approved review first".

- A second request of the same change → 409; a non-typed kind (`"rm -rf"`) → 400.

- **Known limits:**
  - The review runs in the API process. A reload (dev `--reload`) or a restart interrupts it; finished experiments are
    reused on the next start.
  - Experiments share the CPUs with whatever else trains. Time-limited AutoGluon children under load fit fewer models,
    which biases Δ slightly downwards for budget-limited runs. Run reviews one at a time for clean numbers.
  - The cost-ratio Δ on a small holdout (German: 200 rows) is wide; its use is the decline / catch shift, not the cost
    difference.
  - Segment Δ is G5's routed vs **its own** global model (G5's per-model time limit), in AUC even on cost runs.
  - Claude sometimes proposes weak hypotheses (Taiwan: ablate the payment columns as "possibly post-outcome"). The
    journal rejects them with numbers; nothing is kept without a CI above 0.
  - Recalibration is served as the equivalent raw-score threshold; the probabilities shown stay the raw ones.
  - Domain gaps are suggestions: their wording varies between runs of the same review.
