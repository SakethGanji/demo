## A. scripts/smoke.py and `make smoke`

`scripts/smoke.py` is one httpx script that chains the calls the UI makes. It prints a ✓ or ✗ line per step with a key
number and exits 1 on any failure. `make smoke` runs it against :8000 and starts the API itself if nothing answers there
(`--start-api`, log in `backend/data/smoke-api.log`). `SMOKE_ONLY=core,samples,autopilot` picks sections.

S6 pushed a smaller smoke.py at the same time as this session. Mine covers the same chain plus profile, fairness, the
samples and Autopilot, so the merge kept mine.

Real bugs it found and fixed:

- **export.py vs a later threshold.** After `POST /runs/{id}/threshold`, the exported script applied the new threshold
  and then compared the leaderboard with the one recorded at fit time, giving max |Δ| = 0.113. The run now records
  `fit_threshold` the first time the threshold changes. The script scores the leaderboard at that threshold and applies
  the current one afterwards. Result: max |Δ| = 0.
- **TF-IDF models named in `hyperparameters`.** When a body listed both TFIDF_LR and TFIDF_SVM itself, nothing was
  "added", so raw text was not kept and both failed with "No valid features". `resolve_fit_kwargs` now keeps raw text
  whenever a TF-IDF model is in the hyperparameters.
- **Top words failed a run.** Under good_quality with refit_full, a `_FULL` TF-IDF child can have no in-memory
  estimator, and `text_top_words` raised an AttributeError that failed the whole fit. Children without an estimator are
  now skipped, and top words never fail a run.

## B. Autopilot (layer 1 + layer 2)

**Backend** (`app/autopilot/`, `app/llm.py`)

- `engine.py`: a thread per autopilot inside the API process. It calls the API over HTTP, the same way the UI does, so
  every step is a real `POST /api/runs` with `source: autopilot` and `parent_run_id`, and goes through the Gym's
  validation. State is one JSON file per autopilot in `data/autopilot/`. After a restart, autopilots resume: an
  in-flight run is followed to its end, and any other unfinished step is marked interrupted and redone.
- Strategy:
  1. Profile the data.
  2. Fast baseline: medium_quality, 5-fold bagging, no stacking. For text the models are TF-IDF LR and SVM, for
     tabular GBM, XT and LR.
  3. Audit, in the worker pool. cleanlab `find_label_issues` runs on the baseline's out-of-fold p̂ for training rows
     and its held-out p̂ for holdout rows, ranked by the normalised margin. The audit also finds exact duplicates,
     near-duplicate conflicts (cosine ≥ 0.97 on TF-IDF→SVD and one-hot embeddings) and outliers (cleanlab
     `OutOfDistribution`, lowest 0.3 %). Datalab needs `cleanlab[datalab]`, which is not installed, so the
     near-duplicate and outlier checks call the same building blocks directly.
  4. The inbox: wait for your answers, or under `auto` accept suggestions with c ≥ 0.9.
  5. Apply the answers as a new dataset version (`DatasetStore.create_version`). It gets `lineage.json` with the
     root row of every row and every change, and the same holdout rows minus dropped ones, with folds carried over.
  6. Retrain.
  7. A loop of decisions over this menu: rebalance (`predictor_kwargs.sample_weight = balance_weight`), calibrate the
     threshold (binary), reduce latency (refit_full + set_best_to_refit_full + infer_limit), escalate the preset
     (medium → good → high, each tried once; with a latency requirement also one stack layer, refit_full and
     infer_limit), add families, synthesise minority-class text (layer 2 only), or stop.
  8. The final step, marked Met or Not Met with every check.
- **Scores.** Every step's holdout predictions are re-scored against the newest labels on the rows that are still in
  the holdout. The baseline is therefore compared like with like after the inbox corrects holdout labels. Both the
  "own labels" score and the "current" score are kept and shown.
- **Latency.** p50 and p95 of 40 one-row `predictor.predict` calls on the served model, measured in the worker pool.
- **Which step is kept.** Steps are ranked by: met all; then the number of requirements holding; then the smallest
  relative shortfall Σ gap/|target|; then the primary score. A step that ranks lower is dropped, and the log says why
  (for example "It broke p95_latency_ms, which held on …").
- **Layer 2.** `app/llm.py` calls the claude CLI with `-p --model claude-sonnet-5-5 --output-format json` (retried
  once), then the Anthropic API, with a 60 s timeout. It reuses S6's `_via_cli` and `_via_api`. The prompt holds the
  menu and a state digest (steps with scores, p95 latency, worst recall and unmet checks, inbox stats, dataset
  versions, budget spent and left). The reply is `{action, time_limit, rationale}`. An action that is not on the menu,
  or no answer, makes layer 1 decide that step, and the decision records why. Every decision stores its layer, source,
  model and seconds, and what layer 1 would have chosen.
- **Synthetic examples.** For a text class under 6 % share, Claude writes 40 tickets in the style of real training
  examples. The rows are placed in training folds only, marked in the lineage, never put in the holdout, and shown in
  the UI.
- **Budget.** Σ wall time of the training steps ≤ B. Time limits are planned for a 1.4× overrun, which was measured:
  refit, scoring and latency come on top of the time limit. An earlier version overspent 616/600 s; this version stays
  within the budget.
- API routes: `POST/GET /api/autopilot`, `GET /api/autopilot/{id}`, `…/inbox`, `…/inbox/answer`, `…/inbox/bulk`,
  `…/resume`, `…/cancel`, `GET /api/autopilot/menu`. README has a table.
- `POST /api/vela/ask` answers a question from the run's or the autopilot's computed facts: the leaderboard, holdout
  scores, importance, Vela findings, steps, verdict and log. It uses the same caller. With no model, it returns
  `answer: null` and "No model available".

**UI** (`features/autopilot/live/`). In live mode the scripted prototype is replaced and the SIMULATED label is gone.
Mock mode keeps the prototype with a SIMULATED pill, and PrototypeBanner has no pages left.

- **Brief:** dataset, label info, goal, requirements as inequality rows with the symbol, total budget B, autonomy
  (Ask me / Auto ≥ 0.9), who decides (Claude → fixed / Fixed only), the plan, and earlier autopilots.
- **Run page:**
  - IterationString, RequirementGauge and DataChanges are reused and fed from the real steps. Dropped runs hang off
    the string as branches, and the inbox is the diamond.
  - The stage shows the id, runs, budget, dataset version and the deciding layer.
  - Inbox: m(x) with its where-list bound to the selected row, the planted-error recall box, filters by kind, the
    bulk-accept c slider with a live count, per-row confirm / relabel (with a class picker) / drop / skip, and "Apply N
    Answers & Retrain".

  - Requirements: f* against each target, ΔF̄₁ = F̄₁(f*) − F̄₁(f₀) with numbers, and Σtᵢ ≤ B, with every symbol
    defined, including f₀'s score on the original and the corrected labels.
  - Dataset versions; the result with Compare With Baseline, Explain and Open In Gym; the runs table (own and current
    scores, Δ, τ₉₅, decided by).
- **Vela sidecar:** the question box works in live mode. It asks about the autopilot on `#/autopilot?ap=…`, otherwise
  the run in view, and shows "answered by Claude CLI · claude-sonnet-5-5" or "no model available".

## Open

- **One-row latency of text ensembles.** AutoGluon's `infer_limit` is passed, but it judges by batch throughput
  (504 rows/s here), while our p95 is one row per call and includes text featurisation. The strong GBM-on-n-grams
  configs (F̄₁ ≈ 0.95) take 70–250 ms per row on this 4-CPU box. With a 50 ms limit, layer 1 ends Not Met by 0.0002.
  Measured p95 also varies by ±10 ms between identical models.
- `e2e/registry.live.spec.ts` line ~171 expects Autopilot's PROTOTYPE banner in live mode. The build plan said to
  remove it once Autopilot is real, and S7 does not edit tests, so that one Playwright assertion is now stale. S9
  should update it.
- Datalab is not installed (it needs `cleanlab[datalab]`). The audit uses cleanlab's filter, rank and outlier modules
  directly.
- Regression autopilots skip label issues (no class probabilities). They run baseline → loop → verdict.
- Autopilots run in API threads. `make dev`'s reload restarts them and they resume, but a run's wall time then counts
  from the resume.
