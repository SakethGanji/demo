# G3 · Expected loss: PD × LGD × EAD, with stress scenarios

**What it does.** Expected loss is a choice inside Build. It reads three columns from the table:
- whether each loan defaulted;
- how much of the exposure was lost (LGD);
- how much was owed at default (EAD).

One run trains three AutoGluon models and computes EL = PD · LGD · EAD per loan. It checks ΣEL against the realised loss on the holdout, breaks EL down by segment, and re-scores the loans under stress scenarios. The results live on the run page (`#/expected-loss?run=`) and in Registry (version → **Expected Loss** tab).

It is zero-config:
- The G0 roles pick the default flag, LGD, EAD, the segments, the columns to leave out and the split.
- The stress scenarios come from the column names.

A user who just clicks through gets a checked result.

## Backend

### Sample: `samples_g3.py` (new module; `samples.py` is untouched)
- **`loan-losses`:** 20,000 seeded loans.
  - **Columns:**
    - `loan_id`, `application_date`;
    - `product` (card / personal / auto / sme), `region`;
    - `income`, `credit_score`, `debt_to_income`, `utilization`;
    - `credit_limit`, `current_balance`, `collateral_value`, `term_months`;
    - `defaulted`;
    - `lgd` and `ead`, filled in for defaulters only.
  - **The generator's formulas** are in the module docstring:
    - logit PD is driven by score, DTI, utilisation, income and product;
    - LGD = product base − 0.45 · collateral cover + noise;
    - EAD = balance + CCF·(limit − balance) for revolving products, and the balance otherwise.
- **How it is registered:** through `SAMPLES_G3`, which `datasets.ensure_samples` and the list order in `main.py` merge in. This way no existing fingerprint changes.

### Engine: `el/core.py`, a new run kind `expected_loss`
- **Where it runs:** in the existing run worker, through `run_other`, so it has the same queue, events, SSE, cancel and MLflow logging as other runs.
- **How it fits:** one F4/F6 split of the default flag gives one holdout for all three models. Each fit goes through F12's `prepare_fit`/`fit_predictor`.

  | Model | Problem type | Eval metric | Trained on | Output |
  | --- | --- | --- | --- | --- |
  | PD | binary | log loss | every loan | P(default) |
  | LGD | regression | RMSE | defaulted loans only | clipped to [0, 1] |
  | EAD | regression | RMSE | defaulted loans only | ≥ 0 |

  Both metrics are proper for the mean, so the product is unbiased when each part is.
- **Holdout output:**
  - **Portfolio:** ΣEL vs Σ realised (L = y·LGD·EAD) and their ratio, with a 95% bootstrap CI (400 resamples of loans), plus ΣEAD̂ and the EL rate.
  - **Each model:** PD's AUC, log loss, Brier score and mean PD̂ vs the default rate. LGD's and EAD's MAE, RMSE, R² and mean predicted vs actual, on the defaulters.
  - **Segments:** per segment column, n, defaults, ΣEL, share, mean PD̂ and LGD̂, EL rate, realised loss and EL/realised.
- **Stress:** `shock_frame` applies `pct`, `pp`, `add` or `set` shocks.
  - Values stay in their natural range: ≥ 0 for non-negative columns, and ≤ max(1, observed max) for shares. Clipped values are counted.
  - `stress` re-scores the shocked loans with all three models and reports ΔEL overall, per component mean and per segment, plus whether EL moved the way the scenario expects.
- **Default scenarios, found from column names:** income −10%, utilisation +15pp, collateral −20%, credit score −20, and "Mild downturn" (all of them at once). Each expects EL to go up.

### API: `el/api.py`
| Route | What it does |
| --- | --- |
| `GET /api/expected-loss/detect?dataset_id=` | The inputs and their evidence, from `intake.detect`. LGD and EAD are often a *secondary* role, because both are also leaks of the default flag. |
| `POST /api/expected-loss/runs` | `{dataset_id}` is enough. Every input can be overridden: pd/lgd/ead columns, segments, drop_columns, split, time_limit (60 s per model), presets (`medium_quality`), fit_kwargs. Bad input is refused with 400: an LGD outside [0, 1], a target that is not two-valued, the same column twice. |
| `GET /api/expected-loss/runs/{id}` | The result, plus saved custom scenarios. |
| `POST /api/expected-loss/runs/{id}/stress` | `{name?, shocks:[{column, op, value}], expect?}`. Returns 400 for an unknown column or a % shock on a category. It reuses the run's stored holdout scores as the baseline (≈ 0.8 s warm). The last 12 custom scenarios are kept on the run. |

### Registry
- **Build:** `build_other` copies the three predictors and `meta.json`, measures latency (single loan ≈ ms, a batch of 2,000) and hashes the files.
- **Serving:**
  - `/predict` and `/score` return PD̂, LGD̂, EAD̂ and EL per loan.
  - Batch scoring adds `pd, lgd, ead, expected_loss` columns, totals by segment, and PSI of the inputs and of EL against the run's holdout.
- **Excluded:** the tabular-only guards (`("forecast", "anomaly")` → `+ "expected_loss"`) keep tabular-only features away from EL runs: Reason codes, monitoring, Doctor, etc.

### Model card
An "Expected loss (PD × LGD × EAD)" section in JSON, Markdown and HTML, plus a paragraph in the card view. It holds:
- the three models (target, rows, best model, holdout check);
- the holdout ratio with its CI;
- the stress table.

### G0 (zero-config)
- **New suggestion `expected_loss`:** "Expected loss (PD × LGD × EAD)", score 97. It needs a yes/no target plus a column with the LGD role and one with the EAD role (primary or secondary).
- **Prefill:** pd, lgd, ead and segments (segment + geography roles).
- **EAD's confidence went from 0.85 to 0.9,** so `ead` shows as "exposure at default" (with leak as its second role) rather than "leaky". It is still left out of the PD-only (yes/no) flow.

**Stress (acceptance: the right direction and a reported amount).** Every default scenario moved EL up, as expected:

| scenario | ΔEL | Δ% |
| --- | --- | --- |
| income −10% | +96 k | +2.8% |
| utilization +15pp | +430 k | +12.5% |
| collateral_value −20% | +128 k | +3.7% |
| credit_score −20 | +507 k | +14.8% |
| Mild downturn (all four) | +1.25 M | +36.5% |

## Limits and open problems

- **PD calibration depends on the fit.** With the zero-config `medium_quality` ensemble, mean PD̂ matches the default rate (11.9% vs 11.7%). A GBM-only fit (`hyperparameters: {GBM: {}}`) over-predicted PD (13.6%) and gave ΣEL/realised = 1.25, outside ±10%. There is no separate PD calibration step (e.g. a logit-intercept shift on the tuning slice); the hero shows mean PD̂ vs the observed rate, so it is visible. The smoke therefore runs the zero-config path (≈ 2 min), not a speed-reduced one.
- **The ±10% check is one holdout of 472 defaults.** The bootstrap CI is wide (about ±14%), and two zero-config runs gave 1.068 and 1.085. The time limit makes AutoGluon's ensemble vary between runs.
- **Stress scenarios shock inputs independently.** Utilisation +15pp does not move `current_balance` with it, and there is no macro model. Each scenario is a "what if these inputs were different" re-score, not a forecast. The default scenarios are name-driven; a table without income/utilisation/collateral/score-like names gets none, and the user adds their own.
- **LGD/EAD learn from defaulters only** (1,512 training rows here). LGD is a point regression; the optional quantile LGD was not built.
- **Stress runs on the holdout loans,** not on a new book. To stress a new book, score it in Batch & Drift (EL per loan); there is no batch stress yet.
- **Version size:** the three `medium_quality` predictors take ≈ 544 MB on disk. There is no refit_full or infer_limit for EL versions; the build says "skipped".
- **Not in the Model Doctor or Vela.** G10 should expose `POST /api/expected-loss/runs` and `/stress` as tools. Mock mode shows a note only.
- **Smoke leftovers:** each smoke run adds an EL run and a `smoke.expected-loss` version.
