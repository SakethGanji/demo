## Cause, confirmed

Before F6 every split was random (stratified). The credit-default sample had no customer or date, so the problem
could not even be shown. With the new sample, the random split puts **1,170 holdout rows (1,100 of 2,225 holdout
customers) next to rows of the same customer in training**, and **1,906 training rows are dated after the
out-of-time cut-off** (2024-06-20). Its score therefore mixes memory of the customer with knowledge of the future.

## What changed

**Splits (`backend/app/splits.py`).** `STRATEGIES = (random-stratified, group, time, time-group)`. Non-random splits
take parameters (`group_column`, `time_column`, `cutoff`, `tuning_share`), and the parameters are part of the key
(`split_key(target, strategy, params)` hashes target + params). Random keys are byte-identical to F4's, and the
`targets` smoke gets the same SHA `2fe5b7eb4a` and RMSE 2,434.33, so no migration was needed. Fold codes in the file:
0–4 train fold, −1 holdout, −2 excluded, −3 tuning. The file also lists `holdout`, `tuning`, `excluded`, `cutoff`,
`tuning_cutoff` and a `diagram` (rows, entities, dates and positive rate per role, shared entities, rows per period).
- **group**: holdout = one StratifiedGroupKFold fold (≈ 20 % of rows). Tuning = one group fold of the rest
  (s = 0.2). Train folds are 5 entity-disjoint StratifiedGroupKFold folds.
- **time**: τ defaults to the time value at the 80th row percentile. Holdout = t ≥ τ, tuning = the latest s of the
  training period (t ≥ τ_T), train = the rest, with folds as 5 contiguous time blocks.
- **time-group**: holdout = rows after τ from customers with no row before τ. Rows after τ from known customers are
  excluded (906 here). Tuning is defined the same way inside the training period, and folds are entity-disjoint.
- Rows whose date cannot be read are excluded. A column that is less than 90 % dates, or a cut-off that leaves fewer
  than 10 rows on a side, gives a 400.

**AutoGluon (worker).** I used AutoGluon's own mechanisms, as the brief asked, after reading the 1.6.3 source.
- Group splits add the stored fold as a column `__ensemble_group_fold` and pass `TabularPredictor(groups=…)`.
  AutoGluon then bags with exactly those 5 entity-disjoint folds (LeaveOneGroupOut over 5 values) and drops the
  column from the features.
- `groups=` on the raw customer id would make one fold per customer (thousands).
- `groups=` also forces bagging, even under `medium_quality`. I checked this: the models come out `_BAG_` with 5
  children.
- Every non-random split passes its tuning slice as `fit(tuning_data=…)` with `use_bag_holdout=True`. Without bagging
  it is the validation set; with bagging it drives the ensemble weights.
- Both are recorded in `resolved` (notes, `data_args.tuning_data`).
- AutoGluon 1.6.3 also has `fit(validation_structure={group_on | time_on | group_time_on})`. I did not use it: it keeps
  the referenced columns as features, while we drop the entity id.

**API.**
- `GET /api/datasets/{id}/split-options` finds date columns (≥ 95 % ISO-like dates, ≥ 10 distinct values) and entity
  columns (an ID-like name, or a high-cardinality string category with repeated values). It returns the warnings and
  the suggested strategy. On the other samples it suggests random for tickets, churn and loan-amount; time for
  transaction-volume; time + group for card-transactions.
- `POST /api/datasets/{id}/splits` draws a split, or reuses it, and describes it.
- `POST /api/runs` takes `split_spec`. For group splits the entity column is dropped from the features by default.
  `tuning_data`, `use_bag_holdout`, `groups` and `validation_structure` are refused when they would clash with the
  split.
- The Gym's `run_body` keeps `split_spec`.
- `POST /api/runs/{id}/split-twin` and `GET /api/runs/{id}/split-comparison` are new. Δ = score(random) − score(split),
  in the metric's direction. `same_config` marks runs whose fit settings match the run in view.

**Sample.** credit-default gains:
- `customer_id`: 8,074 customers, 1–4 applications each, mean 1.49.
- `application_date`: 2022-01-01 → 2024-12-31, sorted by date.
- A customer effect shared across a customer's applications.
- Mild drift: the base rate rises, the credit score separates less each year, and contract workers become risky from
  mid-2023.

The default rate is 7.4 % (5.6 % in 2022 → 9.6 % in 2024). `signal.json` records the drift. The existing pytest's
column count went from 14 to 16. The import smoke posted raw NaN rows as JSON (the new sample has a missing region in
its third row), so it now sends null. That was the only existing step that broke.

**UI.**

    "Use the … split";

  - a timeline of rows per month stacked by role, with τ_T, τ and the default rate per month;
  - for group splits, a group diagram: F / T / H boxes with rows, entities and default rate, |g(·) ∩ g(·)| = 0 chips,
    entities per fold and rows per entity;
  - an Advanced fold-out: entity column, date column, cut-off, tuning share.

The smoke recomputes the following from data.csv and the stored split files, not from the API's own summary:
- every row has one role;
- no customer appears in two of train, tuning and holdout, and no customer spans two bagging folds;
- train dates are before τ ≤ holdout dates, and tuning dates are ≥ τ_T;
- an existing split is not redrawn;
- 4 bad specs give 400.

For each twin, it checks:
- the run used the drawn split (same key and SHA) and the same dropped columns as the random run;
- `use_bag_holdout` and `tuning_data` match the split's tuning rows;
- the rows the run scored equal the split's holdout;
- for group splits, `groups=` is set, every model is bagged, and 0 customers are shared between the fitted rows and
  the scored rows;
- for time splits, every fitted row is before τ.

The comparison step asserts that the out-of-time score is lower than the random one.

## Open problems

- **Time split + bagging.** If a preset or `num_bag_folds` turns bagging on, AutoGluon's bagging folds inside the
  training period are still random. Only `tuning_data` is forward in time. The stored time-block folds are not passed
  as `groups=`, because leave-one-block-out would also train on later blocks. AutoGluon's `validation_structure`
  (`time_on`, `temporal_forward_only`) would fix this, but it keeps the date as a feature.
- **Group splits always bag** (`groups=` forces it), so a `medium_quality` fit takes about 5× longer. The group twin
  took 25 s against 8 s for the random run.
- **Precision of the gap.** The out-of-time gap (0.058) is about the width of one holdout's 95 % interval. It holds
  for this seeded sample, but a single unpaired comparison cannot be more precise than that.
- **Training-set consumers.** Explain, the model card and drift still treat every non-holdout row as training,
  including tuning rows and the rows excluded by time + group.
- **Wizard default.** Random stays the default (with a warning) so that F4 and older flows keep their exact holdouts.
  The suggested strategy is one click away, but it is not applied automatically.
- **Gym and Autopilot** have no split picker. A run started there uses random, unless `split_spec` is in the body:
  the Gym body keeps it on re-run.
- **Detection is heuristic.** A date stored as plain integers (yyyymmdd) is not offered as a date, although the API
  accepts any numeric column as `time_column`.
