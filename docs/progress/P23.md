# P23: Postgres dialect + pool + copy tool (B5, §2.2)

Lane O. Row §9.1 P23, with §11 item 2: Postgres is in the POC and the default for the shared deployment; SQLite stays
the default for local dev.

**Done when "both engines pass the same chain": met.**
- The chain (team → project → upload → next version with a match → edit → run → register → audit verify) passes on
  Postgres and on SQLite.
- So do the concurrency checks: two uploads to one root, and one queue with two workers.
- The copy tool moved a populated SQLite DB into Postgres:
  - it was killed mid-table and resumed;
  - counts and hashes are equal on all 46 tables;
  - the audit chains and verify-all pass afterwards;
  - the chain then passes again on the copied DB, running as the restricted app role.

## How to run it

| Setting | Meaning |
|---|---|
| `ENSEMBLE_DB_URL=postgresql://user@host/db` | Postgres. Unset means SQLite (`$ENSEMBLE_DATA_DIR/ensemble.sqlite3`). `ENSEMBLE_DATABASE_URL` (B5's name) also works. |
| `ENSEMBLE_DB_OWNER_URL` | Optional. Migrations, and the copy tool, run as this owner role. |
| `ENSEMBLE_DB_APP_ROLE` | Optional, with the owner URL. The app role gets the §2.2 grants. |
| `ENSEMBLE_DB_POOL_MIN` / `_MAX` / `_TIMEOUT_S` | The pool: 1 / 20 / 30 s. |

- Credentials are read from the environment only. Nothing stores a URL, and `migrate_pg` prints it with the password
  redacted.
- Use a libpq password file or a password in the env var.
- The lake (Parquet blobs) stays under `ENSEMBLE_DATA_DIR`. Only the metadata moves.
- Workers and fit subprocesses inherit the env, so `workerd`, the fits and the heavy pool use the same DB.

**Postgres used here:** the container already had `postgresql-16` (16.15, Ubuntu apt) under `/usr/lib/postgresql/16`.
- I ran `initdb` into `/var/tmp/p23pg` (trust auth on a unix socket, port 5433).
- Roles: `ens_owner` (owns the database `ensemble` and schema `public`, with CREATE revoked from PUBLIC) and `ens_app`.
- A second database, `ensemble_single`, is used with the superuser as a single role.
- Driver: `psycopg[binary]==3.3.9` + `psycopg-pool==3.3.3`. Both installed cleanly from wheels and are pinned in
  `requirements.txt` / `.lock`.

| Piece | File | Notes |
|---|---|---|
| Dialect layer | `backend/app/db_pg.py` (new) | Details below. |
| `Database` | `backend/app/db.py` | Details below. |
| §2.2 schema | `backend/app/catalog/pg_schema.py` (new) | Details below. |
| Copy tool | `backend/app/lake/migrate_pg.py` (new) | `python -m app.lake.migrate_pg --sqlite <data_dir>/ensemble.sqlite3 [--batch N] [--verify-only] [--dry-run] [--json out]`. Details below. |
| Queue | `backend/app/jobs/queue.py` | `_sql()` is now a no-op, because the dialect layer rewrites the parameters. The advisory-lock statement is written `:k`. The claim on Postgres is `… LIMIT 1 FOR UPDATE OF j SKIP LOCKED) AND status = 'queued' RETURNING *`, after the per-resource `pg_advisory_xact_lock` (P22). |

**Dialect layer (`db_pg.py`).**
- **Pool.** One `psycopg_pool.ConnectionPool` per (pid, URL). A forked child makes its own.
- **Transactions.** One `with db.connect()` is one transaction: committed at the end, rolled back on an exception.
- **Rows.** They read like `sqlite3.Row`: by index, by name (case-insensitive fallback), `keys()`, `dict(r)`.
- **Errors.** psycopg errors are re-raised as `sqlite3.IntegrityError` (constraints and triggers, SQLSTATE 23xxx) or
  `sqlite3.OperationalError`, with the original error chained. The existing `except sqlite3.…` handlers work unchanged.
- **Types.**
  - `numeric` loads as int when whole, otherwise float (SUM of bigint);
  - a `bool` parameter is sent as 0/1.
- **`translate()`.** It runs per statement and is cached.

| SQLite | Postgres |
|---|---|
| `?` and `:name` | `%s` and `%(name)s` |
| `%` | `%%` |
| `INSERT OR IGNORE` | `… ON CONFLICT DO NOTHING` |
| `INSERT OR REPLACE` | `ON CONFLICT (pk) DO UPDATE` (pk map: catalog_meta, table_stats, diff_cache) |
| a bare column on the right of `DO UPDATE SET` | `<table>.<col>` (Postgres calls it ambiguous) |
| `IS NOT x` / `IS x` | `IS DISTINCT FROM` / `IS NOT DISTINCT FROM` |
| two-argument `MIN` / `MAX` | `LEAST` / `GREATEST` |
| `LIKE` | `ILIKE` (SQLite's LIKE ignores ASCII case) |
| `IN ()` | `IN (NULL)` |
| a mixed-case alias | quoted |
| `PRAGMA table_info(t)` | `information_schema` in the sqlite3 shape |
| other PRAGMAs | no-op |
| `BEGIN IMMEDIATE` | `pg_advisory_xact_lock(<one key>)`: the version writer, split restore and the P10 migration keep SQLite's single-writer guarantee |
| `CREATE TRIGGER IF NOT EXISTS <name> …` / `DROP TRIGGER IF EXISTS <name>` | the Postgres twin by name (`… ON <table>`), so `reset.py`, split restore and the P01 backfill run unchanged |
| DDL: `INTEGER` / `REAL` / `BLOB` / `AUTOINCREMENT` | `BIGINT` / `DOUBLE PRECISION` / `BYTEA` / identity |

- `executescript` splits on `;` outside literals and comments.
- `borrow(url)` is a pooled connection with `close()`, for `lake/pages.meta_con`.

**`Database` (`db.py`).**
- `Database(path, url=None)` reads `ENSEMBLE_DB_URL` and sets `.dialect` (`sqlite` or `postgres`). `.url` is kept in
  memory only.
- On Postgres it migrates once per process and URL: as the owner when `ENSEMBLE_DB_OWNER_URL` is set, otherwise
  through the pool.
- Portable SQL:
  - `LIGHT_COLS` casts the two profile fields;
  - `rowid` becomes `id` in ORDER BY.

**§2.2 schema (`pg_schema.py`).**
- **Tables, columns and indexes.** The same DDL strings SQLite uses, translated: `db.SCHEMA` (+ `batch_jobs.data_date`),
  catalog `SCHEMA` + RUN/DATASET/MV/DSR columns + `INDEXES`, `P01_DDL` + `P01_COLS` + `P01_INDEXES`,
  **`ix_datasets_list`**, `P10_DDL` (**`lake_migrations`**) and `LEGACY_DDL` (**`split_files`**). Columns are added
  with `ADD COLUMN IF NOT EXISTS`.
- **Functions.** `json_extract(text, path)`, `json_valid(text)`, `ens_ro()` (raises SQLSTATE 23000 with the trigger's
  message), and a `sqlite_master` view (tables, indexes, triggers) for the existence checks.
- **Triggers.** Every SQLite trigger, with the same name and message:
  - `splits_ro_u`, `splits_ro_d`, `vt_ro_u`, `tf_ro_u`;
  - `ri_ro_u` (UPDATE OF the four hash columns), **`ri_ro_d`**, `blobs_key_ro` (UPDATE OF sha256, key, bytes);
  - **`ds_hash_ro`**, with the P10 WHEN clause in `IS DISTINCT FROM` form;
  - `audit_ro_u`, `audit_ro_d`. As on SQLite, these are made once the P01 backfill has run.
- **Grants**, with `ENSEMBLE_DB_APP_ROLE`:
  - `audit_log`, `splits`, `run_inputs`, `version_tables`, `table_files`: SELECT and INSERT only (plus
    `UPDATE(split_id, match)` on run_inputs, which the P10 migration re-points);
  - every other table: SELECT, INSERT, UPDATE, DELETE;
  - USAGE on the sequences.
- **Idempotent.** An advisory lock serialises concurrent starts (API + workers). The step is skipped when
  `catalog_meta pg_schema` holds the current schema hash.

**Copy tool (`migrate_pg.py`).**
1. Builds the §2.2 schema.
2. Refuses a non-empty target, a table missing from the target or a column missing from the target.
3. Copies in FK order (from `pg_constraint`), rows in rowid order, in batches. Each batch commits together with its
   `pg_copy_progress` row, so a crash resumes after the last committed batch.
4. Values go across verbatim. `catalog_meta` and `teams` are upserts where the source wins (the schema step had
   written `tm_default` and step rows). Identity sequences are moved past the copied ids.
5. Re-applies the schema, so the audit triggers go on now that the copied `backfill_p01` is present.
6. **Verifies:**
   - per table, the count and an order-free content hash (sha256 of the sorted per-row sha256);
   - per team, `verify_audit_chain` on Postgres.

**The carried notes, all done:**
- `ix_datasets_list` is in the Postgres DDL;
- `audit_log.details` / `decision` are TEXT;
- `prev_hash`, `row_hash` and `audit_head:*` are copied verbatim, and the head row is read `FOR UPDATE` on Postgres
  (`schema.audit`);
- `pii_salt:*` rows are copied verbatim (shown below);
- `lake_migrations`, `ds_hash_ro` (with its WHEN clause) and `split_files` are carried;
- every SQLite trigger (10, by `grep CREATE TRIGGER`) has a Postgres twin.

## Deviations and notes

- **Timestamps and JSON stay TEXT on Postgres**, not `timestamptz` / `jsonb` (§2.2).
  - The audit chain hashes the stored text, and the carried note asks for details/decision as TEXT.
  - Byte-equal copying and one code path for both engines matter more here.
  - JSON paths go through the `json_extract` function. Every place that needs a number casts it.
- **`BEGIN IMMEDIATE` maps to one global advisory lock**, not a per-root row lock.
  - It keeps SQLite's semantics for the version writer, split restore and the P10 migration. These are short
    transactions with no I/O.
  - Version numbers are still allocated by `UPDATE dataset_roots … RETURNING` inside that transaction.
  - A per-root key would allow more parallel commits. It is not needed at POC scale.
- **The audit head lock.** On both engines the head is first taken with an upsert (`ON CONFLICT DO UPDATE SET value =
  value`), which locks the row. On Postgres the read is then `FOR UPDATE`, as the note asks.
- **Grants mode (owner + app role) limits two admin paths.** Split restore and admin reset `DROP TRIGGER`, which only
  the table owner may do. With grants on, those two would fail (not exercised here); run them with the owner URL. Without
  `ENSEMBLE_DB_APP_ROLE` (one role), they work as on SQLite (checked above through the app's own statements).
- **Not built (optional):** running the long 10M writes as jobs with progress on the P22 queue (edit commit, Doctor
  apply, Feature Lab SQL write). I skipped it; it stays a follow-up before X5's scale gates. The in-process threads
  listed in the tracker (stats profile was already moved in P22; annotations, shift, Doctor label job, Autopilot) are
  also unchanged.
- **audit_log partitioning** (§2.2, at more than 5M rows) is not built. It is a trigger-based change for later.
- **Lane overlap** (minimal, as the rules ask):
  - `lake/pages.py` `meta_con()`: 4 lines;
  - `lake/writer.py` and `lake/splitstore.py`: one SQL string each (`IS DISTINCT FROM`, the match cast);
  - `engine/worker.py`, `engine/store.py`, `registry/store.py`, `reset.py`, `datasets.py`: portable SQL only.
  - Nothing in `lake/store.py` (P10b).
- **Scratch.** The venv, data dirs, Postgres cluster (`/var/tmp/p23pg`), APIs and workers are in scratch. They were
  stopped and removed at the end. No predictors or seeds were added to the repo.
