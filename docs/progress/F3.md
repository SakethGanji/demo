# F3 · One-row latency

Status: **done. `SMOKE_ONLY=latency,core make smoke`: 29/29 steps green in 301 s; `SMOKE_ONLY=samples,anomaly`: 13/13
green (the shared register / latency code and anomaly versions still work); `npm run build` passes.**
Acceptance met: support tickets are served at **τ₉₅ 4.4 ms for one row** (200 calls in the build's worker; 3.4 ms in a
predict worker's benchmark; 4.5 ms for the predictor inside `POST /score`, **6.9 ms end to end over HTTP**), against
**18.1 ms** for the run's ensemble as served, at an **accuracy cost of −0.030** (holdout 0.9130 vs 0.9433), shown in
Register before the choice and on the version after. No model that reads AutoGluon's n-gram features gets under
10 ms on this machine; the reason is measured below.

## Where the time goes (support tickets, 4 CPUs, one row per call)

| | p95 one row |
| --- | ---: |
| AutoGluon feature pipeline alone (`transform_features`: types, fill, categories, text statistics, 3,071 → 1,179 n-gram columns) | 13–15 ms |
| LightGBM, whole pipeline (persisted) | 14–22 ms |
| TfidfLogReg, whole pipeline (it reads only the raw `body` text, but the pipeline computes all 1,179 features) | 12.0 ms |
| **TfidfLogReg, pipeline pruned to `body` (8 → 5 generators, 1,179 → 1 feature), predictions identical** | **4.4–4.5 ms** |
| WeightedEnsemble_L2 of a medium_quality run (13 models incl. RF/XT) | 330–460 ms |

So the floor for any model that reads the n-grams is the pipeline (~10–13 ms), and the per-call model cost of LightGBM
on 1,178 columns (`lightgbm._data_from_pandas`) adds the rest. Pruning the pipeline to what the served model reads is
what makes ≤ 10 ms possible; it uses AutoGluon's own `_remove_features_out` on each generator, stage by stage from the
last (the mechanism AutoGluon uses after fit to drop unused features). The predictor-level call of the same method
does not prune the inner stages of `AutoMLPipelineFeatureGenerator` (it raised `KeyError` for the n-gram stage), so
`app/registry/fastpath.py` walks the stages itself.

Distillation (`predictor.distill(teacher_preds='soft', augment_method='spunge')`, GBM student) is wired and
measured but does not help here: LightGBM_DSTL holdout 0.894 (smoke) / 0.902 (a medium_quality run) at τ₉₅ 15–18 ms,
worse than plain LightGBM (0.944) and slower than TF-IDF; the augmentation shuffles text values. AutoGluon's
`teacher_preds='hard'` with `augment_method=None` crashes in 1.6.3 (`softclass_lgbobj`: `IndexError`), so it is not
offered.

## What changed

**Backend.**
- `registry/fastpath.py` (new): `needed_features` (union of `model.features` over `get_minimum_model_set`),
  `prune_generator` / `prune_pipeline` (in place) and `pruned(p, m)` (on a deep copy, swapped in for a measurement),
  `warm` (persist + three one-row calls), `one_row` (p50 / p95 / max over n calls after 3 warm-ups), `batches`
  (b = 1, 10, 100, 1,000: ms per call and µs per row), `pareto`.
- `GET /api/runs/{id}/latency`: per model also `served_ms_p50/p95` (as a deployed copy would be served) and
  `pipeline` (pruned, inputs, features before → after); `frontier` = models no other model beats on both served τ₉₅
  and validation score; `cpus`. Cache key moved to the new field.
- Register (`build.py`): options `serve_fastest`, `distill` (+ time limit, student hyperparameters), `prune_pipeline`
  (default on, with `clone_for_deployment`). `infer_limit` with **`infer_limit_batch_size = 1`** selects on each
  candidate's measured one-row τ₉₅ as served (otherwise as before: per-row time in batches). refit_full refits `all`
  when infer_limit or serve_fastest picks among models. Deploy copy: pipeline pruned and **kept only if the holdout
  predictions are unchanged** (max |Δp| recorded; 0.0 in every build). Measure: cold first call, warm-up, one-row over
  200 calls, batches; stored as `result.serving` (and `result.distill`).
- Predict workers: `pool.load_predictor` persists and warms each predictor when it loads it; `HeavyPool.warm_path`
  warms a version in every worker. A ready version is warmed after its build and again on promotion to Production.
- `POST /api/registry/versions/{id}/score` (new, the online path, no SHAP): a deployed version ≤ 200 MB and ≤ 100
  rows is served **in the API process** from a small cache (persisted, warmed), else in a predict worker; per-version
  serving metadata is cached so a call does not parse the version's result JSON; returns `predict_ms`, `worker_ms`,
  `server_ms`, `where`, `warm_before_call`. Anomaly versions score each row like Try It; forecast versions are refused
  as in `/predict`. `POST …/benchmark` measures in a predict worker and stores `result.serving_benchmark`;
  `GET /api/registry/serving` lists what is warm in the API process. The admin reset clears these caches.
- `/predict` (Try It) and the anomaly predict path are unchanged.

**UI.** Register: the frontier plots **τ₉₅ as served** by default (toggle: batch t̂), joins the Pareto frontier,
and a click serves that model; `infer_limit` has "batch 1 (online)" in ms per call vs "batch 1,000" in µs/row;
"serve the fastest model"; Advanced: distill (time limit) and prune the pipeline; the preview shows the chosen
model's τ₉₅, the pipeline it keeps and **the accuracy cost against the best model** with the speed-up. The one-row
box reads the as-served numbers (and the whole-pipeline number beside it). Version Overview: a **Serving** card (τ_q
= Q_q{T₁…Tₙ} with every symbol defined, cold vs warm, the pruned pipeline with max |Δp|, batches table, "Measure in a
predict worker", "Call /score 50× from this browser" with predictor / server / browser p50 / p95); the infer_limit
table shows τ₉₅ in ms for batch size 1 and the serve-fastest rule; a distill line with teacher vs student holdout.
Build steps list `distill` when used. Gym Deploy: `infer_limit_batch_size` (default 10,000 · 1 online · 100 ·
1,000) with what AutoGluon does at b = 1 (it subtracts the pipeline's time per row first and stops if that alone is
≥ λ). The deployment trade-off table stacks below 1,750 px (it overflowed at 1,600).

**Smoke** (`latency` section, new; `SMOKE_ONLY` lists it): train the ensemble (GBM, XGB, two TF-IDF models) → the
frontier as served (fastest and best on it; a model whose pipeline prunes to < 10%) → register with
`infer_limit = 0.01, infer_limit_batch_size = 1` (rule: argmax s_val among candidates within λ; served = chosen;
pruned predictions unchanged; version τ₉₅ < ensemble τ₉₅) → approve, promote, wait until warm in the API process,
first `/score` already warm and equal to Try It, 200 timed calls, 60 via a worker → benchmark in a worker (per-row
cost falls with batch size) → serve fastest (argmin τ₉₅) → distill (student served) → Gym fit with
`infer_limit_batch_size = 1` (validation refuses 0). Timing checks compare behaviour, not fixed ratios.

## Open problems

- **≤ 10 ms costs 3 points of accuracy on support tickets.** Nothing that reads the n-grams is served under ~13 ms
  here. A cheaper text featurisation inside the pipeline (fewer n-grams via `_feature_generator_kwargs`, or a GBM on
  TF-IDF of the raw text only) at fit time would be the next step; it is a training choice, not a registration one.
- Latency numbers vary ±30% between runs on this 4-CPU machine (LightGBM τ₉₅ 14–36 ms in the same hour). The smoke
  asserts behaviour; the numbers above are single measurements.
- The browser's own round trip goes through Vite's `/api` proxy in development (≈ 9 / 13 ms p50 / p95 in the
  screenshot); the 6.9 ms HTTP figure is a direct client.
- In-process serving runs the predictor on the API's event loop for a warm, small version (≈ 3–5 ms per call); heavy
  traffic would want a dedicated serving process. Versions over 200 MB or 100 rows go to the workers.
- Pipeline pruning relies on AutoGluon's private generator methods (`_remove_features_out`, `generators`); it is
  checked per build (unchanged predictions or not kept) but could break on an AutoGluon upgrade.
- refit_full + serve_fastest / one-row infer_limit is wired (`refit_full(model='all')`) but the smoke's run is not
  bagged, so it is not exercised there. Distillation is not shown on the frontier before the build (its student only
  exists after it).
- Not touched: registry scoring of raw transactions with F2's supervised anomaly model (out of scope).
