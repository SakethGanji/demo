## Result

- A delta is a new per-table plan action, `delta`, next to new / rewrite / append / carry / drop / skip. It works on
  any table of a multi-table version. The version's other tables are carried with the same sha.
- The delta is applied to the parent's table **by key**:
  - the plan's `tables.<t>.key`, else the parent table's confirmed key;
  - neither → **400 `delta_key_required`**.
- Each row's operation comes from the `_op` column (`tables.<t>.op_column` renames it):
  - `I` / `U` / `D`, the words insert / update / delete, and `M` / merge / upsert are understood, in any case;
  - `tables.<t>.ops {"<value>": "insert" | "update" | "delete" | "upsert"}` maps other values;
  - a file without the op column is all upserts.
- `/check` reports per table: inserted / updated (and how many updates change nothing) / deleted / missing,
  updates of missing keys, inserts of existing keys, rows before and after, the holdout rows deleted, and the mode.
- The commit writes one of three things:
  - **insert-only** → one `append` part next to the parent's reused parts (`change: 'appended'`);
  - **anything else** → the table is rewritten (`change: 'rewritten'`);
  - **nothing changes** → the table is carried.
- `GET …/diff v(n-1) v(n)` gives exactly the delta's counts: added = inserted, changed = updated (minus no-op
  updates), removed = deleted.
- **Holdout identity:** updated and untouched rows keep their `__row_id`, so their folds carry by join. The new rows
  get the seeded share.
- The chain gives **identical output on SQLite and on Postgres**, with the same table shas.

## What was built

| Piece | Where | What it does |
|---|---|---|
| **`Delta`** | `dataset_versions.py` (new class, next to P06's `Matcher`) | One DuckDB connection. | **Check** | `lake/upload._check_multi`, `_delta_check`, `_delta_for` | **Typing:** a delta table is typed with the parent table's types (as for an append). | **Commit** | `lake/upload._write_delta` (called from `_commit_multi`) | Classified again on the writer's connection. The parent is immutable, so the counts are the check's.<br>• **append:** ids from `reserve_row_ids` above the table's max, then `w.append` (the parent's keys are re-checked);<br>• **rewrite:** ids for the inserts from the root counter, then `w.write(result_sql)`. The parent's keys are declared again;<br>• **both:** the key the delta was applied by is saved as a confirmed key, and the split is carried by join (`SS.carry_into`);<br>• **carry:** `w.carry` + `w.carry_splits`.<br>Manifest `ops[]` gets `{op: 'delta', table, mode, change, counts, first_row_id, source_file, applied_by}`. The commit answer has `deltas: {table: …}`. |
| **One file names its table** | `lake/upload._sources` | A single uploaded file now takes the plan's `table` even when the plan has `tables`. Before, a lone `delta1.csv` became table `delta1`. With `{table: 'loans', tables: {loans: {action: 'delta'}}}` it is the delta of `loans`. Several files still take their file names, as in P12. |
| **Hint on the P06 path** | `lake/upload.check` | One file with an `_op` column sent as a plain next version gets the warning `looks_like_delta`, saying how to PATCH it as a delta. Nothing is applied without the plan. |
| **Reading appended tables** | `frames.read` (`frames.py`), `lake/frame.iter_rows` / `read_ids_label` | `pa.concat_tables(…, promote_options="default")`. ## Deviations and notes for dependants

- **Files outside the row (all lane D):**
  - `lake/upload.py`: the check and commit live there (as in P05, P06 and P12);
  - `frames.py` and `lake/frame.py`: one-line `promote_options` fixes, described above.
    `lake/migrate.py:505` (F-X2's) has the same `concat_tables` over a migration's parts. Those parts are all written
    by one COPY, so it is not affected, and it was left alone.
  - `lake/writer.py` and `catalog/datasets_api.py` are **not touched**. That keeps clear of P21 / F-JOBS in
    datasets_api.
- **Insert / update semantics** (§5.6 says to warn, not refuse):
  - an insert of an existing key is applied as an update (`insert_of_existing_key`, warning);
  - an update of a missing key is applied as an insert (`update_of_missing_key`, warning);
  - a delete of a missing key is `missing` (warning).
- **"Insert-only" is decided on effect, not on the op letters.** A delta whose updates change no value, and which has
  no deletes and no new column, is still written as an append part. A delta that changes nothing at all carries the
  table. When every table is carried, writer dedupe returns the parent version.
- **The diff's `changed` equals `updated − updated_unchanged`.** In this chain every update changed a value, so
  `changed` = `updated` = 40.
- **A missing column** in a delta is not an error. Updated rows keep the parent's values and inserted rows get
  missing values (warning `delta_columns_missing`). This allows partial-column update feeds.
- **New columns** need `allow_new_columns`. They force a rewrite, and existing rows get missing values.
- **Not built (T2, §5.6, triggered):** `table_files.role ∈ upsert/delete` merge-on-read, and the `upserts` +
  `deletes` two-file form. Today a delta is one file with an op column (or all upserts).
- **A delete removes the row, including holdout rows.** These are counted in `holdout_rows_deleted`, with a warning.
  The new rows get the seeded holdout share. A non-primary table has no split of its own here (as in P12's rewrite).
- **Default version:** a delta version follows P06's rule for `upload_version` (`make_default` on the commit). In the
  chain, v3 stayed off the default because v2 was the default and no `make_default` was sent.
- **U2:**
  - the action picker gains `delta` (with key, op column, op mapping and allow_new_columns);
  - the check shows `tables[].delta` (counts, mode, `key_from`) and the delta warnings;
  - the commit answer has `deltas`;
  - the 400s `delta_key_required` / `delta_duplicate_keys` (`keys`, masked for PII-tagged key columns) /
    `delta_op_unknown` / `key_invalid`;
  - `looks_like_delta` on a plain upload is a good place for a "Apply as a delta" button.
- **F-JOBS:** if the upload commit becomes a job, `_write_delta` needs nothing extra. It is plain DuckDB SQL on the
  writer's connection, with no request context.
- Scratch data dirs, the Postgres cluster and the API processes were removed or stopped. The venv is in the session
  scratchpad only.
