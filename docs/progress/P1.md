## Step 1 · Schema + backfill (no behaviour change)

All new code is in `backend/app/catalog/`. `Database()` calls `schema.migrate`, which is idempotent: CREATE IF NOT EXISTS, and an ALTER only for a column that is missing.

**Tables:**
- `projects`;
- `lineage_edges` (src_kind, src_id, dst_kind, dst_id, relation, actor, meta, inferred, created_at; unique per edge; indexed both ways);
- `annotations` (tags and notes; soft delete);
- `champions` (pending → approved / rejected / superseded);
- `catalog_meta`.

**New columns:**
- **runs:** `project_id`, `parent_run_id`, `source`, `kind`, `primary_metric`, `primary_score`, `greater_is_better`, `predictor_state`, `predictor_bytes`, `state_changed_at`. Indexed on dataset, project, parent and status.
- **datasets:** `project_id`, `parent_id`, `root_id`, `sha256`, `n_rows`, `op`.

**Edge relations** (they run downstream: src is upstream):

| Relation | From → to | Meta |
|---|---|---|
| `derived_from` | dataset → dataset | op, rows before and after, number of changes |
| `trained_on` | dataset → run | — |
| `branched_from` | run → run | source, patch, experiment, review_id, hypothesis_id, verdict |
| `built_from` | run → version | — |

**Backfill** (`schema.backfill`):
- It runs once per database at API start and is idempotent: only NULL columns are filled, and edges are INSERT OR IGNORE. `force=True` re-runs it.
- **Datasets:** read every `lineage.json` for parent, root and op. Each dataset root gets one default project, `prj_<root>`.
- **Runs:** read `config.parent_run_id`, `source` and `patch`, plus `result.experiments_extra` (the segment and group-split runs, which have no parent in their config).
- **Registered versions:** `model_versions` gives the `built_from` edges.
- A `derived_from` edge whose child has no valid `root_rows` is marked **`inferred`**, and compare never pairs across it.

`insert_dataset` changed from `INSERT OR REPLACE` to an upsert. REPLACE deletes and re-inserts the row, which would wipe the new columns on every re-profile.

## Step 2 · `DatasetStore.derive(parent, df, keep_idx, op, changes, …)`

`derive()` is now the one way to make a dataset version:
- **root_rows:** the parent's `root_rows` mapped through `keep_idx` (a bool mask or positions), then `-1-i` for each synthetic row.
- **splits:** by default, the parent's split mapped through the kept rows.
- **writes:** `lineage.json`, the version's columns and a `derived_from` edge. `create_version` itself records the version and the edge, so nothing can bypass it.

**The 7 writers now call it:**
- data_doctor_api, featurelab_api, shift_api, annotations_api, active_learning_api, anomaly/api;
- autopilot/engine, both its relabel/drop and synthetic-row paths.

Each writer keeps its own lineage extras (fixes, transforms, `shift_weights`, `annotations`, …) through `extra`.

**Two bugs fixed on the way:**
- Active learning wrote `root_rows = range(n)`, ignoring the parent's mapping.
- Anomaly review wrote `root = its own parent`.

**Other hooks:**
- The SQL refresh and the monitoring window record a version with `paired=False`. They hold new rows, so the edge is inferred.
- `RunStore.create` writes `trained_on`, plus `branched_from` when the run has a parent. The meta carries source, patch, experiment and review_id; experiments and reviews pass review_id through `patch`.
- `RunStore.merge_result(experiments_extra=…)` writes the `branched_from` edges for segment and group-split runs.
- `RegistryStore.create_version` writes `built_from`.
- A review branch's `hypothesis_id` and `verdict` come from the parent's review journal the first time the tree is read. They are stored on the edge once the review has ended.
- `vela/review.py` and `vela/experiments.py`'s logic are untouched. The only edit in `experiments.py` is one line: the scan for child runs became an indexed query.

## Step 3 · Light list queries

**New in `RunStore`:**
- `list(**filters)`: dataset_id, status, project_id, parent_run_id, source and kind are filtered in SQL. A list value means IN. It takes an optional `limit`.
- `list_light()`: the indexed columns only, with no JSON parsed; paged.
- `children(run_id)`: from the edges.

**Callers moved:** every backend full-table `RunStore.list()` caller now filters in SQL:
- GET /api/runs (and its kind filter);
- split-comparison;
- cost-comparison;
- the Gym's history (`limit=40, status=succeeded`);
- the registry card's reject-inference lookup;
- the experiments list (`parent_run_id, source`).

`GET /api/runs` also takes `project_id`, `light=true`, `limit` and `offset`. Of the evaluation's 13 callers, the rest are UI full-list fetches. The Models page now scopes them per project in SQL (see the limits).

## Step 5 · Lineage tree + compare

**`GET /api/lineage/{kind}/{id}`** (kind is dataset, run, version or project):
1. One CTE walks up to the root dataset, and one walks down over the edges from there.
2. It returns the nodes (datasets, runs, versions, each with its tags and note count), the edges, the reviews (status, by, mode) and the project's champion.
3. `GET /api/runs/{id}/children` uses the edges.

**`POST /api/compare {a, b}`** (`catalog/compare.py`); a and b are runs or versions. A version is scored by its source run's holdout predictions, and the response says so.
- **Paired** only when all of these hold:
  - same root;
  - both datasets have a root-row mapping (`root_rows`, or the dataset is the root);
  - same label and problem type;
  - at least 30 shared holdout root rows (synthetic rows never pair).
- **Paired result:** Δ = b − a with a percentile bootstrap CI from **`stats.paired_bootstrap`**. Metric: AUC for binary, accuracy for multiclass, −RMSE for regression. Relabelled rows are scored on each side's own labels, with a warning.
- **Otherwise:** `"different holdout, not paired"`, with the reason, each side's own holdout score and an unpaired difference with no CI.
- It reads only stored artefacts, so it works on evicted runs.

**UI:**
- `Lineage.tsx` (Registry) is now the selected version's project tree.
- Models gets a **Lineage** tab inside the page; no new nav item.
- The tree (`ProjectTree.tsx`) goes dataset → versions (with op) → runs → branches → registered versions:
  - agent and experiment branches are collapsed under **Review rv_…** (status, by, n branches, k kept);
  - a dot's colour shows the source (you, experiment, agent, Gym/patch, twin);
  - a chip shows the verdict (kept / rejected / other);
  - chips show slimmed / evicted, the champion and tags;
  - ◇ marks an inferred edge.
- **CompareRuns** gets a **Δ Against <first run>** card (`PairedDelta.tsx`). It shows paired Δ with the 95 % CI and rows, or the unpaired label and its reason.

## Step 4 (minimal) · Projects, tags and notes, champion

**Endpoints:**
- `GET /api/projects` (counts and champion), `GET/PATCH /api/projects/{id}`;
- `GET/POST /api/annotations/{kind}/{id}` (`{tag|note, by}`), `DELETE …/tags/{tag}?by=`;
- `POST /api/projects/{id}/champion {version_id, by, comment}`:
  - the version must be in the project, ready and approved;
  - a newer request withdraws an older pending one;
  - audited as `champion_requested`.
- `POST /api/champions/{id}/decide {approve, by}`:
  - four eyes, with names compared through the registry's `identity_key` (" ALICE." = alice);
  - approval supersedes the old champion;
  - audited as `champion_approved` / `champion_rejected`.

**UI:**
- A **project** select in the Models header. It writes `?project=` and the runs list is fetched with `project_id`.
- A tags-and-notes strip on the run page and on the Registry's version Overview. It writes as the Registry's "acting as" name.
- On the version Overview, a **Champion** card with the ★ badge, **Make champion…** and Approve / Reject when a request is pending.

## Step 7 · Retention

**Policy:** `config.RETENTION_POLICY` is labelled **"needs model-risk approval"**:
- slim after 7 days;
- evict after 30;
- evict failed runs after 3;
- the top 3 are pinned;
- the `keep` tag pins.

Nothing runs on a timer.

**Endpoints:**
- `GET /api/retention/plan` is the dry run. Per run it gives: bytes, age, state, pins with reasons, the action and the bytes it would free. A slim is estimated at 60 % freed until it is measured.
- `POST /api/retention/run {by, confirm: "retention", run_ids?, tier?}`:
  - **admins only:** `ENSEMBLE_ADMINS`, default `admin`;
  - pinned runs get 409 with their reasons;
  - each action is written to the audit log as `retention_slim` / `retention_evict`, with bytes before and after.

**Tiers:**
- **present.**
- **slimmed:** `delete_models(models_to_keep='best')` + `save_space()`. Tabular predictors only.
- **evicted:** the predictor folder is deleted, and an `EVICTED.json` tombstone is written (when, by whom, bytes, what is kept). Kept: `config.json`, the result (leaderboard, metrics, hashes), `holdout_predictions.csv` and the `reviews/` journals.

**Pinned:**
- the source runs of non-rejected versions;
- the champion, Production and Staging;
- runs under a queued or running review (the base run and every branch);
- the top 3 per (project, dataset, metric);
- runs tagged `keep`;
- queued and running runs.

### The `predictor_path` audit and the 410 guard

37 modules read `predictor_path` or load predictors: `grep -rln "predictor_path|predictors.get|TabularPredictor.load"`. Every HTTP way into them is a route under `/api/[<kind>/]runs/{run_id}/…`, so there are two guards.

1. **Middleware (`catalog/api.py: evicted_guard`).** A route on an evicted run gets **410 "re-fit from config"**, pointing at `GET /api/runs/{id}/gym` for the body.
   - It is an **allow-list**, so a new route is guarded by default.
   - Stored-only routes stay open (`retention.STORED_ONLY`):
     - the run itself, events, experiments, the review and its journal;
     - holdout predictions, oof, export.py;
     - split- and cost-comparison;
     - the Gym body, scores, the Doctor, the stored job states.
   - The ladder is served from its stored copy; `?refresh=true` gets 410.
   - Everything else gets 410: predict, explain, SHAP, feature importance, what-if, register, experiments (POST), ladder refresh, slices, shift, threshold, …
2. **`PredictorCache.get`.** When the folder is gone and a tombstone exists, it raises `EvictedError`, which an exception handler turns into a 410.

Background workers (the heavy pool, the job modules) are reached only through guarded routes. The agent's tools call the HTTP API, so they are guarded too.

## Known limits

- **The Models table still reads the full run shape.** It uses leaderboards, thresholds and configs. It is now scoped per project in SQL, but it is not on `list_light`. Moving the table and Home onto the light list is a UI rewrite. The API is ready: `GET /api/runs?light=true&project_id=…&limit=…`.
- **Hypothesis id and verdict are filled from the journal when the tree is read,** not at creation. The review does not pass `hypothesis_id` to the experiment endpoint, and `vela/review.py` was left alone.
- **No timer.** Retention runs only by an admin call until model risk approves the policy.
- **The slim estimate is coarse.** The plan assumes 60 %; one small run measured 98 %.
- **Registered version folders** follow the bank's retention period. They are not touched, and deleting one would still need an audited four-eyes step (not built).
- **Admins and approvers are names,** not authenticated identities. There is no sign-in, as in the registry.
- **A review's own branches are pinned only while it runs in this API process.** A review interrupted by a restart no longer pins.
