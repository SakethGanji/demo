# X4: governance and authz check (read-only, lane ⟂)

Plan: `docs/plans/data-platform-final.md` §9.1 row X4, §6, §5.10, §11; `C-teams-governance-flows.md` §1.3, §1.5.
Base: `motion-components` @ 48e9cc4. No product code was changed. I reproduced everything from scratch; the phase
reports (P14, P15, P18–P21, P24, F-PII) were used only to find the routes.

**Verdict: not done-when.** There are 4 critical and 6 major findings. Each one has a repro below and the raw output in
`docs/progress/X4/out/`. Most of them come from three root causes:

1. **The coverage gate's idea of a "row-returning GET" is a path regex.** It lists 25 of the 155 GETs. The other
   130 have no `require()`. In enforce mode they answer anyone, including another team's member who has no share
   (90 of them returned 200 to such a caller). Some bodies carry raw PII.
2. **The agent's principal is taken from the request body.** `POST /agent/sessions {user}` is not bound to the caller.
3. **Purge works on blobs and pins.** Values that were copied into run artifacts, results, caches and batch files
   survive the purge.

A fourth critical one stands alone: the SQL source connects to the platform's own Postgres database.

## Critical

### C1. Anyone can run the Vela agent as anyone (agent privilege) · confidence 0.97

`POST /api/agent/sessions {message, user}` takes `user` from the body. The route's only check is `agent.use`, which
allows anyone. The session's tool calls then carry the signed internal header for `user`:
`agent/tools.py:80-83` → `identity.internal_headers(user)` → `AgentProvider`. The API treats them as that person
(`auth: agent`).

So the agent can reach exactly what the named `user` can, whoever started the session. The plan said "never more
than its user"; here, the "user" is whoever the caller names.

Three more gaps on the same routes:
- `POST /agent/sessions/{sid}/confirm`, `/messages` and `/stop` do not check that the caller owns the session. One
  click on someone else's pending write executes it as that person.
- `GET /agent/sessions` and `GET /agent/sessions/{sid}` have no check at all. They list every user's conversations,
  with their tool results.
- In enforce mode, the body-`by` check is skipped for `auth == "agent"` (`deps.py:212`). Any `by` / `created_by` /
  `actor` that a tool puts in a body is therefore recorded unverified.

Repro (`agent.py`; same on SQLite and Postgres in enforce, and in audit mode):

```
Fay (Fraud member) GET  /datasets/{cr v1}/rows                       → 403 forbidden data.preview
Fay POST /registry/versions/{cr mv}/batches (direct)                 → 403 forbidden model.use
Fay POST /agent/sessions {user: "Ben", message: "score credit-default with mv_…", decider: stub}  → 201 (user Ben)
Fay POST /agent/sessions/{sid}/confirm {step_id, approve: true}      → 200; step batch_score done
  → batch_cedbc129 on Credit Risk's model, created_by "Vela agent on behalf of Ben", succeeded
Ana POST /agent/sessions {user: Ana, …}; Fay GET /agent/sessions     → lists Ana's and "Ben's" conversations
Fay POST /agent/sessions/{Ana's sid}/confirm                         → 200; Ana's pending batch_score runs as Ana
```

**Audit trail:** the rows are `agent:batch_score` / `batch_scored`, with actor "Vela agent on behalf of Ben",
`principal_id` null and `auth` `typed`. Nothing records that Fay started the session or confirmed the step
(`audit.txt`: no `agent_session_*` action exists). The read side is limited only by the stub planner: a model decider
follows any instruction. The stub's `find_rows` fails for an unrelated reason (minor m7).

### C4. The SQL source connects to the platform's own database (Postgres), and to other databases under the data dir (SQLite) · confidence 0.9 here, 0.7 for a given deployment

`POST /api/sql/preview` and `/sql/tables` need only `data.upload` on the `project_id` sent, or on `tm_default` (every
principal is a member) when none is sent.

**Postgres.** Any `postgresql://` URL is accepted (`sqlsource/core.parse_url`), and the connection is opened by the
API process with its own environment. So whatever lets the API's OS user in without a password also lets the caller
in:
- peer or trust authentication on the socket;
- `~/.pgpass`;
- `PGPASSWORD`.

The query filter blocks write keywords, but not functions. On the scratch cluster
(`out/postgres_enforce/teams.txt`, `out/postgres_enforce_2/teams.txt`), Fay (Fraud member) in her own project ran:

```
Fay POST /sql/preview {url: postgresql://postgres@/x4f?host=…, query: SELECT actor, action, team_id FROM audit_log …}  → 200, every team's rows
… SELECT display_name, is_admin FROM principals WHERE is_admin = 1                                → 200 [Ada, Adam]
… SELECT id, grantee_team, pii FROM shares                                                       → 200
… SELECT result FROM batch_jobs …                                                                → 200, pii 200 (raw names, SSNs, e-mails, dates of birth)
… SELECT pg_read_file('/etc/hostname')                                                           → 200 "vm"  (a file on the database host)
```

That is every team's governance state, the raw PII that the platform copies into the database (C3's table list), and
file reads on the database host as the connected role.

**SQLite.** The same route reads any `.sqlite` / `.duckdb` file under the data dir, except one literally named
`ensemble.sqlite3`. That includes `mlflow/mlflow.db`, the shared MLflow store of every team's runs, params and
registered models: `SELECT name FROM registered_models` → `pd-x4` (another team's model).

Confidence: 1.0 on this cluster. For a real deployment it depends on how the API authenticates to Postgres; peer
authentication on a socket, as on this cluster, is common.

## Major

### M1. The registry reviewer's name is not bound to the principal in enforce mode · confidence 0.95

`POST /registry/versions/{vid}/review {reviewer}` records `body.reviewer` as the decider. `reviewer` is not in
`deps.BY_FIELDS` (`by`, `actor`, `created_by`, `requested_by`), so the enforce-mode "signed in as" check never sees
it. `four_eyes()` checks both the name and the principal, so a registrant still cannot approve their own version
(1a → 403, 1b → 409). But a real risk reviewer can record the approval under anyone else's name.

```
Rita (risk reviewer) POST …/review {decision: approve, reviewer: "Bo"}       → 200 approved
  audit_log: action approved, actor "Bo", principal_id pr_3d099d0f13df (= Bo's id, looked up from the name), auth typed
Rita POST …/review {reviewer: "Rita", by: "Bo"}                              → 409 "You are signed in as Rita; 'by' says Bo."
```

The same holds on SQLite and Postgres (`decide.txt`). Other name fields outside `BY_FIELDS`:
- `reviewer` on `/runs/{id}/active-learning/answer` and `/annotations/answer`;
- the agent's `user` (C1);
- `actor` as a query parameter (`DELETE …/credit-report/tape?actor=`).

The other decide paths take `by` and are refused in enforce mode when it is not the principal. Lookalike names
(punctuation, accents, Cyrillic / Greek / full-width, zero-width, case) fold through `identity_key` on every decide
path: P21's matrix was re-run for review and found nothing new.

### M2. A maintainer can demote and remove owners, and can appoint risk reviewers, including themselves · confidence 0.95

C §1.3 gives `team.manage` to maintainers only for members **below owner**. Owners, maintainers and policy are
`team.settings` (owner). `teams_api.add_member` / `change_member` choose the stricter action from the **new** role
only (`when=OWNERS`). `remove_member` has no variant. Results:

```
Ana (maintainer) PATCH /teams/cr/members/Bo {role: viewer}          → 200   (an owner demoted)
Ana DELETE /teams/cr/members/Bo                                     → 200   (an owner removed)
Ana PATCH /teams/cr/members/Mo {role: risk_reviewer}                → 200
Ana PATCH /teams/cr/members/Ana {role: risk_reviewer}               → 200   → /authz/check model.review on the team: allow
```

This holds in enforce mode on SQLite and Postgres (`teams.txt`). A maintainer can make themselves, or a colleague,
the person who approves models, champions and `approved_for_model` certifications. They can also take an owner out
of a four-eyes path. C §1.2 makes "risk reviewer in the developing team" at most a flagged state, and a refusal under
`require_independent_reviewer`; it was not meant to be self-service.

### M3. A batch's input and output are never masked · confidence 0.9

Batches hold whatever the scorer was given, often rows with the training data's tagged columns.
`/registry/batches/{bid}` (no check, C2) and `/download` (`model.read`: a viewer gets 200) serve them in clear. There
is no `masked_columns` and no `unmasked=1&reason` path. The same file is behind the agent's `batch_score` tool.

### M4. Admin reset ignores legal holds · confidence 0.95

`reset.check` and `reset.reset` never call `catalog/holds.py`. With `ENSEMBLE_DEMO_MODE=1`, Ada requested a reset,
Adam approved it, and Ada reset (`audit.txt` §3 and the manual repro in the SQLite run). The reset went through
**while legal hold `CASE-RESET` was active on team Credit Risk**:
- deleted: 5 runs, 18 datasets, 1 model version, 18 splits, the certification, contracts, tags and every project;
- the hold row is still `active: true` and points at nothing;
- `GET /runs/{run}` → 404.

This is gated by demo mode and four eyes, but P24's rule is "a destructive path must call `catalog/holds.py`".

### M5. `GET /registry/audit` with no filter returns every team's audit rows · confidence 0.9

The route's objects are `query(version_id)` / `query(model)`. With neither sent, the decision scopes to `tm_default`.
Every principal is a member of `tm_default` (`GET /teams/tm_default`: all 12 people are members). Fay therefore gets
the whole `audit_log` (`limit` ≤ 2000): Credit Risk's rows (26 on Postgres), Collections', authz denials, and
`dataset_rows_read` reasons.

`audit.read` is team-scoped in C §1.3, and `/teams/{t}/audit` does deny Fay (403).

### M6. The audit trail cannot answer "who did this" for agent and spoofed actions · confidence 0.9

- Agent rows have `principal_id` null and `auth` `typed`, even though the request's principal was `auth: agent`
  (`schema._audit_who` keys the lookup on the actor text "Vela agent on behalf of X").
- The real caller of an agent session (C1) is never written.
- A review recorded under another name gets that person's `principal_id` (M1).
- Actions with no audit row:
  - agent session start / confirm / stop;
  - `GET /runs/{id}/fairness` writing `fairness_reports`;
  - upload discard;
  - SQL source previews (a read of an external database);
  - run cancel.
- **Tamper evidence works:** with the append-only triggers dropped (as a database owner could), editing one
  character of a middle row, or deleting a middle row, is caught by `verify_audit_chain` with the first break
  (`tamper.txt`). **But deleting the tail and moving `catalog_meta audit_head` back verifies `ok`.** The head lives
  in the same database, so there is no anchor outside it (m1).

## Minor

- **m1.** Tail truncation is undetectable (above). Publish the head outside the database: a daily signed head in the
  run log or object store.
- **m2.** `POST /datasets/{id}/contract/check` and `POST /datasets/{id}/intake` are `data.read_meta`, yet they write
  `datasets.contract_result` / an intake record (reading the code: a viewer or a grantee team writes to the owner's
  version). Confidence 0.6.
- **m3.** Holds and retention otherwise hold up: run delete, dataset delete decide and purge are refused under a hold (409 `legal_hold`), the retention run skips held and pinned items, and no timer deletes anything (`ENSEMBLE_VERIFY_EVERY_HOURS` only re-hashes). The exceptions besides M4: staged uploads expire after a fixed 7 days (`lake/upload.STAGING_DAYS`), swept when the next upload is
  created: no person, no hold check, no audit row. `DELETE /uploads/{up}` ignores holds.
- **m4.** After a purge, `GET /datasets/{old}/export`, `/runs/{id}/explain` and `/runs/{id}/shap` answer 500
  (`bad part ('base', 'missing')`, `FrameError: A file of … is missing`), not 410 / 409 `purged`. The 500 on export
  also drops the keep-alive connection.
- **m5.** `PATCH /datasets/{id}` (sets the target) is `run.train`, not `data.card`. It is harmless now, but it is the
  wrong key.
- **m6.** `GET /runs/{id}/fairness` is a GET with no check that mutates the run (`merge_result`). Any caller rewrites
  another team's run result and model card.
- **m7.** The agent's `find_rows` tool always fails with 400 "say who is reading": `G.reader()` reads
  `X-Ensemble-Actor`, which the in-process client does not send. Functional, not security.
- **m8.** **Error echoes are clean.** `echo.py` (as Mo / Vic):
  - a delta keyed on `email` with a duplicate → `delta_duplicate_keys` with `keys: [{value: ["•••"]}]`;
  - a filter on `ssn` → 200 with no rows, or 400 naming the column and its type;
  - edit previews (replace an SSN, cast `applicant_name`) → masked.

  Two side notes:
  - `delta_op_unknown` quotes the op column's values. That column is untagged, so this is not a leak, but any value
    placed there is quoted back.
  - The edit preview over-masks: type names show as `•••` in `type_changed` warnings (cosmetic).

## Verified, nothing found

- **Four eyes** on champion, review, retire, dataset delete, admin reset, certification, share, hold release and
  purge: requester lookalikes are refused in both modes, and the principal and the name are both checked
  (`policy.four_eyes`). In enforce mode a `by` ≠ principal is a 409 (decide 1c). Purge: one person cannot approve for
  two teams, and a non-owner gets 403 `owner_required`.
- **Shares:**
  - expiry (`expires_at` +75 s) cuts dataset, rows, export and runs at once (403);
  - the expiry of the certification behind a `certified` scope cuts them too;
  - revoke cuts them, and existing runs still verify;
  - an expired share blocks new frames, joins and join runs (403 `input_not_shared`);
  - lists in enforce mode drop the shared rows (Fay's `/datasets` without Credit Risk rows; Carl's with v1 only while
    the share is live);
  - joins over an unshared input: 403 `input_not_shared` (`governance.txt` §2).
- **Masking on the routes F-PII covered:** in every pass, rows, grid, diff, stats, export (masked), holdout
  predictions, explain worst cases, the SHAP row, anomaly top rows, the AL queue, annotations, intake, split options
  and Feature Lab returned pii 0 for Vic and Carl.
- **The `dataset_read` audit** keeps `q` hashed (F-PII); no raw value was found in any audit row (`purge.txt`
  database scan: `audit_log` absent).
- **The coverage gate** reports `uncovered: []`, so every non-GET route carries `require()` or `public()`.
  - The action per route was read against §1.3 (`out/sqlite_enforce/routes.txt`). Wrong keys: m5, M2's variant,
    m2's writes on read keys.
  - `POST /runs` checks `data.preview` on the dataset plus `run.train` on the project, so cross-team training needs
    a share.
  - Unknown object ids record no decision and fall to the handler's 404. No route was found that then acts on another
    field.

## What dependants need

- **C1:** bind the agent session to `principal(request)`: `user` = the principal's display name, and refuse a
  different one. Check ownership on `GET` / `messages` / `confirm` / `stop`. Audit the session start with the real
  principal. Never skip the `by` check for agent principals: compare against "Vela agent on behalf of <principal>".
- **C2:** make the coverage rule "every GET that names an object carries `require()` or `public()`" (all 130). The
  routes that return values derived from columns (fairness, scorecard, recourse, shift options, credit report, card)
  also need the run mask, or `run.read` plus masking.
- **C3:** purge must also scrub or invalidate:
  - run artifacts that copy data: the predictor's `utils/data`, the model pickles (or mark the run `purged` and refuse
    to serve it), `top.json`, the SHAP cache, `scorecard/report.json`;
  - result JSON: fairness reports, recourse ranges;
  - batch files and `batch_jobs.result.preview`;
  - the export caches under `lake/exports/{v}`;
  - `uploads.check` samples, `datasets.profile`, and `table_stats` of the purged versions.
- **M1 / M6:** add `reviewer` and query `actor` to `BY_FIELDS`, or better, derive the decider from the principal.
- **M2:** choose `team.settings` by the member's current role too (owner, maintainer) and for `risk_reviewer`, and
  give `remove_member` the same variant.
- **M4:** `reset.check` must refuse while any hold is active (409 `legal_hold`).
- **M5:** with no filter, scope `/registry/audit` to the caller's teams, or require `version_id` / `model`.
- **C4:** allow-list the SQL source's roots and hosts (`ENSEMBLE_SQL_ROOTS` only, never the data dir itself). Refuse
  the platform database's host and socket. Connect with a role that has no privileges on the platform schema. Treat
  `/sql/*` as `data.upload` on an explicit project only.
