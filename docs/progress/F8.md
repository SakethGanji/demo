# F8 · Monotonic constraints

Status: **done. `SMOKE_ONLY=monotone,core make smoke`: 27/27 green in 248 s. `npm run build` passes.**

Acceptance met. The test is credit-default with `debt_to_income ↑`, bagged (k = 3) and stacked (L = 1). The registered
version serves `WeightedEnsemble_L3`, whose partial dependence is non-decreasing on a 25-point grid of the column's
quantiles. So is every one of its 200 ICE curves. The smoke checks this in two ways:
- by the API (`GET /registry/versions/{id}/monotone`, on the version's own files);
- independently, from the version's `/score` answers on 200 holdout rows × 25 grid points.

PD goes from 0.059 to 0.185. Without the constraint, 195 of 200 ICE curves of the served model go down somewhere
(the largest drop is 0.015).

## Cause

AutoGluon has no monotone option. LightGBM, XGBoost and CatBoost do: each takes `monotone_constraints`, one sign per
column, by position. But the matrix each model trains on is not the user's table:
- AutoGluon's feature generator drops useless columns, turns two-valued numbers into 0/1 and adds text n-grams;
- each model drops constant columns;
- LightGBM renames columns with special characters;
- XGBoost one-hot encodes categories and puts those columns first;
- at stack level 2, stack features (the base models' predictions) join the raw features.

A list written against the raw columns would land on the wrong features. The stack levels also break monotonicity:
a stacker that sees base predictions and raw features is not monotone unless it is constrained in both.

## What changed

**Models (`backend/ensemble_models/monotone.py`).** Three registered subclasses: `GBM_MONO`, `XGB_MONO` and
`CAT_MONO`. They keep their parents' model names (LightGBM, XGBoost, CatBoost) and families. They take a hyperparameter
`monotone = {constraints: {raw column: ±1}, stack: true}` and turn it into the library's vector at fit time, from the
columns the model is actually about to train on. The hook is `preprocess(..., is_train=True)`: its result is written
into the same params dict that `_fit` then hands to the library.
- **Mapping.** A constrained column gets its sign. A stack feature (special type `stack`) gets +1. Everything else
  gets 0: categories, one-hot columns, n-grams and other numbers.
- **LightGBM.** Renamed columns are mapped back to AutoGluon's names.
- **XGBoost.** The vector is `[0] × (one-hot width) + signs of the other columns`. The width is read from the matrix
  itself. The encoder merges rare levels, so its list of category names can be longer than the block it produces. On
  credit-default that list had 2,063 names for a 136-column matrix: the first smoke run caught it, because XGBoost
  failed on every fold.
- **Check after the fit.** Each model checks that its library holds the vector (`_monotone_verify`), and raises if it
  does not. It records `monotone_applied` (AutoGluon feature → sign) and `monotone_internal` (the name the library
  sees → sign).
- **The stack argument.** Suppose every base model f̂ₘ is monotone with sign s in x, and a stacker g is
  non-decreasing in each f̂ₘ and monotone with sign s in x. Then g is monotone with sign s in x. AutoGluon's weighted
  ensemble has wₘ ≥ 0, so it keeps the direction too.

**Request and resolution.**
- `POST /api/runs` takes `monotone = {constraints: {column: increasing | decreasing | none | ±1}, compliant_only: true}`.
- `engine/monotone.normalise` refuses:
  - non-numeric columns, with the reason: a category has no order; text becomes n-grams; dates become parts; IDs are
    not quantities;
  - the label, dropped and unknown columns, and unknown words;
  - multiclass and quantile labels (a softmax couples the classes);
  - `distill` (it trains unconstrained students). Registration with `distill` is refused as well.
- `resolve_fit_kwargs` swaps GBM / CAT / XGB for the `_MONO` keys. With `compliant_only` on (the default), every other
  family is left out, including the TF-IDF models a text column would add. With it off, they are kept and named in a
  note.
- The Gym validation runs the same normalisation and returns `monotone = {compliant, left_out, unconstrained}`:
  - an error when no compliant family is on;
  - a warning when non-compliant families are kept;
  - info on how stacking stays monotone.
- Its family counts and fit-time estimate fold `_MONO` back into GBM / XGB / CAT.

**After the fit** (`engine/monotone.report`, stored as `result.monotone`):
- where each constraint landed: the feature generator's links (raw → AutoGluon features) and the models that
  constrain it;
- per model: the signs its library received, its stack level, and whether it is monotone by construction (a
  constrained model whose stack inputs are all monotone by construction, or a weighted ensemble of such models);
- an ICE check of every model on 100 holdout rows, and of the best model on 200 rows with 30 curves kept for the UI.

The check is `ice_check`. It takes raw holdout rows, sets column j to each grid point (the column's quantiles), and
scores them through the predictor's own `predict_proba` / `predict`, so the check passes through AutoGluon's whole
pipeline. A curve violates the constraint where sⱼ·(ICEᵢ(g₊₁) − ICEᵢ(g)) < −10⁻⁹.

**Endpoints, registry, export.**
- `GET /api/runs/{id}/monotone?model&constraints&rows&grid&curves` works for any binary or regression run. With
  `constraints=col:increasing` it checks a run trained without constraints: that is the "before" view.
- `GET /api/registry/versions/{id}/monotone` checks the version's served model from its own files (cloned, pipeline
  pruned).
- The registry build stores the same check. The model card's validation section and its Markdown / HTML record the
  constraints, the AutoGluon features they landed on, ICE curves violating, PD range, and "served model monotone".
- `export.py` marks monotone runs as needing `ensemble_models`. The exported script now also puts the package on
  `PYTHONPATH` for AutoGluon's Ray fold workers: they do not inherit `sys.path`, so a bagged export failed with
  `No module named 'ensemble_models'`. This was a latent bug for bagged TF-IDF exports too. Checked: the export of the
  monotone run reproduced its leaderboard exactly (8 models, max |Δ score| = 0).

**UI.**
- **Gym, Advanced → Models: Monotone Constraints card.**
  - ↑ increasing / none / ↓ decreasing for every numeric feature (label and dropped columns excluded);
  - a "compliant families only" switch;
  - the families that honour the constraints, the ones left out or kept, and the validation messages;
  - a formula panel, with every symbol defined: sⱼ·(f(x₋ⱼ, b) − f(x₋ⱼ, a)) ≥ 0, the stacker g with ∂g/∂f̂ₘ ≥ 0, and
    wₘ ≥ 0.
- **Explain → Monotonicity** (binary and regression runs):
  - pick a feature and a model; for unconstrained runs, also a direction;
  - ICE curves (red where they step against sⱼ) and the PD in bold;
  - the formulas ICEᵢ(g), PD(g) and the violation rule, bound to the run's n, G, grid range, sⱼ and ε;
  - curves and steps violating, the largest step, whether PD is monotone, and the PD range;
  - a table of every model: level, family, the signs its library received ("debt_to_income +1 · 3 stack inputs +1"),
    monotone by construction, and ICE ✕ / n.
- **Model card:** a Monotone Constraints table in section 5, with the check's rule and method.

## Before → after (credit-default, y = defaulted, debt_to_income ↑, same split, k = 3, L = 1, eval_metric ROC AUC)

| | before (same body, unconstrained: GBM, XGB, CAT, RF, LR) | same families, unconstrained (GBM, XGB, CAT) | after (constrained, GBM_MONO, XGB_MONO, CAT_MONO) |
| --- | --- | --- | --- |
| served model | WeightedEnsemble_L3 | WeightedEnsemble_L3 | WeightedEnsemble_L3 |
| ICE curves of the served model going down somewhere | **195 / 200** | 199 / 200 | **0 / 200** (and 0 / 200 through the version's `/score`) |
| largest step down | 0.0151 | | 0 |
| PD non-decreasing on the grid | yes (the average hides it) | | yes, 0.059 → 0.185 |
| models monotone by ICE | 2 of 12 (WeightedEnsemble_L2, LinearModel_BAG_L1) | | **8 of 8** |
| served model's holdout ROC AUC | 0.7743 | 0.7568 | 0.7557 |

Reading it:
- **The constraint itself costs about nothing here.** 0.7568 → 0.7557, well inside a holdout ROC AUC interval of about
  ±0.03 on 2,400 rows.
- **The bigger cost is leaving out LinearModel.** The sample is generated from a logistic model, so LR is strong
  here. With compliant families only, it cannot be in the ensemble. A user who wants it can turn "compliant
  families only" off; the report then shows which models break the constraint.
- **The PD check alone is weak.** The unconstrained ensemble's PD is monotone while 195 of its 200 ICE curves are
  not. So the product checks every ICE curve, not only the average.

## Open problems

- **Strength of the check.** It is on a grid: 25 quantiles × 200 holdout rows for the served model, 100 rows for each
  other model. That is evidence, not a proof between grid points. For the tree libraries the constraint is exact by
  construction, and the run's report says which models are monotone by construction.
- **Two-valued columns.** A two-valued numeric column becomes 0/1 in AutoGluon, with the larger value as 1, so the
  order is kept. A third value never seen in training maps to 0 and can break monotonicity on raw inputs.
- **Constrained families only.** Only LightGBM, XGBoost and CatBoost are constrained. There is no monotone neural net
  or linear model; AutoGluon's LinearModel does not constrain coefficient signs. On data where LR carries the
  ensemble, compliant-only costs accuracy (here ROC AUC 0.774 → 0.757).
- **Categorical constraints.** An ordinal category ("low < mid < high") cannot be constrained. Encode it as a number
  first.
- **Stack inputs are always +1.** With `compliant_only` off, a stacker may still learn from an unconstrained base model.
  The run's report and Explain show the resulting violations, but nothing prevents them.
- **Unrelated, seen but not fixed.** The Explain page's sidebar highlights "Experiments", not "Explain". This was
  there before F8.
