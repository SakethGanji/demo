## What was built

All new code is in `backend/app/lake/`.

- **`store.py`** holds the `BlobStore` protocol and `LocalBlobStore`.
  - The protocol has `put_file`, `exists`, `size`, `open`, `uri`, `local_copy`, `delete`, `list` and `tmp_dir`.
  - Keys follow §3.1: `blobs/<aa>/<sha256>.<ext>`, plus `tmp/<writer>/` for writes in progress.
  - `put_file` is write-once:
    1. it hard-links (or copies) the file to a hidden `.part` name;
    2. it sets the file to `chmod 0444`;
    3. it `link`s it into place.

    An existing key is a no-op, so dedupe across datasets costs nothing.
  - The module docstring writes down the contract the P10b `S3BlobStore` (MinIO) must meet:
    - `If-None-Match: *` and `x-amz-checksum-sha256` on writes;
    - a sha-keyed read cache;
    - `delete` removes every object version.

    `open_store()` picks the store from `ENSEMBLE_LAKE_STORE`. Only `local` exists; `s3` gives a clear error.
- **`manifest.py`** has the canonical JSON and every §3.3 hash.
  - **Canonical JSON:**
    - keys are sorted and there is no whitespace;
    - strings and keys are NFC;
    - **a float raises `CanonicalError`**, and so do NaN, integers outside int64, and non-string keys;
    - `ts()` writes timestamps as `YYYY-MM-DDTHH:MM:SSZ`.
  - **Hashes:** `file_sha256` reads in 8 MB chunks. The other hash functions are:
    - `table_sha256`, `schema_sha256`, `data_sha256`;
    - `seal()`, which fills `data_sha256` and returns the bytes and `manifest_sha256`;
    - `SplitHasher` / `split_sha256` / `split_sha256_parquet`: int64-LE `__row_id` ‖ int8 fold per row, streamed. Rows
      must be in strictly increasing order, or it raises;
    - `sample_sha256`, `join_frame_sha256`;
    - `audit_row_hash`, whose genesis is `"0"*64`. The chain is written from P19;
    - `splitmix64` in numpy, checked against a pure-Python copy and the reference value.
- **The startup self-check** is `selfcheck()` / `assert_selfcheck()`.
  - It runs 18 vectors:
    - sha256("abc");
    - the canonical-bytes prefix and NFC handling;
    - data and manifest sha of a fixed manifest;
    - schema, table, split (10 rows) and sample sha;
    - the join sha and a 2-row audit chain;
    - `splitmix64(0) = e220a8397b1dcdaf`, the reference generator's first output, plus a numpy vector;
    - the **10-row split written as Parquet by DuckDB and re-hashed through pyarrow**;
    - a check that floats are refused and that unsorted split rows are refused.
  - The constants were pinned on the locked stack (duckdb 2.0.1, pyarrow 24.0.0, pandas 2.3.3). The table, split and
    sample values were also recomputed independently with `sha256sum` and `struct.pack`.
- **`duck.py`** follows B §5.1.
  - `connect("interactive"|"job")` makes an in-memory connection with:
    - `memory_limit`, `threads` and `preserve_insertion_order=false`;
    - a spill directory under `data/tmp/duck` with `max_temp_directory_size`;
    - extension autoinstall and autoload turned off.
  - `job()` is a context manager that closes the connection and removes its spill directory.
  - `Interactive` is one process-wide connection:
    - each query gets a cursor;
    - `BoundedSemaphore(8)` limits concurrency, and a query that gets no slot in time raises **`DuckBusy` (429)**;
    - a `threading.Timer` calls `cursor.interrupt()` after 10 s, which raises **`DuckTimeout` (504)**.
  - `disk_guard()` raises **`DiskFull` (507)**.
  - The limits come from `ENSEMBLE_DUCK_*` in `config.py`.
- **`writer.py`** holds the `VersionWriter`.
  - **Building a version:** `carry` / `write` / `write_arrow` / `append`, then `key`, `relation` and `split`.
  - **Writing a table:** `write` does a DuckDB `COPY … ORDER BY __row_id` (zstd 3, 122 880-row groups, or 30 720 above
    200 columns) and checks that:
    - `__row_id` is first, BIGINT, has no nulls and no duplicates;
    - no column name has the `__` prefix.

    It cuts the table into parts of at most 8M rows by `file_row_number`, hashes each part in tmp, and puts it in the
    store with a `pending` blob row.
  - **`commit()`** follows §5.2:
    1. It builds the manifest, seals it and puts the manifest blob.
    2. It runs **one `BEGIN IMMEDIATE` transaction**, which:
       - returns the existing version when the `job_id` was already committed;
       - deduplicates on `data_sha256` for `DEDUPE_OPS`, which are today's ops plus `carry`;
       - allocates `version_no` with `UPDATE … RETURNING`;
       - inserts `datasets` (`storage='parquet'`, `manifest_sha256`, `data_sha256`, `sha256 = data_sha256`, `job_id`, and
         a legacy-compatible profile), `version_tables`, `table_files`, `table_keys`, `table_relations` and `splits`;
       - inserts `blob_refs` with `team_id`;
       - sets the blobs to `live` only where they are `pending` or `live`. If one is `purging`, `purged` or missing, it
         rolls back, puts our own bytes again and retries once. A carried part whose bytes we do not hold gives
         `409 blob_gone`;
       - updates the `dataset_root_tables` high-water mark;
       - adds the `derived_from` edge and audits `dataset_created` or `dataset_version_created` plus `split_created`.
    3. After the commit, it settles the default with **compare-and-set** on `dataset_roots.default_version_id` and
       mirrors it to `dataset_cards`.
  - **Rules the commit keeps:**
    - No file I/O or pandas runs inside the transaction.
    - The manifest names `version_no`, so the number is predicted first. If another commit took it, the transaction
      rolls back and the manifest is rebuilt (up to 4 tries).
    - The job and dedupe checks also run read-only *before* the manifest blob is written, so a re-run leaves no
      blob behind. The checks inside the transaction are the ones that decide.
- **Root safety (P01's note).**
  - The writer never changes the root of an existing `datasets` row. A new dataset is a fresh id that is its own root,
    and later versions are fresh rows.
  - `catalog/schema.py sync_version` now **refuses** to delete a `dataset_roots` row that has any of these:
    `dataset_root_tables`, `joins`, `column_tags`, `data_contracts`, `certifications` or a Parquet version. The check
    is `root_has_dependants()`, and the refusal is a `ValueError`.
- **`gc.py`** is a dry run only (§5.10). Nothing is deleted.
  - Phase 1 lists unreferenced blobs: `pending` ones older than 24 h and `live` ones older than 7 days.
  - Phase 2 lists store objects with no row older than 24 h, stale `.part` files and stale `tmp/` writers.
  - Blob names that do not match their bytes are listed as **integrity findings**.
  - `armed` reads `catalog_meta.gc_armed`, which is never set yet. `?dry_run=0` gives `409 gc_disarmed`.
- **`verify.py`** checks a Parquet version:
  - it re-hashes every part against its key and recomputes each table sha from its parts;
  - it re-hashes the manifest and checks that it is canonical and that its `data_sha256` is consistent;
  - it compares the DB rows with the manifest and re-hashes each split, including the split sha recomputed from the
    file;
  - it sets `blobs.verified_*` and `datasets.verified_*`, so the existing DL2 `integrity_gate` blocks training on a
    mismatch.
- **`api.py`** has the routes and the `install(app, settings)` hook:
  - `GET /api/admin/lake/selfcheck` and `GET /api/admin/lake/status`;
  - `POST /api/admin/lake/gc?dry_run=1`;
  - `POST /api/admin/lake/seed`, admins only. It builds a deterministic generated table (zip with leading zeros,
    account_no, date, amount, int, segment, y) in modes `new`, `append` or `carry`, with a declared key and a split;
  - `GET /api/datasets/{id}/manifest`: the stored manifest plus resolved file paths;
  - `GET /api/datasets/{id}/verify`: Parquet versions only. CSV versions keep `POST …/verify`. A failure is audited as
    `dataset_integrity_failed`.
- **`config.py`** gained:
  - `Settings.lake_dir` and `duck_spill_dir`;
  - the `ENSEMBLE_DUCK_*` limits and `ENSEMBLE_LAKE_STORE`;
  - the part, row-group and compression constants;
  - the GC grace periods.
- **`main.py`** got three lines: `lake_api.install(app, settings)` in `create_app()`. It runs the self-check, so a
  mismatch raises `SelfCheckFailed` and the app is not created. It also opens the store (`app.state.lake`) and mounts
  the lake router.

## Deviations and notes for dependants

- **Files outside the P02 list (minimal):**
  - `catalog/schema.py`: the `sync_version` guard and `root_has_dependants`, about 20 lines. This is lane D's own
    P01 file.
  - `main.py`: only the `install()` hook. It also mounts the lake router, since §9.1 needs the routes, and that saves a
    separate `include_router` line.
- **A fix found during verification:** the first seed returned 500 on `GET /datasets/{id}`, because the legacy
  `Dataset` response model needs an integer `n_classes`. The writer now fills a legacy-shaped `profile`:
  - `n_cols`;
  - `n_classes`, the distinct target values (0 without a target);
  - `columns`, `storage` and `tables`.

  `GET /datasets`, `GET /datasets/{id}` and history now list Parquet versions.
- **The legacy consumers still read CSV.** A Parquet version is listed, verified (GET) and has a manifest, but nothing
  else can use it yet:
  - `load_frame`, runs, the old `POST …/verify` and verify-all, export, and the grid;
  - verify-all would report "file missing" for it.

  P05 moves the readers (`frames.py`, `data_gate`) and makes uploads Parquet. Until then, only the admin seed makes
  Parquet versions.
- **The audit hash chain is not written.** Audit rows go through `schema.audit()` without `team_id` or `row_hash`, the
  same as every other post-P01 row. P19 owns the chain; `manifest.audit_row_hash` is ready for it.
- **For P05/P06:**
  - Create versions only through `VersionWriter`. Do not use `record_version` or `sync_version` for Parquet
    data. `sync_version` now raises on a lake root rather than deleting it, so a legacy re-root of a lake dataset
    fails loudly. That path is not reachable today.
  - Call `committed_for_job()` before doing the work of a leased job.
  - Allocate row ids for new rows from `dataset_root_tables.next_row_id` read before writing. Two concurrent writers
    on one root can give siblings the same new ids, which is fine in a tree, but P05/P06 should take ids at commit if
    siblings must differ.
- **For P09:** `w.split()` stores a split it is given and checks that it covers exactly the table's rows. Drawing
  splits, carrying them with `newfold` and the five checks belong to P09.
- **For P10b:** implement the `BlobStore` protocol in `store.py`. `uri()` is the only thing readers use.
- **For P24:** `gc.plan()` is the dry run. Deletes, `gc_armed` and purge are P24's. The writer already re-asserts that
  blobs are `pending` or `live` inside the commit and re-puts its own bytes when they are not.
- **`tests/test_upload.py::test_upload_returns_full_profile` fails on the base commit too** (it failed with these
  changes stashed). It is not caused by P02. Tests are not this project's verification method; this is noted only.
