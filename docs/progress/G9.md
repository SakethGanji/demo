# G9 · Load data from a SQL query

**What it does.** Build gets a second way in, next to the CSV upload: **1 · Your table** now has a **CSV file | SQL query** switch. The SQL side comes pre-filled with the demo database and a join that rebuilds credit-default. The user runs a read-only SELECT, previews it, and loads it as a dataset; the query is stored in the dataset's lineage. Smart Intake (G0) then reads the dataset like any upload, so the roles and suggestions are the same as for the CSV. **Refresh ↻** runs the same query again into the next dataset version, with its parent and a row diff. There is no new navigation.

## Backend (`backend/app/sqlsource/`)
- **Connections (`core.py`)** take a SQLAlchemy URL:
  - `sqlite:///file` and `duckdb:///file`: files on the server under the data directory (relative paths are read from it) or a directory in `ENSEMBLE_SQL_ROOTS`. Other paths are refused, and so is the workbench's own `ensemble.sqlite3`.
  - `postgresql://…`: through SQLAlchemy, if a driver is installed (none is pinned; without one, the error says to install `psycopg[binary]`).
  - Anything else gets a 400 that names the supported databases.
- **Read-only, in three layers:**
  1. **The statement:** one SELECT (or WITH … SELECT). A second statement is refused, and so is any write, DDL or admin keyword outside comments, string literals and quoted identifiers.
  2. **The connection:** SQLite opens with `mode=ro` and a 60 s progress-handler timeout; DuckDB with `read_only=True`; Postgres in a READ ONLY session with `statement_timeout`.
  3. **The rows:** `fetchmany(limit + 1)` (default 100,000, max 1,000,000) fetches at most the limit and reports whether there were more.
- **Credentials are never stored.** A password travels in the request (inside the URL or as `password`). Lineage keeps the URL with the password masked (`***`) and `needs_password`. A refresh of such a source asks for the password again.
- **Datasets:** `DatasetStore.create_from_frame` is now the single path for both the upload and the SQL source. `create_from_upload` parses the CSV, then calls it. Lineage goes to `lineage.json` and to `profile.lineage`:
  - `source: "sql"`, the dialect, the masked URL, the query and its hash, the limit and `truncated`;
  - rows, columns, `fetched_at`, the seconds taken and `data_sha` (a hash of the CSV);
  - `version`, `root`, `parent`, and on a refresh the `diff` (rows added, removed and kept, matched as whole rows).
  - The DB keeps `source = 'upload'`, so the schema CHECK and every existing caller are unchanged. The SQL origin is read from the lineage.
- **Refresh:** the same query, URL and limit are run again, and the next version number goes to the family that shares the root.
  - The confirmed or given target carries over (target_source `given`).
  - The new version is named `<name> · v<n>` and gets its own split, because the rows are different.
  - `unchanged: true` when the data hash is the same.
- **Routes:**
  - `GET /api/sql/demo`;
  - `POST /api/sql/tables`, `POST /api/sql/preview` (columns, the first 20 rows, n, truncated, ms);
  - `POST /api/sql/datasets`, which is zero-config: `{}` loads the demo join;
  - `POST /api/sql/datasets/{id}/refresh`, `GET /api/sql/datasets/{id}/versions`.
- **Demo database:** `data/demo/bank.sqlite` is built from the bundled samples on first use and rebuilt when they are regenerated (it is stamped by their mtimes). It has `applications` + `outcomes` (credit-default, split in two so the demo query is a join), `loans` (loan-stream) and `accounts` (account-churn). No `samples*.py` is touched.
- **Model card:** the Data section gives the source as "SQL query" and adds the query, the masked URL, the version, the fetch time and the data hash (JSON, MD and the view).

## UI
- **`src/features/build/SqlSource.tsx`**, in Build's panel 1:
  - the URL, a password field ("never stored", kept in component state only) and **List tables**, which shows the tables as chips with row counts; clicking a chip writes `SELECT * FROM t`;
  - the query, an **Advanced** fold-out (row limit, name, closed by default), **Preview**, and the primary **Load as dataset →**;
  - the preview: n × d, ms, and the first 5 rows.
- **`SqlLineageLine`:** for a SQL-loaded dataset, panel 1 shows "SQL · v2 · URL · fetched …" with **Refresh ↻** (and a password field if the source needs one). After a refresh it shows "+n new, −m gone, k unchanged". The **Lineage** fold-out holds the query and the version table (v, rows, change, data hash; each version links to Build).
- Loading or refreshing selects the new dataset, and "What we found" and "What you can build" follow as for any upload.
- **Zero-config:** the demo URL and query are pre-filled, so one click on Load gives credit-default's 12,000 rows. Smart Intake then finds y = defaulted, t = application_date and g = customer_id, and the top suggestion is "Default risk model" with an out-of-time + group split and the business cost.

## Numbers (smoke `sql`)
- **Guard:** DELETE, a `; DROP` and `WITH … INSERT` are each refused with the reason, and so is a file outside the data directory. A preview with limit 500 returns 500 rows, flagged as truncated, in about 3 ms.
- **Acceptance 1, query → dataset → trains end to end.**
  - Setup: a copy of the demo DB in which the newest 3,000 applications have no outcome yet.
  - The demo join loads **9,000 rows** with the query in the lineage (v1).
  - Intake's top suggestion is binary (y defaulted, time-group split). Its pre-fill trains a quick GBM/RF/LR run in about 48 s, with holdout **ROC AUC 0.747** and accuracy 0.913.
  - The run is registered (ready). The model card shows "Loaded by SQL query" and the join.
- **Acceptance 2, refresh → new version with lineage.**
  - The outcomes are inserted into the source, then Refresh gives **v2: 12,000 rows, +3,000 new, −0, 9,000 kept**, with parent = root = v1, the same query and the target carried over.
  - `/versions` lists [v1, v2]. Refreshing again with no change gives v3 with the same data hash (`unchanged`).
- **Smoke:** `SMOKE_ONLY=sql,core make smoke` passes **24/24 in 149 s** (sql 3 steps, about 50 s). `npm run build` is OK.

## Limits and open problems
- **DuckDB and Postgres are not exercised.** The code paths exist, but neither `duckdb` nor a Postgres driver is in `requirements.txt` (I added no dependency). Both give a clear "install …" error. Only SQLite is covered by smoke.
- **The keyword guard is conservative.** A column literally named `set`, `update`, `delete`, `create` or `into` must be double-quoted. The connection's read-only mode is the real protection; the keyword list is the first layer.
- **The DuckDB path has no query timeout**; SQLite and Postgres have 60 s.
- **No new G0 suggestion.** The SQL source is a way in, not something to build. Its entry is Build's panel 1, and Smart Intake runs on the loaded dataset as on an upload. G10 can wrap `/api/sql/*` as Vela tools.
- **Versions are separate datasets** (`ds_…`), linked only by lineage. Runs on v1 and v2 use different holdouts, because the rows differ. There is no "retrain on the latest version" button yet.
- **Not in the audit log.** Loads and refreshes are dataset events, and the audit log is per registry version. The lineage records who and when only by timestamp, since there is no sign-in.
- **The Makefile's full `SMOKE_ONLY` list** now includes `ml` (missing since G8) and `sql`.
