## What was built

| Piece | Where | What it does |
|---|---|---|
| **The split store** | `lake/splitstore.py` (new) | **A split is a blob** `(__row_id BIGINT, fold TINYINT)`, sorted by `__row_id`, covering exactly the table's rows. Its identity is `split_sha256` (§3.3, writer-independent). Fold codes are unchanged (0..k−1, −1 holdout, −2 excluded, −3 tuning).<br>**`commit_split`** (a split drawn after its version, e.g. the first run on a target): writes the blob, then **one transaction** with `INSERT splits` + `blob_refs` (owner `split`) + audit `split_created`. A concurrent draw of the same key loses the insert and gets the winner's row.<br>**The audit row carries the whole row** (target, strategy, params, seed, share, folds, counts, carried_from, legacy sha), so restore can rebuild a row that was replaced. The writer's `split_created` (carried splits) now carries the same fields.<br>**`integrity(row)` = the five checks of §4.3:**<br>1. the blob re-hashed against its key;<br>2. `split_sha256` recomputed from the file (and its row count);<br>3. the `split_created` audit row records the same split and blob. The chain link is reported as "not written yet (the chain starts in P19)";<br>4. every earlier run on this split id, **or on the same (version, table, split key)**, recorded the same hash. Evidence = `run_inputs.split_sha256` (trigger-protected), or `split_legacy_sha256` against `splits.legacy_sha256` for runs before P09. Runs whose own gate failed or was overridden are not evidence;<br>5. a carried split moved no surviving row to another fold, compared with `carried_from`'s blob.<br>A failure message leads with check 4 when it fails: `split_integrity: <key> of <version> differs from runs r1, r2: …`.<br>**`restore_offer` / `restore`:** see the restore row.<br>**`row_ids(version)`:** a row's root identity by read position. That is `__row_id` for a Parquet version; for a CSV-era version (until P10) the lineage row map, or 0..n−1 for a root. |
| `ensure_splits` | `datasets.py` (`ensure_splits`, `_ensure_lake_split`, `list_splits`) | **For a Parquet version:**<br>• the existing `splits` row is returned and never redrawn;<br>• a missing one is **adopted** from a pre-P09 DL4 JSON (P05–P08 bridges), but only if its bytes still match the hash DL4 recorded (otherwise 409, not laundered). `legacy_sha256` = the JSON's sha256, which is what its old runs recorded;<br>• otherwise it is **drawn** with the unchanged strategy code over the rows in `__row_id` order and committed through `commit_split`.<br>**The positional JSON** that ~40 consumers read through `cfg.splits_path` is now a **view** written from the blob (`view_of {split_id, split_sha256, blob_sha256}`), never a source.<br>`list_splits` lists the `splits` rows: `split_id`, `split_sha256`, `blob_sha256`, `carried_from`, `carried`.<br>**CSV-era versions are unchanged** (DL4 JSON + `split_files`). |
| **Carry by join** (§5.7) | `splitstore.carry_into` / `given_into`, called from `derive()`, `edit_version()` (`datasets.py`), `lake/derive.split_into`, `lake/upload._commit_next` | **Replaces the P06/P07 DL4 JSON bridge.** The parent's split is carried **inside the version commit** (`w.split`, so it lands in the same transaction as the version):<br>`SELECT c.__row_id, p.fold FROM child c LEFT JOIN parent_split p USING (__row_id)`.<br>A new row gets `newfold = splitmix64(__row_id ⊕ seed)`: the holdout under the new-row share, else fold `mix mod k`. `carried_from` and a `carried` summary (`kept_holdout`, `new_rows`, `new_holdout`) are recorded; the manifest gets an op `split_carried`.<br>**A caller's split** (Feature Lab, active learning, annotations, shift weights pass one by position) is written as given. It counts as carried from the parent's split only when **no surviving row changed fold**, so check 5 holds by construction.<br>**Not carried:** structured (group / time) splits are drawn fresh on first use, as before; so is a split whose target column is gone. |
| The `lineage.json` row-map bridge is retired | `lake/derive.lineage_summary`, `lake/upload._write_lineage_summary` | New Parquet versions get a `lineage.json` **without `root_rows` / `parent_rows`** (no 8 MB of ints per 1M rows); it keeps kind, parent and match. The readers now use `__row_id`:<br>• `compare.root_info` → `__row_id` for Parquet (P08's diff no longer calls it);<br>• Autopilot (`_lineage_rows`, `_pred_roots`);<br>• `vela/experiments._roots`;<br>• `engine/annotations.sample_truth`, `annotations_api` → `splitstore.row_ids`. |
| **Run pins** | `engine/api.py` (`split_record`, `_split_gate`), `engine/worker.py` (`record_run_input`) | `cfg.split` carries `split_id`, `split_sha256` and `blob_sha256`; `cfg.split_pin` is set at queue time.<br>The run holds `blob_refs (owner_kind 'run', role 'split')` on the exact blob.<br>`run_inputs` gets `split_id` and `split_sha256` (the hash recomputed from the bytes read). `split_legacy_sha256` is filled only for runs on a JSON split. |
| **The gate** | `engine/api._split_gate` (queue), `engine/worker.splits_gate` + `_pinned_split` (fit) | **At `POST /runs`:** the five checks. A failure → **409 `split_integrity`** naming the checks; it is audited (`dataset_integrity_failed`, `training_refused`) and the version is flagged `verified_ok=0`. An admin override (`integrity_override_reason`, the DL2/DL3 path) lets it train; that is audited, and the run's result records `splits_integrity.override`.<br>**At fit:** the worker reads the **pinned blob**, not the view file. It recomputes `split_sha256`, joins the folds onto the frame by `__row_id`, rewrites the view from the verified blob, runs the five checks again (excluding itself), and requires that the split read equals the pin. |
| Verify | `lake/verify.verify_version` (GET …/verify), `catalog/dsets.verify` (POST …/verify) | Every split of a Parquet version goes through the five checks. Each check is listed with its detail; `problems` name `check n <name>`. New fields: `data_ok` / `splits_ok`.<br>A Parquet version's split failure no longer marks the data as mismatched ("SPLIT MISMATCH", with a remedy that names the failing check and restore-splits). CSV-era versions keep `check_splits`. |
| **Restore from run pins** | `catalog/datasets_api.restore_splits` → `_restore_lake_splits`, `splitstore.restore` | **`POST …/restore-splits {}` only offers.** Per failing split, it offers the split the **earliest run** on it used: that run's pinned blob, re-hashed, its `split_sha256` checked, and the runs that agree with it. If there is no intact pin, it says so.<br>**`{split_key, blob_sha256, by, reason}` applies the offer.** One transaction:<br>• lift the two immutability triggers;<br>• delete the failing row and its ref;<br>• re-insert the original row (its original id, rebuilt from its `split_created` audit row and the blob);<br>• re-create the triggers;<br>• audit `dataset_splits_restored` with both rows.<br>The version is then verified again. A second call → 409 `nothing_to_restore`. |
| **Paired-compare honesty** | `catalog/compare.py` | **Pairing** is the intersection of the two runs' holdout `__row_id` sets. On a Parquet run, `holdout_predictions.row` is already the `__row_id`; on a CSV-era run, a position mapped through the root rows.<br>**`overlap`** = `{n_common, n_a, n_b, share, same_holdout, text}`, where `share = n_common / the larger holdout`. The label is:<br>• **"paired on the same holdout rows"** only when the sets are equal;<br>• **"paired on n of N rows (holdouts differ)"** at ≥ 50 %;<br>• **below 50 %**, no paired Δ: the labelled unpaired table, "paired on n of N rows (holdouts differ) — x % overlap is below 50 %, so no paired Δ".<br>"read modes differ" is reported when the runs' `run_inputs.read_mode` differ. |
| Positional fixes | `engine/worker.load_frames`, `engine/serving.holdout_frame` | A Parquet frame's index is `__row_id`, with gaps after an edit, so position-based lookups must not use `.loc`:<br>• group folds now use `fold[is_train & has_label]`;<br>• `holdout_frame` uses `iloc`. |

## Decisions

- **`split_files` and `datasets.splits_sha256`: read-only for P10, not retired.**
  - Neither is written for any Parquet version any more (chain step 1: 0 rows, `splits_sha256` NULL).
  - Both are still used for CSV-era versions, because those have no `__row_id` table to key a Parquet split on until P10 migrates them.
  - A pre-P09 Parquet version's recorded JSON is migrated lazily, on first use, by `adopt_legacy` (hash-checked).
  - P10 should migrate every CSV-era version's split JSONs with `splitstore.commit_split(…, legacy_sha256=<JSON sha>)` (or `adopt_legacy`), then drop both. That also empties gate 2 outside `lake/migrate.py`.
- **Structured splits are not carried row by row** (P06 and P07 did the same). A group or time split on a derived version is drawn fresh on first use. Carrying it with `newfold` would mix a random draw into a time/group design.
- **Restore lifts the immutability triggers** inside its one transaction, to replace the tampered row by the original id.
  - This is the only app path that deletes a `splits` row. It is audited with both rows, and the triggers are re-created in the same transaction.
  - The alternative, a second row for the same key, breaks the `(version, table, split_key)` uniqueness every lookup relies on.

## Deviations and notes for dependants

- **Files outside the row** (all small, all lane D or shared and noted):
  - `lake/splitstore.py` (new);
  - `lake/derive.py`: `split_into` and `lineage_summary`; `carry_split` and `legacy_bridge` removed;
  - `lake/upload.py`: the carry in `_commit_next`; `_write_legacy_bridge` → `_write_lineage_summary`;
  - `lake/writer.py`: the `split_created` details;
  - `lake/verify.py`: the split section;
  - `engine/api.py`: `split_record` pin fields, `_split_gate`, the 409 mapping for an unreadable split;
  - `engine/serving.py`: one line, `iloc`;
  - `autopilot/engine.py`, `vela/experiments.py`, `engine/annotations.py`, `engine/annotations_api.py`: the row-map readers.
- **`splits.py` is unchanged.** The strategy code is the same (§5.7), drawn over rows in `__row_id` order.
- **`GET /compare?a=&b=`** in the row is `POST /api/compare {a, b}` in this code (GET → 405). The chain uses POST.
- **Check 3's chain link** is reported, not verified. `audit_log.row_hash` is written from P19; until then, a forged `split_created` row passes check 3 (chain step 7), and **check 4 still catches the tamper**. **P19:** verify the link in `splitstore.integrity` once rows are chained.
- **Check 4's evidence:**
  - It joins `run_inputs`, which is trigger-protected, with `runs.config.split.key` and `runs.result.splits_integrity`. Those two are ordinary JSON columns, and someone with DB access could edit them.
  - The protecting hashes themselves (the blob key, `run_inputs.split_sha256`, the run's `blob_refs` pin) are outside any mutable row.
  - P23 (Postgres grants) closes the rest.
- **A carried split with no runs that is tampered** (chain step 13) is detected (checks 3 and 5) but **cannot be restored**: no run pinned it. Re-carrying it from `carried_from` would be a possible follow-up.
- **P22 (lane O):** `engine/worker.py` changed in `load_frames` (`_pinned_split`), `record_run_input` and `splits_gate`. The run config gains `split_pin`. A queued run needs `split_pin` to reach the worker intact.
- **P11:** `serving.holdout_frame` now uses `iloc` (positions).
- **Not fixed, outside the lane:** `vela/doctor.py:152` has the same `df.loc[holdout positions]` pattern. It is wrong on a Parquet version whose `__row_id`s have gaps.
- **U2:** restore is two calls: the offer, then `{split_key, blob_sha256, by, reason}`. Compare responses carry `overlap`; show `overlap.text`, and show no Δ when `paired` is false.
- **Not run here:**
  - a 10M-row timing of the checks (§5.7 estimates ≈ 0.4 s);
  - active learning, annotations and shift-weight writers end to end (they call the same `derive(splits=…)` path checked in-process above);
  - a time split;
  - a pre-P09 JSON changed before adoption (the code refuses it with 409; not exercised).
- **Scratch:** the data dirs, the venv, the worktree of the old head and the API process were in the session scratchpad and were removed.
