No scenario was misdiagnosed in the smoke run. Two runs during development came close; both are reported here:
- **Overfit, first build.** A LightGBM with 600 rounds was diagnosed as label noise. LightGBM keeps its best
  validation iteration, so it never memorised the data (train 0.91, not overconfident), and the logistic target itself
  has an error floor. The scenario now uses a 1-NN, which really memorises the rows.
- **Data-limited, first builds.** On 700 and 2,500 rows the learning curve came out *noisy*. The CI lower bound
  (0.0015) was below ε (0.0020) although the means rose 0.789 → 0.859 → 0.887 → 0.922. The doctor then reported
  "no evidence" (correct by the rule) and offered "rerun with 5 seeds". The final scenario (3,000 rows) is data-limited
  with 3 seeds in the smoke run.

  The smoke handles both outcomes: if the first curve is noisy, it asserts *no-evidence* and follows the offer.

## What changed

**`backend/app/vela/doctor.py` (new): the procedure.**

1. **Measurements.** These run in a worker and are cached on the run by the SHA of the holdout predictions and the
   slices file.
   - **Fit gap:** `predictor.evaluate` on the training rows (fold ≥ 0) and on the holdout, so both scores share one
     threshold and sign. z = (s_train − s_holdout) / SE_boot.
   - **Confidence:**
     - the error floor among the 20 % most confident holdout predictions, with a Wilson interval;
     - the error the model expects there, mean(1 − max p̂);
     - `overconfident` = floor − expected ≥ 0.05 and expected < floor / 3;
     - `cleanlab.filter.find_label_issues(prune_by_noise_rate)` on the holdout's out-of-sample p̂;
     - the number of distinct predictions.
   - **Slice floors:** for each listed F16 slice, its base rate and the loss of predicting that base rate as a
     constant: H(π_S) for log loss, 1 − max share for error, |y − median| for absolute error.
2. **Reads.** It never starts a job itself.
   - Vela's findings;
   - `split-comparison` (F6), with SE_boot of both runs for z;
   - `learning_curve/1`, `active_learning/1`, `annotations/1`, `shift/1` and `slices/1` from the run payload;
   - F15's actions;
   - F3's latency profile.
3. **Checks.** There are 11 checks, each ending as finding (critical / major / minor), clear, no-evidence, missing
   (with an offer) or n/a. Each has a fixed rule, and the rules are returned with every diagnosis.
4. **Ranking.** The primary factor is the most severe finding. Ties are broken by precedence: leakage › shift ›
   label noise › overfit › data-limited › underfit › latency › weak slice › budget › imbalance › weak class. What
   invalidates the measurement comes before what limits the model. The other findings are ranked secondaries.

**The reconciliations the earlier sessions asked for.** Each is in the code and in the check's reason text.

| signal | how the doctor reads it |
| --- | --- |
| cleanlab's noise rate (fires on hard-but-clean data too) | **Prototype:** cleanlab flags 0.199 on hard clean data and 0.199 on 20 % flips alike. The top-confidence error floor separates them: 0.075 vs 0.175. **Rule:** label noise needs floor CI lower ≥ 0.06, not overconfident, and cleanlab ≥ 5 %. **Credit-default:** floor 0.017, cleanlab 3.2 % → clear. |
| train–validation gap (also opened by noisy labels) | Overfit needs z ≥ 3 **and** an overconfident holdout. On the label-noise scenario the gap is large, but the model expects its errors, so overfit is *clear* ("a gap with calibrated holdout confidence is what noisy or overlapping labels leave"). |
| "saturated" learning curve when predictions never change | Saturated with ≤ 1 distinct prediction (or constant p̂) → *underfit* (major, escalate the preset), not "enough data". |
| shift (F15 covariate only) | F6's random vs out-of-time z and F15's verdict each raise it: critical if z ≥ 3 and Δ ≥ 0.02, or strong; major if z ≥ 2, or moderate; minor if slight, or a batch PSI > 0.25. |
| weak slices that are hard by nature | Δ is read next to the slice's base-rate constant. *Fixable* (major) only if the slice's ℓ̄ lower bound is above that constant's loss; otherwise minor ("hard by nature"). |
| noisy learning curve / active learning | *no-evidence*, never a finding; the offer is "rerun with 5 seeds". |

**Prescriptions (one click, existing actions only).**

| kind | where it leads |
| --- | --- |
| `gym_patch` | Vela's handler; the Gym opens with the change: drop a leak, regularise a family, escalate a preset, refit for `infer_limit`, drop a shifting column |
| `split_twin` | `POST /runs/{id}/split-twin` |
| `labelling_queue` | Explain → Labelling Queue, with `slice_id` for a slice |
| `shift_weights` | `POST …/shift/{key}/weights-version`, whose patch goes to the Gym; used only when ESS ≥ 20 % |
| `register` | Register, with `serve_model` = the best model within the latency budget on F3's frontier |
| `inbox` | Explain → Annotators |
| `open_slice` | Explain → Weak Slices, at the slice |

**Offers** (for missing or no-evidence checks) give the endpoint, method and body:
- learning curve;
- out-of-time twin;
- shift check (time source when there is a date column);
- slice search;
- latency profile.

**API.**
- `GET /api/runs/{id}/doctor?latency_ms&measure_latency&served_p95_ms` (in `vela/api.py`).
  - 404 for an unknown run, 409 for a run that is not finished, 400 for forecast, anomaly or imported runs, 422 for
    latency_ms ≤ 0.
  - Determinism: the smoke calls it twice and compares every check's id, status, severity and reason.
- The run payload carries `doctor` (a summary: primary with its prescription's kind and title, secondaries, missing,
  no-evidence, headline).

**Autopilot (`autopilot/engine.py`).**
- **Layer 1** calls the doctor on the best step's run before each decision. The latency budget is the brief's
  requirement, and the served p95 is Autopilot's own one-row measurement, passed as `served_p95_ms`.
- **Mapping to the menu.** Layer 1 walks the doctor's factors in order and takes the first one a menu action answers:

  | factor | action |
  | --- | --- |
  | latency | reduce_latency |
  | imbalance / weak class | calibrate_threshold or rebalance |
  | budget, underfit | escalate_preset |
  | overfit, leakage, shift | **`apply_prescription`** (new menu action: applies the doctor's Gym patch to the step body) |

- **Fallback.** Factors that no action answers (label noise after the inbox, data-limited) are named in the rationale,
  and then the old fixed order decides.
- **Records.** Every decision stores `doctor` (run, headline, primary, secondaries).
- **Layer 2.** Claude's prompt state gains `model_doctor` (primary, secondaries with reasons and prescriptions, checks
  not yet measured, no-evidence), with the instruction to prefer the action that answers it.

**UI.**
- **Explain → Model Doctor** (`DoctorPanel.tsx`):
  - hero: primary factor, severity, source, secondaries, check counts, the prescription button;
  - the why sentence;
  - evidence numbers, formula and rule;
  - Ranked Factors with prescriptions;
  - Checks To Run (offers, Diagnose Again);
  - Every Check (expand: reason, evidence, formula, rule, source);
  - How The Doctor Decides (the procedure and the reconciliations);
  - Advanced: latency budget, measure latency.
- **Results:** a compact Model Doctor card under the metric cards.
- **Vela sidecar:** the same compact card above the findings; its prescription goes through Vela's patch handler.
- **Autopilot decision log:** "Model Doctor on run_…: <primary> (severity), then …" under each decision.

**Fixed on the way (it blocked the overfit check).** Vela's `bootstrap_se` failed on every binary run with string
labels: AutoGluon's roc_auc / f1 scorers take 0/1. So the bootstrap SE was `None`, and Vela's own overfit finding
never fired on such runs. `findings._score` now maps the labels to 0/1 with 1 = the positive class. After the fix,
Vela reports the optimism on a credit-default run (val 0.8262 vs holdout 0.7698, 3.0 SE). The core smoke's Vela step
is still green.

## Open problems

- **Label noise and an outcome that is random given the features look the same from data alone.** After the overfit
  prescription (KNN → 25 neighbours), the doctor names label noise (critical) on that scenario: its target is a
  logistic coin flip. The reason text now says so, and reviewing the flagged labels is what tells the two apart. It is
  still a finding, not a "hard by nature" verdict.
- **The thresholds were set on a prototype and the six scenarios**, not on real failures:
  - z ≥ 3 / 8;
  - floor lower bound ≥ 0.06 / 0.12;
  - overconfidence 0.05 and ⅓;
  - cleanlab ≥ 5 %;
  - out-of-time z ≥ 2 / 3;
  - ESS ≥ 20 %.

  A hard but clean problem with a confident region that is still impure (5–10 % error at the top) could pass the floor
  test.
- **The learning curve's verdict varies between runs** (the fits are not bit-reproducible). The data-limited scenario
  was noisy at 2,500 rows and data-limited at 3,000. The smoke follows the doctor's "more seeds" offer when it is
  noisy rather than loosening the check.
- **The doctor reads the latest of each result** (one learning curve, shift check and slice search per run). A stale
  result stays in force until it is rerun. The diagnosis is computed when the page asks for it (Explain, Results,
  Vela, Autopilot), not pushed at the end of a run.
- **Leakage depends on Vela's check**, which needs the permutation importance. That is off in Autopilot's runs, so
  Autopilot cannot see a leak.
- **Regression and quantile runs** get no label-noise or overconfidence check. Overfit there is the gap alone.
- **Partial coverage of the reconciliations.**
  - The weak-slice reconciliation (base-rate constant) and the underfit path (saturated + constant predictions) are in
    the code but are not one of the six smoke scenarios.
  - The annotations path (F14 consensus changing ≥ 5 % of labels) is read but not exercised.
- **Register cannot be pre-filled from a URL.** The latency prescription's Register button opens Register for the run,
  not with `serve_model` pre-selected; the body is in the API answer.
- **Autopilot rarely has a patchable factor on support-tickets.** It prescribes only what its menu can do; label noise
  (after the inbox) and data-limited have no menu action, so the fixed order still decides those steps. This is said
  in the rationale.
