# P01: schema, backfill and dependencies (lane D)

Plan: `docs/plans/data-platform-final.md` §2.1, §9.1 row P01, §11. Base: `motion-components` @ 6c94d6c.

## What was built

- **The §2.1 DDL, in `catalog/schema.py migrate_p01()`**, called at the end of `migrate()`:
  - every new table and index, created with `IF NOT EXISTS`;
  - every added column (`projects`, `datasets`, `runs`, `audit_log`), added only when missing;
  - the immutability triggers on `splits`, `version_tables`, `table_files`, `run_inputs` and `blobs`.
- **Step ids** are recorded once in `catalog_meta` as `step:p01_ddl`, `step:p01_lineage_check`,
  `step:p01_team_default` and `step:p01_backfill`, using `INSERT OR IGNORE`. A later start leaves them as they are.
- **`ds_hash_ro` is not created.** It belongs to P10.
- **`audit_ro_u` / `audit_ro_d`** are created only after the P01 backfill has written `audit_log.team_id`. That
  backfill is the last UPDATE `audit_log` will ever get.
- **lineage CHECK rebuild.** It runs once, when the stored SQL has no `join_frame`, inside one transaction, and keeps
  the ids:
  - kinds now include `join_frame`;
  - relations now include `joined_from` and `merged_from`;
  - `inferred` already existed.
- **`tm_default`** is seeded in `migrate()`, because the write hooks need it as a foreign-key target before the
  backfill runs.
- **`backfill_p01()`** follows §2.1 steps 1–6. It is idempotent and runs from `main.catalog_backfill` after the P1 and
  F-P2 backfills:
  1. The projects are put in `tm_default`.
  2. **Principals.** Names are collected from:
     - `audit_log.actor`, `datasets.created_by` and `runs.config.by`;
     - `dataset_requests`, `version_requests`, `admin_requests` and `champions` (requested, decided and used by);
     - `ENSEMBLE_ADMINS`.

     There is one principal per `governance.identity_key`, with a deterministic id `pr_` + sha256(key)[:12].
     `system` gets `kind='system'` and no membership. Admins become **owners** of `tm_default`; everyone else
     becomes a **member**.
  3. **`dataset_roots`** is filled from the root rows and `dataset_cards`. The state comes from the versions, with
     the same rule as `dsets.dataset_state`.
     - `ux_roots_name` allows only one live name per project.
     - If a second root has a clashing name, its `dataset_roots.name` gets ` (<root id>)` appended.
     - `datasets.name` is not touched. No row clashed here.
  4. **Versions.**
     - `version_no` is set in `created_at, rowid` order per root, which is the same order as the history's `v`.
     - `team_id`, `n_cols`, `legacy_sha256 = sha256` and `storage='csv'` are also filled.
     - `next_version_no` is set to max + 1.
  5. `runs.team_id` comes from the run's dataset.
  6. `audit_log.team_id` comes from `details.dataset_id`, or else `details.root_id`.
- **Write hooks keep new data in step** (`catalog/store.py`, outside the P01 file list, kept minimal):
  - `record_root_dataset` and `record_version` call `S.sync_version`, which:
    - creates the `dataset_roots` row;
    - allocates `version_no` from the root;
    - sets `team_id`, `n_cols` and `legacy_sha256`.

    The same `UPDATE` clears `version_no` when a dataset changes root, so `ux_versions_no` cannot collide.
  - When a dataset was its own root and then became a version, its stale `dataset_roots` row is removed before
    `drop_if_phantom`.
  - `record_run` sets `runs.team_id`.
  - `move_dataset_tree` moves the root row's project and team, and the team ids of the versions and runs.
- **`catalog/dsets.py`**:
  - `card()` reads `dataset_roots` and falls back to `dataset_cards`. `search()` does the same.
  - Every card and default write goes to both tables through `_write_card`.
  - A rename updates `dataset_roots.name`.
  - Archive and delete sync `dataset_roots.state`.
  - `tree_rows` and history return `version_no`, `team_id` and `storage`. The positional `v` is unchanged.
- **`drop_if_phantom`** also treats a project as in use when a `dataset_roots` row refers to it (the foreign key).
- **`reset.py`** (outside the list, minimal):
  - It deletes the new tables that refer to `datasets` and `projects` before those tables.
  - It drops `splits_ro_d` around the delete and recreates it afterwards.
  - Teams, principals and blobs are kept.
- **Dependencies**:
  - `duckdb==2.0.1` is added to `requirements.txt` and `requirements.lock`.
  - `pyarrow==24.0.0` is now pinned explicitly in `requirements.txt`. The lock version is unchanged; only its
    `# via` comment was updated.
  - `uv pip install --dry-run -r requirements.lock` reports "Would make no changes" on the installed venv.
  - `duckdb 2.0.1`, `pyarrow 24.0.0` and `pandas 2.3.3` import together.

## Deviations and notes for dependants

- **Files outside P01's list:**
  - `catalog/store.py`: the write hooks. Without them, new versions would get no `version_no` or root row.
  - `reset.py`: foreign-key order.
  - `main.py`: a 5-line addition to `catalog_backfill` (lane R also edits `main.py`, in its handlers).
- **`dataset_cards` is still a table**, written alongside `dataset_roots`. Turning it into a VIEW is left for the
  release that drops it.
- **Principals are created only by the backfill.** A name first seen after P01 (Dee above) gets no principal yet.
  P18 owns creating principals at request time.
- **`dataset_roots` rows are deleted in one case**, by `sync_version`: a dataset that was its own root becomes a
  version of another. This is safe now because nothing refers to a root row yet. Once `joins`,
  `dataset_root_tables` or `column_tags` rows exist, P05/P06 should create versions through the VersionWriter
  rather than through this re-root path.
- **`ux_roots_name` clashes** are resolved by appending the root id to `dataset_roots.name`. None occurred on this
  data.
- **The SQLite triggers are SQLite only.** P23 carries them to Postgres.
