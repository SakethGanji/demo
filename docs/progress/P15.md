skew), §11. The input record follows Brief C §4.6 (`docs/plans/C-teams-governance-flows.md`).

**Base:** `motion-components` @ 3926c4c. Merged with P21, F-JOBS and P24/F-PII tracker notes (fcf8357) before the push.
After the merge, the chain was run on both engines and its output was the same.

## Result

- **Registering a P14 join run works.** The build gets a first step, `parity`.
  - The frame is rebuilt from the run's pinned inputs with `frames.materialise`, the one join path. Training used it,
    and batch scoring uses it too.
  - The rebuilt frame is compared with the training frame by `__row_id`, every cell. Here they are byte-equal.
  - After the deploy copy, the version scores the rebuilt frame's holdout rows. Its predictions must equal the ones it
    made on the training frame: 800 rows, max |Δ| = 0.
- **`/card` shows the input record (C §4.6)** in its Data section:
  - the frame;
  - the dataset (team and project);
  - the version, with its contract and certification;
  - three tables: role, version, rows, sha, source file, uploaded by;
  - the join: id, name, spec version, `spec_sha256`, `spec_frozen`, coverage;
  - the split, PII features and protected columns left out;
  - parity `ok`.

  `hashes` gains `inputs: [{table, dv, sha256}]` and `join: {id, spec_sha256}`. `data_file` names the join frame.
- **Batches.** `POST /registry/versions/{v}/batches` with 3 files (`files=` × 3) is scored.
  - The saved join is applied to the files with `frames.materialise`.
  - 500 grain rows give 500 frame rows and 500 scored rows (`rows_equal_grain: true`).
  - The check script compared the batch frame with the training frame's rows for the same `app_id`: every cell equal.
    The scored probabilities equal the predictor's on those training rows (max |Δ| 4.99e-07, from the 6-decimal
    rounding in `scored.csv`).
- **Dropping a column** from one batch file gives 400 `batch_column_missing`, naming the file, the table and the column.
  A missing file, an unknown file, or two files for one table also get a 400, each with a code.
- **`/monitoring` works** on the join version. After a second batch there are two points. The retrain proposal says
  how a join model retrains, instead of building a single-table window (see the deviations).
- **`GET …/inputs.zip`** holds `manifest.json` (the input record and parity), `hashes.json`, `contracts.json`,
  `join_spec.json` and `README.txt`. It holds no rows; checked by searching it for ids from the data.
- **A single-table model is unchanged.**
  - It registers with parity `not_applicable` and an input record with one table.
  - It batch-scores one file, and two files get a 400.
  - Monitoring and `inputs.zip` work (no `join_spec.json`).
- **A tampered join cache blob** (one byte flipped) refuses registration with 409 `parity_mismatch`. The message names
  the recorded and current sha, the refusal is audited as `register_refused`, and no version is created. A tampered
  pinned input (the bureau table's blob) gets the same 409, naming the input. With the bytes restored, it registers
  with parity ok.
- **Approve and promote stay human, with four eyes.**
  - The registrant's own review gets 409, and their own move to Production gets 409.
  - A second person approves and moves the version to Staging.
  - Production then needs the Doctor leak question's `override_reason`; the gate is unchanged by P15.
- **SQLite and Postgres 16 give the same output.** With ids masked, the two outputs differ only in:
  - the fitted model's sha;
  - `hashes.splits_sha256`: the run's split view file, which names its random split id. The input record's
    `split.sha256` is the same on both;
  - the zip's size by 3 bytes, from those hashes.

## What was built

| Piece | Where | What it does |
|---|---|---|
| **Input record** (C §4.6) | `registry/build.input_record` | Built at registration and frozen in `model_versions.result.inputs`. It holds:<br>• `frame`: `join_frame` id, cache sha, `frame_sha256`, rows; or the table;<br>• `dataset`: root, name, team, project;<br>• `version`: dv, v, created_by, reason, contract (`datasets.contract_result`), active certification;<br>• `tables`: name, role, dv, sha256, rows, `source_file`, `uploaded_by`/`uploaded_at`, `from_dv` (carried tables are followed back to the version that wrote them), and `dataset` for another root's input;<br>• `join`: id, name, spec_version, spec, `spec_sha256`, `spec_frozen`, coverage (`joins.validate` now);<br>• `split`: id, key, sha256, target, strategy;<br>• `pii_features` (`column_tags` pii_* mapped through the spec to frame columns; aggregates are not mapped);<br>• `excluded_protected`.<br>Counts and hashes only. |
| **Serving parity** | `registry/build.serving_parity`, `prediction_parity` | These checks, in order:<br>• the spec is the pinned one (`spec_sha256` re-computed);<br>• the training frame's cache file is re-hashed against `cfg.join.cache_blob`;<br>• every pinned input is re-hashed (`joins.check_inputs`);<br>• `frames.materialise(spec, pinned lake tables)` → `serving_frame.parquet`;<br>• one DuckDB `FULL OUTER JOIN … ON __row_id` gives row counts, unmatched ids and per column `IS DISTINCT FROM` counts; column sets and types are compared, and `byte_equal` is reported.<br>Then the version's predictions on the rebuilt frame's holdout rows must equal `holdout_predictions.csv`: the same ids, labels equal, |Δp| ≤ 1e-9.<br>Recorded as `result.parity` (`status ok / mismatch / not_applicable`, `summary`, details). A mismatch fails the build (`serving parity mismatch: …`), audited as `register_refused`. |
| **Registration gate** | `build.register_gate`, `api.register` (one hunk) | For a join run, the frame-level parity runs before a version is created. A mismatch gives 409 `{code: parity_mismatch, message, parity}`, audited `register_refused` on the run. The build repeats the check and adds the prediction comparison. |
| **Hashes** | `build_version` / `build_other` | `hashes.inputs`, `hashes.join`, and `data_file` = the join frame. `frames.path_of` raises for a join frame, so a P14 join run could not have registered before. |
| **Multi-file batches** | `api.create_batch` (`file` and/or `files`), `api.submit_join_batch`, `scoring.join_batch_frame` | **Matching files to tables:** each file is matched to an input table by its stem, case-insensitive. A workbook with more than one sheet gives one table per sheet.<br>**Checks on each file:** its pinned table's schema (`lake_table(Table(v, t)).schema`). The grain may omit the label and `drop_columns`.<br>**Casting:** each column is cast to the pinned kind in pandas, then `TRY_CAST` to the pinned type in DuckDB. Cast failures are counted per column.<br>**Joining:** `__row_id` 0…n-1, then `frames.materialise`, whose grain assert gives 400 `batch_grain_violated` when a batch's n:1 table repeats a key.<br>**Scoring:** the frame goes through the usual `score_batch`: drift, reasons, recourse, shadow.<br>**The summary's `join`:** per table file, rows, sha and cast failures; plus grain_rows, frame_rows, `rows_equal_grain` and spec sha.<br>The batch directory keeps `tables/*.parquet` and `join.json`.<br>**400 codes:** `batch_column_missing` (`table`, `file`, `columns`), `batch_table_missing`, `batch_table_unknown`, `batch_table_twice`, `batch_empty`, `batch_grain_violated`, `ambiguous_tables`. |
| **Card** | `card._inputs_section`, `_inputs_md` | `data.inputs` and `data.parity`, plus a **Data used in development** block in md/html. A version registered before P15 gets the record computed at read time, with `recorded: false` and parity `not_checked`. |
| **inputs.zip** | `card.inputs_zip`, `GET /registry/versions/{vid}/inputs.zip` (`model.read`) | `manifest.json`, `hashes.json`, `contracts.json` (each input version's contract result and certifications), `join_spec.json` and `README.txt`. `rows_included: false`. |
| **Monitoring** | `monitoring_api._proposal` | A join model's retrain proposal is `ready: false`, saying to commit the window's tables as a new version and train on the same join. GET `/monitoring` needed no change: `_train_frame` reads the join frame. |

## Deviations and notes for dependants

- **Parity compares every grain row, not 1,000.** The plan (§7 risk 11) re-materialises 1,000 grain rows. Here the
  whole frame is rebuilt and compared in DuckDB, which streams through the job connection. The rebuild is the same cost
  as the frame was (P14: 3–10 s at 10M rows), and the comparison is one join.
  - It runs twice: in the registration gate (so a mismatch is a 409, not a failed build) and in the build (which adds
    the predictions). At 10M rows that adds up to ~20 s to a registration.
  - The prediction comparison uses the holdout rows only.
- **The batch format.** It is one file per input table, named after the table (`applications.csv`, …), sent as
  `files` (repeatable). A workbook with one sheet per table also works. `file` stays for single-table models.
  - The 400 is synchronous: the join is applied in the request, in a thread. Then the scoring runs on the heavy pool
    as before.
  - Batch sizes are capped by `MAX_UPLOAD_BYTES` per file.
- **The label column is carried into the batch frame as missing.** The frame keeps the training schema, so `defaulted`
  appears in `extra_columns`, as does `app_id`.
- **A join model is not retrained from batch windows.** The monitoring retrain proposal (single-table windows) is
  `ready: false` with an explanation. Building a window as a new version of the input tables belongs with U2 / a
  follow-up.
- **Old versions.** A version registered before P15 has no frozen record. The card and the zip compute one at read
  time (`recorded: false`) and show parity `not_checked` for a join run.
- **PII mapping.** `pii_features` maps grain and n:1 columns through the spec. An aggregate over a tagged column is not
  flagged (no tags exist in the sample). `excluded_protected` lists protected-tagged columns of the input tables that
  are not features.
- **Contract and certification** are read from P21's `datasets.contract_result` and `certifications`. In the sample
  they are none/none. `require_certified_inputs` (P21) was not touched.
- **Files.** Only the five row files were changed. `registry/api.py` has three small hunks: the register gate, the
  batch route accepting `files`, and the `inputs.zip` route. These are next to P21's work: merge carefully.
- **The UI was not touched** (U2: the batch form needs a file per table, plus the card's Data section and the
  `inputs.zip` link), so there was no `npm run build`.
- **Note for every lane:** don't `git pull` under a running API. A worker thread imported a merged `jobs` module
  mid-run (a `finish(… attempt=…)` TypeError). The chain was re-run on both engines from fresh processes.
- The scratch data dirs, the Postgres cluster and the API processes were removed or stopped. The venv is in the
  session scratchpad only.
