# P22: durable job queue + `workerd` (B §5.5)

Lane O. Row §9.1 P22: runner, heavy pool, review, Feature Lab, active learning and learning curve run on a DB-backed
queue with leases, a janitor and fair share. The queue is portable to Postgres: `FOR UPDATE SKIP LOCKED` there, the
same statement inside `BEGIN IMMEDIATE` on SQLite.

**Done when: "no work dies with the API process".** Met, and verified below:
- fits, learning curves, labelling queues, Feature Lab searches, reviews, registry builds and batch scores all run on
  workers;
- agent turns are leased by the API process itself and resumed by the next one.

### Queue semantics (`jobs/queue.py`)

- **Claim:** one statement, `UPDATE jobs … WHERE id = (SELECT … LIMIT 1 {FOR UPDATE OF j SKIP LOCKED}) AND status='queued' RETURNING *`.
  - **SQLite:** inside `BEGIN IMMEDIATE`.
  - **Postgres:** a transaction advisory lock per resource class (`pg_advisory_xact_lock(hashtext('ensemble.jobs.claim.<r>'))`) comes first. Without it, simultaneous claims cannot see each other's uncommitted leases, and fair share was exceeded in the Postgres check below (team A got 3 slots against a cap of 2). Each claim is about 1 ms.
- **Fair share:** candidates are ordered by the team's current leases of that resource (ascending), then priority, then age. A team already at `team_cap` is skipped while another team has queued work there. `team_cap` = half the live workers' slots of the resource, at least 1; `ENSEMBLE_TEAM_MAX_SLOTS` overrides it.
- **Leases:** 60 s, extended every 20 s (`ENSEMBLE_JOB_LEASE_S`, `ENSEMBLE_JOB_HEARTBEAT_S`). Every 2 s the holder checks its row and stops the job if it was cancelled or lost.
- **Janitor** (every worker and the API, every 10 s):
  - an expired lease is re-queued while `attempts < max_attempts` (default 2), otherwise failed, and the kind's `on_dead` hook closes the run, curve, review or build;
  - on the **same host**, a lease whose worker pid is gone is released at once (worker ids are `<role>-<hex>@<host>:<pid>`). `ENSEMBLE_JOB_PID_CHECK=0` turns this off, so only the lease decides, as across hosts;
  - worker rows silent for 3 leases are deleted.
- **Give-back:** a worker stopping cleanly (SIGTERM, or the API shutting down) re-queues its jobs, and that does **not** use up an attempt.
- **Times:** ISO-8601 UTC text from the app, one fixed format; there is no `now()` in SQL.
- **Parameters:** written `:name`; `_sql()` rewrites them to `%(name)s` when `db.dialect == "postgres"`.

### Postgres 16 (scratch instance) and SQLite: the same queue code

I used a minimal psycopg shim (`dialect = "postgres"`, `connect()` yields a psycopg connection with `dict_row`), the
§2.1 DDL for `jobs` / `workers`, and 2 workers × 2 train slots (`team_cap` 2). Team A queued 6 jobs, then team B queued 2.
Four claims ran on 4 threads at once.

```
                      Postgres 16                          SQLite 3.53
4 concurrent claims:  ['a0','a1','b0','b1'] distinct       ['a0','a1','b0','b1'] distinct
leased per team:      {'tm_A': 2, 'tm_B': 2}               {'tm_A': 2, 'tm_B': 2}
heartbeat:            ok → after cancel: cancelled         ok → cancelled
finish:               True {'ok': 1}                       True {'ok': 1}
janitor (lease set 1 s in the past): requeued, status queued   same
```

Before the advisory lock, Postgres gave `['a0','a1','a2','b0']`, and the `:s0` parameter rewrite failed. Both are fixed.
The SQL as sent ends in `LIMIT 1 FOR UPDATE OF j SKIP LOCKED) AND status = 'queued' RETURNING *`.

### Follow-up: P08's profile job on the queue (`lake/stats.py`)

- `stats.schedule()` now queues a `profile` job (resource `duck`, `ref_kind` `table_stats`, `ref_id` the table
  content) instead of using an in-process thread.
- Duplicates: one live job per table content; within a process the check-and-enqueue holds the module lock, and across
  processes a duplicate is a no-op because `run()` finds the stats.
- `ensure(wait_s)` waits through a handle that polls the job, then reads the stored stats.
- `status()` also asks the queue.
- `run()` checks the database, not the process cache, so a long-lived worker never skips a store.
- If no queue can be written, the old thread runs it.

## Deviations and notes for dependants

- **Files outside the row (small, no other lane in them now):**
  - `jobs/api.py` (new, read-only routes);
  - `main.py`: the lifespan hunk (HeavyPool gets `db`, `bind()` calls, the embedded worker, stop with give-back) and
    one `include_router`. P08's `main.py` areas (rows, health) are untouched;
  - `featurelab_api.py`: the route split into `_prepare` + `run_job` / `on_dead`;
  - `registry/store.py` `recover()`: skips rows with live jobs.
- **`engine/worker.py` is untouched**, `data_gate` included. Only its caller (the runner) changed. P09's `split_pin`
  is in the run's `config.json`, which the worker reads from disk; the job payload is only `run_id`, so it arrives
  intact.
- **`lake/stats.py` (P08's)** was changed at the orchestrator's request: `schedule`, `status`, `run`, and the new
  `run_job` / `_JobHandle`.
- **Lanes P08/P09:** I touched none of their files or functions.
- **The fit's anchor** is now the worker's pid (`<run_dir> <pid> anchor`), not the API's. Under dev reload with the
  embedded worker it is still the reloader.
- **Re-lease = start again** for `train`, `lc`, `al`, `featurelab` and `heavy`. The fit writes its own events and
  result, and a second attempt overwrites the first (`run_requeued` marks it). The only resumable kinds are `review`
  (journal) and `agent` (timeline). This is B §5.5's list.
- **Review POSTs over HTTP** retry only on connection refused. Another transport error mid-POST fails the review rather
  than risk posting an experiment twice. GETs retry for up to 600 s.
- **`mem_mb` is 0** for every job until P11's estimator. The claim already filters on `mem_mb <= free`, and a worker
  can declare `mem_mb=N` in `--slots`.
- **Not moved (outside the row):**
  - `annotations_api`, `shift_api`, Data Doctor's label job and Autopilot's own threads still run in the API process
    as before;
  - Autopilot's waits on the heavy pool stay interactive.
- **For P23:**
  - `queue.py` reads `db.dialect` (`"postgres"` switches on the parameter rewrite, `SKIP LOCKED` and the advisory
    lock);
  - every statement goes through `db.connect()`, and rows are read as mappings;
  - `RETURNING` and `ON CONFLICT … DO UPDATE` are used on both engines;
  - times stay TEXT. If §2.2 makes them `timestamptz`, compare with typed parameters instead of strings.
- **A workerd imports `app.main`** for Feature Lab's `_detail`. That builds the FastAPI object, including the lake
  self-check, but runs no lifespan.
- **Scratch:** the venv, data dirs, the Postgres instance (`/tmp/p22pg`, which the postgres user could not reach under
  the scratchpad), the reloader stand-in and all API/worker processes were removed or stopped. No predictors or seeds
  were added to the repo.
