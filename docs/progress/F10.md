# F10 · Reason codes (adverse action)

Status: **done. `SMOKE_ONLY=reasons,core,samples make smoke`: 29/30 green in 322 s. The one failure was F3's
text-sample latency step ("no model faster than WeightedEnsemble_L2's one-row p95"), which depends on timing. Run alone
straight afterwards, `SMOKE_ONLY=samples` passed 3/3. `npm run build` passes.**

**Acceptance.** The credit-default batch (the 2,400 holdout rows, scored by the registered version) has 517 adverse
decisions at the version's threshold t = 0.0910 (F7 cost).
- **515 of them carry 4 reason codes.** The other 2 carry 3, because only 3 features push those applicants toward
  default. A feature with φ ≤ 0 lowers the risk, so the product never cites it. The smoke asserts
  `codes = min(4, features with s·φ > 0)` on every row. The acceptance asks for 4 on every row; the real figure is
  515 of 517.
- **Every code agrees with the SHAP signs.** Every cited φ is > 0, and the codes are ranked by φ.
- **The batch's codes are the online path's codes.** They equal `/score`'s codes for the same rows, and Try It's.
- **The codes hold up against a high-precision estimate of the same game.** With 4,096 coalitions, every one of 132
  cited features also has φ > 0.

## Cause

Before F10, Try It showed the top 5 |φ| from Kernel SHAP for one row, which took about 1–3 s. Nothing produced
adverse-action reasons:
- nothing tied them to the served decision or its threshold;
- there were no plain-English statements and no codes;
- batch output had no reason columns;
- there was no stability check.

Kernel SHAP as Try It ran it (B = 50 background rows, 2,048 coalitions) costs about 100,000 model calls per row. On
credit-default's ensemble that is 0.8–2.8 s per row, too slow for batches.

## What changed

**The engine (`backend/app/engine/reasons.py`, new).**

The decision rule:
- `adverse ⇔ ŷ = the adverse class`, where ŷ is the served predictor's own `predict` at its own `decision_threshold`.
  That threshold is the one calibrated at training, on cost for an F7 run.
- The adverse class defaults to the positive class.
- The push toward adverse is aⱼ = s·φⱼ, with s = ±1.
- The codes are the top K = 4 features with aⱼ > 0, ranked by aⱼ.

The game is interventional SHAP of P(positive):
v(S) = (1/B) Σ_b f(x_S, b_S̄).

**Reference applicants.** By default the background is training rows that the served model *approves* (about 3,000 of
a 4,000-row sample on credit-default). So φ₀ = E[f | approved], and each reason says how this applicant differs from
approved ones. This is the usual adverse-action question. Against the whole population instead (φ₀ = base rate),
fewer features push a near-threshold applicant up. In the first runs 2 of ~600 adverse rows had fewer than 4 codes
with that reference. It can be switched to `population` per model.

**Two estimators, both on the served predictor's own `predict_proba`**, so both work on the F3 deployed copy with its
pruned pipeline:

- **`tree`: exact interventional TreeSHAP** (`shap.TreeExplainer(..., feature_perturbation='interventional',
  model_output='probability')`).
  - It applies when the served model is LightGBM, bagged LightGBM (the mean of its folds) or a weighted ensemble of
    those, and every feature it reads is a raw numeric column passed through 1:1.
  - SHAP is linear in the model, so φ(Σ wₘ fₘ) = Σ wₘ φ(fₘ). On a 1:1 numeric pipeline the game over AutoGluon's
    features is the game over the raw columns. The values are therefore exact for the served model.
  - It is checked on every call: f(x) = φ₀ + Σφ must hold to 1e-6, or the row falls back to Kernel SHAP and the
    reason is recorded.
  - It does not cover categorical splits. shap mishandles LightGBM's categorical splits (an additivity error of 0.048
    in a test), so models with them fall back.
- **`kernel`: Kernel SHAP for any model, vectorised over rows.**
  - Coalitions are allocated the way shap's KernelExplainer allocates them. Sizes are taken in pairs from the edges
    (|S| = 1 and d − 1, then 2 and d − 2, and so on); a pair whose coalitions all fit the budget is enumerated with
    its exact Shapley-kernel weights. The rest of the budget is sampled in complementary pairs. The seed is fixed and
    shared by every row.
  - One `predict_proba` call scores the R·M·B hybrid rows of a chunk.
  - The constrained weighted least squares is solved in closed form for all rows at once, so f(x) = φ₀ + Σφ exactly.
  - The default is B = 16 and M = 128: 2,048 model calls per row, against about 100,000 for Try It's SHAP.
  - All 2^d − 2 coalitions fit the budget ⇒ exact Shapley values.

**Reasons and statements.**
- Statements come from a mapping table per registry model:
  - a code (R01…);
  - "high" and "low" statements for numbers;
  - `{value}` templates for categories;
  - a "missing" statement.
- A number uses "high" when xⱼ ≥ the reference median. A monotone-constrained feature always uses the side its
  constraint makes adverse.

**Monotone constraints (F8).**
- For one background row b, the Shapley value ψⱼ(x, b) is a weighted sum of f(xⱼ, x_S, b_rest) − f(bⱼ, x_S, b_rest).
  If f is monotone with sign sⱼ in xⱼ, each term has the sign sⱼ·sign(xⱼ − bⱼ).
- φⱼ = (1/B) Σ_b ψⱼ, so:
  - **(i)** a constrained feature pushes toward a higher score only through reference applicants it exceeds (for ↑).
    Its statement direction is therefore fixed ("too high"), never inferred from the data.
  - **(ii)** if xⱼ ≥ max_b bⱼ then sⱼ·φⱼ ≥ 0, and if xⱼ ≤ min_b bⱼ then sⱼ·φⱼ ≤ 0.
- (ii) is checked on every explained row and the violations are reported. In the smoke there were 0, with 54 rows
  above the background.

**The stability check.**
- On the adverse holdout rows, every numeric input becomes xⱼ + ε·σⱼ·z (ε = 0.05, σ the reference applicants'
  standard deviation). The codes are recomputed with the same coalitions and background (common random numbers).
- It reports, for the top-4 set: unchanged, first reason unchanged, same order, mean Jaccard, and decision flips.
- It also compares the fast estimator with the same game estimated with 4,096 coalitions.

**API (`registry/api.py`, `registry/scoring.py`).** Everything runs in predict workers. A per-worker `Reasoner` is
cached by the predictor's files and the mapping.
- `GET /registry/versions/{id}/reasons`: the adverse class, t, the reference, the method chosen for the served model,
  and the mapping.
- `PUT …/reasons`: edits the mapping, the adverse class, the reference or `top_k`.
  - It is stored per model in `registry/reasons/<model>.json` and audited as `reason_codes_edited`.
  - Unknown features, duplicate codes and unknown classes → 400.
- `POST …/reasons/stability`: stored beside the version in `reasons_stability.json`.
- Try It adds `reasons`, from the same estimator as batch, so the codes on a notice match Try It.
- `POST …/score` takes `reasons: true`, which runs in a worker even when prediction is in-process. It also takes
  `reasons_reference: true` for the 4,096-coalition audit.
- Batch scoring of a binary version adds these columns:
  - `adverse`;
  - `reason_factors` (the number of features with s·φ > 0);
  - `reason_k_code`, `reason_k`, `reason_k_feature`, `reason_k_phi` for k = 1…4.
- The batch's `summary.reasons` records:
  - rows/s and set-up time;
  - the method used;
  - the largest additivity error;
  - whether the codes agree with the SHAP signs;
  - the monotone check;
  - the codes per row;
  - the most cited codes.
- Progress shows the rows explained so far and rows/s.

**Model card.** The section 5 subsection "Reason codes (adverse action)" contains:
- the rule bound to t and the classes;
- the reference applicants and the method;
- the mapping table;
- the stability and the estimator check;
- the latest batch (rows/s, sign consistency);
- the monotone note.

It appears in JSON, Markdown and HTML.

**UI.**
- **Registry → version → Reason Codes** (new tab, binary versions only):
  - the rule as notation bound to the version's numbers: adverse ⇔ ŷ = Yes ⇔ p̂ ≥ t; aⱼ = s·φⱼ; v(S); f = φ₀ + Σφ;
  - every symbol defined;
  - chips for the method, B, M, d and model calls per row;
  - the reference toggle (approved / everyone);
  - why TreeSHAP does or does not apply;
  - the monotone argument;
  - the editable mapping table, saved per model;
  - the stability check with its five numbers and the estimator check.
- **Try It:** a Reason Codes card with adverse / not adverse at p̂ vs t, and the codes with statements, values and
  φ. Beside it stays the existing Top Reasons (population SHAP, |φ|), with a note on why the two can differ.
- **Batch & Drift:** a "reason codes" cell (adverse count, method, rows/s, most cited). The scored CSV and the
  preview carry the columns.
- **Model card:** the section above.

## Open problems

- **The kernel estimator is sampled.** With d = 12 and M = 128, its top-4 set matches the exact game on 84% of rows.
  The mismatches are near-ties at ranks 4–5 (mean overlap 0.96). M is a constructor parameter (`FAST_COALITIONS`)
  and is not exposed in the UI; M = 512 halves the throughput. Most of the "stability" loss under noise (80%
  unchanged) is of the same size, so it mixes model sensitivity with estimator noise. The common random numbers
  limit, but do not remove, the estimator noise.
- **TreeSHAP coverage is narrow.** It covers only LightGBM on raw numeric columns. These fall back to Kernel SHAP:
  categorical splits, XGBoost's one-hot columns, CatBoost (shap's interventional mode does not support it), date
  parts, n-grams and stack levels. An exact grouped-feature TreeSHAP would be needed for those.
- **Fewer than 4 codes.** An adverse row can have fewer than 4 features pushing toward the adverse class: 2 / 517
  here, and 37 / 530 for the 8-feature LightGBM. The product returns fewer rather than citing a factor that lowers
  the risk. `reason_factors` says why.
- **The statements are templates.** The direction is chosen by the reference median for unconstrained numbers. They
  need compliance review before use in notices. There is no "insufficient credit file" style reason for missingness
  beyond the per-feature "missing" statement.
- **The mapping is per registry model and keyed by feature.** A new version with renamed features gets default
  codes for them. Old entries are kept and ignored.
- **Unrelated, seen but not fixed.** F3's text-sample one-row latency smoke step depends on timing. It failed once in
  the combined run, 18.2 ms with no faster model found, and passed when rerun alone.
