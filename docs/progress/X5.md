## Verdict: **not done**

The governance fixes, the X1–X4 criticals and majors, the migration and the UI hold. Three new critical findings block "done":

1. **K1. A model trained on a 10M-row table cannot be registered.** `build_version` reads the whole table into pandas to pick the holdout rows. The heavy-pool child is OOM-killed at 12.6–13.5 GB, for the single-table run and for the join run, so the 10M parity gate cannot run.
2. **K2. The Model Doctor OOM-kills the heavy pool on any 10M run, and it fires by itself after every fit.**
   - It reads the whole table: `vela/doctor.py:147`, `vela/missing.py:456`.
   - Measured peaks: 7.4, 8.0 and 10.5 GB.
   - After the kill, the GET hangs forever.
   - Every later durable heavy job (registry builds, batch scores) fails at once with `BrokenProcessPool` until the API restarts.
3. **K3. On Postgres, one request with a NUL in a name field breaks dataset history for every dataset, permanently.**
   - Any caller can do it, even with a request answered 400, because the would-deny audit row keeps the NUL and Postgres then cannot read the audit table.
   - The audit table is append-only, so the break survives a restart.

The major list is below. The ones that matter for "done":
- an edit can still drop a declared key or relation silently (X3 M1, through `POST …/edit`);
- `POST /admin/lake/sync-s3` without a bucket stops the API from serving;
- the Autopilot audit's memory is unbounded (≥ 10 GB on 12k rows);
- SIGTERM is ignored while the heavy pool is busy;
- NaN / 1e400 in any pydantic body → 500 on 54 routes;
- the first 10M edit preview holds a request for 51 s at 3.2 GB.

**Confidence.**
- **Core flow: 0.65.** At POC scale (≤ ~1M rows) it is about 0.9: every chain, repro, replay and walk passed. At 10M, train → register → serve does not complete (K1, K2).
- **Governance: 0.80.** Authz, masking, purge, agent, audit chain and holds all hold on every engine × mode. K3, S1 and N1 are the gaps.

## 2. Findings

### Critical

**K1. A model trained on a 10M-row table cannot be registered: the build OOMs in the heavy pool.**
- **Repro** (`scale/scale.py`):
  1. Upload the 10M seed.
  2. `POST /runs {dataset_id, label: "y", time_limit: 60, frame_budget_mb: 300}` → succeeded (rows_used 480,807).
  3. `POST /runs/{id}/register {created_by, model_name}` → 202 `building`.
- **Result:**
  - `dmesg`: `Killed process … anon-rss:13509124kB` (single-table run); `12624132kB` for the join run.
  - The job fails with `BrokenProcessPool`. The version stays `building` until the API restarts (then `failed`).
- **Cause (by reading):** `registry/build.py:245` → `serving.holdout_frame` → `frames.read(ref)` of the **whole** table (`engine/serving.py:144`), then `df.iloc[holdout]`. The `expected_loss` / `survival` / `multilabel` / `segmented` branches do the same (`build.py:666–759`).
- **Impact:** §7 risk 4 and risk 11 at scale. P11's "batched holdout scoring" isn't used by the build; the 10M serving-parity gate cannot run.
- **Fix:** read only the holdout rows (`__row_id` semi-join, batched) and the run's recorded frame; never the table.

**K2. The Model Doctor reads the whole table in the API's heavy pool. At 10M it is OOM-killed, the request hangs, and the pool stays broken for durable jobs. It runs by itself after every fit.**
- **Repro:**
  - `GET /api/runs/{10M run}/doctor` → pool child killed at anon-rss 7.37 GB (`dmesg 3014.9`); the request has no answer after 10 min.
  - The automatic `warm_doctor` (`runner.poll_finished` → `vela.api.warm_doctor`) killed the pool child at 8.00 GB after run_b26bb90e, and at 10.46 GB after the join run.
- **Cause:**
  - `vela/doctor.py:147` (fit gap) and `vela/missing.py:456` (gap analysis) call `frames.read(frames.resolve(cfg))` and ignore the run's sample.
  - `engine/pool.py:157 run_job` submits durable jobs straight to `pool._executor()`, so after one kill every registry build and batch score fails at once: "the process pool is not usable anymore" (`scale/api log`, job jb_a5b916f0576f).
- **Impact:**
  - Any fit on a big table takes the heavy pool down a few seconds after it succeeds.
  - SHAP, predictions, monitoring, builds and batches then fail or hang until a restart.
  - SIGTERM then doesn't stop the API either (J4).
- **Fix:** run the doctor's train-side checks on the run's recorded frame or sample; replace a broken executor in `run_job`; give heavy calls a timeout.

**K3. Postgres: one request with a NUL in a name field makes `GET /datasets/{id}/history` answer 500 for every dataset, permanently.**
- **Repro** (`verify/p1_pg_nul_audit.txt`), fresh Postgres API in audit mode:
  1. `GET /api/datasets/credit-default/history` → 200.
  2. `POST /api/projects {"name":"p","by":"\u0000"}` → **400** ("'by' needs at least one letter or digit").
  3. History of `credit-default`, `loan-losses` and `account-attrition` → **500**, also after a restart.
- **Cause (sweep lane):** the request's would-deny audit row stores the `\u0000`. The history query reads the audit rows, and Postgres cannot read that row ("unsupported Unicode escape sequence"). The audit table is append-only, so there is no repair path short of DB surgery.
- **Related (P2, medium):** a NUL in any query or body string → 500 on about 50 routes on Postgres only (`GET /runs?status=%00`); SQLite answers normally.
- **Fix:** strip or refuse NUL in every text before it reaches the audit row (and in every query or body text); read `details` defensively.

### Major

**J1. X3 M1 through `POST …/edit`: an edit invalidates a declared key and drops a relation silently.**
- **Repro** (`x3/m1_edit_*.txt`, both engines): `customers` with key `cust_id` and relation `app_cust`; `POST /datasets/{v}/edit {table: customers, ops: [add_rows [{cust_id: C001}]]}`.
- **Result:**
  - The preview `checks.warnings` is `[]`.
  - The commit → 201 with no acknowledgement needed. Key `cust_id` valid=False, `GET …/relations` → `[]`.
  - The only trace is a manifest op `relation_dropped` without `acknowledged`.
- This is the tracker's known "edit path doesn't set `relations_acknowledged`", but it is a live path to the silent loss X3 rated major.

**J2. `POST /admin/lake/sync-s3` with no bucket configured makes the API stop serving.**
- `curl -X POST /api/admin/lake/sync-s3?dry_run=1 -d '{"by":"Ada"}'` → 500, then `/api/health` → no answer (`verify/s1_sync_s3.txt`; the sweep saw it 3 times on SQLite and on Postgres).
- `lake/sync_s3.py:126` raises `SystemExit`. It is admin-only, and it was a dry run.

**J3. The Autopilot audit's memory is unbounded.**
- `autopilot.audit.audit` alone on credit-default (12,000 × 16) was OOM-killed at 7.67, 7.69 and then **10.02 GB** as more memory was free (`out/autopilot_audit.txt`; synthetic OOF probabilities).
- F-JOBS recorded 5.6 GB with real OOF. Open note, still open.

**J4. The API ignores SIGTERM while the heavy pool is busy** (open note, still open).
- 04:05:15 `kill -TERM`: "Waiting for connections to close". 04:08:02 still alive; after the client hung up: "Waiting for background tasks to complete". 30 s later still alive → `kill -9` (`out/sigterm.txt`).
- With K2's hung request this means no clean stop at all.

**J5. NaN, Infinity or 1e400 in any pydantic-typed JSON body → 500 on all 54 such routes, for any user.**
- The default 422 handler echoes the input and cannot serialise it. Nesting 1,000 levels deep gives a `RecursionError` (124 routes); a non-UTF-8 multipart body sent to a JSON route gives a `UnicodeDecodeError`.
- Repro: `curl -XPOST /api/runs -H 'content-type: application/json' -d '{"time_limit":1e400}'`.
- DLA4 #1's "400, never 500" holds on the edit path but not here.

**J6. The first edit preview of a 10M version holds the request for 50.8 s at 3.17 GB** (repeat: 9.6 s, 3.07 GB).
- X1 made "preview inside the 10 s interactive budget" a must-fix before the P11 scale gate. It is unchanged, and the re-hash shows no progress.
