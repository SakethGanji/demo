**Plan:** `docs/plans/data-platform-final.md` §5.11, R14, §7 rows 1 and 9, §9.1 row P10, §11.

**Base:** `motion-components` @ acfe988 (F-X1 done).

## Result

- Every CSV-era version is either migrated or reported.
- Old results stay byte-equal:
  - compare (5 run pairs), explain (2 runs) and `POST …/verify` (7 versions) give the same JSON before and after;
  - the only differences are new keys under `storage`.
- Old runs re-verify through their legacy blobs.
- A run on a migrated version reads in `engine_v1` mode and gets the same holdout ids as the old run.
- Grep gate 2 is at zero outside `lake/migrate.py`; gate 1 is at zero.

**`migrate_version`, step by step:**

1. **Verify.**
   - sha256(data.csv) must equal the stored hash.
   - Every split JSON must equal its `split_files` hash and every hash a run recorded for that file.
   - On a mismatch the version is skipped (`lake_migrations`, audit `dataset_migration_skipped`, once per reason). It is never laundered.
2. **Read as the worker read it** (R14): `frame_io.read(the hashed bytes, schema.json)`, or plain `pd.read_csv` before DL4.
3. **`__row_id`:**
   - `lineage.json.root_rows` when it has one unique entry per row (negative synthetic ids kept);
   - `0..n-1` for a root;
   - else fresh ids from the root counter, with `root_rows_source = "none"` and the edge `inferred = 1`.
4. **Write.**
   - pyarrow from that frame, **in data.csv order**;
   - `row_id_sorted = 0` when the ids are not increasing;
   - zstd 3, parts of ≤ 8M rows.
5. **Round-trip proof.**
   - The bytes read back through `frames._v1_column` (`engine_v1`) must equal the frame: every column `equals`, equal dtypes, equal ids.
   - Otherwise the version is skipped (`frame_not_equal`).
   - `csv_reproducible` is recorded (informational).
6. **Blobs:**
   - `legacy_csv` (data.csv);
   - `legacy_json` for each split JSON, `schema.json`, `lineage.json` and sidecar;
   - `frozen_holdout` (`holdout_sample.csv`);
   - the manifest, with a `legacy` block: csv sha and blob, `schema.json` / `lineage.json` shas, `root_rows_source`, `read`, `frame_equal`, `csv_reproducible`, the splits, original op / number / created_at.
7. **One transaction.**
   - The `datasets` row: `storage = 'parquet'`, `manifest_sha256`, `data_sha256`; `sha256 = data_sha256`; `legacy_sha256` kept.
   - `version_tables`, `table_files` and `blob_refs`; blobs made `live`, refusing a blob GC is purging.
   - **A Parquet split per DL4 JSON that covers the rows**, with `legacy_sha256` = the JSON's sha, plus an audit `split_created`. A per-target file is preferred over the pre-F4 `splits.json` when both have the same key; the other becomes evidence only.
   - **Run evidence:**
     - `run_inputs` backfilled for runs made before P05 (`legacy_csv_sha256`, `split_legacy_sha256`, `split_id`);
     - `split_id` set on the CSV-era rows written since P05;
     - run pins on the `legacy_csv`, Parquet split and `legacy_json` blobs.
   - `dataset_root_tables.next_row_id`.
   - Audit `dataset_migrated`.
8. **Folder.**
   - `<id>/` is renamed `<id>.migrated`.
   - A fresh `<id>/` keeps what the app still reads by name: the lineage summary without row maps, sample sidecars, `.generator`, `TOMBSTONE.json`, and **split views** at the `splits_path` old run configs name.
   - Nothing is deleted.
   - A **tombstone** becomes a manifest with no tables; its kept files become blobs.

## Decisions

- **`datasets.sha256` switches meaning** (= `data_sha256`) on migration, as §5.11 says. Readers that must answer as before read `legacy_sha256` explicitly: verify, run re-verify, registry build.
- **The legacy path resolver returns the positional frame.**
  - §5.11 says it maps to `Table(id, 'data')`. It does read that table, but an old run's readers name rows by data.csv position.
  - For a version derived with a row map, `__row_id` ≠ position. Handing them `__row_id` as the index would make explain or slices of an old run look at other rows.
  - New runs on the same version get `__row_id`, as every Parquet run does.
- **Rows stay in data.csv order even when the ids are not increasing** (5 of the 24 live versions). "Read order" became file order in `splitstore` and `_Parent`; for every table the writer makes, that order is unchanged (sorted).
- **Unrecorded split files** (drawn before DL4, never seen since) are migrated with the hash they have, because nothing recorded another. Their status says so ("unrecorded (drawn before DL4 …)"). A run's recorded hash is checked when one exists.
- **`split_files` and `datasets.splits_sha256` are retired, not dropped.**
  - Only `lake/migrate.py` reads or writes `split_files`. It is still needed for a version that is skipped until it is resolved, and the restore flow uses its stored copies.
  - `splits_sha256` is no longer written. Old rows keep the value, and verify still shows it.
- **A stale sample is never rewritten in place.** It becomes a new version (the bytes of a version are immutable now). Before, a sample with no runs was overwritten.

## Deviations and notes for dependants

- **"GET …/verify for 5 versions, before"** gives 409 `not_parquet` on CSV-era versions. The byte-for-byte comparison uses **`POST …/verify`** (DL2), which answers for both storages. The GET answers are recorded too (409 before, 200 ok after).
- **"GET /compare"** is `POST /api/compare {a, b}` (as in P09).
- **Pre-existing bug fixed:**
  - A whole-dataset `POST …/verify` (and so `verify-all`) on a root with two or more Parquet versions failed with `database is locked`.
  - The outer connection held its write transaction while the lake verify wrote on a second connection. It now commits per row (`dsets.verify`).
- **Files outside the row (all small):**

- **P24 (GC):** the passes are in `catalog_meta verify_all:passes`; arm `gc_armed` from them. The migration's `pending` blobs from a failed attempt are ordinary GC candidates after 24 h.
- **P23 (Postgres):** carry `lake_migrations`, `split_files` (only if CSV-era versions remain) and `ds_hash_ro` with its `WHEN` clause.
- **X2:**
  - The migration is idempotent; reset a copy of `data/` to re-run it.
  - `GET /api/admin/lake/migrate` lists per-version outcomes.
  - `GET /api/admin/lake/runs/{id}/verify` re-verifies any run.
- **U lane:**
  - The data grid of a table in data.csv order still pages by `__row_id` (keyset), so a migrated version's rows are shown in id order, not file order.
  - R5's `file_row_number` paging for unsorted migrated tables is not built.
- **Not run here:**
  - a 10M-row migration (here the full job migrated 21 versions, about 200k rows in all, in 2.0 s);
  - a monitoring window end to end (it uses the same `write_frame_version(parent_id=…)` path as the SQL refresh, which was run);
  - Postgres.
- **Scratch:** data dirs, worktrees of the three old heads and the venv were in the session scratchpad and are removed.
