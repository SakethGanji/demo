# G7 · Reject inference

**What it does.** A credit model is trained only on approved applicants, because only they have an outcome, but it is used on everyone who applies. Reject inference adds the declined applicants back under a stated assumption. One run trains four AutoGluon models on the same config:
- **approved only** (the baseline);
- **reweighting** (augmentation);
- **parcelling**;
- **fuzzy augmentation**.

It compares each method with approved-only on a **through-the-door (TTD) holdout**: every applicant of the latest period, approved or declined. The declined applicants are scored with the outcomes they would have had, which the sample keeps aside only for this check. The comparison uses paired CIs, and the page explains the assumption.

Where it lives (no new navigation):
- **Build:** the choice "Reject inference for defaulted" (top on the sample, score 97). It opens `#/reject-inference?dataset=&label=&decision=`, which lights up Build. The yes/no suggestion on the same table now says "only the approved applicants have an outcome … see Reject inference".
- **Models:** the run page `#/reject-inference?run=`, listed in Experiments as kind `reject_inference`.
- **Registry:** the model card of a yes/no model of the same table gets a "Reject inference (through-the-door check)" section, from the latest such run (JSON, MD/HTML and the card view).

## Backend
- **`reject/core.py`: a new run kind, `reject_inference`.** It runs in the run worker via `run_other`, so it gets the same events, SSE and MLflow logging. Every fit goes through F12's `prepare_fit`/`fit_predictor`, with log loss, `medium_quality` and 20 s per model.

  | Model | Trained on | How |
  | --- | --- | --- |
  | f₀, approved only | the approved rows | the baseline |
  | decision model P̂(A = 1 \| x) | every training applicant | AutoGluon |
  | reweighting | the approved rows | w = 1/P̂(A = 1 \| x), with P̂ clipped at 0.1 (so w ≤ 10) and w scaled to mean 1 |
  | parcelling | approved + declined | 10 bands of f₀ over the training applicants. The declined in band b are drawn bad with probability min(0.95, k · the approved bad rate in b), seeded. |
  | fuzzy augmentation | approved + declined | each declined applicant appears twice: as y = 1 with weight q and as y = 0 with weight 1 − q, where q = min(0.95, k · f₀(x)) |

  - **k is the assumption:** a declined applicant is k× as likely to default as an approved one that f₀ scores the same. The default is k = 2, a rule of thumb. It is not fitted, and the Setup's Advanced section lets you set k from 1 to 5.
  - **Weights:** the weighted fits pass AutoGluon's `sample_weight` with **`weight_evaluation=True`**, so early stopping and the ensemble weigh validation rows the same way.
  - **Neural nets are excluded** from every fit (`excluded_model_types = FASTAI, NN_TORCH`). AutoGluon's NNs ignore sample weights. On the first version, FastAI took 96% of the fuzzy ensemble and predicted 0.42 for the declined against a target q̄ of 0.20.
  - **Split:**
    - when there is a date: F6 out-of-time, drawn on the decision column (time strategy), so the holdout is every applicant of the latest period;
    - otherwise: random, stratified by the decision.

    The tuning slice is used for training.
  - **Comparison on the same rows, each method against f₀:**
    - ΔAUC with a DeLong paired CI (F18's `paired_delong`);
    - Δ log loss and Δ Brier with a paired bootstrap;
    - mean p̂ against the bad rate, overall and for the declined;
    - the bad rate among the applicants each model would approve at the old approval rate;
    - calibration by decile.
  - **Verdict:** *better* means a CI excludes 0 in the method's favour and none against it.
  - **The approved-holdout view** is also reported. It is what a lender without hidden outcomes would see.
- **Without hidden outcomes** (any user table), only the approved holdout can be scored. The page and the card say so.
- **No registration:** a reject-inference run is a comparison of methods, so `POST /runs/{id}/register` returns a clear 400. `reject_inference` is in every non-tabular kind guard.
- **`reject/api.py`:**
  - `GET /api/reject-inference/detect`;
  - `POST /api/reject-inference/runs` (works with `{dataset_id}` alone; overrides: label, decision_column, approved_value, k, drop_columns, split, time_limit, …);
  - `GET /api/reject-inference/runs/{id}`;
  - `card_section`.
  - **Refuses with 400:** a non-binary label, no approved or no declined applicants, fewer than 50 declined, or an outcome missing for most approved applicants.
- **G0 detection:**
  - **New role `decision`**, "approve/decline decision (reject inference, excluded)". It is a two-valued column whose values read approved/declined (accepted/rejected, booked, funded, …), or a 0/1 or yes/no flag with a decision-like name.
    - Confidence is 0.95 when the outcome is blank for every declined row (evidence: "'defaulted' is blank for every 'declined' row: outcomes exist only for the approved"), and 0.75 otherwise.
    - It is in `EXCLUDED`, so training pre-fills drop it.
  - **New suggestion `reject_inference`:**
    - It needs a yes/no target with at least 5% blanks.
    - It scores 97 with a confident decision column, else 60 (taking "no outcome" as declined, when at least 15% of outcomes are missing).
  - **Fixed along the way:** the yes/no suggestion's class share counted blank outcomes as a class ("1 is 4.2% of rows" → "7.3%").
- **Sample `samples_g7.py` → `credit-rejects`** (no existing sample touched):
  - 24,000 applications over 2023–24. The true PD is logistic in 10 inputs plus an **unrecorded** u ~ N(0, 1) (what the underwriter learns at interview).
  - The old policy has a score floor of 560 and approves on the legacy scorecard + 0.75·u + noise, so 57.6% are approved. The declines are therefore **not missing at random**.
  - Bad rates: 7.3% approved, 33.9% declined, 18.6% through the door.
  - The declined applicants' outcomes are in `reject_truth.json` (validation only).
  - The formulas are in the docstring.

## Numbers (smoke `ri`, zero-config: only `{dataset_id}` sent)

**Data.** The split is out-of-time on application_date. There are 11,060 approved and 8,124 declined training applicants. The TTD holdout has 4,816 applicants (2,771 approved and 2,045 declined), with a bad rate of 18.4% (7.6% approved, 33.0% declined). One run takes about 75 s.

| method | TTD AUC | ΔAUC [95% DeLong CI] | log loss | Δ log loss [95% CI] | mean p̂ (bad rate 0.184) | declined p̂ (bad 0.330) | bad rate at 57.5% approved | verdict |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| approved only | 0.6803 | — | 0.5000 | — | 0.084 | 0.101 | 11.2% | baseline |
| reweighting | 0.6534 | −0.027 [−0.035, −0.018] | 0.5133 | +0.013 [+0.010, +0.017] | 0.080 | 0.093 | 12.4% | worse |
| parcelling | 0.7090 | +0.029 [+0.022, +0.036] | 0.4551 | −0.045 [−0.054, −0.035] | 0.152 | 0.221 | 10.2% | **better** |
| **fuzzy augmentation** | **0.7258** | **+0.046 [+0.037, +0.054]** | **0.4435** | **−0.057 [−0.063, −0.050]** | 0.128 | 0.168 | **9.9%** | **better** |

- **Acceptance: met.** Two methods improve both TTD AUC and calibration over approved-only, with paired CIs that exclude 0. Δ Brier is −0.0123 [−0.0138, −0.0107] for fuzzy and −0.0120 [−0.0156, −0.0082] for parcelling. The page explains the assumption (k, and what reweighting assumes).
- **Honest reading:**
  - Approved-only **understates the TTD bad rate by more than half** (mean p̂ 0.084 against 0.184; declined 0.101 against 0.330). Both inflating methods move toward the truth but still under-predict. On this sample's generator, a k nearer 3 would fit better. I did **not** tune k on the hidden outcomes: the default stays the rule of thumb.
  - **Reweighting is worse.** It assumes declines are missing at random, which is false here by construction (u). With the score floor, its weights are also extreme (w up to 6.9 after scaling; effective n 7,898 of 11,060).
  - On the **approved holdout only**, the view a lender has, parcelling looks *worse* than approved-only: log loss 0.2755 against 0.2619, AUC 0.6395 against 0.6397. The bias is invisible without through-the-door outcomes.
  - **Variance between runs:** an earlier smoke run (the same code before the NN exclusion, sharing the CPU with another smoke) gave approved-only TTD AUC 0.690 and fuzzy +0.055. The 20 s time limits make AutoGluon's ensemble vary from run to run. The verdicts (parcelling and fuzzy better, reweighting worse) were the same in the three runs.

## Limits and open problems
- **k is unidentifiable from approved outcomes.** The default of 2 is a rule of thumb. No sensitivity sweep over k is run (it would cost three more fits per k value). It would be the natural next panel.
- **No registration of the chosen method.** The run compares methods. To serve one, the user would train it as a yes/no model, and that flow does not take reject-inference rows yet. Registering the best method as a version (Try It, reason codes, recourse) is G11's call.
- **TTD outcomes exist only for the sample** (the sidecar). On a real table, the page compares methods on approved applicants only and says why that is biased. A bank could supply bureau outcomes of declined applicants (performance at other lenders) as a column; that override is not wired.
- **Fuzzy duplicates rows.** AutoGluon's internal validation split can put the two copies of one declined applicant on both sides. That is acceptable for log loss, but it makes validation scores optimistic.
- **AutoGluon NNs are excluded** from every fit, because they ignore sample weights.
- **Not wired:** the Model Doctor and Vela. G11's Doctor could recommend reject inference when a yes/no table has a `decision` role; Vela (G10) can call `POST /api/reject-inference/runs`.
- **Smaller changes:**
  - the Makefile's default `SMOKE_ONLY` now includes `ri`;
  - each smoke run adds one reject-inference run, one approved-only run and a `smoke.credit-rejects` version.
