Promote this workflow to a tool
Registers it as a call target for WorkflowToolNode. Any agent it is bound to can then do the whole close in one call instead of re-deriving it from 27 primitives — and the call is deterministic, replayable and logged node-by-node, which no sequence of 9 model-chosen tool calls is.
Derived from the workflow name. Immutable after the first bind — renaming breaks every stored transcript and every prompt that names it.
A promoted tool always resolves to one version. Publishing v6 does not reach a bound agent until someone adopts it.
This is the only text the model reads when deciding whether to call it — so it describes when to call and what comes back. It is deliberately not the workflow's own description, which reads "weekly close, runs Mondays" and tells a model nothing.

4 of 6 trigger fields exposed. 238 schema tokens by the engine's own estimator — the same number the binder charges against the 6,000 budget.
The two dropped fields carry identity. A model that can set actor_email can attribute a close to somebody else, so they are stripped from the schema and injected last, where nothing in the model's output can override them — the same rule the connectors screen applies to X-User-Id.

Rank is recomputed nightly and on demand; a rank change alone never rebinds an agent, because a binding that moves overnight is a capability nobody can reason about. It proposes, you apply.
The flywheel
What promotion actually does
Three mechanical steps. None of them is new engine work.
1 · Derive input_schema from the trigger node's inputSchema — the model fills it, so it must exist.
2 · Register as a call target for WorkflowToolNode, which has shipped for months.
3 · Bind under the same 24 / 6,000 budget as node and connector tools. No separate allowance.
src/nodes/ai/tools/workflow_tool.py — "enables hierarchical agent systems where one agent can delegate tasks to entire workflows (which may themselves contain agents)." The mechanism was never the missing part. The lifecycle was.

Every promotion is one capability the next agent does not have to re-derive, and it arrives deterministic, replayable and priced. The 10 promoted tools ran 6,850 calls for $45.21; the same work through model-chosen primitives priced out at roughly $2,600 at the per-run medians these workflows replaced.
The risk, stated
Four ways this goes wrong. None of them is hypothetical.
Wrong once, wrong everywhere. attribute_spend is bound to 4 agents. Its 4 recent failures came from 3 agents that never touched the workflow and cannot debug it. Promotion converts one team's bug into every team's bug, at the speed of binding.
Auto-demotion is blunt on purpose. 5 failures in a rolling 10 unbinds a tool from every agent without asking. It will sometimes demote a tool over a transient upstream outage. That is the cheaper error: a demotion costs a click, a wrong close costs a restatement.
Promotion hides depth. One line in a transcript — finance_close_weekly — is 14 nodes and 3 nested agents. Deepest chain in this catalogue is 3 levels. A tool that contains an agent bound to that same tool is a cycle; the binder refuses it at bind time, when it is a message, not at run time, when it is a bill.
The budget makes this zero-sum. 10 promoted tools already consume 2,088 tokens of a 6,000 ceiling. There is no version of this where the catalogue grows to 40 and every agent gets all of them. Promotion is a ranking problem forever, and pretending otherwise just moves the failure to the first bind that throws.
