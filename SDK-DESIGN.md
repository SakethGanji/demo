# The Node SDK — Design

**Design document. No implementation.** Companion to `VISION.md` and `HANDOFF-AGENT-PLATFORM.md`.
UI reference: `design-prototypes/terminal-agent-sdk.html`.

---

## 1. The idea

Every node the workflow builder offers is also a Python callable. An agent — or a human — composes a workflow
by writing a script:

```python
cron  = Cron(expression="0 7 * * 1", timezone="Europe/London")
fetch = HttpRequest(method="GET", url="{{ $vars.EXPORT_URL }}")
check = If(field="body", operation="isNotEmpty")

cron >> fetch >> check
for region in ("US", "EU", "APAC"):
    check.true >> Postgres(name=f"Load {region}", operation="upsert", table="finance.ledger")
check.false >> StopAndError(message="Export was empty")

validate()
test_run(input={"body": SAMPLE})
```

**The requirement that shapes everything: it must be generated, never maintained.** A node added next year
appears in the SDK, in the type stubs, and in the agent's prompt with no file edited anywhere.

---

## 2. Why a script instead of tools

| Surface | Schema tokens per model call | Model calls to build 6 nodes |
|---|---|---|
| 28 node types as 28 tools | ~5,412 | 6+ |
| A 7-tool ladder *(built, measured)* | 1,293 | **18** — observed |
| **SDK: one tool + signature reference** | **~650** | **1** |

Beyond cost: **loops and conditionals**. "One loader per region" is a `for` statement, not twelve tool calls
the model must each get right. And models write Python far better than they emit long tool-call chains.

*(The 650 is honest: 204 for the tool schema plus ~445 for the signature reference the agent needs in its
prompt. An earlier draft claimed 204 by counting only the tool schema.)*

---

## 3. The generation mechanism — the part that must be clean

### One source
`node_registry`, after `register_all_nodes()`. Verified it already carries everything needed:

- All 28 type names are **valid Python identifiers**, no keyword collisions
- `NodeProperty` carries `name`, `type`, `required`, `default`, and `options` **with their values**
- `NodeTypeDescription.outputs` declares named ports — `If → [true, false]`,
  `Switch → [output0…output14, fallback]`, `Loop → [loop, done]`
- Every node has an identical `execute(context, node_definition, input_data)`

### Three projections, all generated from it

| Projection | Consumer | When |
|---|---|---|
| **Runtime callables** | the script that actually runs | built at import |
| **Type stubs** (`.pyi`) | humans — autocomplete, mypy | generated by a script, committed |
| **Signature reference** (compact text) | the agent's system prompt | generated, injected at run time |

### One test pins them together

```
assert set(sdk_runtime) == set(stub_symbols) == set(reference_entries)
       == set(registry.types) - EXCLUDED
```

Drift becomes a failing test rather than a silent bug. **This test is the design.** Without it, the stub and
the prompt rot the first time someone adds a node in a hurry.

### Adding a node

Write the class, register it in `register_all_nodes()` — the one place it already has to go. All three
projections update. Nothing else to touch, no prompt to rewrite.

## 4. API surface

### Constructors — one per node type
`HttpRequest(method=…, url=…)` → a node handle. Name auto-derived from the type, de-duplicated
(`Code`, `Code 2`); `name=` overrides.

### Wiring
| Form | Meaning |
|---|---|
| `a >> b` | main output → main input; returns `b`, so chains read left to right |
| `a.true >> b` | a named port; attributes come from declared `outputs` |
| `a >> [b, c]` | fan out |
| `[a, b] >> c` | fan in (c must accept multiple inputs, e.g. `Merge`) |

### Introspection — inside the script, so it costs no prompt tokens
`list_nodes(group=…, query=…)` → compact index · `describe("Postgres")` → full property list

### Checking
`validate()` → raises `WorkflowInvalid` listing every problem with the fix
`test_run(input=…)` → **dry**: compiles, resolves expressions, counts what *would* happen. Never executes writes.

### Reaching data mid-build
`call_tool(name, args)` — the agent can query a dataset and branch on the result while composing.

### Escape hatch
`Node("SomeType", **params)` — generic constructor for anything the generator cannot express. Guarantees the
SDK is never a ceiling.

## 5. Mapping rules

| Registry concept | SDK form | Note |
|---|---|---|
| node type name | callable of the same name | verified all 28 are valid identifiers |
| `NodeProperty.name` | keyword argument, **camelCase preserved** | these keys *are* the stored workflow JSON; renaming them would create a translation layer that drifts |
| `type: options` | `Literal[...]` in stubs; runtime membership check | option values are in the registry |
| `type: json` | `dict` (a JSON string is also accepted) | |
| `type: collection` + `multipleValues` | `list[dict]` | |
| `required: True` with a non-empty default | **optional** in the SDK | "required" alone is a lie — several required properties ship defaults |
| `displayOptions` (conditional visibility) | accepted, not enforced at construction | too subtle for a signature; `validate()` reports inconsistencies |
| declared `outputs` | port attributes | `.true`, `.false`, `.loop`, `.done`, `.output0` … |

**Excluded from generation: `AIAgent`.** An agent that can place agents inside the workflow it is building
makes cost and recursion unpredictable. Bind it by hand if wanted. The exclusion list is explicit and tested.

## 6. Errors are the feedback loop

Constructors validate **eagerly** and raise:

```
TypeError: SendEmail has no parameter 'recipient'; did you mean 'toEmail'?
           required: toEmail, subject, bodyFormat, body
           at build_workflow.py, line 22
```

This is tighter than validating after the fact, because a traceback naming a line is the single artefact
models read best. Three rules:

1. **Name the vocabulary.** An unknown parameter or port lists the valid ones. A rejection that names what
   *is* allowed lets the model self-correct; a bare "invalid" does not.
2. **Nothing partial on failure.** A failed constructor adds no node.
3. **The traceback goes back to the agent verbatim.** Not a summary of it.

`validate()` covers what a constructor cannot see alone: unreachable nodes, dangling connections, no trigger,
and — worth keeping from the ladder work — *a routing field that does not exist in the upstream node's declared
output*, which is a real mistake a real model made and then fixed when told.

## 7. What the UI gets

Every constructor and every `>>` emits the same `addNode` / `addConnection` events the canvas already
consumes. **~10 lines, and non-negotiable** — without it the script is a magic box.

### But be honest about timing

Composition is pure Python: a 28-line script creating 8 nodes finishes in **single-digit milliseconds**. There
is no line-by-line build to watch, and animating one would be decoration pretending to be telemetry.

**What is genuinely watchable:**
- the model **writing** the script — token streaming, seconds. This is the show.
- `call_tool(...)` inside it — real network
- `test_run()` — real work
- the **failure state** — a raise at line 22 genuinely leaves lines 23-28 unrun

**So the line ↔ node link is provenance, not animation.** Hover a line, its nodes highlight; click a node, its
line highlights. Always true, always useful, honest.

### Layout
`design-prototypes/terminal-agent-sdk.html` — script │ graph │ SDK reference + cost. Every node wears the line
that made it (`line 13 · APAC`); the failing line carries its traceback inline; remaining lines render pending.

### The script is an artifact
Editable and re-runnable by a human, and the **provenance record** — far better at answering "why does this
workflow look like this?" than eighteen tool calls.

## 8. Open questions

1. **Are stubs worth the build step?** Runtime generation alone gives agents everything; stubs only serve
   humans and CI. Recommend yes — a human writing the same scripts is the "programmer surface" story — but it
   is the one piece that can go stale, so the equality test matters more than the stubs do.
2. **Should `>>` mutate an implicit module-level draft, or an explicit object?** Implicit reads far better in a
   script whose entire purpose is one workflow. Explicit is more defensible if scripts ever build two.
   Leaning implicit; revisit if multi-workflow scripts appear.
3. **camelCase parameters in Python look wrong.** Deliberate — they are the stored JSON keys. A snake_case
   surface needs a mapping table, and a mapping table is a thing that drifts.
4. **Where does the signature reference live** — always in the system prompt (~445 tokens every call), or
   fetched by `list_nodes()` on demand (a round trip)? Probably: a short always-on core plus `describe()` for
   detail. Needs measuring against a real model.
5. **`displayOptions` are not enforced at construction.** An agent can set a parameter that its mode makes
   meaningless. `validate()` catches it, but a turn later than ideal.

---

## 9. What would make this the wrong design

- If models turn out to compose more reliably through discrete tool calls than through a script, the ladder
  wins on accuracy and the token argument stops mattering. **Testable**: same task, same model, both surfaces,
  compare success rate. Worth doing before committing.
- If most real workflows are 3-4 nodes, loops never fire and the ladder's per-step visibility is worth more
  than the script's expressiveness.
- If scripts routinely fail late (line 22 of 28), the partial-build state becomes the normal state and the
  experience is worse than eighteen small steps that each succeeded.
