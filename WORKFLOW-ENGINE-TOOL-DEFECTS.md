> - **§1's suggested fix had a landmine.** Introducing list-valued `type` crashes

## 0. Why these three

All three corrupt agent tool use *today*, silently. They were found while planning an MCP
client for the engine (see §5), but none of them depend on that plan — fix them regardless.

Each produces wrong behaviour with **no error**: a parameter silently changes type, a tool
result silently becomes unparseable, or a tool silently disappears from the model's options.
Silent is the operative word — nothing in the logs tells you any of this happened.

Suggested order is 2 → 3 → 1 (ascending risk).

---

## 1. Tool schemas are corrupted before they reach the provider **[READ]**

`src/engine/tool_schema.py`. Pipeline order at `:235-237` is
`ensure_complete_schema` → `harden_schema` → `_normalize_schema_types`.

### 1a. Optional parameters silently change type

Any schema generated by pydantic renders `Optional[int]` as:

```json
{"anyOf": [{"type": "integer"}, {"type": "null"}]}
```

There is **no top-level `type` key**. So:

1. `ensure_complete_schema:151-152` sees no `"type"` and injects `prop_def["type"] = "string"`.
   (It also mutates the caller's dict in place — `dict(schema)` at `:137` is a shallow copy.)
2. `harden_schema` pops `anyOf`, which is in `_OPENAI_STRIP_KEYWORDS` (`:117-120`).
3. Result: `{"type": "string"}`. **An integer parameter is now advertised as a string.**

For Anthropic, `strip_keys` is empty (`:179`), so `anyOf` survives *alongside* the bogus
injected `"type": "string"` — a contradictory schema rather than a wrong one.

Related: `$ref` is stripped but `$defs` is **not** in the strip set, so `$defs` blobs survive
in every request while the `$ref`s that pointed at them are gone. Dead weight on every call.

### 1b. Strict mode forces every optional parameter to be supplied

`:193-197`, recursive into nested objects and array items via `:200-208`:

```python
if provider == "openai":
    props = schema.get("properties", {})
    if isinstance(props, dict) and props:
        schema["required"] = list(props.keys())
```

`additionalProperties: false` is added at `:191` for both `openai` and `anthropic`. Strict is
selected for `gpt-*`, `o1-*`, `o3*`, `o4*` (`src/engine/llm_provider.py:854`) and set on the
function definition at `llm_provider.py:575-576`.

The canonical OpenAI strict-mode remedy is to make optional properties nullable
(`"type": ["string", "null"]`). **This code does not do that.** So a tool with 8 optional
parameters becomes 8 required non-nullable parameters, and the model must invent a value for
every one on every call. `_check_empty_ids` (`src/nodes/ai/ai_agent.py:2579-2582`) may then
reject the invented empties before execution.

### Scope of damage today

Local argument validation is unaffected — `tool_schema_map` is built from the raw
`input_schema` (`ai_agent.py:1727`) and `_validate_tool_args:2178` reads
`properties[key].get("type")`, which is `None` for an `anyOf` property, so the check is
skipped. **The corruption is confined to what the provider sees** — which is exactly where it
matters for tool-call quality.

### Suggested fix

Flatten before hardening: resolve `$ref`/`$defs`, collapse `anyOf: [T, null]` to `T` plus
nullability, and only then apply provider hardening. Under strict mode, express optionality as
`"type": [T, "null"]` rather than by omission from `required`. Add a test with a pydantic-shaped
schema containing an optional int, asserting the provider payload keeps `integer`.

## 2. Tool results over 8,000 characters can become invalid JSON **[READ]**

`src/nodes/ai/ai_agent.py:2191-2252`. Signature at `:2193` is `max_chars: int = 8000`; both
call sites (`:2547`, `:2600`) use the default. Nothing overrides it — no node property, no env
var, no setting.

Branches:

| Condition | Behaviour | Line |
|---|---|---|
| `len <= 8000` | passthrough | `:2201` |
| not JSON-parseable | head 4000 + marker + tail 4000 | `:2208-2215` |
| JSON list > 3 items | `{_compressed, total_items, sample: data[:3], item_schema}` | `:2217-2231` |
| JSON dict | truncate string values > 500 chars | `:2233-2243` |
| **everything else** | **head 4000 + marker + tail 4000** | `:2245-2252` |

The dict branch only rewrites *top-level long strings*. A dict whose bulk is nested objects or
arrays of numbers is copied essentially unchanged, stays over 8,000 characters, and falls
through to the final branch — **a head+tail slice of a JSON object, which does not parse**.

Concrete trigger already in the codebase: `profile_data` returns a `ProfileResponse` whose bulk
is `columns: list[ColumnProfile]` plus a `correlations` matrix — all numeric, no long top-level
strings. Over 8,000 characters it hands the model unparseable JSON.

The list branch is also lossy in a way the model cannot see: items 4+ are discarded and
replaced with a count.

### Suggested fix

Truncate structurally, never syntactically — recurse and elide nested collections with an
explicit marker, so the output always parses. Make `max_chars` configurable. Add a test with a
deeply nested numeric dict over the limit asserting `json.loads` succeeds.

## 3. The dynamic tool filter removes tools the agent has not tried yet **[READ]**

`src/nodes/ai/ai_agent.py:1780-1813`. `_WARMUP_ITERATIONS = 3` at `:1783`; the filter engages
when `iterations > 3` and at least one tool has been called (`:1784`). It is never applied on
the final iteration (`:1781`), which is sent tool-free by design.

Surviving tools are the union of:

1. tools already called this run (`:1786`)
2. meta tools — `memory_store`, `memory_recall`, `spawn_agent`, `delegate_to_skill`,
   `run_script` (`:1782`, defined `:65-74`)
3. tools whose **name appears as a substring** of any string content in the last 6 messages
   (`:1794-1801`)

Applied only when `2 <= len(filtered) < len(tools)` (`:1804`).

**The comment at `:1789-1791` says unused tools are kept "so the model can still discover new
tools". The implementation does not do that.** A tool that has never been called and is never
mentioned by name is dropped from the prompt at iteration 4 and cannot be discovered
afterwards.

**[ASSESSMENT]** This breaks any tool set designed as a progression, where later steps are by
definition unused early. It also makes behaviour depend on incidental prose: short generic tool
names re-enter the set whenever the substring happens to appear in a message (`:1799` is a bare
`if tn in content`).

### Suggested fix

Either retain untried tools explicitly (matching the stated intent), or keep an always-include
set, and replace the substring test with a word-boundary match. Fix the comment either way —
right now it documents behaviour that does not exist.

## 4. Not in scope here, but related

The engine's seven analytics-service call sites are independently broken — no `/api/v1`
prefix, no auth header, and `data_report_tool` targets a `/report` route that does not exist.
That is documented separately in `WORKFLOW-ANALYTICS-INTEGRATION.md` §2 and is **[VERIFIED]**.

Do not repair those tools as part of this work. The plan (§5) is to replace them, and fixing
them first is wasted effort.

## 5. Why these three block the MCP plan **[ASSESSMENT]**

The intended direction is for the engine to consume `apps/analytics-mcp` (27 tools over
analytics-service) instead of maintaining its own analytics tools. Each defect above hits that
plan harder than it hits the status quo:

- **§1** — MCP servers are pydantic-based, so nearly every optional parameter arrives as
  `anyOf`. The corruption would apply to most tools rather than a few.
- **§2** — MCP returns a *list of content blocks*, landing in the "keep first 3 items" branch.
- **§3** — the analytics-mcp tool set is explicitly a ladder (`search_datasets` →
  `describe_dataset` → `run_sql` → `read_artifact`); the later rungs are unused at iteration 4
  and would vanish exactly when needed.

The bridge itself is small — the engine's tool contract is duck-typed
(`{name, description, input_schema, execute}`), and `src/nodes/ai/tools/api_request_tool.py:151-219`
already builds all four at runtime with an `async def execute` closure. That is the pattern to
copy. Details, including the `resolve_tools` sync/async issue and the studio picker work, are
in the session notes that produced this document.
